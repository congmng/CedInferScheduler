# 备用 profile：2026-09-18 在**空闲** GPU 上按同一网格重采

这里放的是 `RTX4090` / `RTX5090` 两份 `Qwen/Qwen3-8B` bf16 profile，
条件与 `profiler/perf/` 里默认的那两份**只有 GPU 占用状态和 vLLM 版本不同**：

| | 默认 `perf/` | 本目录 `perf-v029/` |
|---|---|---|
| vLLM | 0.27.1 | **0.29.0**（= 部署用的 `casr029`） |
| 采集日 | 2026-09-10 | 2026-09-18 |
| attention `max_kv` | 16384 | 16384（同） |
| `measurement_iterations` | 3 | 3（同） |
| 卡上是否有别的任务 | 未知 | **空闲**（4090 用 GPU0/1；5090 用 GPU2/3） |

**为什么不直接替换默认 bundle**：同一网格下，本目录的 FFN 项比默认 bundle
**快 ~1.8×**（`gate_up_proj` / `down_proj` 在 1024、2048 token 上都是 0.56–0.59×），
而 attention 侧（`qkv_proj` / `o_proj`）**完全一致（1.00×）**。换成这份之后：

* `tests/test_plan_service_calibration.py` 的三项会失败：5090 单步代价从
  `14.8 ms` 掉到 `9.68 ms`，而**真机实测 TPOT 就是 14.5–15.0 ms**；
* 也就是说默认 bundle 让模拟器与真机的吻合（模拟 `14.3 ms` vs 真机 `14.5–14.9 ms`、
  `d4090` 模拟 `25.8` vs 真机 `24.6`）**会被破坏**。

两种解释都还成立，**需要定口再改默认值**：

1. **旧 bundle 是在被占用的卡上采的**（部署本身就在 GPU0/1 上与 P/D 容器共存），
   所以它反映的是"部署时真实的可达算力"，而本目录这份是**空闲卡上的上界**；
2. 或者 **vLLM 0.29.0 的 FFN kernel 真的比 0.27.1 快 ~1.8×**，那么真机 14.5 ms
   里有约 5 ms 是 kernel 之外的开销（调度/采样/Python），模拟器缺的是这一项，
   而不是 kernel 变慢了。

在定下来之前：**默认路径继续用 `profiler/perf/`**，本目录只作对照与留证。
A100 没有这个问题（它两次都是 0.29.0，数值逐行一致），只是网格从 `max_kv=4096`
补齐到 `16384`，所以已经直接更新到 `profiler/perf/A100/`。
