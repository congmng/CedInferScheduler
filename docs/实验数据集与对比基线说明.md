本文档固定两件事：**实验用经典数据集的原始来源与我们对它做的定制**，以及
**对比基线与近期 SOTA 系统的对应关系**。正式写作时以这里的 commit / revision
为准。

> ⚠️ **测试对象已切换（2026-09-18 决定）**：下面 §1–§6 里的 trace 都是用
> **Qwen3-8B 的 tokenizer 与 KV 体积（`147.5 KB/token`）**定制的，那批结果
> **保留为"KV 大档"对照**。接下来的主线实验（§0）改用**自研 P-15B**
> （`16.56 KB/token` bf16，比 Qwen3-8B 小 **8.9×**）作为测试对象，依据与口径

## 0. 测试对象：从 Qwen3-8B 切到自研 P-15B（2026-09-18 决定）

**换的理由**：我们所有调度结论的前提是"**KV 是绑定资源**"。而"存算协同什么时候
还值钱"恰恰由 KV 有多大决定，所以用一个 KV 大 9 倍的模型去论证 KV 不是大头时的
调度，逻辑不成立。已测过的 KV 档位是一条单调轴：

| 档位 | KV/token | CASR 相对 SOTA | 出处 |
|---|---:|---:|---|
| Qwen3-8B 全注意力 bf16（现状） | `147.5 KB` | 见 `实验结果汇总.md` §0 主表 | 本文档 §1–§6 的 trace |
| Qwen3-8B 全注意力 fp8 | `73.7 KB` | 基线快 `10–40%`，`casr_lp` 只动 `±2%` | `实验结果汇总.md` |
| 压缩 KV MLA | `31.1 KB` | **`−23.0%`**（优势明显收敛） | `实验结果汇总.md` §0 |
| **自研 P-15B（新增主线）** | **`16.56 KB`（bf16）/ `8.28`（fp8）** | **待测** | 本节的第 1 步 |

所以 P-15B 不是"再换一个模型"，而是把这条自变量轴**再往左推一档**——按已有的
趋势，CASR 的优势应当继续收敛，这正好回答"什么时候不再需要存算协同"。

**口径必须写清（否则数字不可比）**：

1. **算力是借的**：P-15B 的 draft config（`configs/model/DeepSeek/DSV4-P15B-draft.json`）
   里 `profile_model: Qwen/Qwen3-8B`——**FLOPs/延迟用 Qwen3-8B 的 kernel profile，
   只有 KV 几何来自 DSV4 设计**。所以这一轮只能回答"KV 缩小后调度还值多少"，
   不能回答绝对延迟与吞吐上限。
2. **KV 数字要说清是解析值还是实测值**：模拟器收的是解析下界 `16.56 KB/token`；
   vLLM 0.29 对同一套层结构实测 `97.6 KB/token`（差一个数量级，原因已归因，
   见 `DSV4_10-30B跨卡设计.md` §3.1.1，其中 `1.40×` 可自己修回来）。**这一轮要么
   显式声明"用理想 serving 栈的 KV 几何"，要么把解析值/实测值各跑一遍当自变量。**
3. **tokenizer 不变**：`Qwen/Qwen3-8B` 的 tokenizer 继续用，因此现有 trace
   **不需要重新生成**——变的只有 KV 体积与算力 profile 这两个量。

**落地方式**（两步）：

1. **模拟器（现在就能做）**：用 P-15B 的 config 在 4 个域上重跑
   `rr / load / cache_aware / casr / casr_lp` 对照，产出"KV 8.9× 更小后优势收敛
   多少"的曲线。
2. **真机（要先有模型）**：部署形态 **bf16 + 同机 TP=2**（14.87 GB/卡；
   单卡 24GB 放不下，见 `DSV4_10-30B跨卡设计.md` §4.1）。

## 2. 定制方法（可复现）

生成器：`LLMServingSim/workloads/generators/sharegpt.py`（子命令
`python -m workloads.generators sharegpt`）。它本身不是数据集，只是解析器 +
长度过滤 + 到达过程合成。

1. **会话切分**：每条会话按相邻的 `(human, gpt)` 配对切成轮次；第 `t` 轮的
   **输入是前 `t-1` 轮的完整上下文 + 本轮 human 文本**，输出是本轮 gpt 回复。
   这保留了真实对话的"长前缀 + 增量后缀"结构，也是前缀缓存能命中的原因。
2. **tokenizer**：`Qwen/Qwen3-8B`（与真实部署的模型一致），输入用
   `add_special_tokens=False`，得到与模拟器一致的 token 序列。
3. **长度过滤**：丢弃违反 `--min-input-toks` / `--max-input-toks` /
   `--min-output-toks` / `--max-output-toks` / `--max-kv-toks` 的轮次。
   真机受上下文和显存限制，我们把 `--max-input-toks` 压到部署的
   `max_model_len` 以内。
4. **到达过程**：`--sps` 指定每秒请求数，`_next_arrival_ns` 支持
   `poisson` / `uniform` / `burst`；真机回放按 trace 的
   `arrival_time_ns` open-loop 起请求。
5. **文本落盘（真机回放必需）**：加 `--emit-text` 后额外写
   `input_text = tok.decode(in_ids)`。模拟器只读 `input_tok_ids`，真机回放客户端
   （`tests/real_dataset_client.py`）读 `input_text`，两边因此是**同一条 trace**。

### 2.1 真机回放的额外取舍（必须声明）

- 真机客户端走 `/v1/completions` 传**裸 prompt**，不套 chat template，目的是让
  引擎 tokenize 出的序列与模拟器的 `add_special_tokens=False` 尽量一致。
  引擎仍可能加 BOS 等特殊 token，存在个位数 token 的差异。
- `--max-output-tokens` 会截断数据集的原始回复长度（ShareGPT 中位数约
  `638` token）。这是为了把真机单轮时长控制在可重复范围内；截断长度在实验记录
  里固定写出。**这是最大的偏离项**：真实 ShareGPT decode 负载比本实验重得多。
- ShareGPT 原数据不含会话级时间戳，到达时间全部是合成的（Poisson）。

### 2.2 本轮真机 ShareGPT trace 的精确参数
- 产物：`LLMServingSim/workloads/sharegpt-real-qwen3-8b-600-sps14.jsonl`
  （600 请求，44.1 s，Poisson `sps=14`）。
- 生成命令：

```bash
cd LLMServingSim
python3 -m workloads.generators sharegpt \
  --model /home/ubuntu/srz/ced_inference_scheduler/data/Qwen3-8B-tokenizer \
  --source /home/ubuntu/srz/ced_inference_scheduler/data/sharegpt_gpt4/sharegpt_gpt4.jsonl \
  --num-reqs 600 --sps 14 --seed 42 \
  --min-input-toks 512 --max-input-toks 2048 \
  --min-output-toks 0 --max-output-toks 2048 \
  --max-kv-toks 4096 --max-sessions 4000 --emit-text \
  --output workloads/sharegpt-real-qwen3-8b-600-sps14.jsonl
```

- 统计：输入 token `mean 971 / median 845 / p95 1863 / max 2040`；输出 token
  `mean 423 / median 413 / max 1413`（真机回放时被 `--max-output-tokens 16` 截断）。
- 真机部署 `MAX_MODEL_LEN=4096`，因此 `2048` 输入上限留够了余量。
- 已验证：真机回放 5 条，`usage.prompt_tokens` 与 trace 的 `input_toks`
  逐一相等（`1949/606/842/912/701`），说明真机 tokenize 与模拟器一致。

### 2.3 两个定制档：wide（弱复用）与 deep（强复用）

ShareGPT 的会话长度有限，**同一份数据集按不同方式取样会得到完全不同的
前缀复用强度**，而前缀复用正是本项目要考察的轴。因此固定两个档位：

| 档 | 取样方式 | 请求数 | 前缀桶数 | 桶复用 | 产物 md5 |
|---|---|---:|---:|---:|---|
| wide | `--max-sessions 4000`（跨会话取样） | 600 | 460 | `1.30` | `51a00cb6224b928094b529c8c9e980f5` |
| deep | `--max-sessions 200`（会话内多轮） | 356 | 124 | `2.87` | `a3ff202f474f34f46ac4874b83eb2a65` |

（"前缀桶"= `sha256(prompt[:512])` 前 16 位，与 router `classify()` 的口径一致；
桶复用 = 请求数 / 桶数。**class** 数还会按输入长度桶细分，所以 class 复用比
桶复用低——多轮对话长度递增会换 class，这一点在 §4.7 讨论。）

deep 档的生成命令（`workloads/sharegpt-deep-real-qwen3-8b-356-sps14.jsonl`）：

```bash
cd LLMServingSim
python3 -m workloads.generators sharegpt \
  --model /home/ubuntu/srz/ced_inference_scheduler/data/Qwen3-8B-tokenizer \
  --source /home/ubuntu/srz/ced_inference_scheduler/data/sharegpt_gpt4/sharegpt_gpt4.jsonl \
  --num-reqs 600 --sps 14 --seed 42 --max-sessions 200 \
  --min-input-toks 512 --max-input-toks 2048 \
  --min-output-toks 0 --max-output-toks 2048 --max-kv-toks 4096 \
  --emit-text --slo-ttft-ms 500 --slo-tpot-ms 50 \
  --output workloads/sharegpt-deep-real-qwen3-8b-356-sps14.jsonl
```

注意两点：(a) `--max-sessions 200` 把可用轮次限制住了，实际只写出 **356** 条
（文件名如实标注），不是 600；(b) 该文件由 `transformers 5.17.0` 生成，
与 wide 档（锁定的旧 tokenizer 运行时）不是同一版本，**两档之间不做 token 级对比**，
只做"同一档内各策略之间"的对比。

### 2.4 可复现性核验（2026-09-11 复核）

- 原始文件：`data/sharegpt_gpt4/sharegpt_gpt4.jsonl`，`96161473` 字节，
  md5 `e7c90069c89144620fe265843fc4e750`（与上面锁定的 revision 一致；
  下载脚本落在 `data/sharegpt_gpt4/fetch_sharegpt.sh`）。
- trace：`LLMServingSim/workloads/sharegpt-real-qwen3-8b-600-sps14.jsonl`，
  md5 `51a00cb6224b928094b529c8c9e980f5`。
- 用 2.2 节的命令原样重跑一遍（在**当时的环境**里，输出到临时路径），得到
  **逐字节相同**的文件（`cmp` 无差异、md5 相同）。
- **但这条可复现性依赖 tokenizer 运行时版本，不是纯数据决定的。** 2026-09-12
  在缺少 `transformers` 的环境里装回 `transformers 5.17.0` 后重跑同一条命令，
  出现了 **405/600 行不同**：同样文本的 token 数变了，于是
  `--min-input-toks 512 / --max-input-toks 2048` 的长度过滤选中了不同的轮次，
  序列整体错位（`input_tok_ids` 405 行不同，而 `arrival_time_ns` 全部相同）。
  也就是说：**`transformers`/`tokenizers` 必须与生成时锁定同一版本**，
  否则"同一命令"复现不出同一 trace。
- 因此本项目的处理是：**以仓库内的 trace 文件为唯一制品**（记 md5），
  需要加字段时对现有 trace 做**纯增量标注**而不是重新生成。
  例如带 SLO 的版本
  `LLMServingSim/workloads/sharegpt-real-qwen3-8b-600-sps14-slo500-50.jsonl`
  （md5 `523b4d4553fa2ad52bb5ea63f43d0130`）就是把每一行加上
  `slo_ttft_ms=500`、`slo_tpot_ms=50` 得到的；**剥掉这两个字段后与原 trace
  逐行完全一致**（已用脚本断言），所以跑在不同 trace 上的结果仍可直接比较。
- 另一个记录在案的坑：解析 trace 时不能用 `str.splitlines()`——prompt 文本里
  可能含 `U+2028/U+2029` 之类的分隔符，会把一行 JSON 拆断。要用 `split("\n")`。
- 注意：真机回放时还会叠加 `--max-output-tokens 16` 的**运行时截断**
  （`tests/real_dataset_client.py`），trace 文件本身仍保留数据集的原始
  `output_tok_ids`；论文里应把这一项写成"回放客户端截断"而不是"数据定制"。

## 3. 对比基线与近期 SOTA 的对应关系

所有策略都在**同一拓扑、同一 trace、同一批 P/D 容器**上运行；每个策略开跑前
重启 P/D 以清空缓存状态。

| 策略（`--policy`） | 对应系统 / 论文 | 在本文中复现的部分 | 说明 |
|---|---|---|---|
| `rr` | 经典 round-robin | Prefill/Decode 轮询 | 隔离基线，衡量"完全不管缓存与队列"的代价 |
| `load` | vLLM 生产栈的 least-loaded / shortest-queue | 按 `inflight / capacity` 选最空实例 | 经典负载均衡基线 |
| `cache_aware` | **SGLang Router** 的 `cache_aware` 策略；vLLM production-stack 的 prefix-aware router | 最长前缀命中优先，命中实例超过利用率阈值后溢出到最空实例 | 近期 SOTA **路由**基线 |
| `casr`（启发式） | CASR 的快速层近似 | 前缀钉住 + 异构/网络感知的 Decode 代价 | 我们的启发式对照 |
| `casr_lp` | CASR 完整设计 | 慢环 LP `f_ijk`（缓存算力 + 链路字节预算 + 拥塞）+ 快速层 deficit 重放 | 我们的方法 |
| `casr_full` | CASR + 结构弹性 | 在 `casr_lp` 上叠加 `+P/-P` 容器生命周期 | 结构层，当前负载下是否触发取决于瓶颈 |

需要明确区分的"近期 SOTA"边界（避免笼统宣称性能优于所有系统）：

- **DistServe / Splitwise** 解决的是 P/D 解耦后的**资源配比与放置**，本身不做
  请求级缓存亲和路由；我们复现的是它们隐含的"固定 P/D 比例 + 静态放置"设定，
  即 `rr` / `load` 这类不感知前缀状态的基线。
- **Mooncake / NIXL / LMCache** 解决 **KV 的存取与传输路径**；在本实验里它们
  是被复用的传输层，不是被比较对象。
- **Llumnix / Dynamo** 是完整的调度与编排系统；我们复现的是其
  "按队列/利用率做负载均衡"的调度语义（`load`）。
- **SGLang** 的缓存感知路由是我们在**路由层**最直接的 SOTA 对照，因此单独实现
  为 `cache_aware`。

正式论文写作时应固定上述系统的仓库 commit 与论文版本；本表按"问题边界"对齐，
而不是声称复现了对方的完整代码路径。

## 4. SLO 口径（算法与真机实验共用）

### 4.1 选定的应用级 SLO

| 指标 | 阈值 | 含义 |
|---|---|---|
| TTFT | `≤ 500 ms` | 客户端可见的首 token 时间（含 Prefill 计算、KV 跨域传输、Decode 排队） |
| TPOT | `≤ 50 ms` | 首 token 之后的每 token 时间，约等于 `≥ 20 token/s` 的持续生成速率 |

这两个值是**应用级假设**，不是从某一轮实验结果里挑出来的。它可以直接引用
公开基准：MLPerf Inference 的 Llama2-70B **interactive** 类别规定
`ttft <= 450 ms`、`tpot <= 40 ms`（[`mlcommons/inference` 的
`language/llama2-70b/README.md`](https://github.com/mlcommons/inference/blob/master/language/llama2-70b/README.md)）。
本实验取 `500 / 50 ms` 是它的同量级放宽版：我们跑的是 Qwen3-8B 单卡实例、
16 输出 token 的短回复，直接套 70B 基准的严格档会过于苛刻。

真机实测（3 域、
600 请求、`3.5 req/s`、流式客户端）给出的分布是：

| 策略 | TTFT P50 / P95 | TPOT P50 / P95 |
|---|---|---|
| `cache_aware`（SGLang 风格路由） | `331.7 / 666.8 ms` | `46.7 / 60.2 ms` |
| `casr_lp`（本文） | `237.8 / 499.4 ms` | `14.9 / 18.6 ms` |

即 `500/50` 落在两条策略之间：既不是"所有策略都达标"，也不是"所有策略都不达标"，
因此有区分度。为免除"阈值是挑出来的"这一质疑，所有 SLO 结论**必须同时给出
阈值网格**（`TTFT ∈ {250, 500, 1000} ms × TPOT ∈ {25, 50} ms`），
复现命令见 4.4。

### 4.2 算法侧：SLO 如何进入调度

`serving/casr/flow_solver.py` 按设计文档 `c_ijk` 的结构做一阶 TTFT 预测：

```
predicted_ttft_ms = distance + rtt + kv_bytes / bw          # 链路
                  + prefill_service_ms × work_ratio          # Prefill 只算未命中部分
                  + decode_service_ms × queued_fraction      # Decode 排队（不是整段生成）
```

若某 `(class, prefill, decode)` 三元组的预测 TTFT 超过 `ttft_slo_ms`，就在它的
单位代价上加 `slo_penalty`（`p_slo`）——**加有限大惩罚而不是把 pair 删掉**：
当所有可行 pair 都超 SLO（容量不足）时求解器仍必须给出计划，但只要存在达标
pair 就会优先选它。判定结果通过 `diagnostics.slo_violating_pairs` 暴露，
真机 `/routing-state` 可直接审计。

该预测是**一阶模型**，只用于"这个 pair 是否越线"的二值判断，不代表精确延迟；
它用的是实测 service time，而不是排队论公式。`ttft_slo_ms=0` 表示关闭该项，
即此前所有轮次的行为。

### 4.3 真机侧：SLO 怎么被约束和统计

- 客户端 `tests/real_dataset_client.py --stream` 走 SSE，逐请求记录
  `ttft_ms` 与 `tpot_ms`；非流式请求**测不到 TTFT**，因此不参与 SLO 判定。
- router 把 `ttft_ms / tpot_ms / completion_tokens` 写进
  `metrics-<policy>.jsonl`（流式路径此前根本不写 metrics，属已修缺陷）。
- `tests/aggregate_real_comparison.py --slo-ttft-ms 500 --slo-tpot-ms 50`
  输出 SLO attainment、goodput，并可用 `--slo-grid-ttft/--slo-grid-tpot` 出网格。
- **没有**在服务端按 SLO 拒绝请求：SLO 影响的是路由/结构决策，
  请求失败仍然只由 `request-timeout-s`（客户端）与 `downstream_s`
  （router）这两个故障保护决定。

### 4.4 复现


### 4.5 必须声明的偏差

`47–51 s` 那批 LMCache/NIXL 传输毛刺**每一条都必然违反任何合理 SLO**，
且它们不落在同一策略上。因此 SLO attainment 必须与"毛刺数"一起报告
（聚合器的 `glitch_count`），否则排名会随毛刺落点摆动；这也是本报告同时保留
截尾均值的原因。

### 4.6 数据集侧现状：**没有任何数据集承载 SLO**

这一条要写清楚，避免评审误以为 SLO 来自数据：

| 环节 | 现状 |
|---|---|
| trace 字段 | 只有 `arrival_time_ns / input_text / input_tok_ids / input_toks / output_tok_ids / output_toks`，**没有 `slo_*` 或 deadline 字段** |
| 源数据集 | ShareGPT 只有对话文本，**没有时间戳、更没有延迟要求**；到达过程是我们合成的 Poisson |
| 生成器 | `workloads/generators/sharegpt.py` 没有 SLO 相关参数 |
| 算法 | `class_ttft_slo_ms`（按 class 的 SLO）已实现，但**没有数据源能填充它** |

其中最后一条值得展开：设计文档写的是"class SLO"和"高优先级 class 的 SLO 风险"，
但本实验的 class 是由 `(model, prompt 前缀 hash, 输入长度桶, 输出长度桶)`
自动派生的，反映的是**缓存亲和**而不是业务优先级。所以要真正做到
"按业务等级设 SLO"，需要额外引入一条数据通路：

1. trace/生成器增加 `slo_ttft_ms` / `slo_tpot_ms`（请求级）或
   `priority` / `slo_class`（等级级）；
2. 回放客户端逐请求读取，并把它带进 SLO 判定与 attainment 统计；
3. 求解器从 trace 的等级分布构造 `class_ttft_slo_ms`，而不是用单一全局阈值。

公开可用的对话数据集（ShareGPT、LMSYS-Chat-1M、BurstGPT 等）都只提供
**prompt / 到达时间**，不提供延迟要求；明确带延迟约束的公开来源目前是
**基准规范**（如上面的 MLPerf interactive 档）而不是数据集。因此本实验的
合理口径是"数据集提供负载形状，基准规范提供 SLO 量级，实测提供标定"，
三者分开引用。

> `class_ttft_slo_ms` 这个字段，**但没有数据源填充它**；现在 trace → 模拟器 →
> 求解器的通路是完整的（见 §4.8），并且把 `casr_*` 系列 trace 补上了 SLO
> 标注（`tests/annotate_trace_slo.py`，只改这两个字段，到达时间与 token 逐字不变，
> 因此与已记录的实验仍然可比）。

### 4.8 模拟器侧 SLO 通路（2026-09-23 补齐）

真机侧的链路（§4.7）本来就是通的；**模拟器侧此前根本没读 trace 的 SLO 字段**，
所以 `p_slo` 在仿真实验里是死代码。现在补齐为：

| 环节 | 行为 | 位置 |
|---|---|---|
| trace | 行内 `slo_ttft_ms` / `slo_tpot_ms`；CLI `--slo-ttft-ms/--slo-tpot-ms` 兜底 | `workloads/generators/casr.py`（新增参数）、`tests/annotate_trace_slo.py`（给已有 trace 增量标注） |
| 路由 | 行优先、CLI 次之；写进请求对象 | `serving/core/router.py` `load_requests/_load_flat_request` |
| 类 | 每个 class 保留**最紧**的界（与真机 router 同规则） | `serving/casr/prefix_profiler.py` `assign()` / `snapshot()["class_slo"]` |
| 求解器 | 每个 tick 把 class 界发布进 `class_ttft_slo_ms`，覆盖全局 `ttft_slo_ms` | `serving/casr/controller.py` + `flow_solver.apply_slo_overrides()` |
| 产出 | 逐请求 CSV 追加 `slo_ttft_ms` / `slo_tpot_ms` / `slo_ok`（无预算则留空，不写"通过"） | `serving/core/scheduler.py` |
| 汇总 | `tests/compare_casr.py` 打印 `slo_attainment` | 同上 |

**开关与消融**：`configs/cluster/casr_p15b_three_domain_slo.json`（`ttft_slo_ms=500`、
`slo_penalty=10`）是定价版，原版是不定价版；同一份 trace 跑两个配置即可分离
"测量"与"定价"。

### 4.7 请求级 SLO 的数据通路（已实现）

为了让 SLO 将来能真正由数据集驱动，这条链路已经打通并可验证：

| 环节 | 行为 |
|---|---|
| trace | 可携带请求级 `slo_ttft_ms` / `slo_tpot_ms`（生成器 `--slo-ttft-ms/--slo-tpot-ms`；也支持对已有 trace 做纯增量标注） |
| 客户端 | `row_slo()`：**trace 行优先，CLI 兜底**；通过 `X-SLO-TTFT-MS` / `X-SLO-TPOT-MS` 头随请求下发 |
| router | `request_slo()` 读取请求头，把 `slo_ttft_ms/slo_tpot_ms/slo_ok` 写进 `metrics-<policy>.jsonl`；非流式请求测不到 TTFT，`slo_ok` 记 `null`（未测量）而不是"通过" |
| 聚合器 | `row_slo_satisfied()`：**优先用请求级判定**，没有判定才回退到 CLI 阈值；summary 里标 `slo.source = per-request / cli` |

冒烟验证（12 请求、trace 标注 500/50）：metrics 里出现
`"slo_ttft_ms": 500.0, "slo_tpot_ms": 50.0, "slo_ok": true/false`，
聚合器输出 `slo% = 91.7`，说明一条超 TTFT 的请求被正确判为违约。

**按 class 的 SLO 也已接通**（2026-09-12）：router 在
`controller.observe(..., slo_ttft_ms=...)` 时把该请求的预算一并上报，控制面按
class 保留**最紧的那个界**，每个 tick 把它发布进共享求解器配置
（`class_ttft_slo_ms`），并通过 `/routing-state` 的 `class_slo`
（`{classes, tightest_ms}`）暴露。这样"交互类 ≤ 250 ms、批处理类 ≤ 800 ms"
这类**分级预算**可以直接由 trace 驱动，而不是只能给一个全局阈值。

配套的 A/B 开关：客户端 `--ignore-trace-slo`（完全不带 SLO）与
router 侧 `SLO_PENALTY=0`（仍然测量但不参与目标函数），用来把
"测量"和"算法使用"分开消融。

## 6. 第三个数据集：CNN/DailyMail（长上下文）

### 6.1 为什么加它

前两个数据集都没压到**跨域 KV 链路预算**：Dolly 的 prompt 均值只有 `193`
token（约 `28 MB` KV），ShareGPT wide 约 `971` token，而 PD 链路的实测预算
是"`2048` token 前缀约 `37 ms`，折合约 `6.6 req/s`（按 75.5 MB 计）"。
CNN/DailyMail 的文章均值 `1250` token ⇒ **每请求 KV 约 `184 MB`**，
在 `16 Gbps` 链路上单个跨域对只能承载约 `10–11 req/s`。
这正好把问题推到"链路是瓶颈"的区间：谁的 router 把长 prompt 溢到跨域 Decode，
谁就会把链路打满；谁把长 prompt 留在本地，谁就不会。

### 6.2 来源与定制

| 项 | 值 |
|---|---|
| 来源 | `abisee/cnn_dailymail`（HuggingFace datasets，`3.0.0` 的 `validation` 分片） |
| 许可 | Apache-2.0 |
| 文件 | `data/cnn_dailymail/validation.parquet`，`34664725` 字节，md5 `b5aad2f862572f36ea35fbb22b249795` |
| 生成器 | `LLMServingSim/workloads/generators/cnndm.py`（本次新增） |
| 产物 | `workloads/cnndm-real-qwen3-8b-600-sps14.jsonl` 见下方命令 |

**为什么读 Parquet 而不是走 HF 的加载脚本**：`ccdv/cnn_dailymail` 与
旧版 `abisee/cnn_dailymail` 的 loading script 依赖 `cs.nyu.edu` 的原始
story 压缩包，该地址长期不可用；`abisee` 仓库的 `3.0.0` 分片已直接提供
Parquet，所以生成器只读 Parquet（本地文件优先，HF id 兜底）。

定制方法（同样只有三件事，不改写文本）：

1. **prompt 组装**：输入 = 文章 `article`，输出 = 摘要 `highlights`。
2. **头部截断**：`--head-toks 2047` 只保留文章前 2047 个 token。
   这是本生成器**唯一**的文本改动，作用是让所有请求都落在部署的
   `max_model_len 4096` 以内，同时保持"长前缀 + 唯一内容"的形状；
   截断后的 prompt 仍是原文的合法前缀，不是拼接或改写。
3. **长度过滤 + 到达过程**：`--min-input-toks 900 --max-input-toks 2047`、
   `--max-output-toks 64`、`--max-kv-toks 2100`；`--sps 14` 的 Poisson 到达，
   `seed=42`；`--emit-text` 供真机回放；请求级 SLO 写 `TTFT ≤ 500 ms`、

   `source_id`（数据集 `id` 列，可回溯到具体文章）。

### 6.6 同档位的反向结果：过载时 CASR 输给最朴素的 load 基线

同一份峰值 trace 上，`static`（`--no-enable-casr`，即 least-loaded 路由）的
E2E 均值 **9 800 ms**、p95 **18 821 ms**、达标率 4.6%，而 CASR 两臂分别是
17 764–26 103 ms、73–104 s、8.4–27.4%。**"CASR 一定更好"在这一档不成立。**

机制（逐请求落点）：

| 臂 | 落点分布（prefill / decode） | p50 | p95 |
|---|---|---:|---:|
| static | p4 965 / p2 562 / p0 373；**decode 全在 d5090** | 9 472 ms | 18 821 ms |
| casr greedy | p0 768 / p4 713 / p2 419；decode d5090 1371、**d4090 411、d3090 118** | **2 965 ms** | **96 655 ms** |
| casr lp | p4 831 / p0 680 / p2 389；decode d5090 1601、d4090 216、d3090 216/83 | 8 041 ms | 78 149 ms |

也就是：**静态基线把全部 1900 个请求钉在最快的 d5090 上**；CASR 按容量/亲和把它们
摊到三张 decode 上，p50 明显更好（缓存命中 + 分摊），但 20–30% 的请求落到慢 2–3× 的
decode 上排队，**尾部直接崩掉**。这**不是 2026-09-23 这次改动引入的**：把 trace 的
SLO 字段删掉重跑（等价于改动前行为），数字与"有字段但不定价"逐位相同。

结论与下一步：目标函数目前按**服务时间**定价，而饱和档的尾延迟由**慢实例上的排队**决定；
`p_slo`（有限罚）和 `queue_weight`（本仿真配置里长期为 0、真机为 1.0）都只是权宜。
要把这一档救回来，需要在目标里显式给"慢 Decode 的排队"定价（或对 Decode 做
deadline-aware 的准入），而不是继续调 `overflow_penalty` 这类旋钮。

### 6.7 按 6.6 的建议做的两个杠杆，以及它们**都没有**修好这一档（2026-09-23）

按 6.6 的建议实现了两个杠杆，都在峰值档（1900 请求、1250 token、30 rps×60 s）上验证：

| 杠杆 | 实现 | 结果 | 判读 |
|---|---|---|---|
| **目标项：Decode 尾风险定价** | 新增 `tail_weight`：把 `queue_weight` 无量纲的队列占比换成**时间**——`queue_fraction × 本实例步时 × 输出长度系数`，单位秒，与 `c_ijk` 其余项一致 | `tail_weight` 0→5：p50 **6 395 → 5 283 ms（−17%）**，但均值 17 648 → 20 861、p95 73 423 → 84 141（**更差**）；慢 Decode 的流量反而从 146 增到 181 | 它对"均值"有效、对"尾"无效：饱和时把流量从"深队列的快卡"推走，正好推到慢卡上 |
| **router：deadline-aware Decode 选择** | 新增 `deadline_aware_decode`：fallback 不再按"最不忙"，而是按**预计排空时间**（同为 `queue_fraction × 步时`）挑，并优先满足请求预算 | 均值 17 648 → 19 298 ms、达标率 10.5% → **7.7%**、慢 Decode 流量 146 → 288 | 同样把流量推向慢卡：容量归一化的"最不忙"判据其实**已经**隐含了"慢卡更贵" |

两个杠杆都保留在代码里、**默认关闭**（`tail_weight=0` / `deadline_aware_decode=false`），
扫描工具 `tests/sweep_tail_weight.py` 可复现上表。

### 6.8 根因：慢实例上的"类级 straggler 队列"，不是某个 per-pair 价格能修的

把最慢的 100 个请求与最快的 100 个请求拉出来看（SLO+queue 定价臂）：

```text
最慢 100（p50 79 894 ms，其中 99% 是排队）：到达时间集中在 64.1–78.5 s，
         prefill 100/100 落在 p0（RTX3090，884 ms/请求，是 5090 的 3 倍）
最快 100（p50 948 ms）：prefill 85 个在 p4（5090）、14 个在 p2（4090）
```

随后做的三组"排除/集中"实验（同一档、同一臂）：

| 变体 | p50 | p95 | 达标率 |
|---|---:|---:|---:|
| 对照（SLO+queue 定价） | 6 395 ms | 73 263 ms | 10.5% |
| 排除最慢 **Decode**（d1 容量→0.01） | 6 643 ms | 76 159 ms | 8.2% |
| 排除最慢 **Prefill**（p0 容量→0.01） | **4 412 ms** | 87 044 ms | **14.1%** |
| **Decode 全部集中到 d5** | 6 594 ms | **91 016 ms** | 9.5% |
| 基线：`static`（least-loaded，decode 全在 d5） | 9 472 ms | **18 821 ms** | 4.6% |

也就是说：**每去掉一个慢实例，落后队列只是挪到下一个最慢的**；而 least-loaded 基线用
"全部集中在最快队列"换到了 4 倍的尾部（p95 18.8 s vs 73–91 s），代价是中位数差一倍。
30 rps 相对 26 req/s 的 Decode 池是 **2.7× 过载**，这个区间没有放置策略能满足 300 ms
SLO（全臂达标率 4.6–14.1%），差异全在**均值 vs 尾部**的取舍上。

**下一步该做的不是再加一个 per-pair 价格，而是二选一**：

1. **准入/削峰**：预测排空时间超过预算时，在路由端排队/拒绝而不是派发（把过载挡在池外）；
2. **改目标为 min-max**：对最大实例利用率 `z ≥ load_i/K_i` 定价（LP 里就是一个辅助变量），
   让"谁最慢谁最堵"直接进目标，而不是靠 Σ 溢出——这才是"尾风险"的正确形式。

### 6.9 min-max（及其求和版）实现了，但**也不是**这一档的答案（2026-09-23）

按 §6.8 的第 2 条实现并验证：

| 新目标项 | 定义 | 峰值档结果（对照：均值 17 648 / p50 6 395 / p95 73 423 / 达标 10.5%） |
|---|---|---|
| `max_utilization_weight`（min-max） | 辅助变量 `z ≥ (load_i/K_i) × step_i`，对 `z` 定价；用 `step_i` 加权是因为纯利用率会被"把负载摊到慢卡"最小化 | w=20 最好：均值 **16 711**、p50 5 686、p95 **65 018**、达标 9.3%；w=5 反而更差（19 553/78 298），非单调 |
| `backlog_weight`（同量的求和版） | `Σ_i (load_i/K_i) × step_i`，每个流一个线性系数 | w=5：均值 18 503、p50 5 126、p95 77 490、达标 10.6%；把 3090 Decode 的流量从 146 清到 **4**，但尾部不动 |

**min-max 为什么几乎不起作用**：`z` 只约束**最差的那一台**。实测该 tick 上最差的是
Decode（util 1.76 × 0.278 s = 0.49 s/s），而真正制造 straggler 的 RTX3090 Prefill
只有 0.32 s/s —— **它永远进不了 `z`**，所以 p0 队列在任何权重（0/5/20/100）下都原样保留。
求和版能把它算进去，也确实清掉了慢 Decode，但尾部仍未改善。

### 6.10 真正的根因：**峰值期间结构控制器在换机**

把峰值臂的状态机轨迹拉出来（`casr-state-*.jsonl` 的 `instances[*].admission_state`）：

```text
tick 200（峰值中段，约 70 req/s）：
   p0(3090) ACTIVE   p2(4090) WARMING   p4(5090) DRAINING
   —— 全部流量因此落在最慢的 p0 上

全程统计（1900 请求、30 rps 峰值）：
   状态切换 58–60 次；实例-tick 中 DRAINING 483–621、WARMING 69–78
```

也就是说：**弹性机制在过载期间仍然执行 `-P`/`+P`**（把最快的 p4 排空、同时预热 p2），
于是"当前唯一完全可用的 Prefill"会周期性地变成最慢的那台，落在它上面的类就排成长队——
这正是 6.6 里那 100 个 79.9 s 请求的来历。四个目标函数杠杆（尾风险、deadline 选择、
min-max、Σ 积压）都动不了它，因为它们都只在"已经确定可用实例集合"之后才起作用。

**下一步**：修**结构门控**，而不是再加目标项——

1. 池子处于饱和（`offered > Σ 可用容量` 或存在 backlog）时禁止 `-P`，
   或要求被排空实例上没有任何带未完成需求的类；
2. `-P` 的候选必须先把它的类重新安置（迁移预算是"冷 Prefill"），否则保留；
3. 峰值期间 `+P` 只在**预测式**通道触发（`prescale_utilization`），避免"排空 + 预热"同时发生。

### 6.11 结构门控按这三条改完了，真正的 bug 在**调用顺序**（2026-09-23）

三条门控都实现了（`serving/casr/evaluator.py`，默认开启，可在 `structural` 里关掉做 A/B）：

| 门控 | 实现 | 是否作用于这一档 |
|---|---|---|
| 1. 饱和时禁止 `-P` | 反事实解完后检查**剩余池子**的 `prefill_overflow`，> `overflow_epsilon` 就不排空 | ❌ 不作用——评估器本次运行 **一次 `-P` 都没发**（决策只有 23 次 `+P`） |
| 2. 仍持有需求的实例不许排空 | 按 `arrival_rate_ewma > 0` 统计每台 Prefill 上的类需求 | ❌ 同上 |
| 3. 有实例在 WARMING/DRAINING 时不再叠加结构编辑 | 在候选生成后、选优之前拦截 | ⚠️ 生效但影响有限（18 085 vs 17 648 ms 均值） |

**门控没有作用，是因为抖动根本不是评估器发出的**——把状态机轨迹按来源拆开看：

```text
结构决策分布:  {'keep': 1484, '+P': 23}        ← 没有 -P
实例状态分布:  DRAINING 621 个实例-tick、WARMING 69
```

真正的排空来自 `PrefillLifecycle` 的**按需调容**，而它的调用顺序是错的：

```python
# 修复前（controller.build_plan）
self.last_lifecycle = self.lifecycle.update(current_ns, snapshot["prefix_states"], …)
…
self._sample_backlog(current_ns, prefill)      # ← 需求回收在 lifecycle 之后
self._inflate_demand(snapshot["prefix_states"])
```

`lifecycle` 的 `desired = ceil(demand / capacity)` 读的是 `arrival_rate_ewma`，而**过载时这个值
反映的是"已经服务出去的速率"**（背压把到达压住了）。于是：负载越高 → 观测到达率越低 →
`desired` 越小 → **排空最快的 worker** → 剩下最慢的 Prefill 承接全部流量。这就是 §6.10 里
tick 200 那一幕，也是 80 s 排队队列的来源。

**修复（两处）**：

1. 把 `_sample_backlog` + `_inflate_demand` 提到 `lifecycle.update` **之前**（需求先修正，再调容）；
2. `lifecycle.update(..., backlog_rps=...)`，新增 `hold_on_backlog`（默认开）：**有积压时只许扩、
   不许缩**（上限仍受 `max_active_prefill` 约束）。

**同一峰值档的 A/B（LP 臂）**：

| 臂 | 均值 | p50 | p95 | SLO 达标率 | 状态切换次数 |
|---|---:|---:|---:|---:|---:|
| 基线 `static`（least-loaded） | 9 800 | 9 472 | 18 821 | 4.6% | — |
| CASR 修复前 | 17 648 | 6 395 | 73 423 | 10.5% | 58 |
| **CASR + 顺序修复** | 27 609 | 25 467 | **63 524** | **17.3%** | **6** |
| CASR + 修复 + 把最慢 Prefill 定价出池 | 20 247 | 16 188 | 62 871 | 13.2% | 22 |

**结论**：修复把抖动从 **58 次降到 6 次**，尾部与达标率都变好（p95 −14%、达标率 10.5% → **17.3%**，
是这一档所有臂里最高的，基线只有 4.6%），代价是**中位数变差**（6.4 s → 25.5 s）——池子稳定后
慢实例不再被"换走"而是持续分担，中位数因此被拉平。轻载档（80 请求）只付 **+1.6%/+2.9%**
延迟、达标率不变（100%）。

也就是说：这一档**没有免费的午餐**——尾部和均值由"是否让慢实例参与"决定，而 30 rps 对
26 req/s 的 Decode 池本来就是 2.7× 过载。要同时拿到中位数和尾部，只能**加容量或削峰**，
不是再调策略。

### 6.12 (a) 削峰/准入 与 (b) 补容量，两条都试了（2026-09-23）

**(a) 准入（闭环入口）**：模拟器本身有闭环入口 `--client-concurrency`（客户端把请求**留在入口**，
只有池子空出槽位才提交，因此"等待被接纳"的时间不计入请求延迟）。同一峰值档：

| 臂 | 均值 | p50 | p95 | SLO 达标率 | 送达跨度 |
|---|---:|---:|---:|---:|---:|
| 基线 `static`（开环） | 9 800 | 9 472 | 18 821 | 4.6% | 109 s |
| CASR 修复后（开环） | 27 609 | 25 467 | 63 524 | 17.3% | 142.6 s |
| **CASR + 准入 cc=16** | **1 480** | 1 481 | **1 859** | **83.9%** | **189 s** |
| CASR + 准入 cc=32 | 2 006 | 1 953 | 2 698 | 60.5% | 132.9 s |

**这是唯一真正解决 SLO 的杠杆**：均值从 27.6 s 掉到 1.48 s、达标率 17.3% → **83.9%**。
代价写在同一张表里：**同样 1900 个请求的送达跨度从 109 s 拉到 189 s**（吞吐降约 43%）。
准入不创造容量，它只是把"无界排队"换成"有界延迟 + 更长的送达时间"——**报这组数字必须同时报
跨度/吞吐，否则等于用丢负载换指标**。

**(b) 补容量**：三种补法，都在同一峰值档上跑：

| 补法 | 基线均值 | CASR 均值 | CASR 达标率 |
|---|---:|---:|---:|
| 对照（现状） | 9 800 | 27 609 | 17.3% |
| 三个 Prefill 全部常驻（`min=max=3, scale_on_demand=false`） | — | 31 349 | 15.1% |
| **每个域再加一个 Decode**（解码池 26.3 → 52.6 req/s） | 12 312（更差） | 20 871（更好） | 4.8% |
| 容量改用 **bundle 反推值**（`capacity_from_profile: true`） | — | 31 042 | 13.9% |

**没有一种补容量能把 CASR 拉到基线水平**，而且"加 Decode"反而让**基线也变差**（9.8 → 12.3 s）——
因为仿真运行时**根本不是在 Decode 上受限**。

### 6.13 顺带查出的口径坑：仿真运行时用的**不是** profile 容量

`serving/__main__.py` 只在配置写了 `capacity_from_profile: true` 时才调用
`rescale_capacities`；默认路径下：

| 角色 | 运行时容量 | 来源 |
|---|---|---|
| Prefill | **每 tick 被 egress 上界覆盖**（≈70 req/s/生产者） | `controller._egress_bound_prefill_capacity` |
| Decode | **部署占位值 110 / 170 / 230 req/s**（合计 510） | 集群 JSON，没人覆盖 |

而 P-15B 的 bundle 反推值是 prefill 29/61/89、**decode 4.5/9.3/12.5（合计 26.3）**。
也就是说：**仿真里 Decode 的约束被高估了 ~19×**，任何"Decode 是不是瓶颈"的结论在默认配置下
都不成立（§6.1 那张 decode 溢出的表是离线 probe 用反推容量算的，不是运行时行为）。

建议：把 `capacity_from_profile` 设为默认开启或至少在 CASR 配置里显式打开，
并在 `meta`/日志里每次打印实际使用的容量——否则"容量口径"会像这次一样在事后才被发现。

### 6.15 搬运定价改为从链路模型推导，并用它验证"压缩 KV 让搬运划算"（2026-09-23）

**改法**（`serving/core/router.py`）：`kv_exchange_decision` 不再默认使用真机实测常数，
而是从**本集群自己的数**算两边：

```text
transfer_ms = tokens × kv_bytes_per_token / pair_bandwidth(p,d) × 1000 + rtt(p,d)
local_ms    = 该 Decode 所在节点上同域 Prefill 的 service_ms × max(1, tokens / 1024)   # 与 solver 同一张表
```

`link_derived_pricing`（默认 **true**）控制这一点；缺 `kv_bytes_per_token` 或该对的带宽时
**自动退回**实测常数（`93 / 585 / 1351 ms per 1k token`），保证老配置行为不变。

**验证：把 KV 体积当自变量**（域内 1 GB/s、跨域 0.26 GB/s = 任务书与实测区间，
prompt 1250 token，2 req/s 轻载，`local_prefill=auto`，关掉排队外部性以便看纯阈值）：

| KV/token | 域内搬运 | 跨域搬运 | 本地重算 | 运行结果 |
|---|---:|---:|---:|---|
| **P-15B 16,960** | 21.2 ms | 81.5 ms | 355.1 ms | **搬运 44/44（100%）** |
| **Qwen3-8B 147,456** | 184.3 ms | **708.9 ms** | 355.1 ms | 域内搬、**跨域重算**（37 搬运 / 7 重算） |

阈值很清楚：搬运什么时候划算，取决于 `KV_bytes/带宽 < 本地重算时间`。同一张 0.26 GB/s 的跨域链路上，
**P-15B 的 16.56 KB/token 让"跨域搬运"始终成立，Qwen3-8B 的 147 KB/token 必须就地重算**——
这就是"KV 压缩打开存算协同空间"在路由器决策层面的量化版本（CPU 侧 `time = KV/BW` 与
`time = 重算` 的直接比较，不再依赖任何真机常数）。

**顺带发现的一个配置缺口**：域内（同节点）配对在配置里**没有 `intra_node_link_bw` 时**，
`pair_costs` 会给它 0 带宽 → 新模型自动退回旧常数（实测：44 条里 43 条走的是回退路径，
只有跨域的 1 条真正用了链路模型）。补上 `intra_node_link_bw: 1.0` + `intra_node_link_latency: 2000`
之后 44/44 全部走链路模型。**建议把这两个键写进所有 CASR 集群配置**，否则"域内搬运"这一支
永远在用真机常数定价。

**已落地**：`configs/cluster/casr_p15b_*.json`（6 份）都补上了这两个键，并加了一条配置守卫
（`ClusterConfigHygieneTests`，复制配置时漏掉就会红）。

### 6.16 这条轴在系统层面也成立：同算力/同链路，只换 KV 规模（2026-09-23）

负载：1250-token prompt、2→**8 rps 维持 30 s**→2 rps 共 260 请求；算力/服务时间/拓扑完全相同，
只有 `kv_bytes_per_token` 不同（新工具 `tests/run_route_arms.py` 跑 `load / cache_aware / casr_lp`）：

| KV/token | 臂 | 均值 | p95 | TTFT p50 | SLO 达标率 | 搬运比 |
|---|---|---:|---:|---:|---:|---:|

读法：

* **只把 KV 放大 8.7×，TTFT p50 从 148 涨到 221 ms（+49%）**——因为每请求 184 MB 的搬运
  （域内 1 GB/s 下 184 ms）直接进 TTFT，而 P-15B 的 21 MB 只要 21 ms。这就是"压缩 KV"
  在端到端指标上的直接体现，不需要任何跨域假设。
* 8 rps 这一档两种 KV 的 SLO 都还能达标（P-15B 100%；大 KV 下 `load` 100%、`casr_lp` 88%），
  所以差距体现在**延迟**而不是达标率；到了 30 rps 峰值档才变成达标率的差距（§6.6–6.12）。
* 放置：P-15B 下三个臂都把 260 个请求放在同域最快对（p4→d5），压缩 KV 让"就近"既快又便宜；
  大 KV 下 `load` 会自动摊到 p0/p2/p4 三处（每台 KV 池压力不同），说明**KV 体积已经在改变
  路由行为本身**。
