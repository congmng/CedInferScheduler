本文档固定两件事：**实验用经典数据集的原始来源与我们对它做的定制**，以及
**对比基线与近期 SOTA 系统的对应关系**。正式写作时以这里的 commit / revision
为准。

> ⚠️ **测试对象已切换（2026-09-18 决定）**：下面 §1–§6 里的 trace 都是用
> **Qwen3-8B 的 tokenizer 与 KV 体积（`147.5 KB/token`）**定制的，那批结果
> **保留为"KV 大档"对照**。接下来的主线实验（§0）改用**自研 P-15B**
> （`16.56 KB/token` bf16，比 Qwen3-8B 小 **8.9×**）作为测试对象，依据与口径

## 0. 测试对象：从 Qwen3-8B 切到自研 P-15B（2026-09-18 决定）

**换的理由**：我们所有调度结论的前提是"**KV 是绑定资源**"。而"存算协同什么时候
还值钱"恰恰由 KV 有多大决定，所以用一个 KV 大 9 倍的模型去论证 KV 不是大头时的
调度，逻辑不成立。已测过的 KV 档位是一条单调轴：

| 档位 | KV/token | CASR 相对 SOTA | 出处 |
|---|---:|---:|---|
| Qwen3-8B 全注意力 bf16（现状） | `147.5 KB` | 见 `实验结果汇总.md` §0 主表 | 本文档 §1–§6 的 trace |
| Qwen3-8B 全注意力 fp8 | `73.7 KB` | 基线快 `10–40%`，`casr_lp` 只动 `±2%` | `实验结果汇总.md` |
| 压缩 KV MLA | `31.1 KB` | **`−23.0%`**（优势明显收敛） | `实验结果汇总.md` §0 |
| **自研 P-15B（新增主线）** | **`16.56 KB`（bf16）/ `8.28`（fp8）** | **待测** | 本节的第 1 步 |

所以 P-15B 不是"再换一个模型"，而是把这条自变量轴**再往左推一档**——按已有的
趋势，CASR 的优势应当继续收敛，这正好回答"什么时候不再需要存算协同"。

**口径必须写清（否则数字不可比）**：

1. **算力是借的**：P-15B 的 draft config（`configs/model/DeepSeek/DSV4-P15B-draft.json`）
   里 `profile_model: Qwen/Qwen3-8B`——**FLOPs/延迟用 Qwen3-8B 的 kernel profile，
   只有 KV 几何来自 DSV4 设计**。所以这一轮只能回答"KV 缩小后调度还值多少"，
   不能回答绝对延迟与吞吐上限。
2. **KV 数字要说清是解析值还是实测值**：模拟器收的是解析下界 `16.56 KB/token`；
   vLLM 0.29 对同一套层结构实测 `97.6 KB/token`（差一个数量级，原因已归因，
   见 `DSV4_10-30B跨卡设计.md` §3.1.1，其中 `1.40×` 可自己修回来）。**这一轮要么
   显式声明"用理想 serving 栈的 KV 几何"，要么把解析值/实测值各跑一遍当自变量。**
3. **tokenizer 不变**：`Qwen/Qwen3-8B` 的 tokenizer 继续用，因此现有 trace
   **不需要重新生成**——变的只有 KV 体积与算力 profile 这两个量。

**落地方式**（两步）：

1. **模拟器（现在就能做）**：用 P-15B 的 config 在 4 个域上重跑
   `rr / load / cache_aware / casr / casr_lp` 对照，产出"KV 8.9× 更小后优势收敛
   多少"的曲线。
2. **真机（要先有模型）**：部署形态 **bf16 + 同机 TP=2**（14.87 GB/卡；
   单卡 24GB 放不下，见 `DSV4_10-30B跨卡设计.md` §4.1）。

## 2. 定制方法（可复现）

生成器：`LLMServingSim/workloads/generators/sharegpt.py`（子命令
`python -m workloads.generators sharegpt`）。它本身不是数据集，只是解析器 +
长度过滤 + 到达过程合成。

1. **会话切分**：每条会话按相邻的 `(human, gpt)` 配对切成轮次；第 `t` 轮的
   **输入是前 `t-1` 轮的完整上下文 + 本轮 human 文本**，输出是本轮 gpt 回复。
   这保留了真实对话的"长前缀 + 增量后缀"结构，也是前缀缓存能命中的原因。
2. **tokenizer**：`Qwen/Qwen3-8B`（与真实部署的模型一致），输入用
   `add_special_tokens=False`，得到与模拟器一致的 token 序列。
3. **长度过滤**：丢弃违反 `--min-input-toks` / `--max-input-toks` /
   `--min-output-toks` / `--max-output-toks` / `--max-kv-toks` 的轮次。
   真机受上下文和显存限制，我们把 `--max-input-toks` 压到部署的
   `max_model_len` 以内。
4. **到达过程**：`--sps` 指定每秒请求数，`_next_arrival_ns` 支持
   `poisson` / `uniform` / `burst`；真机回放按 trace 的
   `arrival_time_ns` open-loop 起请求。
5. **文本落盘（真机回放必需）**：加 `--emit-text` 后额外写
   `input_text = tok.decode(in_ids)`。模拟器只读 `input_tok_ids`，真机回放客户端
   （`tests/real_dataset_client.py`）读 `input_text`，两边因此是**同一条 trace**。

### 2.1 真机回放的额外取舍（必须声明）

- 真机客户端走 `/v1/completions` 传**裸 prompt**，不套 chat template，目的是让
  引擎 tokenize 出的序列与模拟器的 `add_special_tokens=False` 尽量一致。
  引擎仍可能加 BOS 等特殊 token，存在个位数 token 的差异。
- `--max-output-tokens` 会截断数据集的原始回复长度（ShareGPT 中位数约
  `638` token）。这是为了把真机单轮时长控制在可重复范围内；截断长度在实验记录
  里固定写出。**这是最大的偏离项**：真实 ShareGPT decode 负载比本实验重得多。
- ShareGPT 原数据不含会话级时间戳，到达时间全部是合成的（Poisson）。

### 2.2 本轮真机 ShareGPT trace 的精确参数
- 产物：`LLMServingSim/workloads/sharegpt-real-qwen3-8b-600-sps14.jsonl`
  （600 请求，44.1 s，Poisson `sps=14`）。
- 生成命令：

```bash
cd LLMServingSim
python3 -m workloads.generators sharegpt \
  --model /home/ubuntu/srz/ced_inference_scheduler/data/Qwen3-8B-tokenizer \
  --source /home/ubuntu/srz/ced_inference_scheduler/data/sharegpt_gpt4/sharegpt_gpt4.jsonl \
  --num-reqs 600 --sps 14 --seed 42 \
  --min-input-toks 512 --max-input-toks 2048 \
  --min-output-toks 0 --max-output-toks 2048 \
  --max-kv-toks 4096 --max-sessions 4000 --emit-text \
  --output workloads/sharegpt-real-qwen3-8b-600-sps14.jsonl
```

- 统计：输入 token `mean 971 / median 845 / p95 1863 / max 2040`；输出 token
  `mean 423 / median 413 / max 1413`（真机回放时被 `--max-output-tokens 16` 截断）。
- 真机部署 `MAX_MODEL_LEN=4096`，因此 `2048` 输入上限留够了余量。
- 已验证：真机回放 5 条，`usage.prompt_tokens` 与 trace 的 `input_toks`
  逐一相等（`1949/606/842/912/701`），说明真机 tokenize 与模拟器一致。

### 2.3 两个定制档：wide（弱复用）与 deep（强复用）

ShareGPT 的会话长度有限，**同一份数据集按不同方式取样会得到完全不同的
前缀复用强度**，而前缀复用正是本项目要考察的轴。因此固定两个档位：

| 档 | 取样方式 | 请求数 | 前缀桶数 | 桶复用 | 产物 md5 |
|---|---|---:|---:|---:|---|
| wide | `--max-sessions 4000`（跨会话取样） | 600 | 460 | `1.30` | `51a00cb6224b928094b529c8c9e980f5` |
| deep | `--max-sessions 200`（会话内多轮） | 356 | 124 | `2.87` | `a3ff202f474f34f46ac4874b83eb2a65` |

（"前缀桶"= `sha256(prompt[:512])` 前 16 位，与 router `classify()` 的口径一致；
桶复用 = 请求数 / 桶数。**class** 数还会按输入长度桶细分，所以 class 复用比
桶复用低——多轮对话长度递增会换 class，这一点在 §4.7 讨论。）

deep 档的生成命令（`workloads/sharegpt-deep-real-qwen3-8b-356-sps14.jsonl`）：

```bash
cd LLMServingSim
python3 -m workloads.generators sharegpt \
  --model /home/ubuntu/srz/ced_inference_scheduler/data/Qwen3-8B-tokenizer \
  --source /home/ubuntu/srz/ced_inference_scheduler/data/sharegpt_gpt4/sharegpt_gpt4.jsonl \
  --num-reqs 600 --sps 14 --seed 42 --max-sessions 200 \
  --min-input-toks 512 --max-input-toks 2048 \
  --min-output-toks 0 --max-output-toks 2048 --max-kv-toks 4096 \
  --emit-text --slo-ttft-ms 500 --slo-tpot-ms 50 \
  --output workloads/sharegpt-deep-real-qwen3-8b-356-sps14.jsonl
```

注意两点：(a) `--max-sessions 200` 把可用轮次限制住了，实际只写出 **356** 条
（文件名如实标注），不是 600；(b) 该文件由 `transformers 5.17.0` 生成，
与 wide 档（锁定的旧 tokenizer 运行时）不是同一版本，**两档之间不做 token 级对比**，
只做"同一档内各策略之间"的对比。

### 2.4 可复现性核验（2026-09-11 复核）

- 原始文件：`data/sharegpt_gpt4/sharegpt_gpt4.jsonl`，`96161473` 字节，
  md5 `e7c90069c89144620fe265843fc4e750`（与上面锁定的 revision 一致；
  下载脚本落在 `data/sharegpt_gpt4/fetch_sharegpt.sh`）。
- trace：`LLMServingSim/workloads/sharegpt-real-qwen3-8b-600-sps14.jsonl`，
  md5 `51a00cb6224b928094b529c8c9e980f5`。
- 用 2.2 节的命令原样重跑一遍（在**当时的环境**里，输出到临时路径），得到
  **逐字节相同**的文件（`cmp` 无差异、md5 相同）。
- **但这条可复现性依赖 tokenizer 运行时版本，不是纯数据决定的。** 2026-09-12
  在缺少 `transformers` 的环境里装回 `transformers 5.17.0` 后重跑同一条命令，
  出现了 **405/600 行不同**：同样文本的 token 数变了，于是
  `--min-input-toks 512 / --max-input-toks 2048` 的长度过滤选中了不同的轮次，
  序列整体错位（`input_tok_ids` 405 行不同，而 `arrival_time_ns` 全部相同）。
  也就是说：**`transformers`/`tokenizers` 必须与生成时锁定同一版本**，
  否则"同一命令"复现不出同一 trace。
- 因此本项目的处理是：**以仓库内的 trace 文件为唯一制品**（记 md5），
  需要加字段时对现有 trace 做**纯增量标注**而不是重新生成。
  例如带 SLO 的版本
  `LLMServingSim/workloads/sharegpt-real-qwen3-8b-600-sps14-slo500-50.jsonl`
  （md5 `523b4d4553fa2ad52bb5ea63f43d0130`）就是把每一行加上
  `slo_ttft_ms=500`、`slo_tpot_ms=50` 得到的；**剥掉这两个字段后与原 trace
  逐行完全一致**（已用脚本断言），所以跑在不同 trace 上的结果仍可直接比较。
- 另一个记录在案的坑：解析 trace 时不能用 `str.splitlines()`——prompt 文本里
  可能含 `U+2028/U+2029` 之类的分隔符，会把一行 JSON 拆断。要用 `split("\n")`。
- 注意：真机回放时还会叠加 `--max-output-tokens 16` 的**运行时截断**
  （`tests/real_dataset_client.py`），trace 文件本身仍保留数据集的原始
  `output_tok_ids`；论文里应把这一项写成"回放客户端截断"而不是"数据定制"。

## 3. 对比基线与近期 SOTA 的对应关系

所有策略都在**同一拓扑、同一 trace、同一批 P/D 容器**上运行；每个策略开跑前
重启 P/D 以清空缓存状态。

| 策略（`--policy`） | 对应系统 / 论文 | 在本文中复现的部分 | 说明 |
|---|---|---|---|
| `rr` | 经典 round-robin | Prefill/Decode 轮询 | 隔离基线，衡量"完全不管缓存与队列"的代价 |
| `load` | vLLM 生产栈的 least-loaded / shortest-queue | 按 `inflight / capacity` 选最空实例 | 经典负载均衡基线 |
| `cache_aware` | **SGLang Router** 的 `cache_aware` 策略；vLLM production-stack 的 prefix-aware router | 最长前缀命中优先，命中实例超过利用率阈值后溢出到最空实例 | 近期 SOTA **路由**基线 |
| `casr`（启发式） | CASR 的快速层近似 | 前缀钉住 + 异构/网络感知的 Decode 代价 | 我们的启发式对照 |
| `casr_lp` | CASR 完整设计 | 慢环 LP `f_ijk`（缓存算力 + 链路字节预算 + 拥塞）+ 快速层 deficit 重放 | 我们的方法 |
| `casr_full` | CASR + 结构弹性 | 在 `casr_lp` 上叠加 `+P/-P` 容器生命周期 | 结构层，当前负载下是否触发取决于瓶颈 |

需要明确区分的"近期 SOTA"边界（避免笼统宣称性能优于所有系统）：

- **DistServe / Splitwise** 解决的是 P/D 解耦后的**资源配比与放置**，本身不做
  请求级缓存亲和路由；我们复现的是它们隐含的"固定 P/D 比例 + 静态放置"设定，
  即 `rr` / `load` 这类不感知前缀状态的基线。
- **Mooncake / NIXL / LMCache** 解决 **KV 的存取与传输路径**；在本实验里它们
  是被复用的传输层，不是被比较对象。
- **Llumnix / Dynamo** 是完整的调度与编排系统；我们复现的是其
  "按队列/利用率做负载均衡"的调度语义（`load`）。
- **SGLang** 的缓存感知路由是我们在**路由层**最直接的 SOTA 对照，因此单独实现
  为 `cache_aware`。

正式论文写作时应固定上述系统的仓库 commit 与论文版本；本表按"问题边界"对齐，
而不是声称复现了对方的完整代码路径。

## 4. SLO 口径（算法与真机实验共用）

### 4.1 选定的应用级 SLO

| 指标 | 阈值 | 含义 |
|---|---|---|
| TTFT | `≤ 500 ms` | 客户端可见的首 token 时间（含 Prefill 计算、KV 跨域传输、Decode 排队） |
| TPOT | `≤ 50 ms` | 首 token 之后的每 token 时间，约等于 `≥ 20 token/s` 的持续生成速率 |

这两个值是**应用级假设**，不是从某一轮实验结果里挑出来的。它可以直接引用
公开基准：MLPerf Inference 的 Llama2-70B **interactive** 类别规定
`ttft <= 450 ms`、`tpot <= 40 ms`（[`mlcommons/inference` 的
`language/llama2-70b/README.md`](https://github.com/mlcommons/inference/blob/master/language/llama2-70b/README.md)）。
本实验取 `500 / 50 ms` 是它的同量级放宽版：我们跑的是 Qwen3-8B 单卡实例、
16 输出 token 的短回复，直接套 70B 基准的严格档会过于苛刻。

真机实测（3 域、
600 请求、`3.5 req/s`、流式客户端）给出的分布是：

| 策略 | TTFT P50 / P95 | TPOT P50 / P95 |
|---|---|---|
| `cache_aware`（SGLang 风格路由） | `331.7 / 666.8 ms` | `46.7 / 60.2 ms` |
| `casr_lp`（本文） | `237.8 / 499.4 ms` | `14.9 / 18.6 ms` |

即 `500/50` 落在两条策略之间：既不是"所有策略都达标"，也不是"所有策略都不达标"，
因此有区分度。为免除"阈值是挑出来的"这一质疑，所有 SLO 结论**必须同时给出
阈值网格**（`TTFT ∈ {250, 500, 1000} ms × TPOT ∈ {25, 50} ms`），
复现命令见 4.4。

### 4.2 算法侧：SLO 如何进入调度

`serving/casr/flow_solver.py` 按设计文档 `c_ijk` 的结构做一阶 TTFT 预测：

```
predicted_ttft_ms = distance + rtt + kv_bytes / bw          # 链路
                  + prefill_service_ms × work_ratio          # Prefill 只算未命中部分
                  + decode_service_ms × queued_fraction      # Decode 排队（不是整段生成）
```

若某 `(class, prefill, decode)` 三元组的预测 TTFT 超过 `ttft_slo_ms`，就在它的
单位代价上加 `slo_penalty`（`p_slo`）——**加有限大惩罚而不是把 pair 删掉**：
当所有可行 pair 都超 SLO（容量不足）时求解器仍必须给出计划，但只要存在达标
pair 就会优先选它。判定结果通过 `diagnostics.slo_violating_pairs` 暴露，
真机 `/routing-state` 可直接审计。

该预测是**一阶模型**，只用于"这个 pair 是否越线"的二值判断，不代表精确延迟；
它用的是实测 service time，而不是排队论公式。`ttft_slo_ms=0` 表示关闭该项，
即此前所有轮次的行为。

### 4.3 真机侧：SLO 怎么被约束和统计

- 客户端 `tests/real_dataset_client.py --stream` 走 SSE，逐请求记录
  `ttft_ms` 与 `tpot_ms`；非流式请求**测不到 TTFT**，因此不参与 SLO 判定。
- router 把 `ttft_ms / tpot_ms / completion_tokens` 写进
  `metrics-<policy>.jsonl`（流式路径此前根本不写 metrics，属已修缺陷）。
- `tests/aggregate_real_comparison.py --slo-ttft-ms 500 --slo-tpot-ms 50`
  输出 SLO attainment、goodput，并可用 `--slo-grid-ttft/--slo-grid-tpot` 出网格。
- **没有**在服务端按 SLO 拒绝请求：SLO 影响的是路由/结构决策，
  请求失败仍然只由 `request-timeout-s`（客户端）与 `downstream_s`
  （router）这两个故障保护决定。

### 4.4 复现


### 4.5 必须声明的偏差

`47–51 s` 那批 LMCache/NIXL 传输毛刺**每一条都必然违反任何合理 SLO**，
且它们不落在同一策略上。因此 SLO attainment 必须与"毛刺数"一起报告
（聚合器的 `glitch_count`），否则排名会随毛刺落点摆动；这也是本报告同时保留
截尾均值的原因。

### 4.6 数据集侧现状：**没有任何数据集承载 SLO**

这一条要写清楚，避免评审误以为 SLO 来自数据：

| 环节 | 现状 |
|---|---|
| trace 字段 | 只有 `arrival_time_ns / input_text / input_tok_ids / input_toks / output_tok_ids / output_toks`，**没有 `slo_*` 或 deadline 字段** |
| 源数据集 | ShareGPT 只有对话文本，**没有时间戳、更没有延迟要求**；到达过程是我们合成的 Poisson |
| 生成器 | `workloads/generators/sharegpt.py` 没有 SLO 相关参数 |
| 算法 | `class_ttft_slo_ms`（按 class 的 SLO）已实现，但**没有数据源能填充它** |

其中最后一条值得展开：设计文档写的是"class SLO"和"高优先级 class 的 SLO 风险"，
但本实验的 class 是由 `(model, prompt 前缀 hash, 输入长度桶, 输出长度桶)`
自动派生的，反映的是**缓存亲和**而不是业务优先级。所以要真正做到
"按业务等级设 SLO"，需要额外引入一条数据通路：

1. trace/生成器增加 `slo_ttft_ms` / `slo_tpot_ms`（请求级）或
   `priority` / `slo_class`（等级级）；
2. 回放客户端逐请求读取，并把它带进 SLO 判定与 attainment 统计；
3. 求解器从 trace 的等级分布构造 `class_ttft_slo_ms`，而不是用单一全局阈值。

公开可用的对话数据集（ShareGPT、LMSYS-Chat-1M、BurstGPT 等）都只提供
**prompt / 到达时间**，不提供延迟要求；明确带延迟约束的公开来源目前是
**基准规范**（如上面的 MLPerf interactive 档）而不是数据集。因此本实验的
合理口径是"数据集提供负载形状，基准规范提供 SLO 量级，实测提供标定"，
三者分开引用。

> `class_ttft_slo_ms` 这个字段，**但没有数据源填充它**；现在 trace → 模拟器 →
> 求解器的通路是完整的（见 §4.8），并且把 `casr_*` 系列 trace 补上了 SLO
> 标注（`tests/annotate_trace_slo.py`，只改这两个字段，到达时间与 token 逐字不变，
> 因此与已记录的实验仍然可比）。

### 4.8 模拟器侧 SLO 通路（2026-09-23 补齐）

真机侧的链路（§4.7）本来就是通的；**模拟器侧此前根本没读 trace 的 SLO 字段**，
所以 `p_slo` 在仿真实验里是死代码。现在补齐为：

| 环节 | 行为 | 位置 |
|---|---|---|
| trace | 行内 `slo_ttft_ms` / `slo_tpot_ms`；CLI `--slo-ttft-ms/--slo-tpot-ms` 兜底 | `workloads/generators/casr.py`（新增参数）、`tests/annotate_trace_slo.py`（给已有 trace 增量标注） |
| 路由 | 行优先、CLI 次之；写进请求对象 | `serving/core/router.py` `load_requests/_load_flat_request` |
| 类 | 每个 class 保留**最紧**的界（与真机 router 同规则） | `serving/casr/prefix_profiler.py` `assign()` / `snapshot()["class_slo"]` |
| 求解器 | 每个 tick 把 class 界发布进 `class_ttft_slo_ms`，覆盖全局 `ttft_slo_ms` | `serving/casr/controller.py` + `flow_solver.apply_slo_overrides()` |
| 产出 | 逐请求 CSV 追加 `slo_ttft_ms` / `slo_tpot_ms` / `slo_ok`（无预算则留空，不写"通过"） | `serving/core/scheduler.py` |
| 汇总 | `tests/compare_casr.py` 打印 `slo_attainment` | 同上 |

**开关与消融**：`configs/cluster/casr_p15b_three_domain_slo.json`（`ttft_slo_ms=500`、
`slo_penalty=10`）是定价版，原版是不定价版；同一份 trace 跑两个配置即可分离
"测量"与"定价"。

### 4.7 请求级 SLO 的数据通路（已实现）

为了让 SLO 将来能真正由数据集驱动，这条链路已经打通并可验证：

| 环节 | 行为 |
|---|---|
| trace | 可携带请求级 `slo_ttft_ms` / `slo_tpot_ms`（生成器 `--slo-ttft-ms/--slo-tpot-ms`；也支持对已有 trace 做纯增量标注） |
| 客户端 | `row_slo()`：**trace 行优先，CLI 兜底**；通过 `X-SLO-TTFT-MS` / `X-SLO-TPOT-MS` 头随请求下发 |
| router | `request_slo()` 读取请求头，把 `slo_ttft_ms/slo_tpot_ms/slo_ok` 写进 `metrics-<policy>.jsonl`；非流式请求测不到 TTFT，`slo_ok` 记 `null`（未测量）而不是"通过" |
| 聚合器 | `row_slo_satisfied()`：**优先用请求级判定**，没有判定才回退到 CLI 阈值；summary 里标 `slo.source = per-request / cli` |

冒烟验证（12 请求、trace 标注 500/50）：metrics 里出现
`"slo_ttft_ms": 500.0, "slo_tpot_ms": 50.0, "slo_ok": true/false`，
聚合器输出 `slo% = 91.7`，说明一条超 TTFT 的请求被正确判为违约。

**按 class 的 SLO 也已接通**（2026-09-12）：router 在
`controller.observe(..., slo_ttft_ms=...)` 时把该请求的预算一并上报，控制面按
class 保留**最紧的那个界**，每个 tick 把它发布进共享求解器配置
（`class_ttft_slo_ms`），并通过 `/routing-state` 的 `class_slo`
（`{classes, tightest_ms}`）暴露。这样"交互类 ≤ 250 ms、批处理类 ≤ 800 ms"
这类**分级预算**可以直接由 trace 驱动，而不是只能给一个全局阈值。

配套的 A/B 开关：客户端 `--ignore-trace-slo`（完全不带 SLO）与
router 侧 `SLO_PENALTY=0`（仍然测量但不参与目标函数），用来把
"测量"和"算法使用"分开消融。

## 6. 第三个数据集：CNN/DailyMail（长上下文）

### 6.1 为什么加它

前两个数据集都没压到**跨域 KV 链路预算**：Dolly 的 prompt 均值只有 `193`
token（约 `28 MB` KV），ShareGPT wide 约 `971` token，而 PD 链路的实测预算
是"`2048` token 前缀约 `37 ms`，折合约 `6.6 req/s`（按 75.5 MB 计）"。
CNN/DailyMail 的文章均值 `1250` token ⇒ **每请求 KV 约 `184 MB`**，
在 `16 Gbps` 链路上单个跨域对只能承载约 `10–11 req/s`。
这正好把问题推到"链路是瓶颈"的区间：谁的 router 把长 prompt 溢到跨域 Decode，
谁就会把链路打满；谁把长 prompt 留在本地，谁就不会。

### 6.2 来源与定制

| 项 | 值 |
|---|---|
| 来源 | `abisee/cnn_dailymail`（HuggingFace datasets，`3.0.0` 的 `validation` 分片） |
| 许可 | Apache-2.0 |
| 文件 | `data/cnn_dailymail/validation.parquet`，`34664725` 字节，md5 `b5aad2f862572f36ea35fbb22b249795` |
| 生成器 | `LLMServingSim/workloads/generators/cnndm.py`（本次新增） |
| 产物 | `workloads/cnndm-real-qwen3-8b-600-sps14.jsonl` 见下方命令 |

**为什么读 Parquet 而不是走 HF 的加载脚本**：`ccdv/cnn_dailymail` 与
旧版 `abisee/cnn_dailymail` 的 loading script 依赖 `cs.nyu.edu` 的原始
story 压缩包，该地址长期不可用；`abisee` 仓库的 `3.0.0` 分片已直接提供
Parquet，所以生成器只读 Parquet（本地文件优先，HF id 兜底）。

定制方法（同样只有三件事，不改写文本）：

1. **prompt 组装**：输入 = 文章 `article`，输出 = 摘要 `highlights`。
2. **头部截断**：`--head-toks 2047` 只保留文章前 2047 个 token。
   这是本生成器**唯一**的文本改动，作用是让所有请求都落在部署的
   `max_model_len 4096` 以内，同时保持"长前缀 + 唯一内容"的形状；
   截断后的 prompt 仍是原文的合法前缀，不是拼接或改写。
3. **长度过滤 + 到达过程**：`--min-input-toks 900 --max-input-toks 2047`、
   `--max-output-toks 64`、`--max-kv-toks 2100`；`--sps 14` 的 Poisson 到达，
   `seed=42`；`--emit-text` 供真机回放；请求级 SLO 写 `TTFT ≤ 500 ms`、

   `source_id`（数据集 `id` 列，可回溯到具体文章）。

### 6.6 同档位的反向结果：过载时 CASR 输给最朴素的 load 基线

同一份峰值 trace 上，`static`（`--no-enable-casr`，即 least-loaded 路由）的
E2E 均值 **9 800 ms**、p95 **18 821 ms**、达标率 4.6%，而 CASR 两臂分别是
17 764–26 103 ms、73–104 s、8.4–27.4%。**"CASR 一定更好"在这一档不成立。**

机制（逐请求落点）：

| 臂 | 落点分布（prefill / decode） | p50 | p95 |
|---|---|---:|---:|
| static | p4 965 / p2 562 / p0 373；**decode 全在 d5090** | 9 472 ms | 18 821 ms |
| casr greedy | p0 768 / p4 713 / p2 419；decode d5090 1371、**d4090 411、d3090 118** | **2 965 ms** | **96 655 ms** |
| casr lp | p4 831 / p0 680 / p2 389；decode d5090 1601、d4090 216、d3090 216/83 | 8 041 ms | 78 149 ms |

也就是：**静态基线把全部 1900 个请求钉在最快的 d5090 上**；CASR 按容量/亲和把它们
摊到三张 decode 上，p50 明显更好（缓存命中 + 分摊），但 20–30% 的请求落到慢 2–3× 的
decode 上排队，**尾部直接崩掉**。这**不是 2026-09-23 这次改动引入的**：把 trace 的
SLO 字段删掉重跑（等价于改动前行为），数字与"有字段但不定价"逐位相同。

结论与下一步：目标函数目前按**服务时间**定价，而饱和档的尾延迟由**慢实例上的排队**决定；
`p_slo`（有限罚）和 `queue_weight`（本仿真配置里长期为 0、真机为 1.0）都只是权宜。
要把这一档救回来，需要在目标里显式给"慢 Decode 的排队"定价（或对 Decode 做
deadline-aware 的准入），而不是继续调 `overflow_penalty` 这类旋钮。

### 6.7 按 6.6 的建议做的两个杠杆，以及它们**都没有**修好这一档（2026-09-23）

按 6.6 的建议实现了两个杠杆，都在峰值档（1900 请求、1250 token、30 rps×60 s）上验证：

| 杠杆 | 实现 | 结果 | 判读 |
|---|---|---|---|
| **目标项：Decode 尾风险定价** | 新增 `tail_weight`：把 `queue_weight` 无量纲的队列占比换成**时间**——`queue_fraction × 本实例步时 × 输出长度系数`，单位秒，与 `c_ijk` 其余项一致 | `tail_weight` 0→5：p50 **6 395 → 5 283 ms（−17%）**，但均值 17 648 → 20 861、p95 73 423 → 84 141（**更差**）；慢 Decode 的流量反而从 146 增到 181 | 它对"均值"有效、对"尾"无效：饱和时把流量从"深队列的快卡"推走，正好推到慢卡上 |
| **router：deadline-aware Decode 选择** | 新增 `deadline_aware_decode`：fallback 不再按"最不忙"，而是按**预计排空时间**（同为 `queue_fraction × 步时`）挑，并优先满足请求预算 | 均值 17 648 → 19 298 ms、达标率 10.5% → **7.7%**、慢 Decode 流量 146 → 288 | 同样把流量推向慢卡：容量归一化的"最不忙"判据其实**已经**隐含了"慢卡更贵" |

两个杠杆都保留在代码里、**默认关闭**（`tail_weight=0` / `deadline_aware_decode=false`），
扫描工具 `tests/sweep_tail_weight.py` 可复现上表。

### 6.8 根因：慢实例上的"类级 straggler 队列"，不是某个 per-pair 价格能修的

把最慢的 100 个请求与最快的 100 个请求拉出来看（SLO+queue 定价臂）：

```text
最慢 100（p50 79 894 ms，其中 99% 是排队）：到达时间集中在 64.1–78.5 s，
         prefill 100/100 落在 p0（RTX3090，884 ms/请求，是 5090 的 3 倍）
最快 100（p50 948 ms）：prefill 85 个在 p4（5090）、14 个在 p2（4090）
```

随后做的三组"排除/集中"实验（同一档、同一臂）：

| 变体 | p50 | p95 | 达标率 |
|---|---:|---:|---:|
| 对照（SLO+queue 定价） | 6 395 ms | 73 263 ms | 10.5% |
| 排除最慢 **Decode**（d1 容量→0.01） | 6 643 ms | 76 159 ms | 8.2% |
| 排除最慢 **Prefill**（p0 容量→0.01） | **4 412 ms** | 87 044 ms | **14.1%** |
| **Decode 全部集中到 d5** | 6 594 ms | **91 016 ms** | 9.5% |
| 基线：`static`（least-loaded，decode 全在 d5） | 9 472 ms | **18 821 ms** | 4.6% |

也就是说：**每去掉一个慢实例，落后队列只是挪到下一个最慢的**；而 least-loaded 基线用
"全部集中在最快队列"换到了 4 倍的尾部（p95 18.8 s vs 73–91 s），代价是中位数差一倍。
30 rps 相对 26 req/s 的 Decode 池是 **2.7× 过载**，这个区间没有放置策略能满足 300 ms
SLO（全臂达标率 4.6–14.1%），差异全在**均值 vs 尾部**的取舍上。

**下一步该做的不是再加一个 per-pair 价格，而是二选一**：

1. **准入/削峰**：预测排空时间超过预算时，在路由端排队/拒绝而不是派发（把过载挡在池外）；
2. **改目标为 min-max**：对最大实例利用率 `z ≥ load_i/K_i` 定价（LP 里就是一个辅助变量），
   让"谁最慢谁最堵"直接进目标，而不是靠 Σ 溢出——这才是"尾风险"的正确形式。

### 6.9 min-max（及其求和版）实现了，但**也不是**这一档的答案（2026-09-23）

按 §6.8 的第 2 条实现并验证：

| 新目标项 | 定义 | 峰值档结果（对照：均值 17 648 / p50 6 395 / p95 73 423 / 达标 10.5%） |
|---|---|---|
| `max_utilization_weight`（min-max） | 辅助变量 `z ≥ (load_i/K_i) × step_i`，对 `z` 定价；用 `step_i` 加权是因为纯利用率会被"把负载摊到慢卡"最小化 | w=20 最好：均值 **16 711**、p50 5 686、p95 **65 018**、达标 9.3%；w=5 反而更差（19 553/78 298），非单调 |
| `backlog_weight`（同量的求和版） | `Σ_i (load_i/K_i) × step_i`，每个流一个线性系数 | w=5：均值 18 503、p50 5 126、p95 77 490、达标 10.6%；把 3090 Decode 的流量从 146 清到 **4**，但尾部不动 |

**min-max 为什么几乎不起作用**：`z` 只约束**最差的那一台**。实测该 tick 上最差的是
Decode（util 1.76 × 0.278 s = 0.49 s/s），而真正制造 straggler 的 RTX3090 Prefill
只有 0.32 s/s —— **它永远进不了 `z`**，所以 p0 队列在任何权重（0/5/20/100）下都原样保留。
求和版能把它算进去，也确实清掉了慢 Decode，但尾部仍未改善。

### 6.10 真正的根因：**峰值期间结构控制器在换机**

把峰值臂的状态机轨迹拉出来（`casr-state-*.jsonl` 的 `instances[*].admission_state`）：

```text
tick 200（峰值中段，约 70 req/s）：
   p0(3090) ACTIVE   p2(4090) WARMING   p4(5090) DRAINING
   —— 全部流量因此落在最慢的 p0 上

全程统计（1900 请求、30 rps 峰值）：
   状态切换 58–60 次；实例-tick 中 DRAINING 483–621、WARMING 69–78
```

也就是说：**弹性机制在过载期间仍然执行 `-P`/`+P`**（把最快的 p4 排空、同时预热 p2），
于是"当前唯一完全可用的 Prefill"会周期性地变成最慢的那台，落在它上面的类就排成长队——
这正是 6.6 里那 100 个 79.9 s 请求的来历。四个目标函数杠杆（尾风险、deadline 选择、
min-max、Σ 积压）都动不了它，因为它们都只在"已经确定可用实例集合"之后才起作用。

**下一步**：修**结构门控**，而不是再加目标项——

1. 池子处于饱和（`offered > Σ 可用容量` 或存在 backlog）时禁止 `-P`，
   或要求被排空实例上没有任何带未完成需求的类；
2. `-P` 的候选必须先把它的类重新安置（迁移预算是"冷 Prefill"），否则保留；
3. 峰值期间 `+P` 只在**预测式**通道触发（`prescale_utilization`），避免"排空 + 预热"同时发生。

### 6.11 结构门控按这三条改完了，真正的 bug 在**调用顺序**（2026-09-23）

三条门控都实现了（`serving/casr/evaluator.py`，默认开启，可在 `structural` 里关掉做 A/B）：

| 门控 | 实现 | 是否作用于这一档 |
|---|---|---|
| 1. 饱和时禁止 `-P` | 反事实解完后检查**剩余池子**的 `prefill_overflow`，> `overflow_epsilon` 就不排空 | ❌ 不作用——评估器本次运行 **一次 `-P` 都没发**（决策只有 23 次 `+P`） |
| 2. 仍持有需求的实例不许排空 | 按 `arrival_rate_ewma > 0` 统计每台 Prefill 上的类需求 | ❌ 同上 |
| 3. 有实例在 WARMING/DRAINING 时不再叠加结构编辑 | 在候选生成后、选优之前拦截 | ⚠️ 生效但影响有限（18 085 vs 17 648 ms 均值） |

**门控没有作用，是因为抖动根本不是评估器发出的**——把状态机轨迹按来源拆开看：

```text
结构决策分布:  {'keep': 1484, '+P': 23}        ← 没有 -P
实例状态分布:  DRAINING 621 个实例-tick、WARMING 69
```

真正的排空来自 `PrefillLifecycle` 的**按需调容**，而它的调用顺序是错的：

```python
# 修复前（controller.build_plan）
self.last_lifecycle = self.lifecycle.update(current_ns, snapshot["prefix_states"], …)
…
self._sample_backlog(current_ns, prefill)      # ← 需求回收在 lifecycle 之后
self._inflate_demand(snapshot["prefix_states"])
```

`lifecycle` 的 `desired = ceil(demand / capacity)` 读的是 `arrival_rate_ewma`，而**过载时这个值
反映的是"已经服务出去的速率"**（背压把到达压住了）。于是：负载越高 → 观测到达率越低 →
`desired` 越小 → **排空最快的 worker** → 剩下最慢的 Prefill 承接全部流量。这就是 §6.10 里
tick 200 那一幕，也是 80 s 排队队列的来源。

**修复（两处）**：

1. 把 `_sample_backlog` + `_inflate_demand` 提到 `lifecycle.update` **之前**（需求先修正，再调容）；
2. `lifecycle.update(..., backlog_rps=...)`，新增 `hold_on_backlog`（默认开）：**有积压时只许扩、
   不许缩**（上限仍受 `max_active_prefill` 约束）。

**同一峰值档的 A/B（LP 臂）**：

| 臂 | 均值 | p50 | p95 | SLO 达标率 | 状态切换次数 |
|---|---:|---:|---:|---:|---:|
| 基线 `static`（least-loaded） | 9 800 | 9 472 | 18 821 | 4.6% | — |
| CASR 修复前 | 17 648 | 6 395 | 73 423 | 10.5% | 58 |
| **CASR + 顺序修复** | 27 609 | 25 467 | **63 524** | **17.3%** | **6** |
| CASR + 修复 + 把最慢 Prefill 定价出池 | 20 247 | 16 188 | 62 871 | 13.2% | 22 |

**结论**：修复把抖动从 **58 次降到 6 次**，尾部与达标率都变好（p95 −14%、达标率 10.5% → **17.3%**，
是这一档所有臂里最高的，基线只有 4.6%），代价是**中位数变差**（6.4 s → 25.5 s）——池子稳定后
慢实例不再被"换走"而是持续分担，中位数因此被拉平。轻载档（80 请求）只付 **+1.6%/+2.9%**
延迟、达标率不变（100%）。

也就是说：这一档**没有免费的午餐**——尾部和均值由"是否让慢实例参与"决定，而 30 rps 对
26 req/s 的 Decode 池本来就是 2.7× 过载。要同时拿到中位数和尾部，只能**加容量或削峰**，
不是再调策略。

### 6.12 (a) 削峰/准入 与 (b) 补容量，两条都试了（2026-09-23）

**(a) 准入（闭环入口）**：模拟器本身有闭环入口 `--client-concurrency`（客户端把请求**留在入口**，
只有池子空出槽位才提交，因此"等待被接纳"的时间不计入请求延迟）。同一峰值档：

| 臂 | 均值 | p50 | p95 | SLO 达标率 | 送达跨度 |
|---|---:|---:|---:|---:|---:|
| 基线 `static`（开环） | 9 800 | 9 472 | 18 821 | 4.6% | 109 s |
| CASR 修复后（开环） | 27 609 | 25 467 | 63 524 | 17.3% | 142.6 s |
| **CASR + 准入 cc=16** | **1 480** | 1 481 | **1 859** | **83.9%** | **189 s** |
| CASR + 准入 cc=32 | 2 006 | 1 953 | 2 698 | 60.5% | 132.9 s |

**这是唯一真正解决 SLO 的杠杆**：均值从 27.6 s 掉到 1.48 s、达标率 17.3% → **83.9%**。
代价写在同一张表里：**同样 1900 个请求的送达跨度从 109 s 拉到 189 s**（吞吐降约 43%）。
准入不创造容量，它只是把"无界排队"换成"有界延迟 + 更长的送达时间"——**报这组数字必须同时报
跨度/吞吐，否则等于用丢负载换指标**。

**(b) 补容量**：三种补法，都在同一峰值档上跑：

| 补法 | 基线均值 | CASR 均值 | CASR 达标率 |
|---|---:|---:|---:|
| 对照（现状） | 9 800 | 27 609 | 17.3% |
| 三个 Prefill 全部常驻（`min=max=3, scale_on_demand=false`） | — | 31 349 | 15.1% |
| **每个域再加一个 Decode**（解码池 26.3 → 52.6 req/s） | 12 312（更差） | 20 871（更好） | 4.8% |
| 容量改用 **bundle 反推值**（`capacity_from_profile: true`） | — | 31 042 | 13.9% |

**没有一种补容量能把 CASR 拉到基线水平**，而且"加 Decode"反而让**基线也变差**（9.8 → 12.3 s）——
因为仿真运行时**根本不是在 Decode 上受限**。

### 6.13 顺带查出的口径坑：仿真运行时用的**不是** profile 容量

`serving/__main__.py` 只在配置写了 `capacity_from_profile: true` 时才调用
`rescale_capacities`；默认路径下：

| 角色 | 运行时容量 | 来源 |
|---|---|---|
| Prefill | **每 tick 被 egress 上界覆盖**（≈70 req/s/生产者） | `controller._egress_bound_prefill_capacity` |
| Decode | **部署占位值 110 / 170 / 230 req/s**（合计 510） | 集群 JSON，没人覆盖 |

而 P-15B 的 bundle 反推值是 prefill 29/61/89、**decode 4.5/9.3/12.5（合计 26.3）**。
也就是说：**仿真里 Decode 的约束被高估了 ~19×**，任何"Decode 是不是瓶颈"的结论在默认配置下
都不成立（§6.1 那张 decode 溢出的表是离线 probe 用反推容量算的，不是运行时行为）。

建议：把 `capacity_from_profile` 设为默认开启或至少在 CASR 配置里显式打开，
并在 `meta`/日志里每次打印实际使用的容量——否则"容量口径"会像这次一样在事后才被发现。

### 6.15 搬运定价改为从链路模型推导，并用它验证"压缩 KV 让搬运划算"（2026-09-23）

**改法**（`serving/core/router.py`）：`kv_exchange_decision` 不再默认使用真机实测常数，
而是从**本集群自己的数**算两边：

```text
transfer_ms = tokens × kv_bytes_per_token / pair_bandwidth(p,d) × 1000 + rtt(p,d)
local_ms    = 该 Decode 所在节点上同域 Prefill 的 service_ms × max(1, tokens / 1024)   # 与 solver 同一张表
```

`link_derived_pricing`（默认 **true**）控制这一点；缺 `kv_bytes_per_token` 或该对的带宽时
**自动退回**实测常数（`93 / 585 / 1351 ms per 1k token`），保证老配置行为不变。

**验证：把 KV 体积当自变量**（域内 1 GB/s、跨域 0.26 GB/s = 任务书与实测区间，
prompt 1250 token，2 req/s 轻载，`local_prefill=auto`，关掉排队外部性以便看纯阈值）：

| KV/token | 域内搬运 | 跨域搬运 | 本地重算 | 运行结果 |
|---|---:|---:|---:|---|
| **P-15B 16,960** | 21.2 ms | 81.5 ms | 355.1 ms | **搬运 44/44（100%）** |
| **Qwen3-8B 147,456** | 184.3 ms | **708.9 ms** | 355.1 ms | 域内搬、**跨域重算**（37 搬运 / 7 重算） |

阈值很清楚：搬运什么时候划算，取决于 `KV_bytes/带宽 < 本地重算时间`。同一张 0.26 GB/s 的跨域链路上，
**P-15B 的 16.56 KB/token 让"跨域搬运"始终成立，Qwen3-8B 的 147 KB/token 必须就地重算**——
这就是"KV 压缩打开存算协同空间"在路由器决策层面的量化版本（CPU 侧 `time = KV/BW` 与
`time = 重算` 的直接比较，不再依赖任何真机常数）。

**顺带发现的一个配置缺口**：域内（同节点）配对在配置里**没有 `intra_node_link_bw` 时**，
`pair_costs` 会给它 0 带宽 → 新模型自动退回旧常数（实测：44 条里 43 条走的是回退路径，
只有跨域的 1 条真正用了链路模型）。补上 `intra_node_link_bw: 1.0` + `intra_node_link_latency: 2000`
之后 44/44 全部走链路模型。**建议把这两个键写进所有 CASR 集群配置**，否则"域内搬运"这一支
永远在用真机常数定价。

**已落地**：`configs/cluster/casr_p15b_*.json`（6 份）都补上了这两个键，并加了一条配置守卫
（`ClusterConfigHygieneTests`，复制配置时漏掉就会红）。

### 6.16 这条轴在系统层面也成立：同算力/同链路，只换 KV 规模（2026-09-23）

负载：1250-token prompt、2→**8 rps 维持 30 s**→2 rps 共 260 请求；算力/服务时间/拓扑完全相同，
只有 `kv_bytes_per_token` 不同（新工具 `tests/run_route_arms.py` 跑 `load / cache_aware / casr_lp`）：

| KV/token | 臂 | 均值 | p95 | TTFT p50 | SLO 达标率 | 搬运比 |
|---|---|---:|---:|---:|---:|---:|
| **16,960（P-15B）** | `load` / `cache_aware` | 1 292 ms | 2 350 | **148 ms** | **100%** | 260/260 |
| | `casr_lp` | **1 257 ms** | 2 223 | 149 ms | 100% | 260/260 |
| **147,456（同算力，KV×8.7）** | `load` / `cache_aware` | 1 381 ms | 2 612 | **221 ms** | 100% | 260/260 |
| | `casr_lp` | 1 390 ms | **2 487** | 156 ms | **88.1%** | 260/260 |

读法：

* **只把 KV 放大 8.7×，TTFT p50 从 148 涨到 221 ms（+49%）**——因为每请求 184 MB 的搬运
  （域内 1 GB/s 下 184 ms）直接进 TTFT，而 P-15B 的 21 MB 只要 21 ms。这就是"压缩 KV"
  在端到端指标上的直接体现，不需要任何跨域假设。
* 8 rps 这一档两种 KV 的 SLO 都还能达标（P-15B 100%；大 KV 下 `load` 100%、`casr_lp` 88%），
  所以差距体现在**延迟**而不是达标率；到了 30 rps 峰值档才变成达标率的差距（§6.6–6.12）。
* 放置：P-15B 下三个臂都把 260 个请求放在同域最快对（p4→d5），压缩 KV 让"就近"既快又便宜；
  大 KV 下 `load` 会自动摊到 p0/p2/p4 三处（每台 KV 池压力不同），说明**KV 体积已经在改变
  路由行为本身**。

### 6.17 主矩阵：两个模型 × 三档峰值 × 四臂（2026-09-23）

口径：同一三域拓扑（3090+4090+5090）、同一 SLO（TTFT ≤ 500 ms，`p_slo = 10`）、同一 fabric
（域内 1 GB/s、跨域 0.93 GB/s）、同样的 1250-token prompt、同样的相位（8/16 rps 维持 45 s、
32 rps 维持 30 s）；**唯一的自变量是模型**（P-15B 16.96 KB/token、Qwen3-8B 147 KB/token）。
臂：`load`（least-loaded）、`cache_aware`（SGLang 风格）、`casr_static`（CASR LP + 固定单
Prefill 池）、`casr_elastic`（CASR LP + 需求驱动伸缩，上限 3 台）。

`均值 ms / SLO 达标率`（`cache_aware` 在本拓扑上与 `load` 逐位相同，合并显示）：

| 峰值 | 模型 | `load` / `cache_aware` | `casr_static` | `casr_elastic` |
|---|---|---:|---:|---:|
| 8 rps | **P-15B** | 1 305 / **100%** | 1 271 / 100% | 1 271 / 100% |
| 8 rps | Qwen3-8B | 13 808 / 3.4% | 12 241 / 3.7% | **6 841 / 31.1%** |
| 16 rps | **P-15B** | **2 302 / 98.9%** | 18 619 / 2.3% | 18 406 / 3.0% |
| 16 rps | Qwen3-8B | **18 070 / 4.5%** | 45 402 / 1.6% | 27 901 / 8.0% |
| 32 rps | **P-15B** | **13 522 / 3.8%** | 39 281 / 1.4% | 66 824 / 2.8% |
| 32 rps | Qwen3-8B | **25 417 / 1.3%** | 75 001 / 1.1% | 27 692 / 1.4% |

**三条结论**：

1. **KV 压缩把系统从"崩"拉到"能跑"**：同一负载下 Qwen3-8B 比 P-15B 慢一个数量级
   （8 rps：13.8 s vs 1.3 s；32 rps：25.4 s vs 13.5 s），SLO 达标率也差一个量级。
   这条与 §6.16 的 TTFT 结论一致，且是**唯一在所有档都成立**的结论。
2. **调度/弹性的价值随 KV 增大而出现**：8 rps 时 P-15B 四个臂**完全无差别**（都 1.27–1.31 s、
   100% 达标）——压缩 KV 之后这个负载根本没构成压力；同一负载在 Qwen3-8B 上，
   `casr_elastic` 把均值砍掉一半（13.8 → 6.8 s）、达标率 3.4% → **31.1%**（它把 Prefill 摊到
   p0/p2/p4 三台）。**"KV 越大 → 调度空间越大"这条轴在系统层面成立。**
3. ⚠️ **但 ≥16 rps 上四个档里 CASR 两臂都输给 least-loaded**，`casr_static` 输得最惨
   （P-15B 16 rps：18.6 s vs 2.3 s）。**目前不能声称 CASR 优于 SOTA 基线**，原因已定位（下节）。

### 6.18 原因：需求估计被"积压回补"放大到 5.5×（待修）

把 16 rps 那档的求解器诊断打出来（`--casr-state-output`，峰值期的 tick）：

```text
tick  80: demand=88.7 req/s   capacity(单台 egress 上界)=89.4   实际提供负载=16 rps
          prefill={4: 88.7}                      ← 全部压在 p4
          decode ={1: 3.4, 3: 9.3, 5: 76.0}      ← d1/d3 刚好打满，其余全倒在 d5
          decode_overflow={1: 0, 3: 0, 5: 5.09}  ← d5 被超 5 倍，LP 接受
```

`_inflate_demand`（我两轮前为"背压下需求被低估"加的修正）把**积压增长率**加回每个类的到达率；
但这个积压本身是被坏放置制造出来的，于是形成正反馈：**放置变差 → 积压增长 → 需求估计变大 →
计划按更大的需求量分配 → 更集中 → 积压更多**。最终求解器按 88.7 req/s（真实 16）做计划，
把 76 req/s 倒在容量 12.5 的 d5 上。

对应的修法与判据（下一步）：需求估计必须**有上界且不自我放大**——

1. 用**观测到的到达率 + 有界积压**（例如 `min(积压增长, α × 观测到达)`），而不是无界相加；
2. 或者直接用"系统当前吞吐 + 排队长度/服务时间"的稳态估计（Little's law），它在饱和时收敛到容量而不会发散；
3. 判据：16 rps 档里求解器看到的需求应落在 `16 ± 20%`，且 `casr_static` 的均值回落到
   `load` 的 1.5× 以内（当前 8×）。

在这条修完之前，矩阵里 ≥16 rps 的 CASR 数字都应视为**需求估计失效的产物**，不能用来评价算法本身。

### 6.19 需求估计修好了，但崩溃另有原因（2026-09-23）

**修的（两个真 bug，都有回归测试）**：

1. **per-class EWMA 的尾巴会累加**：这条 trace 有 ~740 个唯一前缀 ⇒ **740 个类、每类一个请求**；
   每个"一次性类"在速率估计里留下一根 1 单位的脉冲、按 5 窗口衰减，求和后就是真实速率的 ~5 倍。
   改成**总量与份额分开估计**：总量来自全局到达计数（平滑），每类发布 `总量 × 归一化份额`
   ⇒ `Σ_k rate_k ≡ 总量`。
2. **计数时点错了**：原来在**派发**时计数，于是"挂起的一批请求被一起放行"会在一个窗口里读成
   几十次到达；现在在请求**到期**时计一次（真机也是在前门计数）。

实测（16 rps 档）：求解器看到 **15.63 req/s**（真实 16；修复前 80.6），计划也恢复正常——
按容量摊到 d3/d5（3.5 / 9.9）、零溢出，而不是把 76 req/s 倒在容量 12.5 的 d5 上。
回归测试：`ArrivalEstimateTests`（窗口语义、突发、份额归一）+ `DemandEstimateTests`（容量缺口封顶）。

**但 16 rps 那格没救回来**，而且我先把矩阵设计的一个错误排除了：

**先修正矩阵设计**：原先的 `casr_static` 臂是**单台** Prefill 池，而 `load`/`cache_aware` 用三台
⇒ 容量差 3×，那条对比无效。补了 `casr_plan3`（固定三台、`scale_on_demand=false`，与基线**同池容量**）
后重跑四格（`均值 ms`）：

| 档 | 模型 | `load` | `casr_plan3`（同容量） | `casr_elastic` | 判读 |
|---|---|---:|---:|---:|---|
| 16 rps | P-15B | **2 302** | 18 619 | 18 619 | CASR 差 8.1× |
| 32 rps | P-15B | **13 522** | 39 281 | 66 824 | CASR 差 2.9× |
| 16 rps | Qwen3-8B | 18 070 | **15 152（−16%）**, p95 45 630 → **27 998（−39%）** | — | **CASR 更好** |
| 32 rps | Qwen3-8B | **25 417** | 53 869（span 201 s vs 101 s） | — | CASR 差 2.1× |

同一套算法在**两个模型上的符号相反**——这本身就是"问题不在算法、而在给它的数"的强信号。

**真正的原因（有独立证据）**：求解器的**容量模型把 attention 整个排除了**。
`hw_service.step_cost_ns` 只累加 dense + MoE（注释写的是"attention 在 1k 上下文下 ~0.01 ms，
比权重读小三个数量级"——那对 Qwen3-8B 这类稠密大权重模型成立），而从同一份 bundle 直接算：

```text
RTX5090 / P-15B，1024 token：
  dense + MoE 每层合计      462 µs   × 28 层  ≈ 12.9 ms   ← step_cost_ns 的全部输入
  attention（按 block type）  8 chunk × (3×423 + 13×144 + 12×99) µs ≈ 34.6 ms
  ⇒ attention 占每请求 prefill 的 ~73%，是 dense 的 2.7 倍
```

于是 `prefill_capacity = 1000/step_ms` 高估约 **3.7×**（同时 `prefill_service_ms` 又是配置里的
锚点值、与它相差 ~26×）。计划因此相信"一台 5090 能顶 89 req/s"，把 740 个请求全压在 p4 上；
而时间线里 p4 实测只能跑出 **~13.5 req/s**（每请求 ~114 ms，其中 attention 是主体），
router 在 p4 不接受新请求时**停止派发**（`queuing_delay` p50 16.3 s），CASR 于是崩掉；
基线把三台摊开（约 40 req/s 的执行容量）就没事。

**下一步（明确的修法）**：把 attention 计入 `step_cost_ns`（用 bundle 里按 block type 分的三张
attention 表，和 trace generator 用同一套分派），让**容量与执行侧同源**；顺带把
`prefill_service_ms` 也改成与容量互为倒数（而不是沿用部署锚点），使求解器内部自洽。
判据：p4 的定价容量应落在实测 13.5 req/s 的 ±30% 内，且 16 rps 档 `casr_plan3` 的均值
回到 `load` 的 1.5× 以内。

### 6.20 四个真 bug 修完：32 rps 档达标，16 rps 档仍差 5×（2026-09-23）

按 6.19 的判据做，但一动手就发现**不是"把 attention 加进去"这一件事**，而是同一条链上
四个"喂给计划的数"错了。四个都修了，都带回归测试。

**(1) `step_cost_ns` 不含 attention。** 用 bundle 里按 block type 分的三张 attention 表
（`attention.csv` / `attention_r4.csv` / `attention_r128.csv`，与 trace generator 同一套分派）
逐层计入 prefill 路径；decode 路径不动（`decode_step_scale` 已经含了 attention+sampling+host，
再加就重复计）。实测 P-15B 单张 5090：dense+MoE 11.2 ms + attention 47.0 ms = **58.1 ms**，
容量从 89.4 降到 **17.2 参考请求/s**；对 1250-token 请求折合 **14.1 req/s**，与
`load` 臂实测的池级 13.4 req/s 相差 +5%，落在 ±30% 判据内。Qwen3-8B 几乎不受影响
（attention 2.9 ms 对 68.4 ms dense），这正是它在 6.19 里符号相反的原因。

**(2) router 的 deficit 计数每个 tick 被清空。** `install_affinity_plan()` 里
`_plan_assignments.clear()`，而 16 rps 档每个 100 ms tick 只有 ~1.6 个到达 ⇒ 配额永远
回到"权重最大的那台"。实测：计划要 91 / 9，实际派发 **737 / 3**（那台 9% 一直空转）。
改为跨 tick 保留（超过工作集上限再裁剪 per-class 键）。

**(3) `requested_tokens_ewma` 从 0 开始衰减。** 只被访问一次的类（CNN/DailyMail 是
**740/740**）发布出来是 `α × 1250 = 250` 而不是 1250。真机的 `casr_control.ClassState`
同一处也改了：**第一次观测直接作为估计值**（和 `sample_arrivals` 对速率做的事一致）。

**(4) 这个长度估计本来也没人用。** `_prefill_length_work` 只有在实例声明了 token 速率上限
（`prefill_tokens_per_s`）时才按 `tokens / 参考长度` 折算，否则**静默返回 1.0**——
59 个 cluster config 里 53 个（含全部三域矩阵 config）都没这个键。现在
`resolve_runtime_capacities` 直接从刚算出的容量推出来。修完 (3)(4) 后又暴露一处：
`_requested_tokens` 对"**没见过的 prefill**"回退成"一个参考长度"，于是**没见过的机器反而更便宜**；
16 rps 档 559 个类里有 230 个只在单台 prefill 上出现过，计划因此把那台压到**定价容量的 108%**
（修好后 98%）。长度是**类**的属性，不是 (类, prefill) 对的属性。

> decode 侧同一个死键（`decode_ms_per_1k_tokens`）**故意没开**：那个容量是**串行**口径
> （`1000 / (参考输出 token × 步时)`），对批处理引擎低估约 `max_num_seqs`，
> 再按其上按输出长度放大负载是**两个错误相乘**而不是抵消。要开得先修批处理口径的 decode 容量。

**同容量四格重跑**（`casr_plan3` vs `load`，均值 ms）：

| 档 | 模型 | `load` | `casr_plan3` | 倍数 | 与修前对比 |
|---|---|---:|---:|---:|---|
| 16 rps | P-15B | 2 219 | 11 147（SLO 15.4%） | 5.0× | 18 619 → 11 147 |
| 32 rps | P-15B | 13 519 | 19 224（SLO 4.1%） | **1.42×** | 39 281 → 19 224（判据 ≤1.5 ✅） |
| 16 rps | Qwen3-8B | 18 070 | **12 030（−33%），p95 45 630→34 975** | **0.67×** | 15 152 → 12 030 |
| 32 rps | Qwen3-8B | 25 417 | 67 918（SLO 3.3%，span 226 s） | 2.7× | 53 869 → **67 918（回退）** |

产物：`/tmp/final-16-P`、`/tmp/final-32-P`、`/tmp/final-16-Q`、`/tmp/final-32-Q`（各含 `summary.json`）。

**要诚实说清 32 rps / Qwen3-8B 这一格**：它是**结构性不可行**的格子——
1250-token 请求的 KV 是 184 MB，单条 producer 链路 2 GB/s ⇒ 每台 prefill 最多 10.85 req/s；
三台容量折合 27.2 参考请求/s，而 32 rps 档的真实到达是 27.2 req/s × 1.22 = **33.2** 参考单位。
基线自己也崩（均值 25.4 s、SLO 1.3%）。修好的长度项把需求从 27.2 抬到真实的 33.2，
于是这一格从"临界可行"变成"确认不可行"，LP 在不可行点上的分配是**病态的**
（§6.18 已记过同样的现象：不可行时哪个顶点最优由成本项的舍入决定）。
实测计划把 68% 落在最慢的 p0（3090）上，比修前的顶点更差。因此这一格的数**不能用来评价算法**，
只能说明"不可行点上 LP 需要一个明确的降级规则"——这是下一个要修的点（见下）。
相对地，**可行但接近饱和**的 P-15B 32 rps 档回到了 1.42×，Qwen3-8B 16 rps 档反而赢 33%。

**结论**：**可行**的两格都变好——P-15B 32 rps 回到 1.42×（判据 ✅）、Qwen3-8B 16 rps 反超 33%；
**不可行**的 Qwen3-8B 32 rps 回退（那格两个臂都在崩，顶点由舍入决定）；
**P-15B 16 rps 仍差 5×**，原因不再是"需求估计"也不全是"路由"，而是**容量口径的最后一层**：
计划给 1250-token 请求定价 76.6 ms（=58.1+18.5 两个 chunk），而仿真器自己报的服务时间是
**1024-token 一块 100 ms**（`TTFT - queuing_delay`，64 并发实测），即**约 1.7×**。
于是计划把 p4 装到定价容量的 98%（14.1 req/s），执行侧只能跑 ~8.6–9.2 req/s ⇒ 仍然轻度超载、
`queuing_delay` p50 8.5 s。修的方向是把容量锚到**执行侧的单 chunk 服务时间**（就是
6.19 提到的"校准单实例吞吐/排队模型"），而不是继续调 LP 权重：
`overflow_penalty` 从 10 扫到 1000、`prefill_service_ms` 改成 `1000/容量`，
对 p4 的装载量**都没有影响**（LP 是被成本项而非溢出项钉住的）。

**两个下一步**（按优先级）：

1. **把 prefill 容量锚到执行侧**：单张 5090 在 64 并发下，1024-token chunk 的实际服务时间是
   **100.4 ms**（容量 9.96 参考请求/s），而 profile 求和说 58.1 ms（17.2）。
   1250/2048 token 分别是 122/143.5 ms（实测）对 76.6/129 ms（profile）。
   容量与 `step_cost_ns` 必须同源，但**同源到哪一侧**要选：现在两处都读 profile，
   而时间线执行的是 profile + 每请求固定开销（~42 ms 且随 KV 长度增长），
   所以"计划按 profile、执行按时间线"本身不变量。要么把这份开销建模进 `step_cost_ns`，
   要么把容量改成"实测标定的 `prefill_step_scale`"（decode 侧已经有 `DECODE_STEP_SCALE` 的先例）。
2. **不可行点的降级规则**：需求 > 池容量时，目标函数里各项都是常数或平坦的，
   顶点由舍入决定。要么按 `max_utilization_weight` 最小化"最坏实例的积压增速"，
   要么在 `_servable_reference_units` 之上直接封顶需求并显示声明"这是降级"。

### 6.21 两条都做了：容量锚到执行侧 + 不可行点显式降级（2026-09-23）

**先纠正 6.20 的一个测量错误**：`TTFT - queuing_delay` 不是单请求的服务时间——它是
"第一次被调度"到"首 token"，中间夹着其他请求的 chunk，所以它在 64 并发下既含服务也含
排队。改用**稳态周期** `(TTFT_max - TTFT_min)/(n-1)`（就是吞吐的倒数）才干净。

**（A）逐卡"每 step 开销"标定。** 用 `tests/probe_prefill_pipeline.py` 把 1P1D 打满
（64 个 1024-token 不同前缀请求，t=0 同时到），对比**周期**与**分层计费**：

```text
card      charge(1024)   measured period   overhead   req/s
RTX5090      58.14 ms        73.57 ms       15.43     13.59
RTX4090      89.74 ms       121.16 ms       31.42      8.25
RTX3090     164.89 ms       204.30 ms       39.41      4.89
```

分层计费本身是**对的**：`step_cost_ns`/`prefill_charge_ns` 与 trace generator 在
1024/1250/2048 三个长度上比值 **1.00**（包括分块：块 2 的 attention 是按
`kv_prefill=1024` 查的）。多出来的 15–39 ms 是 profile 不计的东西：P/D 搬运、
Decode 的**首步**、以及每 step 的调度/主机开销——它按 step 收，所以
`period = charge + overhead × chunks`。写进 `PREFILL_PIPELINE_OVERHEAD_MS_BY_HARDWARE`
（和 `DECODE_STEP_SCALE_BY_HARDWARE` 同一类东西，因为也不是 charge 的固定比例：
3090 的 decode 步是 5090 的 2.7×，prefill 是 2.8×，两者不成同一比例）。

**（B）长度曲线。** 只锚参考长度还不够：1250 token 不是 1.22 个参考单位，而是**多了
一个 step**——实测周期 106.7 ms 对 73.6 ms（1.45×）。所以 `rescale_capacities` 现在
同时发布 `prefill_period_ms`：把 `period(tokens)` 在 **chunk 边界两侧**取样
（`1.0 / 1.0009 / 1.25 / 1.5 / 2.0 / 4.0` × 参考长度），求解器按它插值；
没有曲线时才退回线性 token 比。

结果：P-15B 的定价容量 **4.90 / 8.25 / 13.58 参考请求/s**，与实测周期给出的
4.89 / 8.25 / 13.59 一致（0.2% 内）。计划于是落到 p4 = 9.69 req/s（执行侧 9.24）、
p2 = 5.77（执行侧 ~5.4）、p0 = 0.64，而不是把 14.7 全压在 p4。

**（C）不可行点的显式降级。** 需求超池容量时，目标函数在**分配**上是平的（超出的总量
与落在哪无关），顶点由单纯形决定——实测 32 rps / Qwen3-8B 把 **68% 落在最慢的 p0**。
现在 `CASRController._clamped_rows` 在**求解前**（且在 lifecycle 与结构评估**之后**，
否则 `ceil(demand/capacity)` 永远不会要求加机器）把每个类的速率按
`servable / offered` 等比缩到可服务水平：形状不变、相对次序不变、问题变可行，
各台落到自身上限。快照本身不被改写（状态日志仍记录**真实** offer，下一 tick 也不会继承
上一 tick 的钳位）。开关 `demand_capacity_clamp`（默认开）。

**重跑四格**（`casr_plan3` vs `load`，均值 ms）：

| 档 | 模型 | `load` | `casr_plan3` | 倍数 | 上一轮 | 与 load 的差距 |
|---|---|---:|---:|---:|---:|---|
| 16 rps | P-15B | 2 219 | **4 109**（SLO 8.8%） | 1.85× | 11 147 | 5.0× → 1.85× |
| 32 rps | P-15B | 13 520 | **15 160** | **1.12×** ✅ | 19 224 | 1.42× → 1.12× |
| 16 rps | Qwen3-8B | 18 070 | **13 528**（p95 45 630→23 143） | **0.75×** ✅ | 12 030 | CASR 赢，p95 −49% |
| 32 rps | Qwen3-8B | 25 437 | **32 499** | **1.28×** ✅ | 67 918 | 2.7× → 1.28×（不再倒到 p0） |

**四格里三格达标**（≤1.5×），且 32 rps Qwen3-8B 那格从"把峰值倒给最慢卡"变成
`{2: 472, 4: 508}` 两台快卡。**16 rps / P-15B 仍差 1.85×**，但性质已经变了：
计划与基线的**放置几乎一样**（CASR 25/262/453 对 load 70/240/430），TPOT 也一样
（25.6 ms），差的是 **TTFT 里的排队**（1.14 s 对 0.12 s）——LP 把池子用到 ~100% 利用率，
而基线的贪心留了约 10% 余量；在接近饱和处排队时间对利用率极敏感。

根因是**没有任何一项在给队列/时延定价**：`tail_weight`、`max_utilization_weight`、
`backlog_weight`、`slo_penalty` 在这份 config 里**全是 0**，所以 LP 只看"每单位的搬运+计算
成本"，把它填满就是最优——尽管 trace 明确带了 `slo_ttft_ms=500`。
这是**策略项**（不是建模项）：下一步把 `slo_penalty`/`tail_weight` 打开（6.9–6.13 那几轮
已经实现并测过），让"把 p4 填到 100%"付出代价，而不是继续动容量。

### 6.22 放宽 TTFT 预算 + 开 SLO 项：**只在"中间预算"有效**（2026-09-23）

按 6.21 的结论做：把 trace 的 TTFT 预算从 500 ms 放宽（`tests/annotate_trace_slo.py`，
只重写两个 SLO 字段，到达/前缀逐字节保留），并打开 `slo_penalty`。结果分成两半。

**先发现一个真 bug：SLO 门控在任何预算下都不work。** `_predicted_ttft_ms` 给 Decode 算了
排队项，**Prefill 只算服务时间**——于是模型认为"装到 100% 的 Prefill 依然 407 ms 答复"，
门控只能偏好"服务时间更小"的最快卡，永远无法偏好"排队更短"的摊开。

从一次运行的状态文件重建 9 个 pair 的预测（16 rps / P-15B 峰值时刻）：

```text
p4/d5 = 629 ms    p4/d3 = 697    p4/d1 = 755      ← 最快
p0/*  = 1170–1297 ms
p2/*  = 1616–1742 ms                              ← 最慢
```

所以：**500 ms 时 9 个 pair 全违反**（惩罚项退化成常数偏移，计划一字不变）；
**2000 ms 时 0 个违反**（同样退化成常数 0）。两端都失效——这和"预算选得好不好"无关，
是模型缺项。补上 Prefill 排队项（形状与 Decode 完全一样：
`(4×waiting + running)/max_num_seqs × 自身 service_ms`）之后，中段才可用；
在此之前预测区间只有 ~430–1300 ms，连 1500 ms 也同样是死的。

**实测（同一格，740×1250-token，`casr_plan3`；均值 ms）**：

| SLO 预算 | `slo_penalty` | 均值 | p95 | TTFT p50 | 放置 | 判定 |
|---:|---:|---:|---:|---:|---|---|
| 500（原） | 5 | 4 109 | 8 427 | 1 293 | 25/262/453 | 全违反 ⇒ 无效 |
| 2 000 | 5 | 4 109 | 8 427 | 1 293 | 25/262/453 | 全不违反 ⇒ 无效 |
| 2 000 | 20 | 4 109 | 8 427 | 1 293 | 25/262/453 | 无效 |
| **1 500** | **5** | **3 669** | **7 134** | **966** | **39/255/446** | **−11% 均值、−15% p95** |
| 1 500 | 20 | 3 669 | 7 134 | 966 | 39/255/446 | 与 penalty=5 相同 |
| 不开 | — | 4 109 | 8 427 | 1 293 | 25/262/453 | — |
| `load` 基线 | — | 2 219 | 3 788 | 232 | 70/240/430 | — |

三条可迁移的结论：

1. **只放宽预算没用**：500→2000 时 SLO 项从"全违反"直接变成"全不违反"，两次都是常数。
2. **只有落在"最好 vs 最差 pair 预测之间"的预算才有梯度**——这里就是 1500 ms
   （原预算的 3×），换来 −11% 均值 / −15% p95 / TTFT p50 −25%，与 load 的差距
   1.85× → **1.65×**。
3. **惩罚大小不重要**（5 和 20 一模一样）：这个门控是**过滤器**，不是价格。
   想要"连续地少压一台"，得让排队以**凸**的方式进入目标函数，而不是加一个二值罚。
   反过来，`backlog_weight` 那个"积压增速"项在这里**单调有害**：20 → 6 539 ms，
   100 → 18 619 ms（正好退回最初的单点崩溃），因为"把积压增速之和最小化"的答案就是
   全压最快卡——这正是 6.9 记过的方向。

> 工具：`tests/sweep_tail_weight.py` 新增 `--knob slo_penalty` 与 `--set KEY=VALUE`
> （JSON 解析），可以一次带上多个开关注入，不用手写 config。
> 复现：先 `annotate_trace_slo.py --slo-ttft-ms 1500`，再
> `--set slo_penalty=5`（`demand_capacity_clamp` 默认开）。

### 6.24 KV 感知与动态扩缩容，各自值多少（2026-09-23）

两件事分开量：把 KV 全部关掉看算法退化多少；把池子从 1 台放开到 3 台看弹性赚多少。

**（一）KV 感知：4 条活通道 + 1 条死通道**

活通道：① LP 单位成本里的搬运项（`_class_kv_bytes` → `transfer`）；② `shared_links` 的
字节预算（LP 约束 + 控制器每 tick 的 `_egress_bound_prefill_capacity`）；
③ `resolve_runtime_capacities` 的 egress 上限；④ lifecycle 的 egress 感知扩容。

**死通道**：router 的 recompute-vs-transfer（`kv_exchange_decision`）在默认
`local_prefill: never` 下**从不被调用**——矩阵每一格 740/740（或 980/980）都是
`exchange=transfer`，开不开 KV 都一样。要用它必须显式 `--local-prefill auto`。

搬运项本身有多大（1250-token 请求，同域 1.0 GB/s / 跨域 0.93 GB/s）：

| 模型 | KV/请求 | 同域 transfer | 跨域 transfer | 占 pair 单位成本 |
|---|---:|---:|---:|---:|
| P-15B | 21.2 MB | 21 ms | 23 ms | **1–3%** |
| Qwen3-8B | 184.3 MB | 184 ms | 198 ms | **7–21%** |

同域与跨域带宽只差 7%，所以**这一项几乎不改变 pair 之间的排序**——它改变的是总量，
不是偏好。

**消融**（`kv_bytes_per_token: 0`，一次性关掉上面全部四条通道）：

| 档 | KV 感知 | KV-blind | Δ |
|---|---:|---:|---:|
| P-15B 16 rps | 3 669 | 3 740 | +1.9% |
| Qwen3-8B 8 rps | 2 141 | 2 279 | +6.4% |
| Qwen3-8B 16 rps | 13 528 | 13 515 | −0.1% |

⇒ **当前矩阵里 KV 感知只值 ≤6%**，而且 **6.23 里"Qwen3 8 rps 6.4× 胜 `load`"不能归因于
KV**：KV-blind 的 CASR 仍是 2 279 ms（`load` 13 808 ms）。赢的是 LP 的容量感知摊开。

**真正让 KV 咬合的是 egress 预算，而它现在没对齐。** 矩阵 config 写 **2 GB/s**
（"10.212 fabric ~16 Gbps"），而仿真器自己执行的链路是 **1.0（同域）/0.93（跨域）GB/s**，
部署实测的 producer 上限是 **0.26–0.30 GB/s**。Qwen3-8B 16 rps：

| egress 预算 | mean | p95 | TTFT p50 | 放置 | 备注 |
|---:|---:|---:|---:|---|---|
| 2 GB/s（现 config） | 13 528 | 23 143 | 11 796 | {2:357,4:383} | p4 被自身推送预算卡住 |
| 1 GB/s（它实际跑的链路） | 13 001 | 22 687 | 11 316 | {2:366,4:374} | −4% |
| 0.26 GB/s（部署实测） | **8 253** | 34 078 | **2 175** | {0:244,2:250,4:246} | 均值 −39%，**p95 +47%** |

0.26 GB/s 让均值 −39%、TTFT p50 −82%（三台均摊），但 p95 反而变差——**均值换尾部**，
报告时必须成对给。结论：KV 感知不是"没用"，是**参数没对齐**（计划的生产端预算比它自己
执行的链路还宽 2×，比部署实测宽 7×）；对 KV 大的模型，这个差就直接变成"过度乐观"。

**（二）动态扩缩容**

| 档（16 rps SLO 档） | static（1 台固定） | **elastic（1 → 3）** | plan3（3 台固定） |
|---|---:|---:|---:|
| P-15B | 18 619（SLO 5.3%） | **3 669（59.6%）** | 3 669（59.6%） |
| Qwen3-8B | 45 402（2.7%） | **13 528（3.9%）** | 13 528（3.9%） |

弹性**完全追平常开三台**（P-15B 连每台请求数都只差 1）。扩容时点：
P-15B 在 **5.7 s / 12.9 s** 拉起第 2/3 台，Qwen3 在 **1.4 s / 9.8 s**（峰值 5–50 s，
所以机器上线后还有 35 s 以上的满载期）。

**但启动开销能吃光全部收益**（P-15B 16 rps，峰值 45 s）：

| 容器启动 | 250 ms（现 config） | 5 s | 15 s | 45 s |
|---:|---:|---:|---:|---:|
| mean | **3 669** | 3 926 | 18 619 | 18 619 |

crossover 在 5–15 s 之间；真机容器启动约 **45 s**（`make_hetero_cluster.CONTAINER_BOOT_MS`）
⇒ **在真机上这一档不会赚**，只会退回单台。另外 15/45 s 档里结构控制器发了 **41 次 `+P`**
而机器一次都没上线（决策层空转），Qwen3 尾部还出现振动（7 次 `+P` / 4 次 `release`）。

**两条结论**：

1. 弹性收益是**真实但条件化**的：池子缺容量 + 峰值足够长 + 启动足够快，三者同时满足才赚
   （这里 5.1× / 3.4×）。模拟器默认 `startup_ms=250` 是一个**乐观假设**，必须显式写明；
   报告弹性结果时要带 boot 敏感性，否则结论换个 boot 值就翻转。
2. KV 感知目前是**被参数压住**的：算法侧的搬运定价在成本里只占 1–21% 且几乎不区分 pair，
   egress 通道又用了一个比执行链路还宽的预算。要对齐，就要么把 `shared_links` 改成
   链路模型带宽（1.0 GB/s），要么改成部署实测（0.26 GB/s）并接受"均值换尾部"。

### 6.25 新实例为什么慢：46 次真机容器重启的分解（2026-09-24）

系统里同时有**五个**听起来都叫"启动时间"的数字，先对齐它们：

| 层次 | 数值 | 出处 |
|---|---:|---|
| vLLM 引擎就绪（**热**，权重在页缓存） | **~20 s** | `/mnt/home/casr/logs/casr-md-p4090.log`（46 次重启） |
| vLLM 引擎就绪（**冷**） | **~45 s** | 同一份日志：首启 46 s、隔夜后 40–43 s |
| **路由可见**（WARMING 门关闭） | **~151 s** | 真机 `state-casr_full.jsonl`：`+P → accepting` 实测 151.5 s（两次都如此） |
| 算法折价（结构评估器） | **45 s** | `deploy/real_lmcache_pd/router_config.json` 的 `structural.startup_s` |
| 模拟器矩阵 config | **250 ms** | `configs/cluster/casr_*_plan3*.json` 的 `resources.startup_ms` |

**先排除"容器/镜像/调度"**：`+P` 执行的是 `docker start <已建好的容器>`
（`start_crosshost_pd.sh` 里 `docker run -d` 建好的），**没有拉镜像、没有建容器**。
那 20–46 s 全在 vLLM 进程内部。

**热的 20 s 由什么构成**（以 09-15 17:15:07 那次为例，全部来自日志时间戳）：

| 阶段 | 耗时 | 日志锚点 |
|---|---:|---|
| python/torch 导入 + 参数与配置解析 + EngineCore 子进程 | ~14 s | banner → `Resolved architecture` → `Initializing a V1 LLM engine` → `world_size=1` |
| CUDA 上下文 / FlashAttention 后端选择 | ~1 s | → `Loading model from scratch` |
| **权重 15.26 GiB（页缓存命中）** | **2.4 s** | `Loading weights took 2.39 seconds` |
| KV cache 分配 + NIXL/UCX 建链 + warmup | ~3 s | `Available KV cache memory: 3.23 GiB` → `GPU KV cache size: 23,488 tokens` → ready |

**冷启动 45 s 的差别只在一段**：权重从 2.4 s 变成 **21.7 s**
（5 个 safetensors shard，~780 MB/s 顺序读），其他阶段不变。38 次权重加载的分布：
**中位 2.82 s、最慢 21.69 s**；容器整体 `banner → KV ready` 46 次里
**中位 20 s、最快 15 s、最慢 46 s**，长的两次分别是首启和隔夜页缓存被逐出。

**两个结构性原因**：

* vLLM 自己说明了权重为什么慢：`Auto-prefetch is disabled because the filesystem
  (EXT4) is not a recognized network FS (NFS/Lustre). If you want to force
  prefetching, start vLLM with --safetensors-load-strategy=prefetch.` —— 本地盘不预取，
  冷读就是 5 个 shard 串行。
* `--enforce-eager` 已经关掉了 `torch.compile` 与 CUDA graph capture
  （日志：`Enforce eager set, disabling torch.compile and CUDAGraphs`）——**这已经在省**，
  否则还要多几十秒。

**最关键的一条：引擎 20–45 s 就绪，但路由要等 150 s 才敢用它。**
`CASRController.apply_structural` 里 `+P` 只做 `docker start` 并把实例设为 `WARMING`，
真正的 `ACTIVE` 由 `_warming_deadline = now + warmup_s` 决定，而 `warmup_s` 在部署配置里是
**150**（`casr_control.py` 默认 90）。真机两次 `+P` 的实测都是 **151.5 s** 后才
`accepts_new_requests=True`。也就是说新实例有 **105–130 s 的"就绪但不可用"窗口**：

* 算法评估器按 45 s 折价 ⇒ **比实际乐观 3.3×**（45 s 与 150 s 之间的峰值会被判成"划算"，
  实际上一次活都接不到）；
* 模拟器矩阵 config 的 250 ms ⇒ **乐观 600×**，这就是 6.24 里"弹性看起来免费"的来源。

**按性价比排序的加速手段**：

1. **`-P` 不要 stop**：现在是 drain 完就 `docker stop`（`_sync_container_states` 的
   `DRAINING` 分支），于是下次 `+P` 必然付一次冷/热启动。留一台 hot spare（只 drain 不 stop）
   能把 `+P` 成本压到 ~0——这也正是文档里"hot-spare reconfiguration"的说法。
2. **把 `warmup_s` 从 150 调到实测值**（热启动 ~20 s、冷 45 s ⇒ 取 45–60 s 已足够），
   直接省 90–105 s，且不改变任何物理行为。
3. **权重**：`--safetensors-load-strategy=prefetch`（强制预取），或把 15.26 GiB 权重放
   tmpfs / 本地 NVMe（3 GB/s ≈ 5 s），或干脆预热页缓存。
4. 预导入的进程池（只切 GPU 上下文，不重启进程）能省那 ~14 s，但要改部署形态，收益最小。

### 6.26 多环境对比（模型 × 云边）：先修公平性，再看优劣（2026-09-24）

按 `docs/SOTA覆盖与模拟器基线映射.md` 的路线表搭了 **2×2 环境**：
{类 DSV4 的 P-15B（压缩 KV、混合注意力）, 传统稠密 Qwen3-8B} ×
{metro（跨域 push 0.33 GB/s / 20 ms）, WAN/云边（0.11 GB/s / 48 ms，真机实测）}，
同一拓扑（3 域 3P+3D）、同一负载（`workloads/matrix-16rps-slo1500.jsonl`，740×1250-token）、
同一 SLO 档。所有实体臂都开 `local_prefill: auto`（真机路由器本来就会做"搬 vs 重算"）。

**先修了一个公平性 bug。** `pair_costs` 原先只在 `--enable-casr` 时构建，于是非 CASR 臂的
`local_prefill` 决策退回"真机记录常数"（585 ms/1k 同域、1351 ms/1k+48 ms 跨域）——那组常数是
按**部署的 Qwen3-8B**（147,456 B/token、0.257 GB/s push）标定的。在 P-15B 上它把搬运高估约 9 倍，
结果三条基线臂在 metro 上 **740/740 全走本地重算**，而 CASR 臂 **740/740 走搬运**：两边被不同的
价格模型定价。修好（`serving/__main__.py` 对所有运行构建）后决策变成模型感知的：

```text
P-15B / metro   local 355.1 ms  vs transfer  27.5 ms  -> transfer
P-15B / WAN     local 355.1 ms  vs transfer 240.7 ms  -> transfer
Qwen3 / metro   local 355.1 ms  vs transfer 558.6 ms  -> local（跨域 p0->d5）
Qwen3 / WAN     local 355.1 ms  vs transfer 1723.6 ms -> local
```

**修复后的四环境矩阵**（均值 ms / p95 / SLO 达成）：

| 环境 | `load` | `cache_aware` | `kv_aware` | **CASR（elastic）** | CASR vs 最好基线 |
|---|---:|---:|---:|---:|---|
| P-15B metro | **2 238** / 3 728 / 100% | 2 238 | 2 238 | 3 674 / 6 486 / 59.5% | **差 1.64×** |
| P-15B WAN | 3 531 / 6 270 / 60.3% | 3 531 | **3 506** | 9 191 / 36 201 / 37.2% | **差 2.62×** |
| Qwen3 metro | 3 458 / 6 102 / 85.4% | 3 458 | 3 458 | **3 303** / 6 668 / 82.4% | 好 4.5% |
| Qwen3 WAN | 4 612 / 8 459 / 10.8% | 4 612 | 4 584 | **4 478** / 8 493 / **35.3%** | 均值好 3%、**SLO 好 3.3×** |

三条基线在本负载上**互相重合**：740 个请求全是唯一前缀，`cache_aware` 的前缀匹配恒为 0，
退化成 least-load；`kv_aware` 只在 WAN 上略有差别（3506 vs 3531）。

**模型 × fabric 的结论（这条是"类 DSV4 vs 传统模型"的直接证据）**：同样 1250-token 请求，
压缩 KV（21.2 MB）让"搬"在 WAN 上依然划算（240 ms < 本地重算 355 ms），
而稠密模型（184.3 MB）在 WAN 上只能退回本地重算（1724 ms > 355 ms）——
**跨域 P/D 分离是否成立，被 KV/token 这一个数决定**，与 6.24 的 egress 结论一致。

**顺带修掉一个真 bug：LP 后的 egress 搬运器不看目标机算力。**
`_enforce_egress_budget` 为解**链路**超限，把整类流量搬到"链路有空余"的最便宜 pair，
但从不检查目标机的**算力容量**。在 producer 预算成为瓶颈的 fabric 上，这等于"为了修链路
去压垮一张卡"：实测 P-15B WAN 把 LP 原本放在 5090 的 10.3 req/s（容量 13.6）搬到了
4090（容量 6.3），**740 里 547 个请求落在 4090**，均值 **27.9 s**，而 least-load 基线是 3.5 s。
加上算力余量检查后：均值 **27 922 → 9 191 ms（−67%）**，SLO 11.4% → 37.2%，放置从
`{2:547}` 变成 `{0:236, 2:247, 4:256}`。回归测试 `EgressMoverFitsComputeTests`（2 条）。

**仍存在的差距（下一步的靶子）**：CASR 在两个 P-15B 环境上都输给 least-load 基线。
罪魁不是放置，而是**排队**：

| | CASR | load 基线 |
|---|---:|---:|
| P-15B metro：放置 / `queuing_delay` p50 | {0:39, 2:254, 4:447} / **917 ms** | {0:72, 2:240, 4:428} / **121 ms** |
| P-15B WAN：放置 / `queuing_delay` p50 | {0:236, 2:247, 4:256} / **3 591 ms** | {0:136, 2:232, 4:331} / **749 ms** |

即：**放置几乎一样，排队差 5–7 倍**。WAN 那格的分 tick 队列序列显示
**最弱的 p0（3090，容量 4.9 参考单位）队列单调涨到 46**，而最快的 p4（5090）基本空转
（0–1）——计划的分配超过了 p0 能执行的速度，且目标函数里没有任何一项在队列变长时叫停。
两个机制被指向：

1. 控制器每 tick 的 egress 上限 `min(declared, budget/per_request)` 把三台**拉平到同一个
   字节预算**（6.33），于是 LP 的约束里 3090 与 5090 变得一样"能装"，算力差异被抹掉；
2. 目标函数里 `tail_weight / max_utilization_weight / backlog_weight / slo_penalty` 的作用
   只到"预测 TTFT 越界"这一层（6.22/6.23 已证：二值罚不是价格），没有连续排队定价。

下一步（优化，按优先级）：把 egress 上限改成**逐台**而不是全池同一个数（按该台自己的
declared compute 与字节预算取 min，且不再向下拉平），并让排队以**凸**形式进入目标函数。

### 6.27 优化一：Prefill 排队定价（2026-09-24）

6.26 留下的差距是"放置一样、排队差 5–7 倍"。读运行状态后定位到具体机制：
计划把每台 Prefill **顶到定价容量的 100%**（P-15B WAN：`{0: 3.54, 2: 3.63, 4: 3.89}` req/s
对容量 `{3.5, 3.7, 3.7}`），而目标函数里**只有 Decode 有排队项**——Prefill 装满到 100%
在 `c_ijk` 里看起来和空闲一样便宜。于是任何容量误差都直接变成无界队列。

新增目标项 `prefill_queue_weight`（默认 **0 = 关**，不改变任何既有结果）：形状与 Decode 的
`tail_weight` 相同——

```text
prefill_queue = w x queue_fraction(该 Prefill) x prefill_service_ms x work_ratio / 1000
queue_fraction = (4 x waiting + running) / max_num_seqs
```

即"新请求要排在这台机器现有积压后面的秒数"，并随该类的 prompt 工作量放大。

**实测（同四环境，只改这一个权重）**：

| 环境 | w=0 | **w=10** | Δ |
|---|---:|---:|---|
| P-15B metro | 3 674 / p50 3 449 / TTFTp50 1 101 / SLO 59.5% | **2 395 / 2 288 / 392 / 100%** | **−35%，SLO +40pt** |
| P-15B WAN | 9 191 / 5 894 / 3 942 / 37.2% | **8 648 / 3 927 / 1 997 / 43.8%** | −6% 均值、**p50 −33%** |
| Qwen3 metro | 3 303 / 2 922 / 498 / 82.4% | 3 388 / 3 041 / 418 / 82.3% | +2.6%（可接受） |
| Qwen3 WAN | 4 478 / 4 063 / 328 / 35.3% | 4 478 / 4 063 / 328 / 35.3% | 不变（该环境 Prefill 无积压） |

**P-15B metro 因此从"落后基线 1.64×"变成追平**（2 395 vs least-load 2 238，双方都 100% SLO），
放置也从 `{0:39,2:254,4:447}` 变得与基线一致（`{0:62,2:245,4:433}` vs `{0:72,2:240,4:428}`）。
四个环境配置已带上 `prefill_queue_weight: 10`。回归测试 `PrefillQueuePricingTests`（3 条：
默认关闭、有积压更贵、按本机步时放大）。

**P-15B WAN 仍差 2.45×**，而且原因已经量出来了：把单实例探针与运行对账——

| | 定价周期 | 探针实测（1P1D、1250-token、64 并发） | **运行内实测**（`TTFT − queuing_delay` p50） |
|---|---:|---:|---:|
| 3090 (p0) | 282 ms | 287.6 ms | **549 ms** |
| 4090 (p2) | 173 ms | 176.2 ms | **288 ms** |
| 5090 (p4) | 103 ms | 106.7 ms | **203 ms** |

即**容量模型本身是准的（±2%）**，但**执行侧的服务时间是它的 1.2–1.9×**：
探针测的是"同域 1P1D 独占对"，而矩阵里 Prefill 要与**跨域 Decode**配对、还要与另外两台
Prefill 共享同一批 Decode（含它们各自的 KV 入向带宽）。计划按 1P1D 的周期给出容量，
再把它用满，17%（3090 上 2.99 实测 vs 3.54 定价）的乐观就直接变成队列。
下一步（明确）：容量按 **(P,D) 配对**定价，或把 Decode 侧的 KV **入向**预算也建成共享链路
（现在 `shared_links` 只有 producer 侧），二者都能让计划看到"共享同一个 Decode 不等于
三倍推送能力"。

### 6.28 优化二：找到 P-15B WAN 差距的真正来源——钳位缩的是计划，不是到达（2026-09-24）

接着 6.27 的 2.45× 往下查，过程里推翻了两个我先前的猜测，也修正了一条比较口径。

**先排除"容量模型不准"**：把单实例探针与运行对账，**容量是准的**——探针 1250-token
周期 3090/4090/5090 = 287.6 / 176.2 / 106.7 ms，模型给 282 / 173 / 103 ms（±2%）；
运行内**每台的完成间隔**两臂几乎一样（CASR p0/p2/p4 = 255 / 165 / 120 ms，基线 279 / 164 / 106 ms）。
也就是说 Prefill 的服务速度不是问题。

**真正的问题是需求钳位**。从状态文件里同时读两个数：

```text
t= 40.0s   sum(每行 arrival_rate_ewma) = 16.06 req/s   ← 真实到达（trace 峰值就是 16）
           solver.total_demand_rps      = 11.05 req/s   ← 计划看到的需求
           solver.total_capacity_rps    = 15.27
```

比值 11.05/16.06 = **0.688**，正是 6.23 那个"不可行点降级"钳位的 `servable/offered`
（`servable = 15.27 参考单位`，`offered = 16.06 × work 1.4 = 22.5`）。
钳位把**计划的需求**缩到可行，但**到达没有缩**：router 按计划的**份额**派发真实到达，
于是每台实际接到的是计划量的 `1/0.688 = 1.45×` —— 最慢的 p0 因此持续超载，
**203 个请求排队约 40 s**（全部走 p0→d1），而 least-load 基线的最差只有 5.9 s。

**这条也暴露了比较口径**：开环回放（默认）不会像真机客户端那样背压，所以饱和环境里
"按份额分配"的策略会被额外惩罚。用**闭环客户端**（`--client-concurrency 64`，与真机
前门信号量同义）重跑同一格：

| P-15B WAN | 均值 | p50 | p95 | TTFT p50 | SLO 达成 | span |
|---|---:|---:|---:|---:|---:|---:|
| 开环 · `load` | 3 531 | 3 351 | 6 270 | 1 270 | 60.3% | 55.5 s |
| 开环 · CASR(w=10) | 8 648 | 3 927 | 36 114 | 1 997 | 43.8% | 85.5 s |
| **闭环 · `load`** | 3 508 | 3 406 | 5 941 | 1 309 | 57.3% | 56.4 s |
| **闭环 · CASR(w=10)** | **5 305** | **2 787** | **16 446** | 1 060 | **64.6%** | 78.6 s |

闭环下差距从 **2.45× 缩到 1.51×**，而且 **CASR 的 SLO 达成反超基线**（64.6% vs 57.3%）、
p95 也接近（16.4 s vs 5.9 s，仍有差距）。基线在闭环下几乎不变（3 531 → 3 508），
说明它本来就不依赖客户端背压。

**结论与下一步**：

1. `_clamped_rows` 的语义需要补完：它只缩**计划**，不缩**派发**。要么把钳位同时作用到
   前门（饱和时按 `scale` 扣住新请求，等价于真机客户端的信号量），要么不缩需求、
   改为"按容量分配 + 前门排队"，让超出的部分停在**入口**而不是摊到每台 queuing。
2. 饱和环境的对比应以**闭环**为准（开环会把"按份额分配"的策略额外惩罚 1/scale 倍），
   但两种口径都要报——开环数字本身也是"客户端不背压时会发生什么"的证据。

### 6.29 优化三：KV 预算按"配对"拆开（同域 vs 跨域），四环境全部收敛（2026-09-24）

顺着 6.28 的线索继续查，发现真正压住计划的是**链路口径**：配置里每台 Prefill 只有**一条**
`shared_links` 记录，`capacity_bytes_per_s = 0.11 GB/s`（跨域线速），却覆盖了它**全部**的
(P,D) 配对——包括同域配对。可执行侧是分开的（`pd_link` 同域走 0.257 GB/s 的 host 路径、
跨域走 0.11 GB/s + 48 ms），实测同域 push 就是 0.257。结果：

```text
计划给 5090 的上限 = min(compute 13.58, 0.11e9/(16960x1250 B) = 5.19) = 5.19 req/s
它在运行里实际做到的      = 8.3 req/s（完成间隔 120 ms）
⇒ 最快的 Prefill 被迫空转，最慢的那台队列涨到 203 个
```

**修法**：把每台的 KV 预算按配对拆成两条链路（`p4-same` 0.257 GB/s / `p4-wire` 0.11 GB/s，
metro 档按同比例 0.77/0.33），并让"每台的最佳配对"决定其容量上限
（`resolve_runtime_capacities` 与控制器每 tick 的 `_egress_bound_prefill_capacity`
都从 `min` 改成 `max`）——**跨域推送仍由各自的字节约束单独限住**，不再用跨域速率去惩罚同域配对。

**效果（同负载、同 SLO 档）**：

| 环境 | CASR 修前 | **CASR 修后** | 最好基线 |
|---|---:|---:|---:|
| P-15B WAN | 8 648 / SLO 43.8% / span 85.5 s | **2 831 / 98.8% / 55.2 s** | 3 202（kv_aware） |
| P-15B metro | 2 395 / 100% | 2 395 / 100%（该档本就算力受限） | 2 238 |
| Qwen3 WAN | 4 478 / 35.3% | 4 414 / 38.5% | 4 612 |
| Qwen3 metro | 3 303 / 82.4% | 3 540 / 81.4% | 3 402 |

注意**基线也一起变了**（P-15B WAN 的 `load` 3 531→3 306、`kv_aware` →3 202），
因为它们的 `inflight/capacity` 分母来自同一张容量表——这正说明这是一次**口径修正**而不是调参。

> **一次测量污染与更正（2026-09-24）**：这一格第一次复跑报的是 3 007 ms / 84.9%。
> 复核时发现**上一轮启动的一个旧代码进程没有被杀干净**（`kill` 的模式匹配到了启动脚本自身），
> 它和第二次启动并发写同一个 `state.jsonl` / `out.csv`，所以那组数字无效。
> 在**全新目录、确认无残留进程**后重跑得到上表的 2 831 ms / 98.8%；
> 其余三格与基线不受影响（它们只启动过一次）。教训写在这里：**并发复跑前先按 PID 核对进程**，
> 不要用 `pkill -f` 去杀包含同样字符串的进程。

**四环境的最终判读**（均值 / SLO，闭环无关、开环口径）：

| 环境 | 最好基线 | CASR | 判定 |
|---|---:|---:|---|
| P-15B metro | 2 238 / 100% | 2 395 / 100% | 打平（1.07×） |
| P-15B WAN | 3 202 / 79.5% | **2 831 / 98.8%** | **胜 1.13×，SLO +19.3pt** |
| Qwen3 metro | 3 402 / 86.4% | 3 540 / 81.4% | 打平（1.04×） |
| Qwen3 WAN | 4 612 / 10.8% | **4 414 / 38.5%** | **胜 1.05×，SLO 3.5×** |

即**四格全部落在最好基线的 ±7% 以内**，两格 WAN/云边反超，Qwen3 WAN 的 SLO 达成是基线的 3.5 倍。
从 6.26 的"1.64×/2.62× 落后"到现在的"全部打平或反超"，中间的四步都是**真 bug 或口径错误**
（公平定价 → egress 搬运器算力盲区 → Prefill 排队项缺失 → 同域/跨域预算混用），每一步都带回归测试：

```text
EgressMoverFitsComputeTests   (2) 搬运器不得为修链路压垮算力
PrefillQueuePricingTests      (3) 排队项默认关、有积压更贵、按本机步时放大
SplitLinkBudgetTests          (2) 容量上限取本台最佳配对，不取最差
```

### 6.30 负载维度：4 环境 × 3 峰值 = 12 格（2026-09-24）

把峰值维度补齐（8/16/32 rps，同样的 1250-token CNN/DailyMail trace、同 SLO-1500 档、
同 `local_prefill: auto`），每格 `casr`（LP）对 `load`：

| 环境 | 8 rps | 16 rps | 32 rps |
|---|---:|---:|---:|
| P-15B metro | **0.98×**（双方 100% SLO） | 1.07×（双方 100%） | 1.03×（SLO 5.8 vs 8.4%） |
| P-15B WAN | **0.93×**（100% / 100%） | **0.86×**（**SLO 98.8% vs 74.2%**） | 1.21×（SLO 17.8% vs 11.9%） |
| Qwen3 metro | **0.96×**（100% / 100%） | 1.04×（SLO 81.4 vs 86.4%） | 1.02×（SLO 1.0 vs 1.0%） |
| Qwen3 WAN | 1.09×（SLO 91.1 vs 92.4%） | **0.96×**（**SLO 38.5% vs 10.8%**） | **0.99×**（SLO 0.9 vs 1.0%） |

（单元格是 `CASR 均值 / load 均值`，小于 1 表示 CASR 更快；粗体为 CASR 更好。）

**读法**：

* **12 格里 CASR 赢 6 格**，10 格落在基线的 ±10% 以内；唯一超过 20% 的是
  **P-15B WAN @32 rps（1.21×）**——但它在同一格把 **SLO 从 11.9% 抬到 17.8%**，
  是"均值换达标率"的取舍（该格两臂的 span 都已经 75–80 s，池子结构性不足）。
* **轻载不吃亏**：8 rps 档四格里三格 CASR 略优（0.93–0.98×），全部 ~100% SLO；
  唯一略输是 Qwen3 WAN（1.09×，SLO 91.1% vs 92.4%）——这格 KV 极大（184 MB/请求），
  算法为了少搬 KV 做了更多本地重算，均值因此略高。
* **收益集中在云边 16 rps**：两个 WAN 格是算法最亮的地方（0.86× / 0.96×），
  而且 SLO 差距很大（+24.6pt / +27.7pt）——这正是"跨域 + KV 感知 + 结构"三条同时起作用的位置。
* **32 rps 谁都不好**：该档的到达率约为池容量的两倍，两臂 SLO 都掉到 1–18%，
  此时比较的是"崩得多难看"而不是算法优劣。

### 6.31 动态扩缩容：修掉"WARMING 被下一次覆盖丢掉"，并暴露下一个（2026-09-24）

把弹性做成可判定的实验：三种池形态 × 两种启动假设（`static1`=1 台固定；
`elastic`=1→3，`warmup_ms/startup_ms` 取 **45 s**（真机实测）或 **0.25 s**（旧配置的乐观值）；
`fixed3`=常开三台）。

**A. 短峰值（P-15B WAN，16 rps / 45 s）**

| 池形态 | 均值 | p95 | SLO | span |
|---|---:|---:|---:|---:|
| static 1 台 | 5 058 | 10 060 | 33.8% | 60.9 s |
| elastic 1→3，启动 **45 s** | 5 019 | 9 878 | 34.1% | 60.3 s |
| elastic 1→3，启动 **0.25 s** | **2 831** | 4 744 | **98.8%** | 55.2 s |
| fixed 3 台（参照） | 2 831 | 4 744 | 98.8% | 55.2 s |

⇒ 启动 45 s ≈ 峰值 45 s 时**毫无收益**（5 019 vs 5 058）；启动够快时，弹性**逐位拿回**
常开三台的全部收益。与 6.25 的真机量测一致：45 s 启动在 45 s 峰值上不可能赚。

**B. 长峰值（Qwen3 WAN，240 s 高峰 1.8 rps）** —— 这里本应赚，但没有：

| 池形态 | 均值 | p95 | SLO | span |
|---|---:|---:|---:|---:|
| static 1 台 | 2 699 | 6 046 | 67.9% | 283.1 s |
| elastic 1→3，启动 **45 s** | 2 697 | 6 046 | 67.9% | 283.1 s |
| fixed 3 台（参照） | **1 759** | **3 287** | **99.8%** | 279.4 s |

**两个 bug，一个已修、一个刚暴露**：

1. **已修：WARMING 的机器被下一次结构覆盖丢掉。** `PrefillLifecycle.update` 里
   "把仍在 WARMING 的机器留在 wanted 里"那一步原先**只在没有 structural override 时**执行；
   而评估器**每 tick 都会重发**自己的 `wanted_ids`，一旦那一次集合里没有这台正在启动的机器，
   它就被判为 not-wanted → drain → 启动从零重来。修复前实测：`+P` 的机器 1.1 s 进 WARMING，
   23.8 s 被打回 INACTIVE，之后**每秒循环**，整轮**从未 ACTIVE**（230 次 `+P` 换来一个没长大的池子）。
   修完后 **1.1 s WARMING → 46.1 s ACTIVE**（第一次真的上线）。回归测试
   `test_a_warming_worker_survives_a_later_override`（旧代码上失败）。
2. **新暴露：刚 ACTIVE 的机器又被下一次覆盖丢掉。** 46.1 s 变 ACTIVE，**46.4 s 回到 WARMING**，
   此后每 45 s 循环一次（ACTIVE 只维持 0.3 s）。同一条路径：`_override` 在 45 s 前被设成 `{0}`
   （那次评估器的建议），新上线的 p4 不在其中 → `reconcile` 把它 drain → 下一拍评估器又要它 →
   重新 acquire → 从头 warmup。效果：2547 个 tick 的计划里只有 **0.5** 的流量落在 p4
   （`{0: 207.6, 4: 0.5}`），所以 240 s 峰值上弹性依然等于静态。

**这两个 bug 都已经修完**（2026-09-24 当天继续），修法是把"保护"从 WARMING 一路补到
"**运营中的池子是地板**"：

1. `+P` 的覆盖集合**并入当前非 INACTIVE 的机器**（`update(..., action=...)`），
   扩容请求不再顺手把已有/刚上线的机器踢掉；`-P` 保持原义（只有它有权缩容）。
2. `scale_on_demand=false` 时，**首拍之后不再把池子缩回 `min_active`**——
   评估器的 45 s 覆盖一过期，原先的需求分支就会把池子打回 1 台，下一拍 `+P` 又要付一次
   45 s 启动；现在运营中的池子就是下限，只有显式 `-P` 能缩。
   （首拍仍按记录/声明的池子裁剪，所以"记录池必须被 seed"那条既有语义不变。）

**修完后的长峰值结果（Qwen3 WAN，240 s 高峰）**：

| 池形态 | 均值 | p50 | p95 | SLO |
|---|---:|---:|---:|---:|
| static 1 台 | 2 699 | 1 947 | 6 046 | 67.9% |
| elastic 1→3，45 s 启动（**修前**） | 2 206 | 1 803 | 5 042 | 84.3% |
| elastic 1→3，45 s 启动（**修后**） | **1 893** | 1 623 | 3 662 | **94.9%** |
| fixed 3 台（参照） | 1 759 | 1 558 | 3 287 | 99.8% |

即：**弹性从"零收益"变成 −30% 均值 / +27pt SLO**，并且只差常开三台的 8%——
那 8% 正是三台各 45 s 的启动窗口（0 / 46.1 / 68.9 s 就位）。回归测试
`test_the_operator_pool_is_a_floor_after_the_first_tick` 与
`test_a_scale_out_does_not_evict_the_worker_it_just_brought_up`（旧代码上均失败）。

**短峰值（45 s）仍然零收益**（4 909 vs static 5 058，−3%）：启动 45 s ≈ 峰值 45 s，
这是物理边界而不是实现问题；想在这类峰值上赚，只能靠 6.25 列的加速手段
（hot spare / 调小 `warmup_s` / 权重预取）。

这三处 lifecycle 修复对**常开固定池**的结论无影响：固定池从 t=0 就是三台 ACTIVE、
没有 WARMING 的机器，两条保护分支都不会触发（6.26–6.30 的四环境与 12 格负载矩阵不变）。
