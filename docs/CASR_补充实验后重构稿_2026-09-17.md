# 存算协同的结构化调度：跨域异构 P/D 分离下的 CASR

> **工作稿（2026-09-17，补充实验后重构版）**  
> 本稿依据最新一轮补充实验重新组织问题定义、算法叙述与实验结论。与上一版相比，主要修正三点：
> 1. 不再把 Zamba2 上的 `735/0` 偏斜归因于“KV-aware 指标优于 compute-load”，而明确为 **compute-load 信号失去区分度后，确定性 tie-break 放大偏斜**；
> 2. 将 Q2 从“比较本地重算时间与 KV 搬运时间”修正为 **两个受限资源之间的负载再分配问题**，只有目的地仍有余量时切换才可能产生净收益；
> 3. 用 20/40/60/120 s 峰值扫描补全结构调整的 break-even 条件，明确当前实现是 **hot-spare Prefill reconfiguration**，而不是完整 autoscaler。
>
> 数字与图均可由当前仓库产物复现。模拟侧见 `docs/arena-summaries/` 与 `docs/figs/`，真机侧见 `实验结果汇总.md`。

## 摘要

Prefill/Decode 分离（P/D 分离）把一次大模型推理拆成两个阶段，也引入了一类传统负载均衡没有显式建模的成本：**Prefill 生成的状态是否值得跨实例、跨主机甚至跨域搬运**。在我们的真实集群上，搬运 1000-token prompt 对应的 KV 需要约 **585 ms（同主机）、1351 ms（跨域）和 8223 ms（慢链路域）**，而 Decode 节点本地完成同一段 prefill 的服务时间约为 **93 ms**。与此同时，Prefill 的可用容量并不总由 FLOPs 决定：生产端 KV 推送上限实测约 **0.26 GB/s**，使 Qwen3-8B 的计算容量与 KV 出口容量相差约 **4.7–6.6×**，Zamba2-1.2B 上这一比值进一步扩大到 **23.6×**。这说明模型、计算与状态移动之间已经出现明显的 **compute–state decoupling**。

我们提出 **CASR（Compute–State Resource Scheduling）**，不把 P/D 分离视为固定执行路径，而将其建模为运行时可选择的执行模式，并在统一资源模型下联合处理三类决策：**执行模式（本地 prefill 还是分离执行）、P/D 放置与流量分配、Prefill 池结构调整**。CASR 显式建模 Prefill 计算容量、KV producer egress、共享链路字节预算和 Decode 计算容量；慢层每 1 s 生成流量与结构计划，快层只对新请求做最小扰动的执行决策，不迁移正在 Decode 的 KV。

补充实验改变了我们对系统机制的若干判断。首先，在 Zamba2 场景中，将 `load` 的 tie-break 从最小实例 id 改成轮询即可把 E2E 从 **418.9 s 降至 163.7 s（2.56×）**，而 `kv_aware` 为 174.7 s，说明第一段差距主要来自 tie-break，而不是新的打分指标；在此基础上，CASR 的字节预算规划进一步把 163.7 s 降到 **65.3 s（2.51×）**，结构调整再降到 **43.3 s（1.51×）**。其次，Q2 的真正翻转由 **Decode 利用率**而非输出长度本身决定；修正排队项后，本地 prefill 比例会在 Decode 饱和后从 100% 降至 78–88%。但进一步实验发现，“能切换”不等于“切换有收益”：在 2500-token、单 Decode 饱和场景中，10.4% 请求被转移后，留下请求的 p50 改善 **5.9×**，但被搬运请求的 p50 达 **16.49 s**，使整体 mean/p95 反而恶化。因此 Q2 的正确语义不是比较两条路径的孤立服务时间，而是比较 **系统边际代价，并要求目的地存在资源余量**。最后，结构调整只有在拥塞持续时间超过 45 s 启动时间后才明显有利：20/40/60/120 s 峰值下收益分别为 **0.0% / 3.7% / 22.2% / 41.1%**。

**关键词：** P/D 分离；KV Cache；存算协同；字节预算；跨域调度；结构重构；混合注意力模型

## 1 引言

### 1.1 从固定 P/D 路径到“计算—状态—网络”联合决策

P/D 分离的经典执行路径是：

```text
Request → Prefill → KV handoff → Decode → generation
```

已有系统通常把调度重点放在“选哪台 Prefill、选哪台 Decode、P/D 配多少资源”。这种抽象隐含了一个前提：**一旦采用 P/D 分离，KV handoff 就是固定执行步骤。**

我们的测量表明，这个前提在跨主机、跨域和异构部署下并不总成立。对 1000-token prompt，KV handoff 需要 585–8223 ms，而 Decode 本地完成同一 prefill 只需约 93 ms。此时真正需要回答的首先不是“KV 搬到哪台”，而是：

> **这个请求是否应该进入分离路径？**

进一步地，即使决定走分离模式，单纯按 GPU utilization 或请求数也无法描述真实容量。在 Qwen3-8B 上，单卡计算容量约为 6.6–9.3 req/s，而 184 MB/request、0.26 GB/s 的 producer egress 只允许约 1.41 req/s；Zamba2 的 prefill 更轻，计算容量约 39.2 req/s，但出口容量仍只有约 1.66 req/s。于是系统可能出现：

```text
GPU compute 仍很空闲
        ↓
KV producer egress 已经饱和
        ↓
继续往该 P 路由只会增加状态排队
```

这意味着 P/D 调度不再只是 compute load balancing，而是一个 **compute、state 与 network 的联合资源分配问题**。

### 1.2 三个相互耦合的决策

CASR 将问题分为三个层次，但三者使用同一套资源口径。

| 层次 | 决策 | 典型时间尺度 | 直接消耗的资源 |
|---|---|---|---|
| Q1 | 请求/流量放到哪对 P/D | 请求级 / 秒级 | P compute、D compute、KV egress、shared link |
| Q2 | 本地 prefill 还是分离执行 | 每请求 | D 的额外 prefill compute，或 P compute + KV bytes |
| Q3 | 当前 Prefill 池结构是否值得维持 | 秒级到十秒级 | 新增/减少 producer、出口通道及启动成本 |

关键不是分别设计三个启发式，而是让三层看到**同一个系统状态**。例如，如果慢层认为某台 P 的 egress 已经饱和，快层就不能仍根据瞬时服务时间把更多请求迁过去；如果候选 `+P` 只能增加 FLOPs、却不能缓解真正的出口瓶颈，则结构层也不应该扩容。

### 1.3 三个动机性观察

#### 观察一：执行模式本身是变量

对当前 fabric，本地 prefill 与 KV handoff 的数量级可以相差 6–88×。因此“本地算还是远端算后搬状态”必须成为显式决策。

#### 观察二：Prefill 的真实容量可能由状态出口而非 FLOPs 决定

Qwen3-8B 上计算/出口容量比约 4.7–6.6×，Zamba2 上达到 23.6×。这使“GPU 还很闲”与“系统还能接活”不再等价。

#### 观察三：模型结构会改变 compute/state 比，而不是简单减少 KV

Zamba2-1.2B 的 38 层中只有 6 层带 KV，但这 6 层使用 MHA，每 token 每层约 16 KB；对照的 Qwen3-8B 使用 GQA，每 token 每层约 4 KB。最终 Zamba2 的 KV footprint 仍约为 Qwen 的 **0.85×**，即只减少约 15%，而 Prefill 服务时间却从约 185 ms 降到约 31 ms。这种 **model-induced compute–state decoupling** 会让状态出口相对更重要。

### 1.4 贡献与本文现在真正主张的内容

本文不主张“首次 P/D 分离”“首次 KV-aware routing”或“首次动态调整 P/D 比例”。CASR 的贡献集中在以下三点：

1. **统一的 execution–placement–structure 形式化。** 将本地模式 `f^R` 与分离模式 `f^T` 放进同一个流量问题，使只有真正走分离路径的流量才消耗 P compute、KV producer egress 和跨域链路字节，并让结构反事实复用同一资源模型。
2. **显式的 state-export capacity。** 将 producer egress `E_p` 与共享链路 `B_l` 作为独立容量约束，而不是把它们折叠进 GPU utilization 或请求数；调度的基本单位由 request/s 提升为 `request rate × state bytes`。
3. **通过补充实验给出适用边界，而不是无条件宣称“更聪明的路由更好”。** tie-break 对照表明指标差异不是主要收益；Q2 crossover 表明切换必须考虑资源余量；结构时长扫描给出 `horizon > startup` 的 break-even 条件。

工程上，我们在 vLLM + LMCache/NIXL + Ray 基座上实现两时间尺度控制器，只影响新流量，不迁移正在 Decode 的 KV，以保持最小侵入性。

## 2 背景与相关工作定位

### 2.1 P/D 分离与资源配比

Splitwise 与 DistServe 建立了按 Prefill/Decode 阶段拆分资源、围绕吞吐和 SLO 配置资源的基本范式；后续 semi-PD、P/D-Serve 与 coordinated autoscaling 将配比进一步推进到动态资源管理和异构部署。

CASR 与这类工作的差别不在“是否支持异构”或“是否能调 P/D 比例”，而在容量定义：**Prefill 的结构价值不仅来自 FLOPs，也来自 KV producer/egress channel。** 因此即使 P compute utilization 很低，只要 egress 已经成为绑定资源，`+P` 仍可能有收益。

### 2.2 请求级路由与缓存感知

SGLang/RadixAttention、vLLM production routing、Llumnix 等方法通常利用 `inflight`、queue 或 prefix hit 进行请求级选择。CASR 并不主张一个新的请求打分函数优于这些方法。补充实验已经表明，在 Zamba2 的短 Prefill 工况下，`load_rr`（与 `load` 完全相同的分数，只换 tie-break）为 163.7 s，而 `kv_aware` 为 174.7 s，两者几乎处于同一水平。

因此本文的主张收缩为：

> 当 compute-load 信号失去区分度时，**确定性 tie-break 会放大等价分数带来的偏斜；但真正进一步拉开差距的是字节预算下的全局规划，而不是再换一个局部打分函数。**

### 2.3 KV 数据面

Mooncake、LMCache/NIXL 与 MemServe 等工作已经把 KV cache 作为系统中的一等状态，并提供传输、缓存和分布式存储机制。CASR 直接复用这些数据面能力，不比较“谁传得更快”。

CASR 在控制面关注的是：

- 一个请求会产生多少 **state bytes**；
- producer 每秒真正能导出多少 bytes；
- 多个逻辑 P/D pair 是否竞争同一条物理链路；
- 当状态传输变贵时，是否应该切换执行模式或改变结构。

### 2.4 混合注意力模型与跨域 Prefill

Mamba/Jamba/Zamba/Nemotron-H 等混合架构减少了全注意力层数量，但不会保证系统状态成本同比下降。Zamba2 的实验说明：KV 层数显著减少的同时，每层 KV 可能更宽，且 Prefill 计算下降得更快，因此系统瓶颈反而更容易从 compute 转向 state movement。

PrfaaS 讨论下一代模型在跨数据中心环境中的远端 Prefill 可行性；CASR 与其共享“远端 Prefill 是否值得”的问题，但本文更强调：**是否值得不能由模型类别或固定 token 阈值决定，而应由当前 compute/state/network ratio 和资源余量共同决定。**

## 3 动机性测量

### 3.1 KV handoff 与本地 Prefill 的数量级差异

单流 1P×1D 标定结果如下。

| 路径 | 1000-token KV 搬运 | Decode 本地 Prefill | 比值 |
|---|---:|---:|---:|
| 同主机 | 585 ms | 93 ms | 6.3× |
| 跨域 | 1351 ms（含 48 ms 固定项） | 93 ms | 14.5× |
| 慢链路域 | 8223 ms | 93 ms | 88× |

这说明 Q2 的存在性没有问题：在当前部署下，“绕过远端 P、让 D 本地执行 prefill”确实可能比状态搬运便宜很多。但这只是**服务时间层面的必要条件**，不是“应该永远本地”的充分条件；§6.5–§6.6 将说明，当 D 或 producer egress 接近饱和时，正确目标应是系统边际代价。

### 3.2 Prefill 的容量口径：compute 与 egress 解耦

| 量 | Qwen3-8B | Zamba2-1.2B |
|---|---:|---:|
| 1250-token 状态量 | 184 MB | 157 MB |
| producer egress | 0.26 GB/s | 0.26 GB/s |
| 出口容量 | 1.41 req/s | 1.66 req/s |
| 计算容量（4090） | 6.6 req/s | 39.2 req/s |
| compute / egress | 4.7× | 23.6× |

Zamba2 的 KV footprint 只比 Qwen 小约 15%，但计算吞吐提升显著，因此 **state-export capacity 变成更加独立的结构资源**。

### 3.3 快 Prefill 下，局部 load signal 可能失去区分度

6×RTX4090、同一条 trace、同一静态池，只换模型：

| 模型 | Prefill 服务时间 | `load` 落点 | 结果 |
|---|---:|---|---:|
| Qwen3-8B | ~185 ms | 375 / 360 | `inflight` 有起伏，分数仍能拉开 |
| Zamba2-1.2B | ~31 ms | 735 / 0 | 大量请求到达时分数相同，tie-break 决定结果 |

上一版把 735/0 过度归因于“算力型指标失败”。补充实验修正了这一判断：

- `load`：418.9 s，735/0；
- `load_rr`：163.7 s，368/367；
- `kv_aware`：174.7 s，372/363。

也就是说，**严重偏斜基本由 deterministic tie-break 造成**。真正仍能区分 CASR 与修好 tie-break 的普通路由的是后续全局规划：`load_rr → casr_lp` 仍有 **2.51×** 差距。

### 3.4 链路项的价值随状态体积翻号

同一数据集与到达过程，只改变每请求 KV 体积：

| 每请求 KV | 37.6 MB | 184 MB | 560 MB |
|---|---:|---:|---:|
| 去掉链路项后的相对变化 | −5.6% | +0.6% | +31.8% |
| 跨域带宽需求 | 0.15 GB/s | ~0.5 GB/s | 3.8 GB/s |
| fabric 能力 |  | ~2 GB/s |  |

当请求状态只有 37.6 MB 时，链路项甚至可能是多余约束；到 560 MB/request 时，跨域需求达到 3.8 GB/s，超过物理 fabric，链路预算变成必须项。

因此 CASR 的收益不是固定常数，而主要取决于：

\[
\frac{\text{state bytes per request} \times \text{request rate}}
     {\text{available producer/link bandwidth}}
\]

## 4 CASR 设计

### 4.1 总体架构

CASR 使用两时间尺度控制：

```text
                    慢层：1 s 控制周期
 ┌──────────────────────────────────────────────────────────────┐
 │ Prefix / request statistics                                  │
 │        ↓                                                     │
 │ Worker lifecycle → byte-budget flow planner → AffinityPlan   │
 │        ↓                                                     │
 │ Counterfactual structural evaluation: +P / -P / keep         │
 └───────────────────────┬──────────────────────────┬───────────┘
                         │ plan                     │ lifecycle
                         ▼                          ▼
 Request → fast decision: local prefill OR P → KV transfer → D
```

设计遵循三条原则：

1. **统一资源口径。** 计算用 service capacity 表示，状态移动用 bytes/s 表示，最终都进入同一目标函数或边际时延估计。
2. **先约束再优化。** 先确定 worker 生命周期和资源余量，再生成流量计划；不能让优化器使用尚未可接活的实例。
3. **最小扰动。** 只对新请求做决策；不迁移正在 Decode 的 KV；结构变化限制 `|ΔP| ≤ 1` 并设置 dwell/startup 条件。

### 4.2 状态与符号

| 符号 | 含义 |
|---|---|
| `C` | prefix/request class 集合 |
| `P`, `D` | ACTIVE 的 Prefill / Decode workers |
| `λ_c` | class `c` 的 EWMA 到达率 |
| `h_{c,p}` | class `c` 在 Prefill `p` 上可命中的 token 数 |
| `r_c` | 请求输入 token 数 |
| `b_c` | class `c` 每请求需要导出的状态字节 |
| `f^T_{c,p,d}` | 分离模式：在 `p` 做 prefill、状态交给 `d` |
| `f^R_{c,d}` | 本地模式：直接在 `d` 做 prefill + decode |
| `C^P_p` | Prefill `p` 的计算容量 |
| `E_p` | Prefill `p` 的 producer egress（bytes/s） |
| `B_l` | 共享物理链路 `l` 的容量（bytes/s） |
| `C^D_d` | Decode `d` 的服务容量 |
| `ρ_x` | 对应资源当前利用率 |

Prefix 命中是 worker-local 的，因此未命中工作比例写成：

\[
w_{c,p}=\max\left(0.05,1-\min\left(0.95,\frac{h_{c,p}}{r_c}\right)\right).
\]

### 4.3 Q1+Q2：统一的执行模式与流量分配

请求不是“先选一对 P/D，再事后决定搬不搬”，而是在两种执行模式中分流。

#### 分离模式

```text
request → Prefill p → KV/state transfer → Decode d
```

消耗：

- P 的 prefill compute；
- P 的 producer egress；
- 路径上所有共享链路的 bytes；
- D 的 decode capacity。

#### 本地模式

```text
request → Decode d : local prefill + decode
```

远端 P 完全不执行，因此**不消耗 P compute、P egress 和 P→D 链路字节**；代价是给 D 增加 prefill 工作。

流量守恒：

\[
\sum_{p,d}f^T_{c,p,d}+\sum_df^R_{c,d}=\lambda_c,\qquad \forall c.
\]

主要容量约束为：

**Prefill compute**

\[
\sum_{c,d}f^T_{c,p,d}w_{c,p}\le C^P_p+s^P_p.
\]

**Producer egress**

\[
\sum_{c,d}f^T_{c,p,d}b_c\le E_p+s^E_p.
\]

**Shared link**

\[
\sum_{c,p,d:(p,d)\in l}f^T_{c,p,d}b_c\le B_l+s^L_l.
\]

**Decode capacity**

\[
\sum_{c,p}f^T_{c,p,d}
+\sum_c\left(1+w^R_{c,d}\right)f^R_{c,d}
\le C^D_d+s^D_d,
\]

其中 `w^R_{c,d}` 由 profiler 把本地 prefill 的服务时间折算成 Decode 服务当量。

目标函数可以写成：

\[
\min
\sum_{c,p,d}f^T_{c,p,d}C^T_{c,p,d}
+\sum_{c,d}f^R_{c,d}C^R_{c,d}
+\beta\sum_x\sigma_x,
\]

其中 `σ_x = s_x / nominal_capacity_x`，避免不同量纲的 slack 被同一 penalty 直接相加。

当前实现仍采用两段近似：慢层根据上一 tick 的本地比例求流量计划，快层再对单请求做最终执行模式选择，可视为联合问题的一轮 fixed-point approximation，而不是每 tick 精确重解。

### 4.4 Q2：从“服务时间比较”升级为“系统边际代价比较”

#### 4.4.1 原始判据

上一版快层主要比较：

\[
T_{local}=T_{prefill}(d,L)+Q_D
\]

与

\[
T_{transfer}=T_{handoff}(p,d,b_c)+Q_E.
\]

若 `T_local < T_transfer`，则直接在 D 本地 prefill；反之走分离路径。

这解决了“为什么所有请求都必须搬 KV”的问题，但补充实验说明它仍然不够。

#### 4.4.2 补充实验暴露的两个问题

**问题 A：排队项曾因单位错误实际上无法触发翻转。** 旧实现使用

```text
min(cap, local_ms * ρ / (1-ρ))
```

但 `cap=3.0` 被作为 3 ms 使用，相对于数百毫秒的 handoff 基本不起作用。Decode 利用率升到 125%、TTFT p50 达 9.4 s 时，本地比例仍保持 100%。

将 `cap` 修正为放大因子，并把 producer egress 排队计入 transfer 侧后，本地比例才在 Decode 饱和时降至 **78–88%**。

**问题 B：会切换仍不代表值得切换。** 在 2500-token、单 Decode 近饱和的受控实验中，切走 10.4% 请求使留下的 89.6% 请求 p50 从 1419 ms 降到 241 ms，但被搬走请求的 p50 达 16490 ms，整体 mean/p95 均恶化。这说明简单比较两条路径的瞬时服务时间，会把瓶颈从 D 转移到 producer egress。

#### 4.4.3 修正后的设计语义

Q2 应被理解为：

> **在 Decode compute 与 Prefill/egress/network 这两组受限资源之间，做有门槛的负载再分配。**

因此更合理的判据是比较系统边际代价：

\[
\Delta C_R = T_{prefill}(d,L)+\Delta Q_D(\rho_D)
\]

\[
\Delta C_T = T_{prefill}(p,L)+T_{handoff}(b_c)
+\Delta Q_P+\Delta Q_E(\rho_E)+\Delta Q_L(\rho_L).
\]

只有同时满足：

\[
\Delta C_T < \Delta C_R
\]

以及目的地仍有余量，例如：

\[
\rho_E(p)<\tau_E,\qquad \rho_l<\tau_L,
\]

才允许把本地 prefill 工作转移到分离路径。

> **实现状态说明：** 补充实验已经验证“目的地余量门槛”的必要性，但该 gate 尚未完成主表级重新实现与重跑。因此本文把它作为补充实验后确定的设计修正，而不把当前旧主表宣称为最终结果。

此外，Q2 是否值得启用还取决于本地 prefill 在 D 总工作量中的占比：

\[
\eta_{prefill}=\frac{T_{prefill}}
{T_{prefill}+T_{decode}}.
\]

当 512-token decode 占据约 94% 的 D 工作量时，即使 Q2 发生翻转，把 prefill 移走也几乎不会改善端到端性能；只有 `η_prefill` 足够大且 D 接近饱和时，资源替换才可能显著释放瓶颈。

### 4.5 Q3：基于反事实收益的 Prefill 结构调整

CASR 的结构动作是 `+1 P / -1 P / keep`，当前主要对应 warm/hot-spare reconfiguration，而不是完整 autoscaling。

候选动作统一通过反事实目标评估：

\[
Gain=(H-T_{startup})\cdot(J_{base}-J_{candidate}-holding)
\]

\[
Cost=C_{startup}+C_{warm}+\frac{warm\_bytes}{bandwidth}.
\]

动作条件：

\[
Gain-Cost>
\max(\theta_{abs},\theta_{rel}J_{base}).
\]

当前部署的 `T_startup = 45 s` 已进入有效收益窗口，因此：

\[
H\le T_{startup}\Rightarrow \text{不应启动新 P}.
\]

补充实验直接验证了这一点：

| 峰值持续时间 | `casr_lp` | `casr_full` | 收益 |
|---:|---:|---:|---:|
| 20 s | 14.7 s | 14.7 s | 0.0% |
| 40 s | 29.3 s | 28.2 s | 3.7% |
| 60 s | 43.7 s | 34.0 s | 22.2% |
| 120 s | 87.0 s | 51.2 s | 41.1% |

因此当前 Q3 最准确的表述是：

> **只有当预期的 egress/Prefill 拥塞持续时间长过实例启动时间，并且新增 P 确实增加瓶颈资源（通常是 producer egress channel）时，结构调整才值得执行。**

### 4.6 与执行基座的集成

| 层 | 组件 | CASR 接入点 |
|---|---|---|
| 执行 | vLLM continuous batching / prefix cache | route hook、local/disaggregated mode 标记 |
| 状态传输 | LMCache / NIXL | 实测 producer rate、handoff latency、pending egress |
| 编排 | Ray | worker ACTIVE / DRAIN / START、hot-spare activation |

CASR 不迁移正在 Decode 的 KV，所有结构动作只影响新到流量。这种最小扰动设计牺牲了一部分全局最优性，但显著降低了对 serving engine 的侵入程度。

## 6 评估

### 6.1 真机主结果：当前仍属于“旧口径的上界证据”

旧主表在 `LOCAL_PREFILL_BASELINES=never` 下得到，因此基线被强制 100% transfer，而 CASR 可以本地 prefill。该口径能够说明执行模式选择潜在价值，但**不能作为最终公平主表**。

| 档位 | `load` | `cache_aware` | `casr_lp` | mean 改善 |
|---|---:|---:|---:|---:|
| CNN-short 14 rps | 880.2 | 919.5 | 281.8 | −68.0% |
| Dolly-15k | 770.6 | 802.4 | 286.0 | −62.9% |
| ShareGPT deep | 2725.6 | 3522.8 | 579.2 | −78.8% |
| CNN-short 56 rps | 2830.1 | 2784.9 | 568.0 | −79.9% |
| CNN-XL 3800 token | 20274.8 | 15982.1 | 3320.6 | −83.6% |
| 五域异构 | 1214.0 | 1213.1 | 291.5 | −76.0% |

因此本文目前只把这些数字作为**历史/上界结果**，最终投稿前必须在两边都允许相同 execution options 的条件下重跑主表。

### 6.2 执行模式选择的潜在价值

在相同路由上仅打开 Q2，`load` 从 886.3 降至 344.1（−61%），说明在当前慢 handoff fabric 上，是否允许绕过分离路径确实会改变性能数量级。

但补充实验表明，这个结果不能被概括成“本地重算总是更好”：

- Decode 很空闲时，本地几乎总划算；
- Decode 饱和后，需要把部分 prefill 工作移到 P；
- 如果 P producer egress 也接近饱和，继续 transfer 只是在两个瓶颈之间搬队列。

因此 Q2 的贡献应表述为“**把执行模式变成可决策项，并明确它的资源边界**”，而不是“发现本地重算一定优于 transfer”。

### 6.3 Tie-break 对照：第一段收益不是新指标

6×RTX4090、Zamba2-1.2B：

| arm | E2E mean | p95 | TTFT p50 | Prefill 落点 |
|---|---:|---:|---:|---|
| `load` | 418.9 s | 803.9 s | 418.2 s | 735 / 0 |
| `load_rr` | 163.7 s | 312.5 s | 163.2 s | 368 / 367 |
| `kv_aware` | 174.7 s | 347.3 s | 172.2 s | 372 / 363 |
| `casr_lp` | 65.3 s | 124.5 s | 65.3 s | 372 / 363 |
| `casr_full` | 43.3 s | 89.1 s | 41.6 s | 314 / 290 / 112 / 19 |

由此得到一个比上一版更可靠的 waterfall：

```text
load 418.9 s
   └─ 修 tie-break → load_rr 163.7 s        2.56×
       └─ byte-budget planning → 65.3 s      2.51×
           └─ structural reconfiguration → 43.3 s   1.51×
```

这组结果直接改变论文的创新叙述：**不能再把第一段写成“KV-aware 指标击败 compute-load”；真正属于 CASR 主张的是后两段的规划与结构。**

### 6.4 模型结构改变 compute/state ratio

同一 6×4090、同一 trace，仅替换模型：

| arm | Qwen3-8B | Zamba2-1.2B |
|---|---:|---:|
| load | 210.5 | 418.9 |
| kv_aware | 227.3 | 174.7 |
| rr | 200.6 | 163.7 |
| casr_lp | 85.0 | 65.3 |
| casr_full | 54.9 | 43.3 |

两点最重要：

1. 在 Qwen 上，`kv_aware` 甚至略差于 `load`，说明“更复杂的打分”没有普适收益；
2. Zamba 上 Prefill 快到 `inflight` 很难形成差异，局部 load score 更容易打平，但其 KV footprint 仍为 Qwen 的约 0.85×，因此 state movement 并没有随着计算一起消失。

这支持的不是“混合模型一定更需要 CASR”，而是：**模型变化会改变 compute/state ratio，调度器不能假定瓶颈永远跟着 GPU compute 走。**

### 6.5 Q2 crossover：真正决定翻转的是 Decode 利用率

先固定 1250-token 输入、8 rps、6 个 Decode，仅扫描 output length：16/64/128/256/512 token。

结果本地比例始终为 100%，Decode queue 只有 0–4 ms。原因是 6 个 Decode × 16 slots 提供约 48 req/s 头部空间，远高于 8 rps 到达率。

因此：

> **output length 不是独立的决定变量；它只有通过提高 Decode utilization 才会影响 Q2。**

进一步把 Decode 池缩到 2 台并固定 512-token 输出，随着到达率增加，修正后的 Q2 才在饱和后出现 transfer：本地比例从 100% 降到 **78–88%**。

然而此时 E2E 几乎不改善，因为 1250-token prefill 只占 Decode 总工作量约 6%，512-token decode 才是主要瓶颈。这说明 Q2 还要看：

\[
\eta_{prefill}=\frac{T_{prefill}}
{T_{prefill}+T_{decode}}.
\]

当 `η_prefill` 很小时，把 prefill 从 D 挪走不会释放多少真正的瓶颈资源。

### 6.6 “切换生效”不等于“切换有净收益”

为了构造 Q2 真正可能有用的窗口，我们使用：

- 2500-token prompt，KV ≈280 MB/request；
- 16-token output；
- 1 个 Decode、`max_num_seqs=2`；
- 16 req/s。

本地模式容量实测约 14.9 req/s；两台 Prefill producer 合计额外 egress 能力约 1.72 req/s，因此 16 req/s 刻意位于两者之间。

| 判据 | p50 | mean | p95 | 本地份额 | 本地请求 p50 | 被搬运请求 p50 |
|---|---:|---:|---:|---:|---:|---:|
| 旧规则（不切换） | 1419 ms | 1421 ms | 2639 ms | 100% | 1419 ms | — |
| 修正到可切换 | 251 ms | 2128 ms | 16667 ms | 89.6% | 241 ms | 16490 ms |

表面看，切换成功释放了 Decode：留下的 89.6% 请求 p50 改善 **5.9×**。但被搬走的 10.4% 请求进入几乎没有余量的 producer egress 后，p50 变成 **16.49 s（约 68×）**，使整体 mean/p95 反而变差。

这一负结果非常关键：

> **Q2 不是“谁当前更快就走谁”，而是在两个受限资源池之间做负载再分配。只有接受负载的一侧仍有余量时，切换才可能是系统级收益。**

因此最终设计需要 egress/link headroom gate，不能只使用瞬时 pending queue 快照。

### 6.7 结构调整的 break-even horizon

固定 6×4090、1250-token、8 rps，只改变峰值持续时间：

| 峰值 | 静态池 `casr_lp` | 可 +P `casr_full` | 收益 |
|---:|---:|---:|---:|
| 20 s | 14.7 s | 14.7 s | 0.0% |
| 40 s | 29.3 s | 28.2 s | 3.7% |
| 60 s | 43.7 s | 34.0 s | 22.2% |
| 120 s | 87.0 s | 51.2 s | 41.1% |

容器启动时间为 45 s。20 s 档完全不触发 +P；40 s 只有少量流量在启动后赶上新实例；60/120 s 才出现明显收益。

这验证了结构判据里的有效窗口：

\[
H_{effective}=H-T_{startup}.
\]

结构层的正确主张因此是：**不是“负载高就扩 P”，而是“瓶颈属于 P/egress，且拥塞持续时间足够长时，增加 producer 才值得”。**

### 6.8 跨域、热点前缀与长 prompt

热点前缀负载中，所有策略的 prefix hit 都约为 81.7%，差别主要来自 placement。当 WAN 变慢时，CASR 通过 byte budget 把 P/D 尽量配成同域对，因此 LAN 与 WAN 下可保持接近的结果，而普通 load/rr 会随跨域成本显著恶化。

长 prompt（3750 token，KV 约 402 MB/request）下：

| arm | E2E mean | p95 |
|---|---:|---:|
| load | 293.5 | 570.6 |
| rr | 246.1 | 472.6 |
| casr_lp | 119.2 | 229.5 |
| casr_full | 93.6 | 194.2 |

这类状态更大的 workload 也是 byte-budget placement 与额外 producer channel 最容易产生收益的 regime。

## 7 讨论与适用边界

### 7.1 CASR 什么时候值得

CASR 的价值主要由以下四个量共同决定：

1. **状态压力**：`state_bytes × request_rate / bandwidth` 是否接近或超过 egress/link capacity；
2. **compute–state decoupling**：模型是不是“算得很快，但状态并没有同比变小”；
3. **资源替换空间**：Q2 的接受侧是否有 headroom，且被迁移的 prefill 工作是否是原瓶颈的重要组成部分；
4. **结构时间尺度**：预期拥塞持续时间是否超过 worker 启动/预热时间。

因此以下场景中 CASR 的优势会自然减弱：

- KV 已被压到很小（例如强压缩或极小状态模型）；
- fabric 足够快，producer/link 不构成瓶颈；
- Decode 长期严重饱和，且 Prefill 只占很小的 Decode 工作量；
- 峰值持续时间短于实例启动时间。

### 7.2 当前最重要的限制

1. **公平主表仍需重跑。** 旧真机主表中基线被禁止 local prefill，而 CASR 可以使用，因此不能直接作为最终投稿 headline。
2. **Q2 的 headroom gate 已被实验验证为必要，但尚未完成最终实现和主表重跑。** 当前实验价值是找到了 naive switch 的失败模式与正确设计方向。
3. **producer 0.26 GB/s 是当前 NIXL connector 实测速率。** 虽然 560 MB/request 档的 3.8 GB/s 需求已经超过约 2 GB/s 的物理 fabric，但仍需要 0.25–8 GB/s 带宽扫描，证明 CASR 会随着网络变快自然退化为普通路由。
4. **A100 慢链路域已无法补轮。** 其已有常数与结果可用于复现，但不能继续扩展实机样本。
5. **模拟器只用于同环境内相对比较。** 绝对时延与真机存在已知偏差。

### 7.3 下一轮最优先实验

按论文闭环程度排序：

1. 实现 Q2 的 `egress/link headroom gate`，并在 `local_prefill=auto` 下重跑公平主表；
2. 做 producer/link bandwidth sweep（0.25 / 0.5 / 1 / 2 / 4 / 8 GB/s），画 CASR 收益的 crossover；
3. 主表改成分解式：`load_rr(+same execution options) → byte-budget planning → structural reconfiguration`，避免再把 tie-break artifact 算作算法收益；
4. 在至少一个 prefill-dominant、目的地有余量的场景中验证 Q2 的**正净收益**，与 §6.6 的负结果组成完整边界。

## 8 结论

本文研究的核心不是“如何把 KV 传得更快”，也不是再设计一个更复杂的请求级打分函数，而是：**当 P/D 分离把状态移动变成一等成本后，执行模式、放置和结构必须看到同一套 compute–state–network 资源。**

CASR 将请求拆成分离流 `f^T` 与本地流 `f^R`，显式约束 Prefill compute、producer egress、共享链路与 Decode capacity，并用同一资源模型评估 Prefill 结构调整。补充实验进一步收紧了论文主张：Zamba2 上最极端的 735/0 首先是 tie-break artifact，而不是 KV-aware 指标的胜利；在修好 tie-break 后，byte-budget planning 仍提供 **2.51×** 的进一步改善，结构重构再提供 **1.51×**；Q2 的翻转由 Decode utilization 驱动，但只有接受侧有余量时才可能形成系统级收益；结构动作则只有在拥塞持续时间超过启动时间后才值得执行。

因此，本文最终希望表达的不是“CASR 在所有情况下都更好”，而是一套更明确的判据：

> **当模型计算与状态大小发生解耦、state bytes 接近 producer/link capacity、并且系统存在可利用的计算或结构余量时，调度器应该从 request-count / GPU-utilization 视角升级到显式的 compute–state resource scheduling。**

## 附录 C：影响结论的关键缺陷与修复

| # | 现象 | 根因 | 处理 |
|---|---|---|---|
| 1 | 一次 KV handoff 被重复收 RTT | trace 按层发 SEND/RECV | 聚合为一次 handoff |
| 2 | 长 prompt 模拟活锁 | staging budget 计费/释放粒度不一致 | 按请求统一计费释放 |
| 3 | 基线得到更多容器 | `min-active` 只约束 CASR | 对所有策略统一 inactive set |
| 4 | `+P` 收益无法显现 | P 容量只按 FLOPs | 将 producer egress 作为独立容量 |
| 5 | cache-aware 两侧 tie-break 不一致 | 真机/模拟语义不同 | 对齐实现 |
| 6 | 高负载 LP 异常 | Decode 记账与 LP 负载项缺陷 | 修复并回归 |
| 7 | Q2 在 Decode 125% 时仍 100% local | `cap=3` 被当作 3 ms | 修正排队外生性与 transfer queue |
| 8 | 修后 Q2 过度 transfer | 只看目的地瞬时 pending，不看 headroom | 已定位；需要 egress/link utilization gate |

## 附录 D：Zamba2 profile 摘要

RTX4090 上 Zamba2-1.2B：decode step 约 4.86 ms，prefill@1024 约 25.5 ms；RTX5090 对应约 3.04 ms / 19.5 ms。混合模型的核心意义不是“KV 消失”，而是 Prefill compute 下降得比 state footprint 更快，从而放大 compute/state decoupling。
