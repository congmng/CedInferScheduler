| RTX3090 | 0.29.0 | 2026-09-10 | 16384 |

即 4090/5090 用的是旧引擎、A100 的 KV 轴只到 4096，**这三份不能和 3090 那份同表比**。
本轮把这三域按 3090 的口径统一重采：**vLLM 0.29.0**、
`--max-num-seqs 128 --max-num-batched-tokens 2048 --attention-max-kv 16384
--measurement-iterations 3 --skip-skew`，TP `1,2`，模型 `Qwen/Qwen3-8B`、`bf16`。

| 域 | 主机 | 镜像 | 分片 | GPU |
|---|---|---|---|---|
| RTX4090 | 本机 | `vllm/vllm-openai:casr029` | `--shard 0/2`、`1/2` | 0, 1 |
| RTX5090 | `10.212.70.196` | `vllm/vllm-openai:casr029` | `--shard 0/2`、`1/2` | 2, 3 |
| A100 | `10.70.251.47:2222` | `vllm/vllm-openai:v0.29.0` | `--shard i/4` ×4 | **4,5,6,7** |

> A100 那台 8×80GB 里 0–3 仍被 `mosaic-node-a/b` 占满（80.8/81.9 GiB），**只用空闲的
> 4–7**；宿主的 `vllm/vllm-openai:v0.29.0`（30.5 GB）已在本地，不需要跨网段传 21.5 GB
> 镜像（A100 ↔ `10.212.*` 实测只有 4–13 Mbps）。`buaa` 不在该机 docker 组，用
> `sudo docker` 运行，不修改该机的组成员。

分片产出落在 `/tmp/prof-4090/card{0,1}`（本机）、`~/casr/prof-out-5090/card{0,1}`、
`~/prof-out-a100/card{0..3}`；全部完成后用
`python3 tests/merge_profile_shards.py --out-root profiler/perf --hardware <HW>
--model Qwen/Qwen3-8B --variant bf16 --tp 1,2 <各分片目录>` 合并，再跑
`tests/check_profile_bundle.py`。**每次 `measurement-iterations=3` 且 attention 网格
含 7576 个 shot；实测**单域约 35 分钟**（4090/5090 各 2 分片、A100 4 分片），
attention 阶段每片 3788（A100 1894）个 shot。跑完前不要用旧 bundle 做跨域对比。

#### 结果（2026-09-18 当天跑完）

三域都跑完并合并成功，四域现在是**同一套口径**（vLLM 0.29.0 / CUDA 13.0 /
`tp [1,2]` / `max_kv 16384` / `iters 3` / attention 7576 行），
`python3 tests/check_profile_bundle_consistency.py` 全部 `ok`：

| 域 | vLLM | 结论 |
|---|---|---|
| A100 | 0.29.0 | 数值与原 bundle 逐行一致（x1.00），KV 轴从 4096 补齐到 **16384** |
| RTX4090 / RTX5090 | 0.29.0 | 已替换默认 bundle |

**40/50 换默认之前先补了一个显式的 Decode 开销项**。同网格重采后 FFN 项变成原
bundle 的 **0.56–0.59×**（attention 侧 `qkv_proj`/`o_proj` 是 1.00×），直接换上会让
5090 单步代价从 14.8 ms 掉到 **9.68 ms**，而真机实测 TPOT 是 14.5–15.0 ms。
判定为"**0.29.0 的 kernel 确实更快，缺的是 kernel 之外的开销**"，于是在
`trace_generator` 里加了 `DECODE_STEP_SCALE`（与已有的 `prefill_scale` 同一个机制）：

| 卡 | 0.29.0 bundle 的 kernel 时间 | ×1.5 后 | 真机 TPOT | 需要的倍数 |
|---|---:|---:|---:|---:|
| 5090 | 9.68 ms | 14.5 ms | 14.5–15.0 ms | **1.53** |
| 4090 | 16.63 ms | 24.9 ms | 24.6 ms | **1.48** |
| 3090 | 31.07 ms | 46.6 ms | 43.1–47.1 ms | **1.45** |

**三张卡需要的倍数是同一个常数（1.45–1.53）**——这是判"选 2"的关键证据：
换成旧的 0.27.1 bundle，同样的三个比值是 **1.00 / 0.96 / 1.45**，没有任何一个常数
能同时拟合。也正因为是"按比例"而不是"加一个固定毫秒数"（固定项要 6.0 / 9.7 / 14.0 ms，
差 2.3 倍），实现的是乘性系数而不是加性常数。多出来的那 1/3 是 attention、采样、
调度循环与 host 开销，逐层 eager profile 本来就不计这些。

`hw_service.step_cost_ns(..., decode=True)` 用同一个系数给计划侧定价，所以计划和执行
仍然是在给同一个引擎定价；`decode=False` 返回原始 profile 值（写论文/排查时用）。

2026-09-10 起拓扑扩展为 **4 域 7 实例**（Qwen3-8B，单卡一实例）：

| 实例 | 主机 | GPU | 端口 | 角色 |
|---|---|---|---|---|
| `p5090` | `10.212.70.196` | 0 | 8100 | Prefill |
| `d5090` | `10.212.70.196` | 1 | 8200 | Decode |
| `p3090a` | `10.212.67.68` | 0 | 8100 | Prefill |

`3090b` 只提供 Prefill：该机第二张 3090 仍被 `qemu-system-x86_64 -name conzone` 占用（见上文 GPU 修复记录），因此本域是"仅 Prefill"的异构域。三台 GPU 节点统一使用本地 tag `vllm/vllm-openai:casr029`（= digest `sha256:c2914767605584b6d8f45686b82de173ecc99e781897aa3d0a66dacd72c51ae1`，vLLM `0.29.0` / LMCache `0.5.4`）；`3090b` 原本仅有 `0.27.1`，已通过内网 `docker save | docker load` 从 `3090a` 流式同步并核对版本。

各域业务网卡：`5090=ens6f0`、`3090a=ens18`、`3090b=eno1`、`4090=eno1`。

`4090` 是 Ray 头节点（`ubuntu@10.212.67.167`）。该机 4 张 4090 里 GPU1/GPU3 被他人（`zhangtr` 的 `VQsmooth`）占着约 `8.9 GB`，GPU0/GPU2 完全空闲，因此取 GPU0 做 Prefill、GPU2 做 Decode；Docker 走标准 `--gpus device=<n>`，不需要 `gpu_runtime` 覆盖。镜像与模型都是从 `5090` 传过去的：`ssh 5090 "docker save vllm/vllm-openai:casr029" | docker load`（得到同一 image ID `fba1a5021627`），模型经 `rsync` 落到 `/home/ubuntu/models/Qwen3-8B`。因为 4090 用的是本机 `ubuntu` 账户而不是其它节点的 `buaa`，`router_config.json` 的 host 支持可选字段 `config_dir`（4090 设为 `/home/ubuntu`）。

`p4090` / `d4090` 的 `service_ms` 由同域对 `p4090 → d4090` 标定：Prefill p50 `39.2 ms`、Decode p50 `157.1 ms`。跨域对照 `p4090 → d5090` 为 `42.7 / 142.9 ms`，`p5090 → d4090` 为 `53.1 / 155.5 ms`，说明 4090 的 Prefill 比 5090 略快（`39.2` vs `48.5 ms`）、Decode 略慢（`157.1` vs `144.7 ms`），处于 3090 与 5090 之间的"中间档"异构域。

`3090b` 的 dockerd（`29.1.3`）在启动时没有可用的 CDI 规格，`docker run --gpus` 会报 `could not select device driver ""`，而其 `nvidia` 旧式 runtime 可用。因此 `router_config.json` 的 host 支持可选字段 `gpu_runtime`：设置后部署脚本用 `--runtime=nvidia -e NVIDIA_VISIBLE_DEVICES=<gpu>` 固定设备，未设置则仍用 `--gpus device=<gpu>`。这样无需重启共享机器上的 Docker。

`disagg_router.py` 在单个 HTTP 入口（`:9000`）按请求决定 P 与 D，并通过 `kv_transfer_params.disagg_spec` 指定 LMCache 接收端，因此可在同一批实例上切换不同放置策略：

- `rr`：Prefill/Decode 各自轮询（隔离基线）。
- `load`：按 `in-flight/capacity` 取最轻实例（vLLM 风格基线）。
- `casr`：prefix 亲和把同前缀请求钉在同一 Prefill，Decode 侧按
  `网络代价 + 实测 service_ms + Prefill/Decode 利用率` 选最小代价对。
- `casr_lp`：不再用固定规则，而是让**模拟器同一份 CASR 控制环**算出
  `f_ijk`（OR-Tools LP）并发布 `AffinityPlan`，router 只做快速重放。
- `cache_aware`：**SGLang Router `cache_aware` / vLLM production-stack prefix-aware
  router 的对应实现**：维护每个 Prefill 的前缀索引，优先选命中**最长前缀**的
  Prefill；命中实例的 `inflight / max_num_seqs` 超过
  `weights.cache_aware_load_threshold`（默认 `0.5`）时溢出到最空实例。
  分母必须是引擎真实的 `--max-num-seqs`：曾误用求解器的 `capacity`（req/s），
  in-flight 计数永远到不了它，阈值形同虚设。用于和 CASR 做"近期 SOTA 路由"对比。
- `casr_full`：`casr_lp` + `+P/-P` 结构生命周期，会真的启动/停止 Prefill 容器。
- 消融策略：`random`（随机放置下界）、`casr_noservice`（去掉 `service_ms` 项）、`casr_noaffinity`（去掉 prefix 亲和）。

数据集与基线来源、以及每个策略对应哪个系统/论文，统一记在
`docs/实验数据集与对比基线说明.md`。

### Decode 回退必须走代价模型（2026-09-11）

`build_affinity_plan` 会把 LP 置零的 Decode 记为 `fallback_decode_ids`。真机 router
原先在这条 fallback 上用 **least-loaded**，于是"被代价模型刻意避开的慢实例"因为最空
而不断被选中——在 3-Prefill 拓扑上 `casr_lp` 有 76 个请求落到最慢的 `d3090a`
（均值 `1108 ms`），把整体均值抬了约 `80 ms`，几乎就是它与启发式的全部差距。
现改为 fallback 也用 `_pair_cost`（网络 + `service_ms` + 利用率）。模拟器侧没有这条
real-only 路径（它走 `AffinityPlan` deficit 重放），不受影响。

### 真机 router 与模拟器共用同一份 CASR 代码

此前 `casr` 策略是在 router 里另写的一份启发式代价函数，只能"看起来像"
模拟器。现在 `casr_lp` / `casr_full` 直接 import `serving/casr`，两边跑的是
同一份算法实现，`deploy/real_lmcache_pd/casr_control.py` 只补了**观测与执行**
这一层：

| 共享模块 | 作用 |
|---|---|
| `casr.flow_solver` | greedy / OR-Tools GLOP 的 `f_ijk` 求解器（含缓存感知 `work[p,class]`、容量/共享链路约束、overflow penalty） |
| `casr.evaluator` | `+P/-P` 反事实结构决策（收益阈值、dwell、warm/cold 模式） |
| `casr.plan_builder` | `f_ijk → AffinityPlan` 权重表（模拟器与真机唯一的计划出口） |
| `casr.prefix_profiler` | `derive_class_id`，真机与模拟器用同一套 class 命名 |
| `casr.state` | Prometheus 文本解析 |

真机专有的部分只有三件：

1. **观测**：`RealCASRController.tick()` 用 vLLM 的 `/metrics` 拿
   `num_requests_running` / `num_requests_waiting` /
   `prefix_cache_queries_total` / `prefix_cache_hits_total`，把每个 Prefill 的命中
   增量按 class 摊回 `hit_tokens_ewma / requested_tokens`，得到与模拟器
   `_aggregate_rows` 含义一致的 `work[p, class]`；class id 用 `derive_class_id`
   配 router 的前缀哈希与 token 估算。
2. **执行**：`+P/-P` 通过 Docker Engine API（本机 unix socket）或
   `ssh <host> docker start/stop` 落到真实容器；`local_domains` 决定哪些域走本地
   socket，其余走 SSH。容器名前缀 `casr-md-`。
3. **容量与代价标定**：模拟器把异构算力编码在 `prefill_capacity` /
   `decode_capacity`，真机用实测 `service_ms` 标定同一组键：
   `solver_capacity = max_num_seqs * 1000 / service_ms`，即"该实例在实测单请求
   延迟下每秒可承载的请求数"（P：p5090 `330`、p3090a `235`、p3090b `152`、
   p4090 `408`；D：d5090 `111`、d3090a `38`、d4090 `102`；每实例
   `max_num_seqs: 16`）。结果写在 `router_config.json` 的 `casr` 块里，与模拟器
   cluster 配置的 `casr` 块同名同构，`FlowSolverConfig.from_dict` 是双方唯一的
   解析入口。

   目标函数里还有三个真机标定出来的量，都放在同一个 `casr` 块里，模拟器侧同名生效：

   | 键 | 含义 |
   |---|---|
   | `prefill_service_ms` / `decode_service_ms` | 每实例实测单请求延迟；`compute_weight` 把它折算成"单位流量的算力代价"，否则 LP 会把慢实例当成同域零网络代价的廉价溢出口 |
   | `compute_weight` + `work[p,class]` | Prefill 的算力代价按 `work = 1 - prefix_hit_ratio` 缩放，KVCache 命中越多同一台 Prefill 越便宜——这是"KVCache 感知"进入目标函数的位置 |
   | `utilization_weight` / `utilization_segments` | 按实例利用率的**分段凸**代价（`≈ w · service_s · L² / (2K)`），给 LP 补上"越集中越贵"的边际项；`0.0` 表示关闭，与既有结果一致 |
   | `plan_gain_threshold_rel` / `_abs` | 计划滞回：新解的 objective 不比当前计划好过这个阈值时沿用旧计划（且不递增 `plan.version`，避免快速 router 每个控制周期重置 deficit 计数器）。`0.0` 表示关闭 |
   | `shared_links` | 每台 Prefill 一条 `capacity_bytes_per_s: 2e9` 的推送链路（实测有效带宽 ~16 Gbps），覆盖它的所有 P-D 对。链路按**完整 KV 字节**计费，是"一台 Prefill 每秒只能推 ~6.6 个 2048-token 前缀"这条真机约束进入 LP 的地方；模拟器侧的 `shared_links` 是同一个键、同一套约束 |
   | `kv_bytes_per_token` | 单个提示 token 在一张卡上占的 KV 字节（Qwen3-8B 为 `147456`）。生产端没有显式上报 `kv_bytes_per_request` 时（模拟器的 trace 路径如此），求解器用「观测到的每请求 token 数 × 该值」补出 KV 字节，`shared_links` 的字节预算才能真正按类收费；真机控制器一直显式上报字节，行为不变 |
   | `warmup_enabled` / `warmup_concurrency` / `warmup_min_share` | 真机前缀预热（默认关闭）。开启后 router 为每个 class 缓存一份 prompt，对该 class 在当前计划里的每条 `(class, Prefill)` 边，后台发一次带 `disagg_spec` 的 handoff 把前缀先算好；不经过 `observe`/`record`，因此不污染到达率和延迟指标。`warmup_concurrency` 限制并发预热数，`warmup_min_share` 只预热计划权重不低于它的边。**2026-09-11 实测中性**（见 `docs/异构环境搭建进展.md`），默认关闭 |
   | `overflow_penalty` | **按容量归一化**的溢出罚：约束写成 `load / capacity <= 1 + slack`，`slack` 是"容量的比例"，所以 `10.0` 表示"超载一倍容量"的代价，与约束用的是 `req/s` 还是 `byte/s` 无关。作用在原始单位上时，链路溢出的量级（`1e8–1e9 byte/s`）会把算力项（`~0.2`）完全淹没，LP 会为了压掉 1% 的溢出做大幅迁移，`plan_gain_threshold_rel` 也失去意义 |

   注意 `solver_capacity` 目前是**按单请求延迟折算的上界，不是实测吞吐拐点**：
   它按 `max_num_seqs × 1000 / service_ms` 算，假设吞吐随 batch 线性增长。
   `tests/calibrate_pd_throughput.py` 逐档提并发实测（`p5090 → d5090`）：

   | 并发 | 16 | 24 | 32 | 40 | 48 | 64 |
   |---|---:|---:|---:|---:|---:|---:|
   | 吞吐 (req/s) | 41.3 | 54.0 | 54.7 | 70.2 | 65.8 | 63.0 |

   即在并发 `24–40` 附近饱和在 `60–70 req/s`，而配置里 `d5090` 的
   `solver_capacity` 是 `111`——方向对但偏高约 2×，所以真机运行的
   `decode_overflow` 恒为 0。当前真正绑定的约束是 Prefill 侧的 `shared_links`
   推送预算。把每个 D 实例的实测拐点写回 `decode_capacity` 是下一步工作
   （见 `docs/异构环境搭建进展.md`）。

**运行时依赖**：router 镜像需要 OR-Tools（LP）与 `openssh-client`（跨域
`+P/-P`），由 `deploy/real_lmcache_pd/router_image.Dockerfile` 构建为
`casr-router:latest`：

```bash
docker build -f deploy/real_lmcache_pd/router_image.Dockerfile \
  -t casr-router:latest deploy/real_lmcache_pd
```
`run_real_multidomain_comparison.sh` 会把 `serving/`
挂到 `/casr-serving` 并设 `PYTHONPATH`，`casr_full` 额外挂 `~/.ssh`（只读，
启动时复制到 `/root/.ssh` 并修正权限）。

**可观测性**：`GET /routing-state` 现在带 `casr` 字段，含 solver 后端
（`ortools-glop` 或 `greedy` 回退）、当前 `AffinityPlan` 权重、
最近一次结构决策、`actions`（真实 scale 事件的留痕）、
`plan_events`（每次 `plan.version` 切换，以及触发它的
`incumbent_cost` / `candidate_cost`——排查"计划为什么把 class 搬走"的第一手证据）、
顶层的 `warmup`（`warmed_edges` / `inflight` / `ok` / `failed` / `cached_classes`），
以及 solver 诊断：`work`（每个 class 在每台 Prefill 上的未命中工作比例，用来确认
缓存项生效）、`prefill_overflow` / `decode_overflow` / `link_overflow`
（容量与推送链路约束是否绑定）、`compute_weight` / `utilization_weight`
（目标函数当前权重）。

**到达率估计**：控制面按每个控制周期（`control_interval_s`）统计各
`(Prefill, class)` 的到达**计数**，除以采样窗口长度得到速率，再用 `ewma_alpha`
平滑（首次采样直接采用窗口速率，不从 0 爬升）。不再使用
`1 / (now - last_arrival)`——间隔倒数的均值总是大于平均间隔的倒数，且同毫秒内
到达会把估计打到 `~1e6 req/s`，LP 会因此严重高估负载、把每个 class 过度铺到
所有 Prefill 上并反复迁移冷前缀。`hit_half_life_s` 因此不再参与到达率衰减，
仅为兼容旧配置保留。

## 真实链路标定（3 P × 2 D）

用 `tests/calibrate_real_pd.py` 对每个 P-D 对发 8 个 512-token 前缀请求（`output_tokens=8`），重复 3 轮并取各轮 p50 的中位数，得到 6 个可用的 P-D 对：

| P → D | Prefill p50（3 轮） | Decode p50（3 轮） | 说明 |
|---|---:|---:|---|
| `p5090 → d5090` | `48.2 ms` | `144.7 ms` | 同域、同主机 |
| `p5090 → d3090a` | `48.8 ms` | `434.1 ms` | 跨域，5090 Prefill + 3090 Decode |
| `p3090a → d5090` | `71.7 ms` | `143.1 ms` | 跨域，3090 Prefill + 5090 Decode |
| `p3090a → d3090a` | `64.2 ms` | `410.4 ms` | 同域、同主机 |
| `p3090b → d5090` | `110.6 ms` | `145.4 ms` | 跨域，3090b Prefill + 5090 Decode |
| `p3090b → d3090a` | `99.7 ms` | `421.6 ms` | 跨域，3090b Prefill + 3090 Decode |

按"同一实例跨轮取中位数"回填到 `router_config.json` 的 `service_ms`：

| 实例 | 角色 | `service_ms` |
|---|---|---:|
| `p5090` | Prefill | `48.5` |
| `p3090a` | Prefill | `68.0` |
| `p3090b` | Prefill | `105.2` |
| `d5090` | Decode | `144.7` |
| `d3090a` | Decode | `421.6` |

注意 Prefill 侧的 `prefill_ms` 只反映 Prefill 请求的往返（KV 推送是异步的）：对同一 Prefill 分别发"纯 Prefill"与"带 `do_remote_decode`“两种请求，耗时差在 `0-1 ms` 量级，说明跨域 KV 推送不占用 Prefill 关键路径，其开销体现在 Decode 首次拉取 KV 时。

结论：

1. Decode 延迟主要取决于 Decode 卡的算力（5090 约 `155–162 ms`，3090 约 `409–446 ms`），差异约 `250 ms`。
2. 跨域 KV 传输的额外代价只有约 `35–40 ms`，远小于此前的 `0.93 Gbps` 网卡标称值估计。按 512-token 前缀（2 个 256-token chunk ≈ `75.5 MB`）反推，有效传输带宽约 `16 Gbps`，因此 `router_config.json` 的链路参数已按实测标定为 `bw_gbps=16`、`rtt_ms=0.3`。
3. 每个新起始的 P/D 容器在**首次**发生某个 (P,D) handoff 时会额外付出约 `51 s` 的一次性代价（JIT/内核编译路径），之后同一对恢复为正常延迟。`run_real_multidomain_comparison.sh` 因此在测量前对每个 P-D 对做真实 handoff 预热，避免冷启动污染策略对比。
4. 容器使用 `-v /tmp/casr-vllm-cache:/root/.cache/vllm` 持久化 vLLM 缓存，减少重启后的重复编译。

## 第四域：A100 远程域的链路标定与现状

2026-09-10 尝试把 A100 节点（`10.70.251.47:2222`，本地无 dockerd CDI 问题之外与其它域同构）接成第 4 个域：`p_a100`（GPU0:8100）/ `d_a100`（GPU1:8200），Qwen3-8B 单卡，镜像 `vllm/vllm-openai:v0.26.0`（vLLM `0.26.0` / LMCache `0.5.2`，PD 配置键与 `0.5.4` 同名兼容）。两个实例能起、能过健康检查，`p_a100 → d_a100` 同域 handoff 正常。

### 跨域链路定向复测（iperf3，取 receiver 侧 goodput）

| 方向 | 实测 | `router_config.json` |
|---|---:|---:|
| `a100 → 5090` | `41–124 Mbps`（收 40.8） | `0.041 Gbps` |
| `5090 → a100` | `13–22 Mbps`（收 13.1） | `0.015 Gbps` |
| `a100 → 3090a` | `131–138 Mbps` | `0.131 Gbps` |
| `3090a → a100` | `~11 Mbps` | `0.011 Gbps` |
| `a100 → 3090b` | `~138 Mbps` | `0.138 Gbps` |
| `3090b → a100` | `14.2 Mbps` | `0.0142 Gbps` |

RTT 均为 ~`26 ms`。`5090` 侧 `ip route get 10.70.251.47` 显示走 `via 10.212.70.1 dev ens6f0`，即 A100 与 10.212 内网之间是跨网段路由，比 10.212 内网（`16 Gbps` / `0.3 ms`）慢 2–3 个数量级，且**方向不对称：进入 A100 的方向（10–22 Mbps）明显慢于流出方向（120–140 Mbps）**。

按此链路，一个 256-token chunk 的 KV（`147456 B/token × 256 ≈ 37.7 MB`）推进 A100 需要约 `14–30 s`。因此任何"Prefill 在 10.212、Decode 在 A100"的跨域 handoff 都不可用；A100 域只有在 P、D 同域时才实用。这正是链路感知代价项该起作用的场景。

显存方面，该节点是共享机，需要与其它用户的训练任务共存。`start_multidomain_pd.sh` 因此新增了 host / instance 级的 `gpu_memory_utilization`、`max_model_len`、`max_num_seqs` 覆盖；`router_config.json` 给 `hosts.a100` 设 `gpu_memory_utilization = 0.35`（约 27.7 GB，单卡 79 GB）。

### 故障：LMCache 首个 P-D 握手偶尔死锁（2026-09-11）

- 现象：`run_real_multidomain_comparison.sh` 在 `casr_lp` 一轮的 `warmup_instances`

  `EngineCore` 都停在 100% CPU，Decode 日志停在
  `nixl_channel.py: Replying mem register response` 之后不再打印
  `LMCache hit tokens`。
- 定位：正常的每对 P-D **首次**握手本身就慢（实测同一对第一请求
  Decode 侧 `51.05 s`、第二请求 `0.07 s`，Prefill 侧一直 `44–109 ms`），
  warmup 就是用来吸收这个固定开销的。上述这次不同：握手在注册内存后
  永久不返回，属于 LMCache `v0.5.4` NIXL 通道的偶发死锁，重启容器即恢复。
- 处置：给 `warmup_instances` 加 `WARMUP_TIMEOUT`（默认 `300 s`）：
  超时（`timeout` 退出码 `124`）就打印
  `warmup stalled for <prefill> -> <decode>` 并让整批失败，而不是永久挂起。
  这不会掩盖问题——它把"静默挂 2 小时"变成"几分钟内报错"，重启后再跑即可。
- 复现频率与自愈：一天内两次评测里各命中一次（`lp31` 的 `casr_lp` 轮、
  `lp33` 的 `cache_aware` 轮），都发生在**某轮重启后的第一个 P-D 对**上，
  说明它与"重启后残留状态"相关而不是与某个策略相关。为此
  `warmup_all_pairs` 把 `restart_pd` 和全量预热包成一个最多
  `WARMUP_RESTARTS`（默认 `3`）次的重试单元：某对握手死锁就重启整套 P/D
  并**重新预热全部对**（重启会丢掉已预热对的状态），评测因此能自愈继续。

### 机制：`PRESERVE_INSTANCES`（2026-09-12）

`start_multidomain_pd.sh` 新增 `PRESERVE_INSTANCES=id1,id2`：这些实例
**不做 `docker rm -f`、不重新 `docker run`**，只要求现有容器仍然健康
（`restart_pd` 的健康门禁会把它们一起算进去）。用于"容器还能跑、但这台机器
已经没法新建容器"的节点。

方法学上要说明的一点：**只对 Decode 实例使用这个开关**。Decode 不持有前缀缓存，
保留它不会把上一轮策略的缓存状态带进下一轮；Prefill 一律重建，
所以每个策略仍然是从冷缓存开始。本文的 2026-09-12 Dolly 对比就是在
`DISABLED_INSTANCES=p3090b,p3090a PRESERVE_INSTANCES=d3090a` 下跑的，
拓扑为 Prefill `p5090/p4090` + Decode `d5090/d3090a/d4090`。

### 故障：LMCache PD 缓冲耗尽导致整轮假死（2026-09-11）

- 现象：跑几百个请求后，服务端延迟全部变成 `120 s` 超时（router 下游超时），
  `/routing-state` 的 `inflight` 一直有值，而三个引擎都报 `Running: 0`。
- 定位：Decode 容器日志刷
  `LMCache WARNING: Failed to allocate memory object, retrying... (pd_backend.py:939)`。
  节点上的 `casr-lmcache-pd` YAML 为 `pd_buffer_size: 2147483648` +
  `pd_buffer_device: "cuda"` + `pd_backend_mode: "sync"`。
- 结论：**PD 暂存缓冲放在 GPU 上只有 `2 GiB`**，ShareGPT 前缀大多唯一，
  接收端对象得不到及时释放，累计到约 `347` 个请求就把缓冲占满；此后接收端
  无限重试，所有后续请求都卡到超时。这与并发/域名数无关（降到 `3.5 req/s`、
  2 域同样复现），所以它是"请求数累计"型故障，不是"瞬时并发"型。
- 处置：`start_multidomain_pd.sh` 新增 `PD_BUFFER_DEVICE`（默认 `cuda`，保持原行为），
  实验时用 `PD_BUFFER_SIZE=8589934592 PD_BUFFER_DEVICE=cpu` 把缓冲放到主机内存。
- 实验影响：任何长 trace 都必须检查这一项，否则第 ~300 个请求之后的数据会全部是
  超时值，且不会被中途发现。

**认证问题已于同日结案：不是公钥没加，而是本地 `~/.ssh/config` 只给旧地址
`10.70.251.47` 配了 `IdentityFile ~/.ssh/id_casr_cluster`。** 这把密钥不是
OpenSSH 的默认名字，连 `10.66.0.15` 时它根本没被拿出来试，服务端返回的
`Permission denied (publickey,password)` 因此是"密钥没被选中"，而不是
"被 A100 拒绝"。把 `10.66.0.15` 并进同一个 `Host` 段之后，
`ssh -p 2222 buaa@10.66.0.15` 在 BatchMode 下直接通过
（`hostname` 返回 `ubuntu`、`whoami` 返回 `buaa`、`nvidia-smi` 列出 8 张
A100-SXM4-80GB）。

> 教训：**"认证被拒"和"密钥没被选中"在 ssh 眼里长得一模一样。**
> 换主机地址时要同步检查 `~/.ssh/config` 的 `Host` 匹配，而不是先去重置
> `authorized_keys`。

地址与 SSH 接通后，A100 当天 8 张卡空闲，因此把 `p_a100`（GPU4:8100）/
`d_a100`（GPU5:8200）**真的拉起来了**（`vllm/vllm-openai:v0.26.0`，
单卡 Qwen3-8B，`PD_BUFFER_DEVICE=cpu`）：

```bash
ONLY=p_a100,d_a100 PD_BUFFER_SIZE=8589934592 PD_BUFFER_DEVICE=cpu \

```

两个实例约 `60 s` 内 `/health 200`；router 用 `DISABLED_INSTANCES=`（全开）
重启后 `routing-state` 里 5 个域、**9/9 实例 `healthy: true`**，
拓扑从 `4P×3D` 变成 **`5P×4D`**。请求级验证：

| 组合 | prompt | 结果 |
|---|---|---|
| `p_a100 → d_a100`（同域） | 1024 前缀（实际 530 token） | `total ≈ 295 ms`（prefill `174` / decode `120`） |
| `p_a100 → d5090`（跨域） | 2048 前缀（1062 token，`0.176 GB` KV） | `total ≈ 212 ms`（prefill `135` / decode `78`） |
| `p_a100 → d5090`（跨域） | 4000 前缀（2084 token，`0.316 GB` KV） | `total ≈ 243–326 ms` |

**但是这些数字和 IP 层的链路容量对不上，先不要引用：**

- `iperf3` 单流 `a100→5090` 只有 `115 Mbps`、8 并发流合计 `59 Mbps`；
  `scp` 传 `500 MB` 实测 `9.9 MB/s`（`79 Mbps`）。也就是说
  `a100 ↔ 10.212` 的**路由路径本身确实只有 ~80–150 Mbps**。
- 可 sender 端 LMCache 打点 `Stored 0.3164 GB, put_time 36–49 ms`
  （`6–8 GB/s`，这是**本地 memcpy 的速度**，不是这条链路的）；
  接收端 `Retrieved … 71.9 GB/s` 同样是本地拷贝速度。
- 同时抓两头**所有网卡的字节计数**：4 个请求（每个 `0.316 GB` KV）期间
  a100 `ens81f0` 只发出 `39.6 MB`（`wg0`/`tailscale0`/`ibp*` 都近乎不动），
  5090 侧只收到 `43.1 MB`。**~10 MB/请求过线，而日志声称 ~316 MB/请求。**
- 更值得警惕的是接收端日志本身：4000 前缀那轮是
  `Inference Engine computed tokens: 2080, LMCache hit tokens: 2084, need to load: 3`
  ——**decode 自己把 prompt 重算了一遍**，只从缓存里取了 36 个 token；
  而 2048 前缀那轮是 `computed tokens: 0 … Retrieved 1062/1062`（真搬运）。

**上面的矛盾当天就查清了：不是链路，也不是 NIXL 走了暗通道，而是 P/D 的
同步开关被设错，Decode 根本没有等 KV 落地就读了缓冲区（见下一节）。**
所以"网上没有 316 MB"是**因为那 316 MB 从来没有被读走**——Decode 读的是
上一个请求留下的槽位，答案自然也是乱码，并且返回得特别快。

`router_config.json` 里 a100 的 8 条 `links` 现在填的是**IP 路径实测值**
（`115/96`、`147/86`、`142/94`、`140/101 Mbps`，RTT `41.5 ms`），
新增的 `kvlink-p_a100` 生产者预算按 `140 Mbps = 17.475 MB/s` 折算
（约 `0.23 req/s`/2048-token 前缀）。这三个数是**IP 层容量**，用于调度代价
建模；开关修好之后跨域 handoff 才真正开始在这条链路上搬数据。

### 2026-09-13：P/D 输出正确性缺陷 —— `pd_skip_proxy_notification`

**症状**：健康检查全绿、LMCache 报 `hit tokens: 1009/1009`、延迟正常
（`~300 ms`），但 Decode 的输出是 64 个换行、或 1 个 token 就直接 EOS，
或夹杂乱码（`\ \ \\ \`、`의.\n =,도`、`to to to to`）。用
CNN/DailyMail 的 1600 字符长文（约 1000–1800 token）判断时：

| 配置 | 结果 |
|---|---|
| 本地 prefill（不经 P/D） | 每个请求都给出正确的一句式摘要 |
| P/D，`pd_skip_proxy_notification: true`（旧默认） | 重启后**前 5 个正常，之后 7/12 全是乱码** |
| P/D，`pd_skip_proxy_notification: false` | **12/12 全部在读文章**，延迟 `1.5–2.1 s` |

**根因**：LMCache 的接收端在**分配槽位时**就把 chunk key 注册进索引
（`pd_backend.py:_allocate_and_put` 里 `self.put(key, mem_obj)` 发生在
发送端写入之前）。`pd_skip_proxy_notification: true` 让 Prefill 不等接收端
通知就返回，Decode 随即按"命中"去读那个槽位——读到的还是上一个请求的数据。
短 prompt（不足一个 chunk）根本不会走这条路，所以之前的小 prompt 冒烟测试
一直是"通过"的，缺陷被掩盖了很久。

**这个 flag 是怎么进来的**：最初为了绕开 LMCache `async` backend 强制要求的
ZMQ proxy notification（HTTP proxy 不提供该 socket），当时的做法是切到
`pd_backend_mode: sync` **并保留** `pd_skip_proxy_notification`。实际上
`sync` 模式不需要它——保留它只带来了这个竞态。

**修复**：`start_multidomain_pd.sh` 默认改为不跳过（
`PD_SKIP_PROXY_NOTIFICATION=0`），需要复现旧行为时显式设 1。

**新增门禁 `tests/check_pd_correctness.py`**：所有其他测试只看延迟，
看不出"快速返回的垃圾"。这个脚本给每篇长文末尾加一个随机校验码
（`Access code: QK7M-4319` + `/no_think`），要求模型只回码；KV 没读到就
必然答不出，逐请求可判定，`--max-fail-ratio` 超限即非零退出。标定：

```bash
# 本地实例（对照组）→ PASS 5/5
python3 tests/check_pd_correctness.py --endpoint http://10.212.67.167:8200 --requests 5
# 旧配置的 router → FAIL 3/5（乱码、答不出码）
python3 tests/check_pd_correctness.py --endpoint http://127.0.0.1:9000 --requests 5
```

另外修了启动脚本的一个真实缺陷：`docker rm -f` 在 3090 上返回后名字还没
释放，紧跟的 `docker run` 会报 `container name is already in use` 并让整个
拓扑中止；现在带 5 次重试并在最后校验容器确实存在。

**修复后的验证（同日）**：全部 9 个实例用新默认值重建（`5P × 4D`），

- router 层 8 个长文口令请求 **8/8 通过**（`0.5–0.7 s`）；
- 逐个 P/D 对：`p5090→d4090`、`p4090→d5090`、`p3090a→d5090`、
  `p_a100→d3090a`、`p_a100→d_a100` 共 **10/10 通过**；
  其中 `p_a100→d3090a`（跨到最慢那条链路）`1.3–1.7 s`，明显慢于
  `p5090→d4090` 的 `0.5–0.7 s`——**慢链路代价现在真的出现了**，
  这正是调度器要建模的东西；
- 端到端四策略小规模对比（CNN-short trace，60 请求，单轮）：
  `casr_lp` mean `369.0` / p95 `522.3`；`load` `460.2` / `580.3`；
  `cache_aware`（SOTA 基线）`480.7` / `653.6`；`casr` `499.1` / `886.7`。
  四个 policy 的正确性门禁均 `PASS 0/4`。**注意 `casr` 这次是最差的，
  与缺陷配置下的旧排序相反，说明旧排序确实不可信；但新排序只有 1 轮 60 请求，
  也必须多轮复现后才能写进结论。**

这一轮只是"流程恢复可信"的验证（1 轮 60 请求），**正式对比仍需按修复后的
配置重跑多轮**，见 `docs/实验结果汇总.md` §5.13 与 §5 开头的提醒。

### 2026-09-13：KV 搬运本身没有生效（**比上面更严重的发现**）

修完"读到过期槽位"之后，输出正确了；但**延迟表现和"跨域只用多 0.4 ms"
对不上**，于是继续追。结论是：这套部署里 **Prefill→Decode 的 KV 从来没有
真正搬过去**，之前的"跨域便宜"是采集在没有搬运的路径上的。

**直接证据（按发现顺序）**

1. **Prefill 的 LMCache 引擎根本没起来。** `p_a100` 启动后立刻打：

   ```
   LMCache ERROR: LMCacheEngine marked as init failed: Traceback ...
     File ".../storage_backend/pd_backend.py", line 130, in from_cache_engine_config
       assert config.pd_proxy_host is not None
   AssertionError
   ```

   之后每次请求都在刷 `LMCache is unhealthy, skipping lookup/store
   operation`（`p_a100` 累计 170 条）。也就是说：**Prefill 既不缓存也不推 KV**。
   原因在源码里写得很清楚——`role == "sender"` 时，只要
   `pd_skip_proxy_notification` 为 false，就必须给出
   `pd_proxy_host`/`pd_proxy_port`（ZMQ 通知端点），否则断言失败。

2. **网上没有字节。** 关掉通知开关后，两次 1972-token 的握手在 a100 上只发出
   `3.8 MB`（同窗口的空载基线是 `~14 MB`），而名义 KV 是 2 × 290 MB。

3. **Decode 明明在自己重算。** `d5090` 日志：
   `Total tokens 1450, Inference Engine computed tokens: 1440, LMCache hit
   tokens: 0`；同一实例上"直连（不走 P/D）"与"走 P/D"的 TTFT 都是
   `45–65 ms`（~1100 token），说明 P/D 没有省掉任何 prefill 计算。
   反过来，这也解释了更早那次"P/D 比本地还慢"的观感。

**三种配置，没有一种是"既正确又真的搬"**

| 配置 | 输出 | KV 搬运 | 说明 |
|---|---|---|---|
| `pd_skip_proxy_notification: true` | **乱码** | 早读，等于没用 | 历史默认；Decode 读到上一个请求的槽位 |
| `skip=false`，不给 proxy | **正确** | **完全没有** | LMCache 断言失败 → 引擎死 → Decode 自己重算（等于 2× prefill 计算） |
| `skip=false` + proxy 端点 | **乱码** | **真的搬了** | 本次新实现的通知通道；见下 |

**proxy 通道本次已经实现**（`disagg_router.py` 里的 `KVLandingTracker`）：
sender 用 ZMQ PUSH 把 `ProxyNotif(req_id)` 发到 `pd_proxy_host:pd_proxy_port`，
router 绑定 PULL（`PD_PROXY_PORT`，默认 `55900`）并在发 Decode 之前等这个
通知；`/routing-state` 会给出 `kv_landings` 计数。实测（`p5090→d5090`、
`p3090b→d5090`、`p_a100→d5090`、`p4090→d5090` 四对）：

- 通知确实到了：`received 6 / waited 4 / timeouts 0`；
- Prefill 侧 `Stored 0.2109 GB`，`put_time` 冷启动 `400 ms`、之后 `27 ms`；
  Decode 侧 `Inference Engine computed tokens: 0, LMCache hit tokens: 1341,
  need to load: 1340` → `Retrieved 1341/1341, size 0.2109 gb, cost 6.65 ms`
  ——**KV 真的传过去了、也真的装进去了**；
- **但输出仍然是乱码**（`••••••`、`####`、空串），四对全挂，连
  "同镜像同域"的 `p5090→d5090` 也一样。

也就是说：搬运链路通了，**传过去的 KV 用不了**（数据布局/位置映射层面
的问题，属于 LMCache 0.5.x 的 PD 数据面）。这不是网络、不是配置开关，
而是这套 `enable_pd + transfer_channel: nixl` 组合从未被端到端验证过——
历史上所有"handoff 验收成功"的样本（34 token、几百 token 的冒烟）都**不足
一个 chunk 或压根没进这条路径**。

**对已有结论的影响（必须写进论文口径）**

- `docs/实验结果汇总.md` §5.10/§5.11 里"跨域 handoff 只多 `0.4 ms`、
  链路代价只在饱和时出现"的**实测输入是无效的**：那两轮里 KV 根本没跨网络。
  `router_config.json` 的 `links`/`kvlink-*` 因此需要**重新标定**（不是微调，
  是重做）。
- 所有真机对比结论（§5.1–5.13）都建立在"Decode 自己重算 prompt"的系统上：
  延迟数字是真实的，但它度量的是**一个不做 KV offload 的 P/D 拓扑**，
  不能用来论证"KV/存算协同"的收益。
- 现有默认配置保留"输出正确"的那一档（不给 proxy，`PD_SKIP_PROXY_NOTIFICATION=0`），
  并在启动脚本里显式打印警告；只有显式设置 `PD_PROXY_PORT` 才打开通知通道。

**下一步（按优先级）**：① 让 KV 数据面真正可用——先试 vLLM 原生的
`NixlConnector`（`--kv-transfer-config` + proxy 回填 `kv_transfer_params`），
它不走 LMCache 的 PD 缓冲；② 若仍不行，回到 LMCache 的 PD 布局问题（对
chunk 形状、`MemoryFormat`、`last_chunk_toks` 做逐字段比对）；③ 数据面可用后，
重新标定 `links`/`kvlink-*` 并重跑全部真机对比。

### 2026-09-13：换到 vLLM 原生 NixlConnector，KV 搬运真正生效

按上面的 ①，把 P/D 的 KV 传输从 LMCache 的 PD backend 换成 **vLLM 自带的
`NixlConnector`**，一次跑通。

**改动**

- 启动脚本新增 `KV_TRANSFER_BACKEND=native`（默认已切到 native）：实例改用
  `--kv-transfer-config '{"kv_connector":"NixlConnector","kv_role":"kv_both",
  "kv_port":<每实例唯一>,"kv_connector_extra_config":{"backends":["UCX"]}}'`，
  不再挂 `LMCACHE_CONFIG_FILE`。**每个实例必须有自己的握手端口**：该端口来自
  环境变量 `VLLM_NIXL_SIDE_CHANNEL_PORT`（不是配置键），同主机两实例都默认
  5600 会直接 `Address already in use`；同时用
  `VLLM_NIXL_SIDE_CHANNEL_HOST` 播本机地址，远端 Decode 才能连上。
- router 新增 `PD_TRANSFER_BACKEND=native`：Prefill 腿只发
  `{"do_remote_decode": true, "do_remote_prefill": false}`，并把 **Prefill
  返回的 `kv_transfer_params`（remote block ids / engine id）回填给 Decode
  腿**——这正是官方 disaggregated proxy 的做法，之前被丢掉了。
- **版本必须一致**：vLLM 0.29 与 0.26 之间 NIXL 元数据格式不兼容
  （先是 `NIXL compatibility hash mismatch`，放开检查后变成
  `Failed to decode NixlAgentMetadata: Object missing required field
  block_strides`）。因此 `router_config.json` 给每台 host 加了
  `kv_group`（`5090/3090a/3090b/4090` = `v029`，`a100` = `v026`），
  router 在 native 模式下只保留实例数最多的那一组，并在启动时打印
  `[kv] native mode keeps kv_group='v029'; dropped p_a100, d_a100`。
  A100 要重新入网，需要把它的镜像升到与其它域相同的 vLLM 0.29。

**验证（同日）**

| 检查 | 结果 |
|---|---|
| router 门禁（4P×3D，8 个长文口令请求） | **8/8 PASS** |
| 跨主机同版本 `p5090 → d4090` | **3/3 PASS**，中位 `454 ms` |
| 同域 `p5090 → d5090` | **3/3 PASS**，中位 `387 ms` |
| 跨域到慢卡 `p5090 → d3090a` | **3/3 PASS**，中位 `1010 ms` |
| a100 同域 `p_a100 → d_a100`（0.26 内部） | **2/2 PASS**，中位 ~`1.2 s` |

**连接器自己打的传输指标**（这是最硬的证据）：

```

  Avg MB per transfer=176.625, Throughput=106.25 MB/s

  Avg MB per transfer=176.625, Throughput=343.04 MB/s
```

即跨主机每次真的搬 `176 MB`，有效带宽 `106–343 MB/s`（`0.85–2.7 Gbps`），
与 10.212 内网 16 Gbps 标称值一致量级。

**对算法标定的直接影响**：KV 一旦真的过网，跨域代价立刻显形——
同域 `387 ms` vs 跨域 `454 ms`（+`67 ms`/请求），到慢卡 `1010 ms`。
旧 `links`/`kvlink-*`（在"根本没有搬运"的路径上标出来的）必须用这批数据
重做，`docs/实验结果汇总.md` 的 §5.10/§5.11 结论作废。

#### 标定：native 路径的 KV 代价（`tests/calibrate_native_pd.py`）

新脚本按官方两腿流程扫 prompt 长度（**每个样本用唯一前缀**，否则第二发开始
就命中 Decode 自己的缓存，会把代价测没），对 `total_ms` 与 `prompt_tokens`
做最小二乘：

| 链路 | 截距 | 斜率 | 有效带宽 |
|---|---:|---:|---:|
| `p5090 → d5090`（同主机） | `163 ms` | **`585 ms` / 1k token** | `257 MB/s` |
| `p5090 → d4090`（跨主机 10.212） | `211 ms` | **`1351 ms` / 1k token** | `111 MB/s` |
| `p5090 → d3090a`（跨主机，慢卡） | `415 ms` | **`1364 ms` / 1k token** | `110 MB/s` |

**参照系**：同一个 Decode 本地把同样 ~1000 token 的 prompt 算完只要
`~93 ms`（TTFT 实测）。也就是说——

> 在这套集群上，**一次 KV 搬运比 Decode 自己重算慢 8–15 倍**。
> 1000-token 的 prompt：本地重算 `93 ms`，同主机搬运 `752 ms`，
> 跨主机搬运 `1571 ms`。

这不是坏消息，而是**本项目最该被调度器利用的结构**：搬运不是"便宜到可以忽略"
（旧模型假设 2 GB/s 就是这样来的），而是一份**很贵的资源**，只有在
"Decode 侧排队/超载、或 Prefill 侧算力空闲" 时才值得花。当前 LP 的
pair-cost 模型默认"每个请求都会搬运"，还没有"搬运 vs 本地重算"这个决策项，
这是下一步算法要做的事（见 `docs/实验结果汇总.md` §5.14）。

`router_config.json` 已按实测更新：跨域 `bw_gbps` `16 → 0.88`、
`rtt_ms` `0.3 → 48`，`kvlink-*` 生产者预算 `2e9 → 1.15e8 B/s`，
并写入 `_kv_cost_comment` 记录上表。

#### 算法：把"搬不搬 KV"变成一个显式决策（`LOCAL_PREFILL`）

既然搬运比本地重算贵 `8–15×`，**"要不要搬"本身就该是调度决策**，而不是默认动作。
router 新增 `kv_exchange_decision()`：逐请求比较两条路的建模代价，

```
搬运 = 跨域固定项 + slope(链路) × tokens/1000 + Prefill 队列项
本地 = 93ms/1k ÷ speed(Decode) × tokens/1000 + Decode 队列项
```

取小者执行；`LOCAL_PREFILL=auto|never|always` 可做 A/B。
**能力归属**：只有 CASR 系列默认启用（`auto`），经典基线
（`rr/load/random/cache_aware`）保持"总是搬运"——那正是 CASR 要对比的系统；
`LOCAL_PREFILL_BASELINES=auto` 可让基线也拿到这个能力做公平性消融。
每个请求的 `exchange: local|transfer` 与两条路的估计值都写进
`metrics-<policy>.jsonl`，`/routing-state` 里有 `exchange_local` /
`exchange_transfer` 计数。

首轮效果（CNN-short，60 请求，SLO `TTFT 500 / TPOT 50 ms`）：
**`casr_lp` 64/64 全部走本地重算，mean `−66.4%`、p95 `−82.2%`、
SLO 达标 `62.5% → 93.8%`、goodput `3.76 → 9.94`**；而基线 `load` 64/64
仍在付搬运费。这就是"存算协同"在这套硬件上最直接的落点：
**不是把 KV 搬得更快，而是知道什么时候根本不该搬。**

### 操作教训：不要在 `start_multidomain_pd.sh` 重建窗口内 kill 运行脚本

这次事故的直接诱因是一次打断。`run_real_multidomain_comparison.sh` 的每个
策略循环是"**先 `docker rm -f` 再 `docker run`**"，中间有几十秒的空窗。
在这个窗口里 `kill -9` 掉脚本（或它的子进程）会留下"容器已删、新容器没起来"
的状态；本次 5090 恰好又碰上 GPU2 掉总线，于是 p5090/d5090 再也没起来。

更重要的代价：**p5090/d5090 原本是"能服务的旧容器"**——参考 3090a 的经验，
主机状态变坏时旧容器往往还能继续跑。重建把它们删掉之后，这份回退能力也没有了。

- 要停一个正在跑的实验，优先 `kill` 掉**客户端**（`real_dataset_client.py`），

  `start_multidomain_pd.sh` 在跑，再删容器；
- 重建前后各记一次 `nvidia-smi`，把"容器问题"和"主机 GPU 掉总线"区分开；
- 共享节点上的 `gpu-reset` / 重启**先取授权再执行**（本次即按授权完成），

### 跑法与踩的坑

```bash
mkdir -p ~/casr-a100-profile && tar xzf casr-profiler-a100.tgz -C ~/casr-a100-profile
python3 -m venv ~/casr-venv && ~/casr-venv/bin/pip install vllm==0.29.0
cd ~/casr-a100-profile
TMPDIR=~/casr-tmp PIP_CACHE_DIR=~/casr-tmp/pip HF_HOME=~/casr-tmp/hf \
VLLM_CACHE_ROOT=~/casr-tmp/vllm CUDA_VISIBLE_DEVICES=4 VLLM_USE_FLASHINFER_SAMPLER=0 \
  ~/casr-venv/bin/python3 -m profiler profile Qwen/Qwen3-8B --hardware A100 --tp 1,2 \
  --dtype bfloat16 --max-num-batched-tokens 2048 --max-num-seqs 128 \
  --attention-max-kv 4096 --measurement-iterations 3 --skip-skew
```

1. **必须设 `VLLM_USE_FLASHINFER_SAMPLER=0`**：宿主只有 CUDA 12 的 `nvcc`，而
   torch 是 cu130，flashinfer 的 JIT（`csrc_sampling.cuda.o`）必然编译失败，
   报 `EngineCore failed to start`。关掉它、走 vLLM 自带采样即可。
2. **采集期间日志会"静止"**：rich 的进度条在重定向到文件时不刷新，`attention` 阶段
   20–25 分钟没有任何新行；用 `/proc/<pid>/stat` 的 tick 增量（EngineCore ≈ 1 核满载）
   判断"在跑"而不是"卡死"。
3. 单卡按 TP 度数顺序跑（引擎恒 `tensor_parallel_size=1`，用缩过的 config 模拟各 rank，
   见 `profiler/core/engine.py`），所以 `--tp 1,2` 不需要两张卡。

## 2026-09-15 晚：日志/缓存全部迁出系统盘、A100 改走 venv、Ray 控制面重启

起因是巡检发现 **3090a 根盘只剩 8.8 GB（99%）**，同时五台机器的 `docker logs`
（`/var/lib/docker`）和 Ray 默认会话目录（`/tmp/ray`）都落在系统盘上。

### 数据盘目录约定（唯一来源：`router_config.json` 的 `hosts.<domain>`）

| 域 | 数据盘路径 | 设备 / 可用 | 写权限 |
|---|---|---|---|
| 4090（head） | `/mnt/home/casr/{logs,cache,ray}` | `/dev/nvme0n1`，741 GB | `ubuntu`（本次用 sudo 建好） |
| 5090 | `/data/casr/{logs,cache,ray}` | `/dev/md0`，187 GB | `buaa` |
| 3090a | `/data/sdb/model/casr/{logs,cache,ray}` | `/dev/sdb1`，1.7 TB | `buaa` |
| 3090b | `/data/casr/{logs,cache,ray}` | `/dev/sda2`，870 GB ⚠️ | `buaa` |
| a100 | `/mnt/adminserver-nfsrdma/casr/{logs,cache,ray}` | NFS，759 GB | `buaa` |

⚠️ **3090b 没有独立数据盘**：`/`、`/data`、`/mnt/data` 是同一个 `13T` 的 `/dev/sda2`，
"不进系统盘"在这台机器上物理上做不到，只能保证不进根目录和 `/var/lib/docker`。

改法（`deploy/real_lmcache_pd/start_multidomain_pd.sh`）：

* 每个实例的 vLLM 命令不再直接写进 `ssh "..."`，而是渲染成
  `<log_dir>/<instance>.sh` + `<log_dir>/<instance>.run.sh` 推到目标机再执行；
  `--log-driver=none` 且容器内 `>> /casr-logs/<instance>.log`，日志只落在数据盘，
  `/var/lib/docker` 不再增长（脚本本身可审计，也方便复现启动参数）。
* vLLM 编译缓存用 `VLLM_CACHE_ROOT=<cache_dir>`（docker 侧是
  `-v <cache_dir>:/root/.cache/vllm`），不再写 `/tmp/casr-vllm-cache`。
* 新增 `DRY_RUN=1`：只生成 `/tmp/casr-multidomain-plan.sh` 不执行，改启动参数前先看一遍。
* **坑**：KV 的 JSON 以前是给 `ssh "… '{\"k\":\"v\"}' …"` 这种双层引号写的，
  现在命令走脚本文件，必须去掉反斜杠（脚本里已做 `kv.replace('\\"', '"')`），
  否则 vLLM 收到的是非法 JSON。

### A100 为什么改走 venv

三个叠加的限制，导致这台机器**不能再用 docker 起 P/D**：

1. `buaa` 已不在 docker 组（`docker:x:121:wyc`，`/var/run/docker.sock` 为 `root:docker 660`）；
2. `buaa` 不在 sudoers（`buaa is not in the sudoers file`），唯一有 sudo 的 `guest`
   账号现在 **sshd 只允许公钥登录**（`Permission denied (publickey)`），我们进不去；
3. 本地数据盘 `/mnt/lmcache-raid0`（14T、7% 用量）是 `root` 所有、`buaa` 不可写，
   所以连"找个数据盘放日志"都只能落到 NFS。

因此 A100 域改为 `launcher: venv`：

```bash
# 建 venv（脚本在数据盘，pip 走清华源 + 重试；默认 PyPI CDN 会中途 ReadTimeout）
/mnt/adminserver-nfsrdma/casr/venv            # vllm==0.29.0 + lmcache==0.5.4，与 casr029 镜像同版本
/mnt/adminserver-nfsrdma/casr/venv-build.sh   # 重建用
# 起停（和 docker 域同一条命令，脚本按 launcher 分派）
bash deploy/real_lmcache_pd/start_multidomain_pd.sh                  # 全量
ONLY=a100 bash deploy/real_lmcache_pd/start_multidomain_pd.sh        # 只重启 A100 域
DRY_RUN=1 ONLY=a100 bash deploy/real_lmcache_pd/start_multidomain_pd.sh   # 只看计划
```

venv 路线上踩到的两个坑（都已在脚本里处理）：**must** 用 `CUDA_VISIBLE_DEVICES`
绑卡（docker 侧靠 `--gpus device=N`，裸 venv 不设就会落到 cuda:0——A100 的 0–3 号卡
是别人的业务，会直接报 `Free memory on device cuda:0 (5.42/79.25 GiB) is less than
desired 0.35`）；以及 LMCache 必须单独装，否则 connector 初始化报
`ModuleNotFoundError: No module named 'lmcache'`。

venv 域的进程管理：`<log_dir>/<instance>.run.sh` 先按 pid 文件 kill 旧进程再
`setsid nohup` 起新的，pid/脚本/日志三者同目录，出问题直接看 `<instance>.log`。
