# 跨域 P D 存算协同调度的开源项目基座与代码借鉴建议

## 1 结论先行

第一版建议采用“**SGLang 或 vLLM + LMCache/Mooncake + 独立调度控制器**”的组合，而不是从头实现推理引擎、KV Cache 和网络传输。

- **首选研究基座：SGLang**。它同时具备 Prefix Cache、PD 分离相关能力和较易改造的 Python 调度路径，适合快速验证 cache-aware P capacity、P-D affinity 和 Structural Gain。
- **稳妥工程基座：vLLM**。生态、文档和 profiling 工具更成熟，Prefix Caching、KV Connector、distributed serving 接口便于复用；需要自己补较多 P/D 控制逻辑。
- **KV/网络层首选：Mooncake 或 LMCache**。Mooncake 更适合研究跨节点 KV 传输和 KV-aware 调度；LMCache 更轻量，适合作为 vLLM/SGLang 的远程 KV 存储组件。
- **不建议第一版直接使用：NVIDIA Dynamo、llm-d**。它们能力强，但部署、组件和 Kubernetes 依赖较重，容易让课题变成平台集成工作。

## 2 候选项目对比

| 项目 | 主要能力 | 对本课题的直接价值 | 需要改造的部分 | 建议角色 |
|---|---|---|---|---|
| [SGLang](https://github.com/sgl-project/sglang) | 高性能 serving、RadixAttention/Prefix Cache、PD disaggregation、路由与多节点能力 | 直接提供 P/D 推理路径和 Prefix 状态；适合插入 P-D affinity 与缓存感知容量 | 外接慢时间尺度 controller；暴露 P/D queue、cache hit、KV transfer、GPU profile | **首选完整基座** |
| [vLLM](https://github.com/vllm-project/vllm) | 成熟推理引擎、Prefix Caching、KV Connector、分布式执行、丰富 benchmark | 生态最好，便于做可复现实验和异构 GPU profiling | P/D 分离及跨域控制器需较多自行拼接；需确认所选版本的 disaggregated serving 接口 | **首选稳妥基座/强基线** |
| [Mooncake](https://github.com/kvcache-ai/Mooncake) | KVCache-centric serving、Transfer Engine、分布式 KV Cache 管理、Prefill/Decode 分离 | 直接复用 KV 传输、远程缓存和网络感知组件；适合验证跨域 KV traffic 与 warm/cold | 研究控制器、P 行增删和实验 instrumentation 需自行实现 | **KV/网络层首选** |
| [LMCache](https://github.com/LMCache/LMCache) | KV Cache offload、远程存储、vLLM/SGLang connector、cache 命中与复用 | 以较小改动加入 Prefix 状态、复制、重算和 cache value 观测 | 不提供完整 P/D 资源重构算法；跨域拓扑调度需外加 | **轻量存储组件** |
| [NVIDIA Dynamo](https://github.com/ai-dynamo/dynamo) | 面向生产的 disaggregated inference、KV-aware routing、NIXL 传输、资源编排 | 可借鉴 planner、KV transport、worker/router 分层设计 | 系统较大，GPU/NVIDIA/Kubernetes 依赖明显，改造成本高 | 后续工程化/对照 |
| [llm-d](https://github.com/llm-d/llm-d) | Kubernetes 上的分布式 LLM 推理、网关和调度、模型服务编排 | 借鉴控制平面、服务发现、拓扑和弹性部署 | 不是适合算法原型的最小基座；需要 K8s 集群 | 后续部署层/对照 |
| [TensorRT-LLM](https://github.com/NVIDIA/TensorRT-LLM) | NVIDIA GPU 高性能 kernel、批处理、KV cache 与多 GPU serving | 适合做异构 GPU 的高性能 profile 和性能上限 | C++/CUDA 复杂，研究调度改造不如 Python serving 友好 | 性能 profile/强基线 |
| [Ray Serve](https://github.com/ray-project/ray) | 服务副本、资源调度、弹性和多节点编排 | 可借鉴 P/D worker 生命周期、placement group 和扩缩容 | 不负责推理内核、Prefix Cache 或 KV transfer | 编排层可选 |
| [DistServe](https://github.com/LLMServe/DistServe) | 经典 P/D 分离研究原型与调度思想 | 适合理解 P/D 拆分、批处理和实验指标 | 研究原型通常不适合作为长期工程基座，需核对版本和维护状态 | 论文/算法参考 |
| [Splitwise](https://github.com/Relaxed-System-Lab/Splitwise) | Prefill/Decode 解耦、资源分工和系统研究原型 | 可借鉴 workload 建模和 P/D 资源分配实验 | 代码工程化程度和新版本兼容性需要单独验证 | 论文/模拟器参考 |

## 3 与研究设计的模块对应关系

| 研究模块 | 推荐复用项目 | 复用内容 | 自己新增的最小代码 |
|---|---|---|---|
| P/D worker 与请求执行 | SGLang 或 vLLM | 引擎、batch、token generation、API | P/D 角色标记、状态上报 hook |
| Prefix Cache | SGLang Radix Cache 或 vLLM Prefix Caching | 命中、复用、缓存条目与容量管理 | 按 prefix class 聚合 hit length、热度 EWMA |
| KV 传输/远程存储 | Mooncake 或 LMCache | KV 序列化、RDMA/网络传输、远程 cache | 跨域 BW/RTT 采集、复制成本与 warmup 计时 |
| D 选择 | SGLang/vLLM router，或 Mooncake router | 基于队列/容量的请求路由 | P-D cost matrix 和 affinity 比例 |
| P-D 分配 | 自建 controller | 无需改动推理内核 | min-cost flow 求解 F* |
| 结构重构 | 自建 controller + Ray/K8s API | 实例启停、drain、健康检查 | counterfactual + Structural Gain + dwell time |
| 异构 profile | vLLM/SGLang benchmark，必要时 TensorRT-LLM | 不同 GPU、上下文、batch 的吞吐测量 | 生成 μP、μD profile 表 |
| trace-driven 扩展 | 自建 simulator；可借鉴 DistServe/Splitwise workload | 请求、prefix、网络和队列 trace | 与真实 controller 共用 cost/model 接口 |

## 4 推荐的两条落地路线

### 路线 A 研究优先

**SGLang + LMCache + 独立 Python Controller**。

1. 用 SGLang 启动两个域的 P/D worker，先固定资源结构。
2. 通过已有 Prefix Cache 统计接口采集 hit prefix length、cache size 和热点。
3. 将 P/D queue、GPU profile、RTT/BW 汇总到 controller。
4. controller 生成 A、C、μP、μD，调用 min-cost flow 输出 P-D affinity。
5. 只允许 P 的 `+1/-1/relocate`，对 cold/warm 候选做反事实评估。
6. 通过 SGLang worker API 或 Ray/Kubernetes 进行扩容、drain 和缩容。

这条路线最贴合“存算协同调度”论文主线，新增代码集中在 controller 和观测 hook，预计不需要修改 attention kernel。

### 路线 B 工程优先

**vLLM + LMCache 或 Mooncake + Ray Serve/Kubernetes Controller**。

1. vLLM 负责 P/D worker 和 Prefix Caching。
2. LMCache 先实现跨实例 Prefix 状态复用；若需要更强的跨域 KV 网络实验，再换 Mooncake Transfer Engine。
3. controller 作为独立服务，通过 metrics/API 获取队列、吞吐、cache hit 和链路状态。
4. Ray Serve 或 Kubernetes 负责实例生命周期；controller 只输出目标 P pool 与 affinity。

这条路线生态和基线复现更稳，但需要更多适配 P/D 分离和跨域 KV 传输接口。

## 5 建议的代码改造边界

### 必须自己实现

- `StateCollector`：统一采集 λ、输入长度、prefix hit、P/D queue、GPU throughput、RTT/BW。
- `CapacityEstimator`：根据 `effective_tokens = ISL - hit_prefix_len` 计算 cache-aware μP；由 profile 表计算 μD。
- `CostMatrixBuilder`：构造可行矩阵 A 和 `c_ij = transfer + queue + decode`。
- `FlowMatcher`：min-cost flow/LP 求 F* 与 J*。
- `StructuralEvaluator`：生成 ±1 P、cold/warm、relocate 候选，计算 `G(a)=J(S)-J(S_a)-C_reconfig(a)`。
- `ReconfigExecutor`：扩容、warm 复制、drain、缩容和 affinity 更新。

### 不要自己实现

- Transformer attention、continuous batching、token sampling。
- Prefix Cache 的底层 hash、block 管理和 eviction 基础机制。
- KV 序列化、RDMA/UCX/NIXL 传输协议。
- Kubernetes 调度器或完整服务发现系统。
- 新的 request-level D router；第一版直接复用基座能力。

## 6 具体仓库阅读顺序

1. SGLang：先看 `runtime`、`router`、`radix_cache`、PD disaggregation 相关目录。
2. vLLM：重点看 `v1/engine`、`kv_connector`、`worker`、Prefix Caching 与 metrics。
3. LMCache：看 connector、remote backend、cache lookup/store 和统计接口。
4. Mooncake：看 Transfer Engine、KV Cache Manager、scheduler/router 和 benchmark。
5. Ray Serve 或 llm-d：最后再看实例生命周期与跨节点部署，不要一开始引入。

## 7 最终建议

若目标是尽快做出论文原型，优先选择 **SGLang + LMCache + 自研 Controller**；若希望后续接近生产并获得更成熟的 benchmark 和生态，选择 **vLLM + Mooncake/LMCache + 自研 Controller**。无论选哪条路线，论文创新都应放在 controller 的“cache-aware effective capacity + P-D matrix + counterfactual Structural Gain”上，而不是声称重新实现了推理引擎或 KV 存储系统。

项目链接均为公开仓库入口；在正式锁定基座前，应再固定 commit/tag，并记录 CUDA、GPU、Python 与模型版本，避免上游快速变化造成实验不可复现。
