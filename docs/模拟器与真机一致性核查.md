# 模拟器能否支持"模拟真实情况"：一次同 trace 的对照核查

更新时间：`2026-09-15`（本文以附录形式累积；§结论保留 09-12 的原始判断，
最新状态见 **附八**）

## 结论（先说）

**（09-12 原始判断）不能。** 用同一条 Dolly trace 同时跑模拟器与真机后，
不仅绝对时延差 `3–5` 倍，**策略排序还会反转**：模拟器里 `casr_lp` 比
`load` 差 3 倍，真机上是好 2.3 倍。排序反转意味着这不是"整体缩放系数"
问题，而是会改变算法选择的模型误差。

> **2026-09-15 更新**：上面这一轮对照是在"运行时加载了过期 chakra"的状态下
> 做的（见 **附八**）——跨域 P/D handoff 在模拟器里根本没按选中的 Decode
> 发送，多域运行会直接死锁。修掉"改了没生效"并加了三道具名门禁之后，
> 模拟器已能在 3 域上跑完 200 请求的真实 trace（达成 13.5/14 req/s，
> TTFT 均值 89 ms、队列均值 5 ms）。**"排序反转"这一条必须重测后才能引用**；
> 当前可引用的判断是：绝对时延在 KV 重量级区间与真机同量级，短 prompt 档
> 仍偏慢 2–3×（残余在 Decode 侧约 2×）。

## 对照条件

- 数据集：`workloads/dolly-real-qwen3-8b-600-sps14.jsonl` 的 16-token 截断版
  （`...-out16.jsonl`，与真机 `MAX_OUTPUT_TOKENS=16` 对齐）。
- 模拟器：`configs/cluster/casr_real_qwen3_8b_three_domain.json`
  （6 实例：每域 1 Prefill + 1 Decode，Qwen3-8B TP1，真实 profile）。
- 真机：Prefill `p5090/p4090` + Decode `d5090/d3090a/d4090`，
  3 轮 × 600 请求，SSE 流式口径。
- 模拟器取 200 请求（同一 trace 前缀），真机为 1800 请求；
  两者都是同一到达过程。

## 结果

| | 均值 | P50 | P95 | TTFT P50 |
|---|---:|---:|---:|---:|
| 模拟器 `LOAD` 基线 | `473.3 ms` | `474.9 ms` | `801.5 ms` | `75.4 ms` |
| 模拟器 `CASR-LP` | `1469.4 ms` | `1461.6 ms` | `2535.0 ms` | `1199.9 ms` |
| 真机 `load` 基线 | `824.7 ms` | `905.9 ms` | `1220.4 ms` | `~305 ms` |
| 真机 `casr_lp` | `354.2 ms` | `344.6 ms` | `449.0 ms` | `~243 ms` |

> **注意（2026-09-13 晚更正）**：这里的真机 `load 824.7 ms` 是**修复前**的
> 基线——`disagg_router._pick_load` 当时用字符串 `inst.id` 破平局，
> 把 `77%` 的 Decode 钉在最慢的 `d3090a`。用正确基线重测同一档
> （`docs/实验结果汇总.md` §5.1）后 `load` 是 `348.7 ms`，
> 与 `casr_lp` 同级。本节的对照只用于说明"模拟器当时的偏差方向"，
> **不要再引用 `824.7` 作为真机基线**；`casr_lp 354.2 ms` 不受该缺陷影响，
> 仍是可用的真机锚点。

**排序**：模拟器 `LOAD 473 < CASR-LP 1469`；真机 `CASR-LP 354 < load 825`。
方向完全相反。

## 原因定位

逐实例分布显示，差异不在"选哪一类实例"，而在**单实例吞吐能力**：

| | Prefill 分布 | Decode 分布 | 单个 Decode 的均值时延 |
|---|---|---|---|
| 模拟器 `LOAD` | `30 / 34 / 36 %` | `28.5 / 29.0 / 42.5 %` | `356–602 ms` |
| 模拟器 `CASR-LP` | `2.5 / 2.0 / **95.5** %` | `4.0 / 15.0 / **81.0** %` | `1028–1618 ms` |
| 真机 `casr_lp` | — | `d5090 **100%**` | 端到端均值 `354 ms` |

真机上 `casr_lp` 同样把 Decode 集中到单个 `d5090`，端到端均值 `354 ms`
（该实例实测饱和吞吐 `65 req/s`，而实际负载只有 `3.5–14 req/s`）；
模拟器里把 `81%` 流量放到单个 Decode 后，其均值时延涨到 `1463 ms`、
TTFT P50 到 `1200 ms`——**模拟器的单实例有效吞吐比真机低一个量级**。

这正是文档早先记录过的计算模型偏差（模拟器算一次 2048-token prefill 要
`1.30 s`，真机因为绝大部分命中前缀缓存只要约 `0.1 s`）。Dolly 档前缀零复用，
所以真机也要实打实算 prefill；即便如此，模拟器的单实例吞吐仍明显偏低。

把配置里的容量从**估算值**换成**实测值**
（`configs/cluster/casr_real_qwen3_8b_measured_cap.json`，
Decode `26/57/65`、Prefill `235/408/330`，来自 `calibrate_pd_throughput.py`）
后，结论不变：`CASR-LP` 均值 `1503.5 ms`、`97.5%` 仍压在一个 Prefill 上。
**所以问题不在容量参数，而在计算/排队模型本身。**

## 要让模拟器"能支持真实情况"，需要做的事（按优先级）

1. **校准单实例吞吐/排队模型**：让"同一 trace、同一拓扑下把负载集中到一个
   实例"的模拟结果与真机一致（真机 `d5090` 单实例可吃下整个 Dolly 档）。
   这是排序反转的直接原因，也是唯一必须解决的问题。
2. 补齐 `cache_aware` 基线（模拟器缺这个 SOTA 对照）。
3. 把 KV 传输模型换成实测链路行为（至少要能表达 PD 缓冲耗尽与传输停顿）。
4. 拓扑对齐到 2P+3D。

在 1 完成前，**模拟器结果只能用于算法逻辑（可行性、流守恒、消融方向）的
自检，不能用来支持"相对 SOTA 的优势"这类性能结论**；性能结论必须以真机为准。

## 附：2026-09-12 的对齐进展

### 已完成：补齐 `cache_aware` 基线（用户清单第 ② 项）

模拟器此前只有 `LOAD/RR/RAND/CUSTOM`，缺的正是真机对比用的 SGLang 语义路由。
现在在 `serving/core/router.py` 里实现为 `--request-routing-policy CACHE_AWARE`：

- 按**最长前缀命中**选 Prefill：复用 `request_block_hashes` 的同一条链式哈希，
  从 `kv.npu_pool.get_cached_block()` 数出连续命中块数（路由期探测，不分配）。
- 允许**落后一个块**仍算命中（与 SGLang 一致，避免一个被驱逐的块把整个类踢走）。
- 命中实例负载 `(waiting*4 + running)/max_num_seqs ≥ 0.75` 时**溢出**到最空的实例；
  若没有实例命中，则退化为 least-loaded。
- Decode 侧按需仍用 least-loaded，和真机实现一致。

回归测试 `tests/test_router_cache_aware.py`（5 例）覆盖：最长命中优先、
忙时溢出、只剩一个候选时仍选命中、全冷时退化 least-loaded。
`94 passed`。

首次模拟对比（deep trace，200 请求，`--enable-prefix-caching`）：

| 策略 | 均值 | P50 | TTFT P50 | `npu_hit_tokens` 均值 |
|---|---:|---:|---:|---:|
| `LOAD` | `20630 ms` | `20647 ms` | `9179 ms` | `166` |
| `CACHE_AWARE` | `18531 ms` | `17846 ms` | `7122 ms` | **`314`** |
| `CASR-LP` | `22000 ms` | `21274 ms` | `8834 ms` | `253` |

机制方向正确（`CACHE_AWARE` 命中显著高于 `LOAD`，时延随之下降），
**但绝对值差真机 20–60 倍**，正是下面要解决的计算/排队模型问题。

### 已定位：绝对值偏差的两段来源

用 256-token 单请求探针（RR 路由到 3090）与 profile 逐层求和对比：

| 项 | 值 |
|---|---|
| profile 预测（RTX3090，256 tok，逐层求和 ×36 层） | `91.6 ms`（`0.358 ms/token`） |
| 模拟器实测（同一请求） | `145–171 ms`（`0.4–0.67 ms/token`） |

即**基础 prefill 成本本身就有 `1.6–1.9×` 的膨胀**（多出来的部分与真机观测到的
"prefill POST 比纯算力多 ~50–180 ms"量级相当，怀疑是 KV 落盘/推送被计入）。

更关键的是**集中负载下的二次膨胀**：同一 Dolly trace 在 `LOAD`（分散）下
prefill 服务 P50 为 `61.8 ms`，在 `CASR-LP`（把 95.5% 流量压到一个 Prefill）下
变成 `792 ms`（`13×`）。换算下来批次计算约 `194 ms`，其余约 `600 ms`
与"**每个请求的 KV 推送被串行计入**"吻合（~10 请求 × ~55 ms）。
真机同样集中（`casr_lp` 的 Decode 100% 在 `d5090`）却只有 `354 ms` 端到端，
因为 NIXL 推送是并发流水而不是串行。

### 下一步（对齐工作的实际任务）

1. **KV 推送并发化**：把 producer 侧 egress 从"每请求串行服务时间"改为
   "受 `shared_links` 带宽约束的并发通道"，这是消除二次膨胀的关键。
2. **基础 prefill 成本校准**：把 1.6–1.9× 的固定膨胀定位到具体环节
   （需解析 `inputs_root` 下的 Chakra ET 图，把节点时间与 ASTRA-Sim 结果对齐）。
3. 校准后用同一批真机 trace 回归：目标是模拟器与真机在同一策略上的
   **排序一致**，绝对值进入同一量级。
4. 拓扑对齐 2P+3D（当前模拟器配置是每域 1P+1D）。

在第 1、2 项完成前，模拟器仍只适合做算法逻辑自检。

### 补记：`cache_aware` 两侧语义已对齐（2026-09-13）

真机 router 的 `_pick_cache_aware` 与模拟器的 `_cache_aware_select` 原本语义不同：

| | 真机 | 模拟器（修正前） |
|---|---|---|
| 命中者排序 | 按 `inflight/capacity` 取最小 | 按列表顺序取"第一个未忙" |
| 平局 | 字符串 id（**缺陷**） | 列表下标 |

两处都已统一为**按"本次请求分配后的负载"排序**（真机 `(inflight+1)/capacity`、
模拟器 `(queued+1)/max_num_seqs`），再比较是否超过溢出阈值；
并列时才落到 id 顺序。真机侧的字符串平局问题见
`docs/异构环境搭建进展.md` 的"`load` 基线退化成静态钉死"一节。
回归测试 `tests/test_router_cache_aware.py`（6 例）覆盖最长命中优先、
忙时溢出、容量并列时的选择与全冷退化。

## 附二：2026-09-12 晚间的进一步定位（含一处对上一节的修正）

### 新增工具：可复现的标定harness

`tests/calibrate_simulator.py`：给定 cluster 配置、硬件、prompt 长度与并发数，
自动生成同构 trace、跑模拟器、并同时给出
「profile 逐层求和 / 模拟器实际计费 / 真机锚点」三列与比值。
用法见文件头；真机锚点用 `--real-anchors` 传入（`router_config.json` 的
service time + `calibrate_pd_throughput.py` 的饱和吞吐）。

### 修正：profile 时间**是被正确使用的**

上一节把偏差归为"基础 prefill 成本膨胀 1.6–1.9×"。用标定系数做分解后，
这个说法需要更正。对同一 256-token 请求，把**计算节点时间**乘以 `s` 再测 TTFT：

| `s` | TTFT |
|---:|---:|
| `1.0` | `116.5 ms` |
| `0.25` | `116.4 ms` |
| `100` | `3255.8 ms` |

线性拟合 `TTFT(s) = s·C + F` 得 **`C = 31.7 ms`、`F = 84.8 ms`**。
`C` 与 profile 逐层求和（`30.9 ms`）**一致**——计算时间是准的。
缩小时看不到变化（被 F 淹没），放大 100 倍才显形，这也是上一节误判的原因。

也就是说：**模拟器的 prefill TTFT = 正确的 profile 计算 + 一笔约 85 ms 的
固定底噪**，且这笔底噪不随 token 数缩放。KV egress 只占其中约 `7 ms`
（把 `comm_size` 置零后 TTFT 116.5 → 109.7 ms），剩下约 `78 ms` 来源未定，
候选是 P/D handoff 路径、末尾 `MEM_STORE`、或每个 batch 的固定事件开销。

### 已排除的候选

- **roofline 覆盖**：ASTRA-Sim 的 `Workload::issue_comp` 在
  `roofline-enabled` 为真时会忽略 trace 里的实测时间、改用解析模型重算；
  但生成的 `system/system.json` 里没有这个键（默认 false），
  且 ×100 标定能被完整反映，说明当前走的是 `issue_replay`（用实测时间）。
  **这条路径不是本次偏差的来源，但它是未来要改模型时的关键开关。**
- **权重从 DRAM 加载**：`config_builder` 的默认 `weights` 放置是 `npu`（本地），
  没有 MEM_LOAD 双重计费。
- **KV egress 串行**：只占 ~7 ms，不是主因（上一节的猜测需要修正）。

### 当前可用的对齐手段

cluster 配置支持可选的 `sim_calibration.prefill_scale`（默认 `1.0`，
不影响任何既有结果），用于在找到那 85 ms 底噪之前把 prefill 侧拉回实测曲线。
配合 `tests/calibrate_simulator.py` 可逐硬件标定。
**注意**：它只缩放计算项，因此无法消除固定底噪——按上面的分解，
即使把计算缩到 0，TTFT 仍有约 85 ms。所以它只是过渡手段，
真正要做的是定位那 85 ms。

## 附三：2026-09-12 深夜——找到并修掉主因（链路参数）

### 突破：`link_bw` 配错，且 KV 推送在关键路径上

顺着"计算缩放无效 ⇒ 关键路径不是计算"这条线索去看生成的

npus_count: [1, 9]

### 仍然存在的差距：单实例并发响应过陡

对齐后重跑三策略（Dolly 200 请求，3 域）：

| 策略 | 均值 | P50 | TTFT P50 | Decode 分布 `d3090a/d4090/d5090` |
|---|---:|---:|---:|---|
| `LOAD` | `433.5 ms` | `442.6 ms` | `47.4 ms` | `28.5 / 30.0 / 41.5 %` |
| `CACHE_AWARE` | `433.5 ms` | `442.6 ms` | `47.4 ms` | `28.5 / 30.0 / 41.5 %` |
| `CASR-LP` | `559.1 ms` | `502.9 ms` | `163.0 ms` | `8.0 / 27.5 / 64.5 %` |

（Dolly 零前缀复用，所以 `CACHE_AWARE` 退化为 least-loaded、与 `LOAD` 完全相同——
这本身说明新基线实现是对的。）

但**排序仍与真机相反**：模拟器 `LOAD 433 < LP 559`，真机 `casr_lp 354 < load 825`。
逐实例拆开看原因：

| | 实例 1 | 实例 3 | 实例 5 |
|---|---:|---:|---:|
| `LOAD`（分散） | `567.3 ms`(n=57) | `472.9`(n=60) | `313.2`(n=83) |
| `CASR-LP`（集中） | `628.5`(n=16) | `632.6`(n=55) | **`519.2`(n=129)** |

LP 把 129 个请求（≈`8.5 req/s`）压到实例 5，该实例自身时延从 `313` 涨到 `519 ms`；
真机同样集中（`casr_lp` 的 Decode 100% 在 `d5090`）时，`d5090` 的端到端均值仍是
`354 ms` 且无排队——因为**真机实例的实测饱和吞吐是 `65 req/s`**，`8.5 req/s`
远在它的线性区。

所以剩下的差距在**单实例的并发/批处理模型**：模拟器里一个实例处理约
`8.5 req/s` 就出现 66% 的时延劣化，真机到 `65 req/s` 才饱和。
候选原因是 decode step 的批量上限或其耗时随批量增长的方式
（真机上批量 16 条序列共享一次 step，step 时间近似不变）。

这是**最后一块**：修掉它，模拟器才能复现真机的策略排序。

## 附四：2026-09-13 凌晨——批处理模型没问题，问题在网络模型的"域"概念

### 先纠正上一节的一个判断

上一节说"模拟器单实例在 `8.5 req/s` 就降 66%，真机 65 req/s 才饱和"，
据此推断批处理模型有问题。**这个推断是错的。** 用对齐后的 1P+1D 配置直接
压不同到达率（同一 5090 实例、同一条 prompt、16 输出 token）：

| 提供速率 | 实际吞吐 | 均值 | 排队 P50 |
|---:|---:|---:|---:|
| `14 req/s` | `13.9` | `261.5 ms` | `0.1 ms` |
| `30 req/s` | `29.3` | `263.8 ms` | `0.1 ms` |
| `60 req/s` | `56.9` | `291.3 ms` | `10.7 ms` |

即**单实例吞吐 ≥ `57 req/s`，与真机实测的 `65 req/s` 同一量级**，
批处理/并发模型是好的。之前看到的"8.5 req/s 就劣化"是那次运行里
**别的环节**造成的假象。

### 真正的差异：模拟器不区分"同域"与"跨域"

把同一请求分别放在「同节点 1P+1D」和「跨节点 1P+1D」两种拓扑上跑：

| 拓扑 | TTFT |
|---|---:|
| 同节点（P、D 都在 node0） | `68.3 ms` |
| 跨节点（P 在 node0、D 在 node1） | `68.3 ms` |

**完全一样**——因为 `config_builder._create_network_config` 生成的是
`topology: [FullyConnected, FullyConnected]` + 单一 `bandwidth/latency`，
ASTRA-Sim 眼里所有实例两两等距。而真机上：

| 场景 | 代价 |
|---|---|
| 同域 P→D（KV 不出节点） | ≈ `0`（实测同域 pair 无传输开销） |
| 跨域 P→D（16 Gbps / 0.3 ms） | `2048`-token 前缀约 `19 ms`，短 prompt 约 `2 ms` |

所以模拟器里 **4090 的 Prefill 显得更划算**（kernel 更快，传输又不额外收费），
于是 `CASR-LP` 选了 `p4090→d5090`；真机 `CASR-LP` 三次运行都是
**`p5090→d5090`（同域）100%**。排序反转的根因在这里，不在批处理。

### 已做的第一步：给求解器补 `pair_costs`

`serving/__main__.py` 现在会按集群的链路模型生成 `pair_costs` 传给共享求解器
（**同节点 rtt=0、bandwidth=0（免费）；跨节点用 `link_latency`/`link_bw`**），
语义与真机 router 的 `if p.domain == d.domain: free` 一致。

但只补求解器还不够：**求解器按 `kv_bytes/带宽` 计价，而模拟器的网络模型
对每一层 send 收的是固定链路费**，两者对同一个跨域传输的估计相差数倍
（求解器约 `12 ms`，模拟器实际约 `60 ms`）。
结果是计划按一个便宜的价格选了跨域 pair，而模拟器按更贵的价格收费——
实测 `CASR-LP` 的均值反而从 `559` 涨到 `1832 ms`。
**所以这一步必须与下一步同做。**

### 下一步（明确且有限）

1. **让网络模型表达域结构**：`_create_network_config` 需要支持
   节点内链路与节点间链路两套参数（节点内可给主机内带宽，如 `50 GB/s`），
   使同域 P→D 在**时间模型**上也接近免费。这一步做完，
   时序模型与求解器定价才会一致。
2. 然后把求解器的跨域单价校准到模拟器实际收取的值（用上面的 1P/1D 跨节点探针
   反推），再重跑三策略，检查排序是否与真机一致。

在这两步完成前，模拟器可以用来回答"某个调度决策在本模型下是否可行、
流量是否守恒"，但**不能用它的绝对时延或策略排序去支持性能结论**。

## 附五：2026-09-13——"模拟器选 4090"的真正原因：它在解另一个问题

上一节把偏差归给"网络模型不区分域"，并补了求解器的 `pair_costs`。
继续挖下去发现**主因是实验设置不对等，不是时序模型**。

### 证据：模拟器的 Prefill 根本是 INACTIVE 的

用 `--casr-state-output` 把每 tick 的状态 dump 出来后，`instances` 显示：

```
inst 0 (p3090a): INACTIVE      inst 4 (p5090): INACTIVE
inst 1 (d3090a): ACTIVE        inst 5 (d5090): ACTIVE
inst 2 (p4090):  ACTIVE        inst 3 (d4090): ACTIVE
solver.structural.wanted_ids = [2]
```

即模拟器的 CASR **只让一个 Prefill（p4090）保持活跃**，所以"99.5% 流量去 4090"
根本不是代价模型选出来的——那台实例是唯一在服役的 Prefill。

根因是集群配置里的 `casr.lifecycle.min_active_prefill = 1`：模拟器的
lifecycle 从最小活跃集开始、按需扩容，而**真机的 `casr_lp` 用
`--scale-backend ""`，完全不执行结构动作**，三个 Prefill 一开始就都在跑。
**两边跑的不是同一个实验**，排序自然对不上。

### 修正设置后的结果

把对比设置对齐（`lifecycle.min_active_prefill=3`、`max=3`，
并关掉 `structural.enabled`），6 个实例全部 ACTIVE 后重跑：

| | Prefill 分布 | Decode 分布 | 均值 | P50 | P95 |
|---|---|---|---:|---:|---:|
| 模拟器 `CASR-LP`（修正后） | `27.5/35.8/36.7%` | `21.7/26.7/51.7%` | `1722.8 ms` | `859.5 ms` | `5619.5 ms` |
| 真机 `casr_lp` | `p5090 100%` | `d5090 100%` | `354.2 ms` | `344.6 ms` | `449.0 ms` |

### 修正后仍存在的两个差距（下一轮的目标）

1. **模拟器的 LP 会向最慢的 Decode 溢出**：`d3090a`（`decode_service_ms 581.8`，
   是 d5090 的 2.1 倍）拿到 `21.7%` 流量。真机 LP 在同样负载下
   **一个请求都不给它**。原因是模拟器里 `utilization_weight` 的拥塞定价
   在它的负载水平上把流量推给了空闲但慢的实例；真机在 `3.5–14 req/s`
   下拥塞项可忽略、算力项主导。
2. **绝对量级仍差约 5 倍**（p50 `859.5` vs `344.6`），且与 `load` 的
   对比关系也未复现。

### 可复现的对齐产物

`configs/cluster/casr_real_qwen3_8b_three_domain_aligned.json` 现在同时固定了：
实测链路（`link_bw=2.0` GB/s、`link_latency=0.3 ms`）、实测容量
（decode `26/57/65`、prefill `235/408/330`）、
**与真机一致的活跃集**（`min_active_prefill=3`）以及 `structural.enabled=false`
（真机 `casr_lp` 不做结构动作）。

### 方法学结论（重要）

仿真与真机对比时，**必须先对齐"活跃实例集"与"是否允许结构动作"**，
否则两边在解不同的问题，任何时序差异的讨论都没有意义。
这一条比之前几轮的任何时序参数都更关键。

## 附六：2026-09-13——LP 的"溢出"不是拥塞项造成的，而是代价曲面近乎退化

### 排除了两个假设

上一节猜"`utilization_weight` 的拥塞定价把流量推给慢实例"。做了两件事后否掉：

1. **把 service time 换成真机实测值**
   （`prefill 68.0/39.2/48.5`、`decode 421.6/157.1/144.7`，
   异构比从 profile 外推的 `2.09×` 提到实测的 `2.91×`）：
   Decode 分布 `24.2/32.5/43.3%`，均值 `1743.7 ms`——**几乎没变**。
2. **`utilization_weight: 1.0 → 0.0`**：
   Decode 分布 `25.0/34.2/40.8%`，均值 `1670.5 ms`——**几乎没变**。

### 真正的原因：三个同域 pair 的代价几乎相同

把实测 service time 代进 `_pair_cost`（`compute = (prefill_ms×work + decode_ms)/1000`，
同域传输为 0）：

| pair | 域 | `compute` | 网络 | 合计 |
|---|---|---:|---:|---:|
| `p4090 → d4090` | 同域 | `(39.2+157.1)/1000 = 0.196` | `0` | **`0.196`** |
| `p5090 → d5090` | 同域 | `(48.5+144.7)/1000 = 0.193` | `0` | **`0.193`** |
| `p4090 → d5090` | 跨域 | `(39.2+144.7)/1000 = 0.184` | `+0.012` | `0.196` |

三者差别在 `0.003` 以内——**LP 面对的是一个近乎退化的解空间**，
"把全部流量给哪一个 pair"是任意顶点。真机的 LP 同样面对这个退化，
它的实现（hysteresis + deficit 回放 + 连续控制）恰好收敛到
`p5090→d5090`；模拟器的实现收敛到"摊在三个 pair 上"。

而两种落点的**执行代价完全不同**：模拟器里分散方案的均值 `1743.7 ms`，
集中方案（`LOAD` 在同一配置下）只有 `433.5 ms`——**同一组实例、
几乎相同的分布，时延差 4 倍**，说明模拟器的时延还强烈依赖配对方式，
这一点尚未解释。

### 结论与建议

1. **模拟器目前不能支撑"策略排序"类结论**。已经排除的原因包括：
   链路参数（已修）、活跃集/结构动作（已修）、拥塞定价（非主因）、
   批处理吞吐（实测 ≥57 req/s，正常）。剩下的是
   **LP 在退化解空间上的选择** 与 **配对方式对时延的影响**，
   两者都需要专门的算法级调试，而不是参数对齐。
2. 真机侧的可比性仍然成立：三档数据集 × 六策略 × 3 轮的主表
   （见 `docs/实验结果汇总.md`）全部来自同一拓扑、同一 trace、
   同一冷启动流程，**不受模拟器这些问题影响**。
3. 如果后续要用模拟器做性能论证，建议的最小路径是：
   先固定"每策略的有效活跃集"与"是否允许结构动作"，
   再给 LP 加显式的平局打破规则（例如同代价时优先同域 pair），
   最后重新标定配对方式对时延的影响。

## 附七：2026-09-13——域感知网络模型与真实 P/D 配对（已实现）

附四把"模拟器不区分同域/跨域"记成了一条网络参数问题。继续挖下去发现，
它其实是**三个叠加的缺口**，只修其中任何一个都不会让排序变对。

### 缺口一：拓扑里没有"域"这一维

`config_builder._create_network_config` 一直只生成
`topology: [FullyConnected, FullyConnected]` + 单一 `bandwidth/latency`，
`_compute_network_dims` 也只是把实例拍平成 `[tp, instances]`。3 域部署
（每台机器 1P+1D）里 `total_npu = 9`，于是变成 `npus_count: [1, 9]`：
9 个 NPU 两两等距，`p5090 → d5090`（同主机）与 `p4090 → d5090`（跨主机）
在时间模型上完全同价。

### 缺口二：router 从来没选过 Decode 半边

`serving/core/request.py` 的 `decode_instance_id` 在整个 `serving/` 里
**只被写入过一处**——`Scheduler.add_decode`，也就是 Prefill 跑完之后。
Prefill 执行期间它是 `None`，于是 `Scheduler._build_batch` 里
`targets` 恒为空集、`batch.pd_decode_npu_offset` 恒为 `None`，
Chakra 转换器就回落到 legacy 的相邻 rank：KV 每层发给
`npu_id + num_npus`，也就是 **Prefill 实例自己的"发送槽"NPU**。

用 `ASTRA_DEBUG_DIM` 打点（临时给 `MultiDimTopology::send` 加的文件输出）
可以直接看到这一点：

```
3 域 aligned 配置，CASR-LP 60 请求：
  740 次 src=0 dst=1 dim=1 dims=3
  740 次 src=3 dst=4 dim=1 dims=3
  740 次 src=6 dst=7 dim=1 dims=3
```

`dims=3` 说明新拓扑已经生效，但 `dst` 全是 `src+1`、`dim` 全是 1（域内）——
**求解器按 `rtt + kv_bytes/带宽` 定价的那一跳，在时间轴上从来没有被收过费**。
这也解释了附六里"同一组实例、几乎相同的分布，时延差 4 倍"的怪象：
LP 选的是"模型里的便宜 pair"，而执行侧只按"相邻 rank"收费，两边说的不是一回事。

### 缺口三：转换器末尾的 output send 没跟着走

`LLMConverter.convert_prefill` 的每层 KV send/recv 会用
`pd_decode_npu_offset`，但末尾那次 "Send output" 仍然写死
`comm_dst = npu_id + num_npus`。一旦真的把 KV 发到选中的 Decode NPU，
这两个文件就互相不认（ASTRA-Sim 的 chunk id 是
`(tag, src, dst, size)`，而 recv 侧的 `dst` 取的是**运行它的那个 rank**），
两边同时阻塞。实测表现：单请求就挂死，`log.log` 里
`sys[0] iteration 1 ... exposed communication 188566898957 cycles`。

### 实现

1. **ASTRA-Sim 的层次语义**（`MultiDimTopology::get_dim_to_transfer`）：
   多维拓扑是一条层次链，`dim0` 最内层、`dim_{n-1}` 最外层。跨层的
   point-to-point 传输由**最外层那个不同的维度**承载，所以改成从外层往回扫。
   原来"返回第一个不同的维度"会在两个端点 local rank 也不同的时候，
   把跨域传输按域内链路收费。只差一维的传输（所有集合通信、任何同节点 pair）
   结果不变。
2. **域感知拓扑**（`config_builder`）：配置里声明
   `intra_node_link_bw` / `intra_node_link_latency` 后，若每个节点拥有的
   NPU 槽数相同，实例维会被拆成 `[…, slots_per_node, num_nodes]`，
   除最外层（节点）外的每一维都取域内链路。3 域部署因此生成
   `npus_count: [1, 3, 3]`、`bandwidth: [50, 50, 2]`、
   `latency: [1000, 1000, 300000]`。不声明就不改拓扑，既有结果逐 bit 不变。
3. **配对在到达时确定**（`Router.name_decode_at_arrival`，仅在声明了域内链路
   的配置上开启）：请求到达时同时选出 Prefill 与 Decode，和真机
   `disagg_router._pick_decode` 的时机一致。写入 `decode_instance_id`
   之后，`batch.pd_decode_npu_offset` 才会被填上，KV 才会真的发往被选中的
   Decode NPU——**这一步才是让求解器的跨域单价落到时间轴上的开关**。
4. **求解器单价对齐**：`pair_costs` 的跨域 `rtt_ms` 由 `link_latency` 改为
   `num_hidden_layers × link_latency`。模拟器每层收一次链路时延（36 次），
   而求解器只收一次 RTT，原来少算了一个层数的倍数。
5. **转换器末尾 output send** 改用与每层 KV 相同的目标 NPU；Prefill 实例的
   额外"发送槽"rank 在动态配对下写入空 ET（ASTRA-Sim 会为控制器 NPU 的
   整个托管范围加载 workload，缺一个文件就会中断整组加载）。

### 验证：受控探针

`tests/calibrate_pd_handoff.py` 构造**同构**双节点（两边同样硬件，因此算力
完全相同），跑单一 prompt 长度，按 `RAND` 均匀混出同域/跨域两种 handoff，
只比较两桶的 TTFT：

```bash
python3 tests/calibrate_pd_handoff.py --hardware RTX5090 --tokens 512 \
    --num-reqs 24 --spacing-s 0 --out /tmp/pd-handoff.json
```

| inter 链路 | 跨域 TTFT 增量 |
|---|---:|
| `8 GB/s` / `0.3 ms` | `+1.98 ms` |
| `2 GB/s` / `0.3 ms`（实测内网） | `+43.87 ms` |
| `0.5 GB/s` / `0.3 ms` | `+278.19 ms` |

同一份 trace、同样的实例，只改跨域链路，增量随链路单调放大——**域模型现在
真的在收钱，而不是只写在配置里**。（`2 GB/s` 档的 `43.9 ms` 与
"36 层 × 0.3 ms + 75.5 MB / 2 GB/s = 48.5 ms"同量级。）

同一批 3 域 aligned 配置的 200 请求 replay（Dolly，`LOAD`）按 pair 分桶：

| | n | TTFT 均值 |
|---|---:|---:|
| 同域 handoff | 76 | `56.8 ms` |
| 跨域 handoff | 124 | `85.6 ms` |

改之前两个桶的差只是硬件组合噪声（"同域 47.0 / 跨域 51.5"），现在差距来自
链路本身。

### 仍然存在的限制（重要）

1. **只支持单卡实例（`num_npus == 1`）。** 多卡实例的 Prefill 有额外的
   "发送槽"rank，而 ASTRA-Sim 按控制器 NPU 的托管范围整组加载
   `llm.<npu>.et`：动态 receiver 让这些 rank 没有图，缺文件会中断整组加载
   （实测 `tp=2` 场景 `sys[0]` 卡在 `exposed communication 4.3e12 cycles`）。
   `_compute_domain_layout` 因此对 `num_npus > 1` 返回 `None`，声明域内链路的
   配置会直接报错而不是悄悄给出错的结果。真机部署是每实例 1 卡，不受影响。
2. **LP 仍然铺开，不集中。** 3 域 `LOAD` 与 `CASR-LP` 的均值/分布几乎相同
   （`2183.5 ms`，同/跨域 `76/124`），即 LP 把流量摊在 9 个 pair 上，
   而真机 `casr_lp` 是 `p5090→d5090` 100%。成因见附六：算力项主导、
   pair 代价曲面近乎退化，需要显式的平局打破/迟滞才能收敛到单个 pair。
3. **绝对量级仍未对齐。** 这一轮改的是"哪一跳收多少钱"的结构，不是单实例
   吞吐标定；模拟器 3 域均值仍在秒级，真机在百毫秒级。

因此：域感知的**结构**已经和真机一致（同域便宜、跨域按实测链路收费、
pair 在到达时确定），但**排序类结论仍然不能由模拟器给出**，
直到第 2 条（LP 收敛）解决。

## 附八：2026-09-15——"改了没生效"是死锁的真因，以及三道具名门禁

### 现象与误判

用对齐后的 3 域配置重放真实 trace（CNN-short，200 请求，14 req/s）时，

### 根因

1P1D 配置碰巧 `decode_npu_id == 相邻 rank`，所以一直"正常"，

### 绝对时延偏差的根因：链路 RTT 被按层计费

单请求复放（`/mnt/home/casr/results/sim-sweep`，零排队，TTFT 即服务时间）：

| prompt tokens | 32 | 254 | 512 | 1024 | 1250 |
|---|---:|---:|---:|---:|---:|
| 模拟器 TTFT (ms) | 1898.3 | 2746.7 | 3732.6 | 5689.2 | 6552.8 |
| 真机（5090 锚点） | ~50 | 111 | — | — | — |

线性拟合给 `TTFT ≈ 1460 ms + 3.8 ms/token`，即存在一个 **~1.5 s 的固定开销**。
用 profiler 数据核对：32-token 的 36 层计算量只有
`36 × 415.8 µs ≈ 15 ms`（`dense.csv` 各层 @32 token 之和 + lm_head 0.77 ms），
所以这 1.5 s **不在计算模型里**。

决定性实验（同一份 32-token 单请求，只改 `link_latency`）：

| `link_latency` | 48 ms（当前配置） | 1 ms | 0 |
|---|---:|---:|---:|
| 模拟器 TTFT | **1898.3 ms** | 159.3 ms | 122.3 ms |

差值 `1898 − 159 = 1739 ms ÷ 47 ms ≈ 37`，与 Qwen3-8B 的 36 层吻合：
**模拟器在每一层都计了一次链路 RTT**（当前配置把 A100 的 41.5 ms 级 RTT 取成了
全拓扑统一的 48 ms，本地实例也照收）。真机的一次 prefill 是单次前向，
不存在每层一次跨域往返。

这解释了为什么：短 prompt 慢 ~38×、长 prompt 慢 ~10×（1250 token 时固定项被摊薄）、
而 TPOT（decode 侧每 token）反而与真机一致。

### 附十之一：上面第 1 条已修（2026-09-16 下午）

#### 修复 1：P/D KV 交接从"每层一次"改成"每批一次"

定位过程：单请求 32-token 的 TTFT 是 **1898 ms**（真机 50 ms），而 ASTRA-Sim 日志里
`exposed communication = 1,898,352,373 cycles`（≈1.9 s）——计算本身只有 15 ms
（profiler 数据：36 层 × 415.8 µs @32 token + lm_head 0.77 ms）。

把 ET 图拆开数节点：`instance0_batch0/llm.0.et` 有 **send=37**、`llm.1.et` 有 recv=37，
载荷 36 × 131072 B（每层 KV）+ 9,723,904 B（lm_head 输出），全部 src=0→dst=1。
链路延迟实验（只改 `link_latency`）给出 `(1898−159)/47 ≈ 37` —— **每一层都付了一个完整 RTT**。

根因：`trace_generator` 给**每个** `qkv_proj` 行都写 KV 字节，而 Chakra 转换器对
"名字含 v_proj 且 comm_size>0"的行各发一对 SEND/RECV，ASTRA-Sim 对每条消息收满额
链路延迟。真机的 NIXL push 是**流水线**的，RTT 只付一次。

修法：新增 `_aggregate_kv_handoff()`，把整批 KV 的字节汇总到**最后一个** `qkv_proj` 行
（字节总数不变，传输项仍随 KV 大小线性增长），RTT 只付一次；interleaved/PP 路径按
`batch_tag` 分组，各自保留一次交接。

#### 修复 2：prefill 输出不再搬 logits

`_emit_final_layers` 把 `lm_head` 的输出标成 `REMOTE`，转换器按该行 `output_size` 发包，
于是 32 token 的**整个 logits 张量（9.7 MB）**被当成 P/D 交接载荷（真机只回采样 token）。
新增 `_finalize_prefill_handoff()` 把这一行的输出改成 `4 B × 请求数`。

#### 修复 3：生成器补 `pair_costs`

真机 `casr_control.py` 显式构造 pair 代价：**同域免费**、跨域只算实测 RTT、
容量只在 `shared_links` 里计一次（并注明"按 pair 再算 bytes/bw 是双重计费"）。
模拟器配置里**没有这个键**，于是 `_pair_cost` 退化成 `|NPU 序号距离| × 0.001` ——
最便宜的边取决于实例碰巧被列出的顺序，也是 CASR 计划落到奇怪实例的原因之一。
生成器现按同一口径输出 `pair_costs`（4 个同域 = 0 ms，跨域 = 实测 41.5 / 48 ms，
bandwidth 一律 0），并加了回归测试。

### 附十之六：`load` 改用真机的 inflight 口径 + 搬运档 decode 也按代价选

### 附十之八：结构弹性 A/B —— 三处模拟器缺口与一处未解

工况：3 域小集群、强制搬运（`LOCAL_PREFILL=never`）、`STOP_BEFORE_RUN=p4090`
（warmup 后停掉 p4090 作为备用，运行池 = p5090 + p3090a）、
`cnndm-long-elastic-240s-qwen3-8b.jsonl` 前 300 请求（0.5→1.8→0.5 req/s）：

* 真机 `casr_lp`（scale-backend 为空，没有执行器）：E2E p50 **5154.6 ms**、
  p95 6428.1、TTFT p50 4945.7、TPOT 15.0；落点 **p5090 291 / p3090a 9**，
  备用 p4090 **零流量**（停容器 + 计划里排除都生效）。
* 真机的结构评估器仍然在决策（`state-casr_lp.jsonl` 里 45 次 `-P`
  "remove Prefill 1"），只是没有执行器所以池子没变——这一点以前没记录过。

对照暴露了三处模拟器缺口（都已修）：

1. **没有 backlog 项**。真机 `casr_control._sample_backlog` 用"Prefill 等待队列的
   增长速率"补回未被接纳的报价负载（上限 `backlog_rps_multiple × observed`），
   否则观测速率在过载时会塌到"服务速率"，LP 恰好在你最需要扩容时被告知
   "需求 == 容量"。真机这一档的 demand 被抬到 **8.33 req/s**（真实 ~1.8），
   模拟器则一直停在观测值、capacity 显示 108 req/s，于是所有 `+P` 反事实都被判
   "gain below threshold"。新增 `CASRController._sample_backlog/_inflate_demand`
   （同公式、同 EWMA、同上限），回归 `tests/test_backlog_demand.py` 7 条。
2. **生命周期自带按需扩缩容**。模拟器的 `PrefillLifecycle` 会按观测需求自己改池子
   大小，于是"关闭结构动作"的那一臂也照样扩容（备用 p4090 接了 101 个请求）。
   新增 `lifecycle.scale_on_demand`（默认 true 保持既有行为，对齐臂置 false）。
3. **搬运请求绕过并发预算**。`add_decode` 只查 KV 池、把请求直接塞进 `running`，
   强制搬运档下单个 Decode 能堆到 100+ 并发，每步都按最坏批量计价；
   补上 `max_num_seqs` 检查（与真机 vLLM 的拒绝语义一致）。
   另外 `replay_real_run.py` 现在会把部署的 `max_num_seqs`（16）传给模拟器——
   之前用默认 128，等于换了台引擎。

**未解**：即使补完上面三处，模拟器在强制搬运档的 **decode 阶段仍是真机的 ~20 倍**
（sim E2E p50 26271 ms 对真机 5154.6，TPOT 1461 ms 对 15.0）。单请求复测时两种模式
的 TPOT 都是 15.3 ms，说明不是每 token 模型；反压计数也为 0，说明不是准入路径。
剩下的解释是模拟器的执行循环**逐批串行推进**：强制搬运下每个 prefill 批次要
~1.8 s（1250 token + 交接），decode 的批次要等它让出时间片，所以 300 请求的
跑法会把 decode 拖垮，而本地重算档（prefill 与 decode 在同一实例的同一批流里）
不受影响。这条要验证需要动调度循环，另开。

#### 附十之八补记：同一次 A/B 里，真机 `casr_full` 把自己打崩了

同配置、同 trace，只把执行器打开（`casr_full` = `--scale-backend docker`）：

* `casr_lp`（决策记录但不执行）：**300/300 完成**，E2E p50 5154.6 ms。它的控制器
  在同一轮里做了 **45 次 `-P`** 决策，但因为没有执行器，池子没变。
* `casr_full`（决策 + 执行）：控制器在过载期间把 **p5090 与 p4090 的容器都停掉**
  （`p5090` 状态 `Exited (0)`，4090 域 8100 端口不再响应），运行池塌到只剩 p3090a，
  之后的 **10 分钟内 0 个请求完成**（`metrics-casr_full.jsonl` 为空），只能中止实验并
  原地恢复容器。

原因是控制器的经济学：`idle_cost_fraction=0.1` 让"少养一台 Prefill"在 60 s
评价窗口里总是显得划算，而决策只看**已接纳**的负载（真机的 backlog 项把它抬到
8.33 req/s，但仍远低于 LP 看到的 108 req/s 容量），于是 `-P` 在池子正被打满时
被判定为有正收益并真的执行了。**模拟器侧的同一套经济学也一直在投 `-P`**
（`casr_lp` 臂 224 次 `keep` 里大量是 "counterfactual remove Prefill"），只是这一轮
模拟器的 `+P` 从未触发、`-P` 也没被允许生效，所以没暴露出同样的崩法。

这属于**控制器缺陷**（真机与模拟器共用同一套成本模型），不是模拟器特有：
下一步应当在 `-P` 的判据里加入"该实例当前是否在承载负载/是否低于本轮的
最小可用容量"，或者让 holding cost 与实测利用率挂钩，而不是常数比例。

#### 附十之八之二：`-P` 守卫（同日修复，真机复验两次才定稿）

第一版只对**候选实例**做检查（`running`/`waiting` 为空才可移除）。在真机上
立刻复验 `casr_full`（较轻的一档：1.05 req/s、两个 Prefill、90 请求）——
**仍然把 p5090 停掉**，只完成 4 个请求就再次瘫掉。原因是轻载下每个实例在两次
请求之间本来就是空的，逐候选检查抓不住。

第二版把判据提到**池子级别**并补上部署侧的 `inflight`（"已派发未完成"，贯穿
整个请求生命周期，真机 `RealInstance` 一直维护着）：

```python
pool_busy = any(item.waiting or item.running for item in active_prefill)
if len(active_prefill) > min_active and not pool_busy:
    for candidate in ...:
        if candidate.running or candidate.waiting or candidate.inflight > 0:
            continue
```

效果：模拟器两臂的 `-P` 全部消失（160 次 `keep`，池子稳定在 2 台，落点
`p5090 226 / p3090a 73`）；空转 pool 的 `-P`（holding cost 想回收的场景）与
`max_num_prefill` 上限等既有行为不变。回归：`tests/test_length_and_elasticity.py`
新增/改写 3 条（池子忙时不允许缩、空转池仍可缩、`inflight>0` 的候选被跳过）。

**遗留**：真机 `casr_full` 目前**不建议在共享集群上再跑**，除非在下一次窗口里
盯着；更强的判据（把 `-P` 与实测利用率挂钩，而不是常数 `idle_cost_fraction`）
还没做——它同时影响模拟器的弹性档收益，属于控制器经济学的范畴，已单列。

#### 附十之九：KV 字节该用精确观测 —— 弹性档终于有了正确的经济学

`-P` 守卫之后，弹性档依然不触发（`+P` 全部 "gain below threshold"）。查 LP 的
诊断发现 **`link_overflow` 每一个实例都是 0**，而该档实际已经跑到出口预算的 ~20 倍
——也就是说**真正卡住这套 fabric 的约束（producer 出口 0.26 GB/s）在模型里完全不可见**。

根因在 KV 字节的取法：`_class_kv_bytes` 用 `requested_tokens_ewma` 推字节，
而**每条 prompt 唯一**的工作负载里每个类只被观测一次，EWMA 永远停在
`alpha × tokens`（1250 token 的 prompt 记成 250，低估 5 倍）。KV 字节是 prompt 的
物理属性、不是需要平滑的速率，于是改成**精确观测优先、EWMA 仅作回退**
（`requested_tokens` → `requested_tokens_ewma` → `default_kv_bytes`）。
真机 router 与模拟器共用 `casr.flow_solver`，两边一起生效。

效果（模拟器，3 域强制搬运 + 一个备用，300 请求）：

| 臂 | E2E p50 | p95 | TTFT p50 | Prefill 落点 | `+P` |
|---|---:|---:|---:|---|---:|
| static（结构动作关） | 62375.1 ms | 74706.2 | 22983.0 | p5090 291 / p3090a 8 | 0 |
| elastic（结构动作开） | **35491.1 ms（−43%）** | 92849.2 | 13569.6 | p5090 176 / p3090a 20 / **p4090 104** | **3** |

LP 侧同时可以看到 `link_overflow` 升到 2.9–5.0（超过预算 4–5 倍），`+P` 第一次
有了正收益、复活的 p4090 承接了 104 个请求。**这是本项目里弹性档第一次在
模拟器里同时具备正确的约束与正确的收益。**

真机复验（`casr_full`，同 trace 的 90 请求、有人盯着）：**90/90 完成**，
E2E p50 1640.8 ms、TTFT p50 1424.3、p95 3372.1；控制器做了一次合理换血
（移除空闲的 p3090a、`+P` 拉回更快的 p4090），5090 与 4090 全程在线，
不再出现上一轮的塌陷。

同口径的两臂对照（都是 90 请求、强制搬运、备用 p4090）：

| 臂 | n | E2E p50 | p95 | TTFT p50 | Prefill 落点 | 决策 |
|---|---:|---:|---:|---:|---|---|
| `casr_lp`（不执行） | 90 | 1646.9 | 3235.8 | 1427.1 | p5090 90 | `-P` 39 / keep 94 |
| `casr_full`（执行） | 90 | 1640.8 | 3372.1 | 1424.3 | p5090 89 / p4090 1 | `-P` 3 / keep 277 / **`+P` 2** |

这一档**两边都没有拿到弹性收益**（差 0.4%，在噪声内）：90 请求 ≈ 1.05 req/s 的
负载压不满两台 Prefill，`+P` 拉起的那台只接到 1 个请求。这与之前模拟器里的结论
一致——**弹性只有在"池子被打满且持续时长远超启动时间"时才回本**；模拟器里
300 请求（1.8 req/s 峰值、240 s 高压相）才出现 −43%。

要把真机的弹性 A/B 做成有意义的对照，需要用 `cnndm-long-elastic-240s` 那条
300 请求的 trace 重跑两臂（每臂约 15–20 分钟），这是下一轮的第一件事。

#### 附十之十：重载弹性 A/B（300 请求、1.8 req/s 峰值、强制搬运）

同一条 `cnndm-long-elastic-240s` trace、同样"两台在跑 + 一台备用（p4090）"、
同样强制搬运，只差执行器：

| 臂 | n | E2E p50 | p95 | TTFT p50 | TPOT | Prefill 落点 |
|---|---:|---:|---:|---:|---:|---|
| 真机 `casr_lp`（不执行） | 300 | 5114.7 ms | 6696.9 | 4899.6 | 15.0 | p5090 290 / p3090a 10 |
| 真机 `casr_full`（执行） | 300 | **946.5 ms（−81.5%，5.4×）** | 4737.0 | **721.3** | 15.0 | p5090 299 / p4090 1 |
| 模拟器 static（结构动作关） | 300 | 62375.1 ms | 74706.2 | 22983.0 | — | p5090 291 / p3090a 8 |
| 模拟器 elastic（结构动作开） | 300 | **35491.1 ms（−43%）** | 92849.2 | 13569.6 | — | p5090 176 / p3090a 20 / p4090 104 |

结论分两层：

1. **方向一致、机理一致**：真机在饱和档下弹性把 E2E p50 砍到 1/5.4（TTFT 4899.6 →
   721.3 ms），模拟器同样出现正收益（−43%、`+P` ×3、复活的备用承接 104 个请求）。
   "过载持续 ≫ 启动时间才回本"这条也更清楚了：轻载档（90 请求、1.05 req/s）
   真机两臂打平（1646.9 vs 1640.8），重载档才有 5.4×。
2. **绝对量级仍然差 12–37×**（真机 5114.7 / 946.5 对模拟器 62375.1 / 35491.1）。
   这正是附十之八记下的未解项——**持续强制搬运**档里模拟器的 decode 阶段被
   昂贵的 prefill 批次拖住（逐批串行推进），负载越重偏差越大：轻载档只有 1.5–1.9×。

另外记一个真机侧现象：`casr_full` 在 4 分钟内做了
`-P(p3090a) → +P(p4090) → +P(p3090a) → -P(p5090) → -P(p3090a)` 五次切换，
池子在 1–3 台之间来回。虽然最终拿到了收益，但**控制器的抖动**明显（dwell 3 s、
评价窗口 60 s 都不足以稳住），这属于控制器质量问题，值得单独一轮收紧。

#### 附十之十一：那 12× 里大部分是"闭环 vs 开环"的差别

把时间轴摊开看才发现问题不在计时模型：真机的 TTFT 从 t+30 s 起就**稳定在
4.7–5.5 s**（队列达到稳态），模拟器却**线性增长**到 42 s（队列无界累积）。

| 窗口 | 真机 n / TTFT p50 | 模拟器 n / TTFT p50 |
|---|---:|---:|
| t+0–30 s | 24 / 1561 ms | 29 / 3064 ms |
| t+30–60 s | 47 / 4712 | 54 / 9495 |
| t+60–90 s | 49 / 5373 | 54 / 17000 |
| t+90–120 s | 46 / 4737 | 54 / 25023 |
| t+120–150 s | 42 / 5538 | 54 / 33281 |
| t+150–180 s | 50 / 4718 | 54 / 42491 |

原因：**真机客户端是闭环的**（`real_dataset_client.py --concurrency 8`：系统慢下来时
它压住源头，每窗口只有 42–50 个请求进入），而**模拟器是开环回放**（按 trace 的
到达时刻全部灌进去，每窗口 54 个）。同一份 trace、同一套容量，闭环会自我限流、
开环则把队列堆到爆——**这才是 12× 差距的主要来源**。

修法：模拟器新增 `--client-concurrency N`（0 = 保持历史开环行为），到上限就暂停
路由；并且被推迟的请求**按实际提交时刻计时**（真机客户端也是从那一刻起算）。
只加上限而不改计时口径会得到更差的数字（实测 E2E p50 从 62375 变 47994），
因为那样等于把"等待被提交"的时间也算进请求延迟。

修正后（300 请求、强制搬运、两台在跑）：

| 臂 | E2E p50 | TTFT p50 | 对照 |
|---|---:|---:|---|
| 模拟器 static（闭环 8） | 6535.4 ms | 4158.0 | 真机 `casr_lp` 5114.7 → **1.28×**（此前 12×） |
| 模拟器 elastic（闭环 8） | 6062.6 ms | 2087.0 | 真机 `casr_full` 946.5 → 6.4× |

静态档对齐到 1.28×；弹性档模拟器只有 −7%（TTFT 4158 → 2087），真机是 −81%。
差别在**落点**：真机 `casr_full` 把慢的 3090a 换出后 299/300 都走 p5090（TTFT 721 ms），
模拟器的计划仍按容量把流量摊在三台 prefill 上（p5090 158 / p3090a 75 / p4090 67），
慢实例继续拉高尾部。这属于路由/放置层面的差异，是下一处要查的点。

**补查（同日）**：这个"摊开"其实是**计划随时间演进**的结果，不是路由不听话。
把两边的 `flows` 逐 tick 摊开看：

* 模拟器 elastic：t≈76 s / 114 s 时计划是 `p4090→d4090` **95%**，t≈155 s 换成
  `p5090→d5090` **90%**——落点（p4090 67 / p5090 158）与两段计划吻合。
* 真机 `casr_full`：t≈95600 / 95672 / 95744 计划 `p5090→d5090`、`p5090→d4090`，
  t≈95818 / 95891 换成 `p4090→d4090`；落点按 30 s 桶看也是 p5090 主导
  （28/54/54/48/59/46/10），同样跟着计划走。

也就是说**两边都忠实执行自己的计划**，差异在"计划选谁、什么时候换"：
模拟器的 `+P` 分别在 t=22/70/119/170/220 s 触发、把 p4090 拉起后确实接了 67 个请求，
但它的计划在 p4090 与 p5090 之间来回切；真机的计划更早、更久地停在 p5090 上，
于是 TTFT 只有 721 ms。**下一处要查的是计划本身的稳定性与选择**（同一份 LP、
同一套容量，为什么两边的解不同），不再涉及路由执行。

LP 的输入对比（各自的 `state-*.jsonl`）显示两边**输入量级相当**：

| 栈 | 需求 p50 / 峰值 | 求解器容量 | 类别数 p50 |
|---|---:|---:|---:|
| 模拟器 elastic（闭环 8） | 6.49 / 10.74 | 167 | 138 |
| 模拟器 static（闭环 8） | 5.74 / 9.64 | 108 | 134 |
| 真机 `casr_full` | 0.00 / 9.40 | 122 | 304 |
| 真机 `casr_lp` | 5.47 / 12.00 | 167 | 222 |

所以"同一份 LP 给出不同解"并不是输入差一个数量级，而是**切换时机**：真机的计划在
高压相里较早、较久地停在 p5090，模拟器则在 p4090/p5090 之间来回。要注意真机的
类别数是 304（与请求数一一对应），模拟器只有 ~135——它的前缀剖面把一部分 prompt
归并了，这会影响 LP 看到的类别粒度，值得单独核对。

**下一步（离线回放）**：既然真机每 tick 的计划已经落盘（`state-*.jsonl` 里的
`flows`/`plan`），可以把**真机录制的计划**逐 tick 灌进模拟器执行，把"控制器决策"
与"路由/模型执行"分离——若灌真机计划后模拟器的时延贴近真机，说明剩下的差距全在
控制器选点；若仍差很多，则说明执行侧还有缺口。这是目标里"便于后续回放离线对齐"
最直接的一次应用。

#### 附十之十二：灌入真机放置后，残差定位到"搬运请求的 decode 每步成本"

新增两个回放开关（都进了 `tests/replay_real_run.py`）：

* `--replay-placement`：把真机 `metrics-*.jsonl` 里**逐请求的 (prefill, decode)**
  映射到模拟器实例号后灌进去（真机 request id 是 `ds-<trace 序号>`，与模拟器的
  trace 序号一一对应），绕过计划/策略选择；
* `--client-concurrency 8`：闭环回放（见附十之十一）。

用真机 `casr_lp` 那一档（300 请求、强制搬运、两台在跑）的**精确放置**回放：

| | n | E2E p50 | TTFT p50 | TPOT p50 | Decode 落点 |
|---|---:|---:|---:|---:|---|
| 真机 `casr_lp` | 300 | 5167.8 ms | 4895.2 | **14.9** | d5090 291 / d4090 4 / d3090a 5 |
| 模拟器（灌同样放置） | 300 | 9908.6 ms（1.92×） | 3306.1 | **401.8（27×）** | 与真机逐位一致 ✓ |

放置已经**逐位一致**，TTFT 甚至比真机更好（3306 vs 4895），但 **decode 阶段炸了**。
再用 40 请求 + INFO 日志复核：decode 实例（d5090）全程只有 **6 个并发、0 排队**
（不是批量过大），而 **TPOT p50 仍有 244.5 ms**——约是同一批数据本地重算路径
（15.3 ms）的 16 倍。

所以现在可以确定：

1. **残差不来自放置/计划**（灌入真机放置后仍在）；
2. **不来自批量过大**（并发只有 6，`max-num-seqs 16`）；
3. 而是**"KV 由别的实例搬过来"这件事本身让模拟器的 decode 每步贵了 ~16×**
   （本地重算路径的 decode 是准的，15.3 ms）。

这条把范围收得很窄了：下一步只需查搬运请求在 decode 侧的 trace/图里多了什么
（怀疑每步都带了一次 KV 注入/内存搬运节点，而真机的接收是与生成重叠的），
不用再碰放置、闭环、容量这些已经对齐的部分。

**再补两个证据（同日）**：

* **零负载时搬运请求的 decode 是准的**：同样灌入真机放置、只跑 2 个请求
  （强制搬运，p5090→d5090），模拟器给出 `TTFT 700.6 ms / TPOT 15.3 ms /
  E2E 929.9 ms`——TTFT 与 TPOT 都与真机同量级（真机 TTFT ~850 ms、TPOT 15.0）。
  所以"每步贵 16×"**不是搬运请求的固有成本，只在有负载时出现**。
* **不是批量过大**：40 请求的 INFO 探针里 decode 实例（d5090）全程
  `Running 6 reqs, Waiting 0 reqs`，`max-num-seqs 16` 远没打满，但 TPOT 仍是 244.5 ms。

两条合起来指向**执行循环的相互等待**：零负载时 decode 独占时间线（15.3 ms），
一旦 prefill 侧有 1250-token 的大批次在跑（单批 ~1.5 s），decode 的每一步就要
等它让出时间片，于是每步被拉长到几百毫秒。ASTRA-Sim 的逐 NPU 日志显示各 NPU
都在以 1 ms 的粒度推进，说明瓶颈不在单个 NPU 的算子，而在**模拟器主循环一次只
推进一个批次**这个调度方式上。要修就得让 prefill 与 decode 的批次真正并行推进，
这是执行循环层面的改动（已单列，不再与放置/闭环/容量混在一起）。

**再进一步（同日）**：主循环其实是 ASTRA-Sim **事件驱动**的（`controller.read_wait`
返回哪个 NPU 完成），各 NPU 在同一时间线上并行，所以"一次只推进一个批次"的说法
不准确。直接量 decode 批次本身的代价：

* 保存 40 请求探针的 trace 文本后统计，**decode 批次的 `comp_time` 合计 ≈ 15.3 ms**
  （363 个节点，最大项是 `lm_head` 0.74 ms + 36 × `gate_up_proj` 0.22 ms）——
  计算侧完全正确，与真机 15.0 ms 一致。
* 但请求自己的 token 时间戳显示**成串发出**：560 个间隔里 p50 = 0 ms（同一批的 token
  同时落），却有 **9.8% 的间隔 > 100 ms，最大 1137 ms**。

也就是说 decode 的**每步算得对，但步与步之间在等**——0.244–0.402 s/token 是
"每批 15 ms + 期间平均等 ~1 s"摊出来的。下一步要查的是：decode 实例在两次
批次之间到底等什么（候选：等待该实例上待接入的 handoff、或等待 prefill 侧
在同一时间线上的发送节点完成）。这条已经不需要再碰放置/闭环/容量/批量成本。

数据：真机 `/mnt/home/casr/results/small3-0916/`（含 763 条 `state-casr_lp.jsonl`
逐 tick 控制面快照），模拟器 `/mnt/home/casr/results/sim-small3-v4/`。

#### 附十之十三：把 handoff 从"Decode NPU 上的一个图"改成"一条链路"

上一条把残差定位到"decode 步与步之间在等"，然后查到了等的是什么：**等在
Decode NPU 上执行的 KV RECV 图**。

证据链（真机 300 请求强制搬运，`/mnt/home/casr/results/small3-elastic-heavy/`）：

* 逐 NPU 日志里 Decode 的这行是决定性的：`sys[2] iteration 96 finished,
  11769128045 cycles, exposed communication 10393369252 cycles`——它的
  88% 时间花在"暴露通信"上；Prefill 侧同理（`sys[0]` 10.97 s / 11.77 s）。
* 把 KV 字节清零（`SIM_DISABLE_KV_EGRESS=1`）跑同一个回放，TPOT p50 从
  260.4 ms 掉到 **15.4 ms**，其余不变——即"每步贵 16×"完全来自这段 RECV。
* 真机这边恰好相反：d5090 在全程接收 300 次 handoff 的同时保持 **TPOT p50
  14.9 ms**；p5090 自己的 `prefill_ms` p50 只有 **195 ms**（就是 1250 token 的
  计算量），根本没有被发送拖住。真正被串行化的是**推送本身**：300 × 184 MB
  在 240 s 内推完 ≈ 0.23 GB/s，与部署实测的 585 ms/1000 token（≈0.25 GB/s）
  同量级。

于是把 P/D handoff 建成**链路资源**而不是两个 NPU 图（新模块
`serving/core/pd_link.py`）：

* `PdHandoffLink` 给每个 Prefill 实例一条 FIFO 出口，`bytes / bandwidth`
  占用出口、再过 `latency` 落地；落地时才把请求交给 Decode（同机用实测的
  0.3 GB/s + 1 µs，跨域用配置里的 `handoff_link_bw`/`link_latency`）。
* Prefill 的 trace 不再带这段 KV SEND（`batch.pd_kv_send_tokens = 0`，token
  数留在 `batch.pd_link_tokens` 供前端计价），批次完成条件也不再等 Decode
  的 NPU；Prefill 与 Decode 各自按自己的时间线推进。
* 前端每个 iteration 把到期的 handoff 交给 Decode，并在 `pass <tick>` 里带上
  下一个落地时刻，所以空闲集群不会漏醒。
* `pd_handoff_model: "graph"` 可退回旧行为，便于对照。

同一轮还修了两个各自独立的缺陷：

* **TTFT 记账**：搬运请求的 TTFT 原先在 *Prefill* 完成时打点，于是整段
  handoff（0.6–1.7 s）被算进了请求的第一个 inter-token gap，TPOT 直接虚高。
  现在 TTFT 与真机客户端一致，记在**第一个输出 token**上。
* **池子 churn**：`PrefillLifecycle` 每 tick 都按**瞬时负载**重挑 `min_active`
  个 worker，于是"刚接到请求的那个 worker"在下一 tick 就被判为最忙而被
  drain——弹性档实测：p5090 在第 0 号请求到达的那一 tick 就被关掉，整个回放
  247/300 次 handoff 都跨域（真机是 290/300 同机推送）。现在池子在规模不变时
  保留已有 worker，首次选取用显式 `initial_active_prefill`（回放工具直接从
  录制里读）或"有在跑请求的 → 算力高的 → id 小的"顺序。

回放结果（真机 `casr_lp` 300 请求、灌真机放置、闭环 8）：

| | n | E2E p50 | TTFT p50 | TPOT p50 |
|---|---:|---:|---:|---:|
| 真机 | 300 | 5167.8 ms | 4895.2 | 14.9 |
| 模拟器（旧：图模型） | 300 | 9908.6（1.92×） | 3306.1 | 401.8（27×） |
| 模拟器（新：链路模型） | 300 | 4914.3（**0.95×**） | 4700.3（0.96×） | 14.3（**0.96×**） |

其他回放档位（同一轮改动后）：

| 档 | 真机 E2E / TTFT / TPOT | 模拟器 | 比值 |
|---|---|---|---|
| 短 prompt `load`（200，本机重算） | 280.0 / 44.9 / 15.0 | 333.4 / 38.3 / 18.9 | 1.19× |
| 短 prompt `casr_lp` | 273.6 / 44.5 / 15.0 | 304.8 / 33.8 / 17.6 | 1.11× |
| 长 prompt `casr_lp`（120） | 314.7 / 103.3 / 13.6 | 371.0 / 132.5 / 15.4 | 1.18× |
| 长 prompt 强制搬运（120） | 2002.9 / 1774.1 / 14.5 | 1203.5 / 984.6 / 14.3 | 0.60× |

回归：`tests/test_pd_link_handoff.py`（链路 FIFO/落地时刻、池子稳定性，以及
一个 gate 住的端到端：`SIM_PD_LINK_E2E=1` 要求强制搬运档的 TPOT < 30 ms 且
TTFT > 400 ms）。回放工具 `tests/replay_real_run.py --replay-placement`
现在会把"录制里真实用过的那几个 Prefill"写进派生 arm 配置
（`<out>/arm-config.json`），否则生命周期只能靠启发式猜池子。

剩下的差：模拟器比真机快 4–40%（长搬运档 0.60×）。两个已知来源——(1) 跨域
推送速率用一个配置常数（0.11 GB/s = 0.88 Gbps 的 kvlink 预算），而部署实测的
推送是 115–314 MB/s；(2) 真机 TTFT 里含路由器/队列的额外等待，模拟器的闭环
客户端只认得自己的并发上限。两者都在 20–40% 量级，不再是结构性错误。

#### 附十之十四：执行侧对齐之后，剩下的差回到"计划怎么分流量"

同一轮改动之后重跑小集群强制搬运 A/B（300 请求、闭环 8、`LOCAL_PREFILL=never`，
`/mnt/home/casr/results/sim-small3-elastic-v11/`）：

| 臂 | 计划分流量 (p,d) | TTFT p50 | E2E p50 | E2E mean |
|---|---|---|---|---|
| static（v11） | (0,1) 159 / (4,5) 141 | 763 / 836 ms | 977 / 1203 ms | 1087 ms |
| elastic（v11） | (0,1) 252 / (4,5) 47 | **4690** / 836 ms | 4898 / 1203 | 3221 ms |
| static（v10，图模型） | 0:207 / 2:92 / 4:1 | 4158 ms | 6535 ms | 6544 ms |
| elastic（v10，图模型） | 0:158 / 2:75 / 4:67 | 2087 ms | 6062 ms | 5801 ms |
| 真机 casr_lp / casr_full | 290/10、299/1 | 4895 / 718 ms | 5139 / 944 ms | — |

两点：

* **执行侧的 27× 已经消失**：v11 的 TPOT p50 = 14.3 ms（真机 14.5–14.9），
  TTFT 也回到 0.76–0.84 s 的正常量级（同机搬运 184 MB / 0.3 GB/s ≈ 0.61 s + 
  prefill ~0.13 s）。
* **但"弹性增益"换了个地方消失**：elastic 臂把 84% 的流量压在 (p5090,d5090)
  这一条链路上，另外两条同机链路空闲；单链路服务率 0.3/0.184 ≈ 1.63 req/s，
  而闭环客户端常驻 8 个在飞请求，排队深度 8/1.63 ≈ **4.9 s**，正是实测到的
  TTFT p50 4.69 s。也就是说：链路本身没算错，**是计划把流量分歪了**。

这解释了为什么"结构弹性显示不出收益"在换了几种场景后仍然复现：执行侧越准，
暴露出来的越是**计划/路由**的缺口——现在的 LP 只按 RTT + 服务时间 + 队列占比
打分，`pair_costs[*].bandwidth_bytes_per_s` 还是 0（生成器为避免与
`shared_links` 重复计价而留空），所以它看不见"这条链路上还排着多少字节"。
真机路由器那侧是看得见的（`disagg_router._pair_cost`：`rtt + link_inflight_bytes /
bandwidth`，注释里明确写了"按占用而非串行化计价"）。

顺带确认了一件事：仓库里那条弹性验收门
（`tests/run_casr_elasticity_long.py`，要求 elastic 均值收益 ≥10%）**在本轮改动
之前就是红的**——用改动前的 `serving/` 重跑，输出与改动后逐位相同
（static 1525 / elastic 1788，−17.2%，`/mnt/home/casr/results/sim-elastic-e2e-presession/`）。
所以这不是本轮引入的回归，而是上面这条计划侧缺口的另一个表现：elastic 臂多开的
worker 是被计划"看见"了，但流量并没有按链路占用重新分配。

**下一步（单列）**：让 LP/路由按链路占用计价——
`pair_costs` 填上每对的推送速率（同机 0.3 GB/s、跨域 0.11 GB/s，即部署实测的
585 ms / 1351 ms per 1k token），并把 `shared_links` 的占用作为决策输入，而不是
只作为事后约束。判定标准就是这两条曲线：v11 static/elastic 的分流量应趋于均衡，
弹性门回到 ≥10%，且重放三档（短/长/强制搬运）的比值不退化。

#### 附十之十五：计划里的"服务时间"也必须换成模拟器真正执行的那套

接着上一条查下去，发现**不是链路占用没计价，而是计划用的每实例代价常数与
模拟器执行用的不是同一份**。

真机 `metrics-*.jsonl` 里逐实例的 TPOT（1250-token prompt、16 输出 token）：

| Decode | 真机 TPOT | profiler 单步 | 部署 `service_ms` 折算 |
|---|---:|---:|---:|
| `d5090` | 15.0 ms | 14.8 ms | 9.0 ms/token |
| `d4090` | 24.6 ms | 25.8 ms | 9.8 ms/token |
| `d3090a` | 43.1–47.1 ms | 31.3 ms | 26.4 ms/token |

部署的 `service_ms`（d4090 157.1 ms vs d5090 144.7 ms）只差 **1.09×**，而 profiler
和真机都在 **1.7×**。原因是 `service_ms` 是在 96 请求 / 并发 8 / 16 输出 token
的条件下测的，那时各卡都被并发拉平；单步 decode 是权重读取（带宽受限），
真实差距 1.7×。计划按 1.09× 计价、执行按 1.7× 收费，于是 LP 把 452 个请求里
的 82 个丢给了 `d4090`，均值从 1525 ms 涨到 1788 ms（附十之十四）。

修法（`serving/core/hw_service.py`）：**相对差距取自 profiler（跑起来真正执行
的那份），绝对量级锚定在部署实测值上**——最快的卡保留 `service_ms` 原值，其余
按 profiler 单步比缩放；prefill 同理按参考长度（`capacity_reference_tokens`）
换。校准后：decode `d5090 144.7 / d4090 245.3 / d3090a 276.7`，顺序与真机
TPOT 一致（`d4090` 比值 1.70×，与真机 1.64× 吻合）。

效果（同一个小集群强制搬运 A/B，300 请求、闭环 8）：

| 版本 | static | elastic | 说明 |
|---|---|---|---|
| v10（图模型） | 6544 ms | 5801 ms | TPOT 199–215 ms，执行侧错了 |
| v11（链路模型） | 1087 ms | 3221 ms | 执行侧对了，但计划把 84% 压单链路 |
| v12（+服务时间校准） | 4268 / p50 4915 | 4268 / p50 4915 | 计划单宿到最快的一对；两臂不再互相伤害 |
| 真机 | casr_lp p50 5139 | casr_full p50 944 | |

v12 的 p50 4915 ms 与真机 `casr_lp` 的 5139 ms 只差 5%，TTFT/TPOT 也同量级
（4701/14.3 vs 4895/14.9）——**但两臂相同**，因为计划现在认定"最快的那一对
（p5090→d5090）就够了"，多开的 Prefill worker 拿不到流量。

**下一步（单列，已经定位到具体常数）**：计划的**容量**常数仍与执行脱节。
配置里 `prefill_capacity 63/45/59`、`decode_capacity 65/45/57`（req/s）来自
短 prompt 标定，而执行侧在 1250-token prompt 上：local 重算每个请求要吃
132 ms prefill + 41 步 decode ≈ 0.76 s 的单引擎时间（实测该臂只跑到
1.62 req/s，`span` 正好等于 trace 时长，即引擎被打满），也就是**每实例
~1.3–2 req/s**，比 63 低 30 倍。容量不真实 → LP 看不到拥塞 → 单宿 → 弹性
worker 永远拿不到流量，弹性验收门因此只能得到 0.0%（已从 −17.2% 修到不互相
伤害，但还赚不到）。修法与本轮一样：用 profiler 的每请求服务时间反推容量
（必要时按观察到的 prompt 长度缩放），再跑
`tests/run_casr_elasticity_long.py`（现已支持 `--base-config`，可以换成
排除 A100 的三域配置）判定 elastic ≥ +10%。

**已经写好但默认关闭的那一步**（`serving/core/hw_service.py::rescale_capacities`，
用 `casr.capacity_from_profile=true` 打开）：按 profiler 单步反推容量，得到
`prefill 9.34 / 2.74 / 6.58`、`decode 4.21 / 2.01 / 2.44`（req/s，参考长度），
比配置里的 `63/45/59`、`65/45/57` 低一个数量级。实测打开后静态臂 p50 从
4915 ms 掉到 1056 ms——它把 111/300 个请求甩到 **跨域** 的 (p4090,d5090) 上，
因为路由的拥塞项是 `service × inflight / capacity`（引擎队列），容量一变小，
这条项就压过去，于是为了躲引擎队列而付出 1.67 s 的跨域搬运。真机路由器不会
这么做：它的拥塞项是**链路**占用（`inflight_bytes / bandwidth`），同域对网络项
为 0。所以打开这个开关之前，得先把路由的拥塞项从"引擎队列"改成"链路队列"，
否则是把一个对齐问题换成另一个。默认保持关闭，行为与上表 v12 一致。
