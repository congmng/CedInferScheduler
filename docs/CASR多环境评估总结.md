# CASR 多环境评估总结（2026-09-24）

把 `docs/SOTA覆盖与模拟器基线映射.md` 的对照路线落到**四环境 × 三峰值 × 多臂**上跑完，
并逐个消除比较中暴露的口径错误。本文是结论汇总；逐项过程见
`docs/实验数据集与对比基线说明.md` §6.19–6.31。

## 1 环境与口径

| 维度 | 取值 |
|---|---|
| 模型 | `casr/P15B`（类 DSV4：压缩 KV 16 960 B/token、混合注意力）／`Qwen/Qwen3-8B`（传统稠密 147 456 B/token） |
| fabric | metro：跨域 push 0.33 GB/s / 20 ms，同域 0.77 GB/s；WAN/云边：0.11 GB/s / 48 ms，同域 0.257 GB/s（真机实测） |
| 拓扑 | 3 域，每域 1P+1D（0/1=3090，2/3=4090，4/5=5090） |
| 负载 | CNN/DailyMail 1250-token、零复用，峰值 8 / 16 / 32 rps（各 45/45/30 s 高峰） |
| SLO | TTFT ≤ 1500 ms、TPOT ≤ 50 ms（500 ms 会让所有 pair 同时越界，见 §6.22） |
| 臂 | `load` / `cache_aware`（SGLang 语义）/ `kv_aware`（Mooncake 式 producer 出口定价）/ **CASR（LP 计划）** |
| 存算协同 | 所有臂都开 `local_prefill: auto`（搬 KV vs 本地重算，逐请求决策） |
| 计划口径 | 容量 = 执行侧 period 倒数（含每 step 开销、按 prompt 长度插值）；KV 预算按**配对**拆分（同域/跨域） |

## 2 负载矩阵：12 格（单元格 = CASR 均值 / `load` 均值，<1 表示 CASR 更快）

| 环境 | 8 rps | 16 rps | 32 rps |
|---|---:|---:|---:|
| P-15B metro | **0.98×**（100% / 100% SLO） | 1.07×（100% / 100%） | 1.03×（5.8% / 8.4%） |
| P-15B WAN | **0.93×**（100% / 100%） | **0.86×**（**98.8% / 74.2%**） | 1.21×（**17.8% / 11.9%**） |
| Qwen3 metro | **0.96×**（100% / 100%） | 1.04×（81.4% / 86.4%） | 1.02×（1.0% / 1.0%） |
| Qwen3 WAN | 1.09×（91.1% / 92.4%） | **0.96×**（**38.5% / 10.8%**） | **0.99×**（0.9% / 1.0%） |

* **12 格赢 6 格**，10 格在 ±10% 以内；唯一 >20% 的是 P-15B WAN @32 rps（1.21×），
  但同一格 SLO 从 11.9% 抬到 17.8%。
* 轻载（8 rps）不吃亏；**收益集中在云边 16 rps**（两个 WAN 格）。
* 三条非 CASR 臂在本负载上重合（740 个唯一前缀 ⇒ 前缀匹配恒为 0，`cache_aware` 退化成 least-load）。

## 3 优势一：KV 感知的存算协同（当前配置下的消融）

把 `kv_bytes_per_token` 置 0（同时关掉搬运定价、egress 上限与链路预算），16 rps：

| 环境 | **KV 感知** | KV-blind | Δ | SLO（感知 / blind） | 决策 |
|---|---:|---:|---:|---|---|
| P-15B metro | **2 395** | 5 750 | **+140%** | 100% / 6.9% | transfer 740 → local 740 |
| P-15B WAN | **2 831** | 5 797 | **+105%** | 98.8% / 7.0% | transfer 719+local 21 → local 740 |
| Qwen3 metro | **3 540** | 5 952 | **+68%** | 81.4% / 7.6% | transfer 293 + local 447 → local 740 |
| Qwen3 WAN | **4 414** | 6 162 | **+40%** | 38.5% / 7.0% | transfer 160 + local 580 → local 740 |

即：**"搬还是重算"这条决策值 40%–140% 的时延和 7%→81–100% 的达标率**，
而且它的形状随模型与 fabric 改变（见 §5）。这也是为什么 6.24 那次消融只测到 ≤6%：
当时的 config 把同域与跨域用同一个 0.11 GB/s 卡住，两个臂都被压成"全本地"，差别被抹平了。

## 4 优势二：动态扩缩容

同一 fabric（WAN）、同算法，只改池形态与容器启动假设：

| 场景 | static 1 台 | **elastic 1→3** | fixed 3 台 | 结论 |
|---|---:|---:|---:|---|
| P-15B，16 rps / 45 s 峰值，启动 **0.25 s** | 5 058 | **2 831**（100% SLO） | 2 831 | 弹性**逐位**拿回常开池的全部收益 |
| P-15B，同上，启动 **45 s**（真机） | 5 058 | 4 909 | 2 831 | 启动 ≈ 峰值 ⇒ **零收益**（物理边界） |
| Qwen3，240 s 峰，启动 **45 s**，修好 lifecycle 后 | 2 699（67.9%） | **1 893（94.9%）** | 1 759（99.8%） | **−30% 均值 / +27pt SLO** |

后者此前测出"弹性完全无收益"，根因是三个 lifecycle 实现 bug（WARMING 被下一次结构覆盖丢掉、
`+P` 覆盖集合不含刚上线的机器、`scale_on_demand=false` 时池子被缩回 `min_active`），
修完后三台在 0 / 46.1 / 68.9 s 就位。**弹性不是自动的优势**：
它要求"池子缺容量 + 峰值长于启动 + 启动足够快"三者同时成立，
报告任何弹性收益都必须同时给出启动假设。

## 5 模型的影响：类 DSV4 vs 传统稠密

同一拓扑、同一负载、同一算法，只换模型（KV 16 960 vs 147 456 B/token）时结论**会反转**：

* **存算协同的方向反了**：1250-token 请求在
  * P-15B：同域搬运 27.5 ms（0.77 GB/s）／跨域 240.7 ms，而本地重算要 355 ms
    ⇒ **WAN 上也值得搬**（transfer 719/740）；
  * Qwen3：同域 558.6 ms、跨域 1 723.6 ms，本地只要 355 ms
    ⇒ **只能本地重算**（WAN 上 local 580/740）。
* **容量口径的瓶颈换了**：Qwen3 的 KV 大到让**同域 push 成为容量上限**
  （0.257 GB/s ÷ 151 MB/请求 = 1.70 参考请求/s，而算力是 11.53），
  即"存"直接决定了"算"能开多大；P-15B 则是算力受限（4.90 / 8.25 / 13.58）。
* **消融幅度不同**：KV 感知对 P-15B 值 +140%（metro）/+105%（WAN），
  对 Qwen3 值 +68%/+40%——压缩 KV 让算法有更多可调空间，稠密模型则被"必须本地重算"锁死。
* **弹性收益同样取决于模型**：Qwen3 的 240 s 弹性收益 −30%，P-15B 在 45 s 峰值上
  即使启动很快也只是"追平常开池"（因为池子本来就够）。

**结论**：`跨域 P/D 分离是否划算` 不是部署属性，而是 **(KV 规模, fabric, prompt 长度) 的函数`；
用传统稠密模型得到"WAN 上必须本地重算"的结论，不能外推到压缩 KV 模型，反之亦然。

## 6 不足与脆弱性（诚实列表）

1. **饱和档仍略输**：32 rps 的 P-15B WAN 是 1.21×（SLO 更好）；两臂 SLO 都掉到 1–18%，
   此时比较的是"崩得多难看"。
2. **对输入口径敏感**：这一轮的结论建立在四步口径修正之上（对照臂统一链路定价、
   egress 搬运器看算力、Prefill 排队进目标函数、KV 预算按配对拆分）。
   每一步之前，算法都被"根本不成立的前提"拖成落后 1.6–7.9×。
   换句话说：**算法的收益有一半来自把口径修对**，另一半才是策略本身——
   这是需要写进论文的边界，而不是可以省掉的实现细节。
3. **排队定价仍是启发式**：`prefill_queue_weight` 是线性权重（试出来 10 最好），
   不是从队列论推出的最优价；饱和区的尾延迟仍靠它兜底。
4. **弹性依赖启动假设**：45 s 真机启动让 45 s 峰值上的弹性收益为 0；
   要在这类峰值受益，必须先做 6.25 的加速（hot spare / 调小 `warmup_s` / 权重预取）。
5. **未覆盖的 SOTA 机制**：SLO 驱动的 P:D 比例搜索、实例迁移（Llumnix 类）、
   快速冷启动（ServerlessLLM 类）都还没有对照臂（见覆盖文档 §1 的"未实现"行）。

## 7 复现

```bash
cd LLMServingSim
# 四环境 × 三峰值 × 两臂
for m in p15b qwen3; do for f in metro wan; do for p in 8 16 32; do
  tests/run_route_arms.py \
    --cluster-config configs/cluster/casr_${m}_3dom_${f}_auto.json \
    --dataset workloads/matrix-${p}rps-slo1500.jsonl \
    --arms load,cache_aware,kv_aware,casr_lp --out-root /tmp/env-${m}-${f}-${p}
done; done; done
# KV 消融：把 casr.kv_bytes_per_token 置 0（configs/cluster/abl-kv0-*.json）
# 弹性：configs/cluster/casr_{p15b,qwen3}_3dom_wan_{static1,elastic45,elastic250}.json
```

产物：`/tmp/v2-*`（四环境 CASR）、`/tmp/lnk-*`（四环境基线）、`/tmp/p8-*`、`/tmp/p32-*`（负载档）、
`/tmp/kvabl-*`（KV 消融）、`/tmp/el2-*`、`/tmp/el3-*`、`/tmp/el7-B`（弹性）、`/tmp/lnk-summary.json`。
