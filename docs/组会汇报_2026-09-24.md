# 组会汇报：跨域异构 P/D 分离的 KV 感知存算协同调度

> 汇报日期 2026-09-24 ｜ 主线：**前缀状态 → 容量 → 计划 → 结构** 的闭环调度
> 数据来源全部标注在文中（`docs/*.md` 与 `/tmp` 下的运行产物）。

## 0 一页速览

| 问题 | 我们的答案 |
|---|---|
| 为什么要换模型 | 传统全注意力模型的 KV 随上下文线性涨（Qwen3-8B **147.5 KB/token**），跨域搬运 184 MB/请求，P/D 分离在广域网上不划算；DSV4 系列的压缩注意力把 KV 压到 **10%** |
| 我们怎么跑 | 官方 DSV4 在 3090/4090/5090/A100 上**起不来**（mHC 依赖 sm90+、o_proj 依赖 fp8 GEMM）。我们自己写了 **vLLM 原生的小模型 P-15B**（14.376 B 总参 / 1.655 B 激活），**复刻同一套 KV 几何**：**16.56 KB/token（比 Qwen3-8B 小 8.9×）** |
| 算法是什么 | 五层闭环：**观测（前缀类状态）→ 容量（单步成本/服务时间/链路预算）→ 计划（类级 LP）→ 路由（快速层执行）→ 结构（±P 反事实）** |
| 数据从哪来 | 评测：CNN/DailyMail（`abisee/cnn_dailymail` 3.0.0 validation）pack 到 1250 token；profile：在真机上按 4 类 category × 网格扫，产出 bundle |
| 效果 | 12 格（4 环境 × 3 峰值）里 **6 胜 / 5 平（≤10%）/ 1 负**；KV 感知值 **+40%~+140%**（SLO ~7% → 81–100%）；弹性在长峰值上 **−30% / +27pt SLO** |

## 1 传统模型 vs DSV4 系列：KV 大小与随上下文长度的变化

### 1.1 DSV4 系列是什么（来自官方说明，仓库内快照 `reference-dsv4-flash-readme.md`）

| 项 | DeepSeek-V4-Pro | DeepSeek-V4-Flash |
|---|---|---|
| 参数 / 激活 | 1.6 T / 49 B | 284 B / 13 B |
| 上下文 | **1 M token** | **1 M token** |
| 注意力 | **混合注意力：CSA（压缩稀疏）+ HCA（重压缩）** | 同 |
| KV 收益 | 1M 上下文下只需 DeepSeek-V3.2 的 **10% KV**（FLOPs 27%） | 同 |
| 其它 | mHC 超连接、Muon 优化器、32 T token 预训练 | 同 |

### 1.2 KV/token 对照（这张表是本汇报的核心对照）

| 模型 | 注意力形态 | **KV/token（bf16）** | 4K | 32K | 128K | 相对 Qwen3-8B |
|---|---|---:|---:|---:|---:|---:|
| Qwen3-8B | 全注意力 GQA（8 kv head × 128 × 36 层） | **147.5 KB** | 590 MB | 4.7 GB | 18.9 GB | 1.00× |
| Llama-3.1-8B | 全注意力 GQA（8 × 128 × 32 层） | 128 KB | 512 MB | 4.0 GB | 16.4 GB | 1.15× 更小 |
| MLA 基线（同规模） | 全层 MLA latent | 31.1 KB | 124 MB | 996 MB | 4.0 GB | 4.7× 更小 |
| **P-15B（我们的自研小模型）** | **MLA + CSA(4)/HCA(128) 混合** | **16.56 KB**（fp8 8.28 KB） | **66 MB** | **530 MB** | **2.12 GB** | **8.9× 更小** |

（1M 上下文外推：Qwen3-8B ≈ 147 GB、P-15B ≈ 16.6 GB。表中 4K/32K/128K 取自
`docs/DSV4-P15B设计.md` §5。）

**随上下文长度怎么变**：全注意力与压缩注意力都是**线性**增长，但斜率差 8.9×；
而且压缩不是"少存一点"，是**换机制**——每 `ratio` 个 token 压成一个状态：

| 层类型 | 每状态宽度 | 多少 token 一个状态 | KV/token |
|---|---:|---:|---:|
| 全 MLA（3 层） | `head_dim + rope` = 576 值 | 1 | 1,152 B |
| CSA ratio=4（13 层） | `2·coff·head_dim` = 2048 值 | 4 | 1,024 B |
| HCA ratio=128（12 层） | `2·1·head_dim` = 1024 值 | 128 | **16 B** |
| **合计** | | | **3×1152 + 13×1024 + 12×16 = 16,960 B = 16.56 KB** |

> ⚠️ **口径提醒（必须在汇报里讲清）**：16.56 KB 是**解析值（设计下界）**，
> 不是任何 serving 栈的实测。同一套层结构在 vLLM 0.29 上实测 **98 KB/token**
> （compressor 状态用 fp32 缓存、`tokens_per_state` 没传给 spec），其中 **1.40×** 可自己修回来。
> 仿真里用 **16,960 B**（cluster config 的 `casr.kv_bytes_per_token`）。

### 1.3 我们为什么跑不了完整模型，跑的是什么

**硬约束**（`docs/DSV4-P15B设计.md` §1）：

1. 目标机是 3090(sm86) / 4090(sm89) / 5090(sm120) / A100(sm80)；
2. 官方 DSV4 路径的 **mHC** 只有 sm90/sm100/sm120 的 deep_gemm kernel
   （4090 上直接 `hyperconnection.hpp: Unsupported architecture`），
   **o_proj 依赖 fp8 DeepGEMM**（无 fp8 GEMM 的卡报 `weight_scale_inv`）——
   **不是机器占用问题，是模型起不来**；
3. 所以我们**自己写了一个 vLLM 原生的小模型**：`deploy/vllm_p15b/`（6 个文件）
   + `profiler/models/p15b.yaml` + 三份 config（r0 / r4 / r128）+ 注册钩子；
   profiler 用 `load_format: dummy`，**不需要 checkpoint、不需要训练**。

**与官方的差异（有意为之）**：

| 项 | 官方 | P-15B | 为什么 |
|---|---|---|---|
| mHC 超连接 | 有 | **没有** | 只占 0.012% 参数 / 0.3% FLOPs，却把路径锁死在 sm90+ |
| hash routing | 前几层有 | 没有 | 训练技巧，与 KV 设计无关 |
| shared expert | 有 | **没有** | 简化（加回 = +0.275 B 参数、激活 +18%） |
| indexer | 多头 | **单头** | 固定的是 top-k 行为而不是头数 |
| fp8 权重/KV | 硬要求 | 默认 bf16（fp8 可选） | sm80/sm86 没有 fp8 GEMM |
| 压缩层前向 | FlashMLA / FlashInfer-sparse | 纯 torch（可换自研 Triton） | 前者只有 Hopper+ |

### 1.4 我们模型的层级架构

**规格**：28 层、hidden 2560、20 个 attention head（`head_dim=512`）、
**1 个 KV head（MLA latent）**、`q_lora/o_lora` 640/512、MoE **48 专家 top-3**、
vocab 65536、`max_position_embeddings=4096`；
**14.376 B 总参 / 1.655 B 激活**，bf16 权重 **28.75 GB**（部署用 **TP=2**，14.38 GB/卡）。

**层类型展开**（沿用官方交替模式 `[0,0] + [4,128]×k + [0]`）：

```text
idx   0  1 | 2   3 | 4   5 | ... | 24  25 | 26 27
type  0  0 | 4 128 | 4 128 | ... | 4   128 | 4  0
      └─全 MLA─┘ └──────── CSA(4) / HCA(128) 交替 ────────┘ └MLA┘
      3 层        13 层 CSA + 12 层 HCA
```

**单层结构**：

```text
x = x + Attention(RMSNorm(x))     # MLA latent + 滑窗(coff×ratio) + 压缩状态 + indexer top-512，联合 softmax
x = x + MoE(RMSNorm(x))           # gate + 48 专家取 top-3，标准 pre-norm，无 mHC
```

**参数量/激活分解**（模块树实测，`DSV4-P15B设计.md` §4）：
MoE 占 **91.9%**（13.21 B / 14.38 B）；激活 1.655 B。

## 2 算法设计（按层说明）

一句话：**在「前缀亲和类 k × Prefill i × Decode j」上求连续流量 `f[i,j,k]`，
最小化「网络搬运 + 排队 + 算力 + 拥塞 + 超容」，再在同一目标上做一步结构反事实。**

### 层 0 · 观测层（`serving/casr/prefix_profiler.py`）

| 观测量 | 定义 | 参数 |
|---|---|---|
| 类 k | **前缀指纹 × 输入长度桶 × 输出长度桶** | 前缀按 block（16 token）链式哈希，最多 512 token |
| 到达率 λ_k | 1 s 窗口计数 → EWMA；**总量来自全局计数，每类发布"总量 × 归一化份额"** | `ewma_alpha=0.2` |
| 命中文档 | 每 (Prefill, 类) 的命中 token EWMA | 半衰期 10 s |
| 缓存占用 | 每 (Prefill, 类) 的 block 驻留 | 由 KV pool 直接读 |

> 这一层修过两个真 bug：per-class EWMA 的"尾巴累加"（Σrate 会到真实值的 5 倍）、
> 以及**在派发时刻计数**（挂起批次放行会被读成几十次到达）。现在在请求**到期时**计一次。

### 层 1 · 容量层（`serving/core/hw_service.py`）

| 量 | 定义 | 来源 |
|---|---|---|
| 单步成本 | 逐层 dense + **attention（按 block type：全因果/窗口 4/窗口 128）** + MoE + head | bundle 逐层查表 |
| 参考周期 | **`charge + 每 step 开销 × chunk 数`**（同域 1P1D 打满实测：5090 73.6 ms、4090 121.2、3090 204.3） | 实测标定 |
| Prefill 容量 `K^P_i` | `1000 / period(参考长度)`；长度因子走**周期曲线**（chunk 边界两侧取样） | bundle + 实测 |
| Decode 容量 `K^D_j` | `1000 / (参考输出 token × 步时)`，步时按卡标定（5090 1.55×、4090 1.48×、3090 2.26×） | 真机 TPOT 标定 |
| KV 预算 `C_l` | **按配对拆分**：同域 push 0.257 GB/s、跨域 0.11 GB/s + 48 ms RTT（metro 档同比放大 3×） | 真机实测 |
| 请求工作量 `w[i,k]` | `(1 − hit) × clamp(t_k·K^P_i / T_i, 1, 8)` | 观测 + 容量 |

### 层 2 · 计划层（`serving/casr/flow_solver.py`，OR-Tools GLOP）

```text
min  Σ f[i,j,k]·c[i,j,k] + p_ovf·(ΣσP_i + ΣσD_j + ΣσL_l) + 拥塞项
s.t. Σ_{i,j} f = λ_k                                需求守恒
     Σ f·w[i,k] / K^P_i ≤ 1 + σP_i                  Prefill 容量
     Σ f·o_k    / K^D_j ≤ 1 + σD_j                  Decode 容量
     Σ f·b_k    / C_l   ≤ 1 + σL_l                  链路字节预算（按配对）

c[i,j,k] = w_net·(δ_ij + rtt_ij + b_k/BW_ij)         网络
         + w_q·(4Q_j + R_j)/S_j                       排队（Decode）
         + w_pq·queue_fraction(i)·P_i·w[i,k]         排队（Prefill，本轮新增）
         + w_c·(P_i·w[i,k] + D_j·o_k)/1000           算力
         + 1[TTFT_hat > SLO_k]·p_slo                  SLO 软罚
```

* **拥塞项**：容量均分 8 段的分段线性凸价，边际价 `w_u·s·(2t+1)/(2m)` ⇒ 总价 `≈ w_u·s·L²/2K`
  （第一单几乎免费、最后一单值一整次服务时间）。没有它，LP 会把所有类堆在最便宜那台。
* **溢出按容量比例计价**（不是原始单位）——否则 LP 会为微小溢出做大迁移、丢掉已预热的 KV。
* **三条后处理**：低需求类合并（`single_home_below_rps`）、类数上限、**egress 搬运器**
  （链路超预算时整类搬到还有余量的最便宜对，且**目标机必须有算力余量**）。
* 默认控制周期 1 s、计划 TTL 4 s；仿真用 100 ms 以便观察。

### 层 3 · 路由层（`serving/core/router.py`，毫秒级）

1. **按类查计划**，取该类的 Prefill 权重；类不在计划里就按**聚合份额** deficit routing
   （权重按"期望 − 已派发"轮转，避免连续打到同一台）。
2. **Decode 选择**：按 `δ + rtt + 链路占用 + 队列` 选最省的 pair。
3. **存算协同（搬 vs 本地重算）**：逐请求比较
   `transfer = b_k/BW_ij + rtt_ij + 生产者出口积压` 与
   `local = 本节点 Prefill 步时×(t_k/参考长度) + 排队外部性`，取小者。

### 层 4 · 结构层（`serving/casr/evaluator.py` + `lifecycle.py`，秒级）

* 动作：`keep / +P(cold) / +P(warm) / −P`；每次动作都用**同一套目标**重解一次 LP（反事实）。
* 判据：`gain = max(0, H − startup)·(J_base − J_cand − holding) − cost`，超过阈值且过 dwell 才执行；
  `−P` 额外要求"剩余池子不饱和"且候选机空闲。
* 生命周期：`WARMING →（启动完成）→ ACTIVE`；扩容请求**不得踢掉已在运行的机器**，
  运营中的池子是下限，只有显式 `−P` 能缩容。

### 关键参数一览

| 参数 | 值 | 来源 |
|---|---|---|
| `capacity_reference_tokens` / `decode_reference_tokens` | 1024 / 16 | 配置 |
| `utilization_segments` / `utilization_weight` | 8 / 1.0 | 配置 |
| `overflow_penalty` | 10 | 配置（= 真实部署） |
| `ttft_slo_ms` / `slo_penalty` | 1500 / 10（本轮档） | 由 trace 提供、trace 覆盖全局 |
| `kv_bytes_per_token` | **16960（P-15B）**／147456（Qwen3） | 设计闭式／实测 |
| `local_prefill` | `auto`（所有臂一致） | 真机路由器行为 |
| 容器启动 | **20 s（热）/ 45 s（冷）** | 46 次真机重启实测 |

### 3.2 profile 数据收集方式

**工具**：`profiler/`（在 vLLM 里按层挂钩计时的自研 profiler），四类 category × 网格：

| category | 扫描轴 | 用途 |
|---|---|---|
| Dense | tokens（几何网格） | embedding / qkv_proj / o_proj / mlp … |
| per_sequence | 序列数 | lm_head / sampler |
| **Attention** | **(prefill_chunk, kv_prefill) × (n_decode, kv_decode) 4D 网格** | 前缀长度与 batch 结构 |
| MoE | (tokens × activated_experts) | 48 专家 top-3 |

**采集配方**（`tests/run_p15b_profile.sh`）：
`max_num_seqs=128`、`max_num_batched_tokens=2048`、attention `max_kv=16384`、
每点测 3 次；**因为 profiler 每次只建 1 层，P-15B 的三种 block type 必须分三次跑**
（`r0 / r4 / r128`，canonical 名不同以便合并），再 `tests/merge_profile_types.py` 拼成一份 bundle；
多卡并行用 `--shard i/n`（`tests/merge_profile_shards.py` 合并），校验用
`tests/check_profile_bundle.py` / `check_profile_bundle_consistency.py`。

**产出**：`profiler/perf/<HW>/casr/P15B/bf16/tp<N>/{dense,attention,attention_r4,attention_r128,
moe,per_sequence}.csv + meta.yaml`。已采四张卡：

| 卡 | tp 覆盖 | tp1 的 dense / attention / moe 行数 |
|---|---|---:|
| RTX3090 / RTX4090 / RTX5090 | tp1, tp2 | 2 517 / 4 112 / 39 |
| A100 | tp1, tp2, tp4 | 同上 |

（Qwen3-8B / Llama 的 bundle 在同一目录结构下，做对照。）

**这些数在算法里怎么用**：`hw_service.step_cost_ns` 逐层查表 → `rescale_service_times` /
`rescale_capacities` 推出每台的服务时间与容量 → 长度曲线（chunk 边界两侧取样）→
LP 的容量约束与代价项；Decode 侧用真机 TPOT 标定的 `decode_step_scale`。

## 4 模拟实验环境与效果

### 4.1 环境矩阵

| 维度 | 取值 |
|---|---|
| 模型 | **P-15B（类 DSV4，16.56 KB/token）** / Qwen3-8B（传统稠密，147.5 KB/token） |
| fabric | **metro**：跨域 push 0.33 GB/s / 20 ms，同域 0.77 GB/s；**WAN/云边**：0.11 GB/s / 48 ms，同域 0.257 GB/s（**真机实测**） |
| 拓扑 | 3 域，每域 1P+1D（3090 / 4090 / 5090） |
| 负载 | 1250-token 零复用，峰值 **8 / 16 / 32 rps**（高峰 45 / 45 / 30 s）＋ 240 s 长峰值档 |
| SLO | TTFT ≤ 1500 ms、TPOT ≤ 50 ms |
| 臂 | `load`（least-load）/ `cache_aware`（SGLang 语义）/ `kv_aware`（Mooncake 式 producer 出口定价）/ **CASR（LP 计划）**；全部共享同一个 `local_prefill: auto` |

### 4.2 主结果：12 格（CASR 均值 / 最好 SOTA 臂均值，<1 表示 CASR 更快）

| 环境 | 8 rps | 16 rps | 32 rps |
|---|---:|---:|---:|
| P-15B metro | **0.98×** | 1.07× | 1.03× |
| P-15B WAN | **0.93×** | **0.88×** | 1.21× |
| Qwen3 metro | **0.97×** | 1.04× | 1.02× |
| Qwen3 WAN | 1.09× | **0.96×** | **0.99×** |

**6 胜 / 5 平（≤10%）/ 1 负**（那一负是 P-15B WAN @32 rps，但同格 SLO 从 11.9% → 17.8%）。
两条读法：

* `cache_aware` 在 12 格里与 `load` **逐位相同**——本矩阵是零复用长文本池，
  最长前缀匹配恒为 0 ⇒ 退化；这是该路线的下限，不是它的价值。
* `kv_aware` 是最好 SOTA 臂的 4 格**全部出现在跨域或大 KV**处（P-15B WAN 三档 + Qwen3 metro 8 rps）。

### 4.3 消融：收益来自哪里（16 rps）

| 能力 | 对照 | 效果 |
|---|---|---|
| **KV 感知存算协同** | 关掉 `kv_bytes_per_token`（搬运定价 + egress 上限 + 链路预算一起消失） | P-15B metro **+140%**、WAN **+105%**；Qwen3 metro **+68%**、WAN **+40%**；SLO 从 81–100% 掉到 **~7%** |
| **动态扩缩容** | 固定 1 台 / 固定 3 台 | 快启动（0.25 s）时弹性**逐位等于**常开三台；真机 45 s 启动在 45 s 峰值上**零收益**；240 s 峰值 **−30% / +27pt SLO** |
| **排队进目标函数** | `prefill_queue_weight=0` | P-15B metro 3 674 → **2 395**（SLO 59.5% → 100%） |

**启动时间扫描**（P-15B WAN，16 rps / 45 s 峰值）：启动 0.25 s → 2 831 ms（100% SLO）；
**20 s → 4 129 ms（55.0%）**；45 s → 4 909 ms（33.9%）；static 1 台 = 5 058（33.8%）。
收益由 **boot/peak 比**决定：0.67→28%、0.44→42%、0.083→89%。

### 4.4 让结论成立的四步口径修正（否则前面所有对比都不成立）

1. **对照臂与 CASR 统一价格模型**（原先只有 CASR 建 `pair_costs`，基线退回按 Qwen3 标定的真机常数
   ⇒ 在 P-15B 上把搬运高估 ~9 倍，基线全走本地、CASR 全走搬运）；
2. **egress 搬运器要看目标机算力**（原先为修链路把 547/740 请求压到一张 4090）；
3. **Prefill 排队进目标函数**（原先装满 100% 的 Prefill 与空闲一样便宜）；
4. **KV 预算按配对拆分**（原先同域与跨域共用 0.11 GB/s，把 5090 卡在 5.19 req/s 而它实测 8.3）。

（另有 3 处 lifecycle bug：WARMING 被下一次结构覆盖丢掉、`+P` 覆盖不含刚上线的机器、
`scale_on_demand=false` 时池子被缩回 `min_active`。）

### 4.5 结论与不足

* **结论**：在"跨域 + 长 prompt + 压缩 KV"这一象限，CASR 相对最好的 SOTA 路由臂
  **快 12%（16 rps）**、**SLO 高 19.3pt**；KV 感知与结构弹性是它独有的两个增益源
  （路由类方法不规划类级容量、不做结构动作）。
* **不足**：① 32 rps 饱和档均值仍略输（SLO 反超）；② 一半收益来自把口径修对而不是策略本身；
  ③ 排队定价是线性启发式；④ 弹性强依赖启动与峰值长度；⑤ SLO 驱动的 P:D 比例搜索、
  实例迁移、快速冷启动三类 SOTA 还没有对照臂。
