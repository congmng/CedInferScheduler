# 混合注意力模型：profile、模拟与调度实验总结（2026-09-17）

这是一份**汇总**。细节分成两篇：

* 建模与 profile：[混合注意力模型profile.md](混合注意力模型profile.md)
* 调度实验与结论：[混合注意力模型的调度实验.md](混合注意力模型的调度实验.md)

## 0. 一句话结论

换用**真**混合注意力模型（Zamba2-1.2B）之后，KV 没有被"省掉一个数量级"，
但 P/D 的 KV 推送通道成了唯一绑定资源；生产级 least-loaded 路由的打分函数
对这种负载**结构性失效**（735 个请求全钉在一台 Prefill 上，TTFT 419 s），
而按 KV 字节预算规划 + 结构弹性的 CASR 把同一场景压到 43 s。

## 2. Profile：真混合模型的两份 bundle

模型：`Zyphra/Zamba2-1.2B`，38 层 = 32 层 Mamba + 6 层 Mamba&共享注意力
（`layers_block_type` 在第 5/11/17/23/29/35 层），只有这 6 层带 KV。

| hardware | dense | per_sequence | attention | decode 步 | prefill@1024 |
|---|---:|---:|---:|---:|---:|
| RTX4090 | 1824 | 40 | 860 | 4.86 ms | 25.5 ms |
| RTX5090 | 1824 | 40 | 861 | 3.04 ms | 19.5 ms |

分层成本（4090，tokens=1 / ≈1024）：`mamba_mixer` 87.5 / 453.3 µs、
`qkv_proj` 107.6 / 650.6 µs、`o_proj` 19.7 / 109.8 µs、`gate_up_proj`
38.0 / 238.3 µs、`shared_linear` 10.7 / 58.8 µs。

**Mamba 层不是免费的**：decode 步 87 µs 与同层 `qkv_proj` 同量级，prefill
随 token 线性增长。混合模型省的是 KV 显存/搬运，不是算力。

### 多卡并行采集（`--shard I/N`）

一个 shot 的固定开销是 ~3.5 s 的 `torch.profiler` 记账，**与形状无关**
（MNBT=32/MSQ=2 的 20 个 dense shot 也是 3.5 s/个），所以网格只能靠少发或
并行来缩短。`--shard i/N` 保留组合网格里位置 `≡ i (mod N)` 的 shot，在两个
进程/两张卡上各跑一半后合并：

```bash
python3 tests/merge_profile_shards.py --out-root profiler/perf \
    --hardware RTX5090 --model Zyphra/Zamba2-1.2B --variant bf16 --tp 1 \
    /out/card0 /out/card1
```

5090 上 **861 个 attention shot 约 37 分钟**（单卡约 4 小时）。合并脚本会断言
分片两两不交、覆盖完整——重叠或漏采都会产出"能加载但悄悄错"的 bundle。

## 3. 模拟器为混合模型补的能力

原来 `trace_generator` 只会把**一个** `sequence` 模板重复 `num_hidden_layers`
次，对 Zamba2 等于让 38 层都跑完整注意力块（注意力算 38 次而不是 6 次）。

* `profiler/models/zamba2.yaml` 新增 `layer_types`：`mamba` 层走
  `[mamba_norm, mamba_mixer]`，`hybrid` 层走完整的共享注意力 + Mamba 流水线；
  profiler 的 `Architecture` schema 同步加字段并在 load 时校验。
* `trace_generator` 按模型 config 的 `layers_block_type[i]` 选流水线；
  `kv_geometry` 支持 `full_layer_indices`（KV 层是**交错**的，不是前 N 层）。
* `memory_model` 认识 Zamba2 专有层名（`mamba_norm` / `attention_norm` /
  `mamba_mixer` / `shared_linear`），接受 `attention_head_dim` 与
  `attention_hidden_size`（注意力通路 4096 宽而 hidden 只有 2048，弄错
  qkv 权重会差一倍）。
* `hw_service.step_cost_ns`（控制面定价那一步）走同一份逐层流水线，否则
  "计划按 38 个注意力块估容量、时序按 6 个跑"，同一台机器两个数。

## 4. 实验结果

所有表都是 CNN/DailyMail 风格的真实 prompt、8 rps × 90 s 峰值、静态池 2 个
Prefill（spare 用 `inactive_instances` 关掉，见第 7 节），单位秒。

原始 `summary.json` 归档在 [`docs/arena-summaries/`](arena-summaries/)：

| 文件 | 环境 |
|---|---|
| `zamba2-homo4090-1250tok-8rps.json` | 同构 6×4090（第 4.1 节） |
| `zamba2-hetero5090x2-4090x4-1250tok-8rps.json` | 硬件异构（第 4.2 节） |
| `zamba2-homo4090-pack3-3750tok-8rps.json` | 长 prompt（第 4.3 节） |
| `zamba2-homo4090-hotprefix-lan.json` / `-wan.json` | 热点前缀（第 4.4 节） |
| `qwen3-8b-homo4090-1250tok-8rps.json` / `qwen3-8b-kv-aware-only.json` | 全注意力对照 |

### 4.1 同构 6×RTX4090，1250-token

| arm | Qwen3-8B（全注意力） | Zamba2（真混合） |
|---|---:|---:|
| load | 210.5 | 418.9（p95 803.9） |
| cache_aware | 210.5 | 418.9 |
| kv_aware | 227.3 | **174.7** |
| rr | 200.6 | 163.7 |
| casr_lp | 85.0 | 65.3 |
| casr_full | 54.9 | **43.3**（p95 89.1） |

### 4.2 硬件异构 5090×2 + 4090×4，1250-token

| arm | E2E 均值 | p95 | TTFT p50 | span | Prefill 落点 |
|---|---:|---:|---:|---:|---|
| load | 403.0 | 772.0 | 402.7 | 920.4 | 735 → 实例 0 |
| cache_aware | 403.0 | 772.0 | 402.7 | 920.4 | 同上 |
| kv_aware | 179.7 | 363.6 | 176.7 | 488.5 | 372 / 363 |
| rr | 163.7 | 312.5 | 163.2 | 436.8 | 368 / 367 |
| casr_lp | 65.3 | 124.4 | 65.2 | 239.7 | 370 / 365 |
| casr_full | **45.2** | **93.8** | 45.4 | 205.5 | 314/311/91/19 |

TPOT p50 从 3.3 ms 降到 **2.2 ms**：CASR 的 pair 代价把 Decode 更多放到 5090 域，
基线对此完全不敏感。

### 4.3 长 prompt（`--pack 3`，3750 token，KV 402 MB/请求）

| arm | E2E 均值 | p95 | span |
|---|---:|---:|---:|
| load | 293.5 | 570.6 | 691.8 |
| cache_aware | 293.5 | 570.6 | 691.8 |
| rr | 246.1 | 472.6 | 562.2 |
| casr_lp | 119.2 | 229.5 | 304.4 |
| casr_full | **93.6** | **194.2** | 266.8 |

修复前这一档 `casr_lp` 根本跑不完（见第 5 节）。

### 4.4 热点前缀（2×1024 共享头，1250-token）

| arm | 局域网（0.11 GB/s / 48 ms） | 广域（0.05 GB/s / 80 ms） |
|---|---:|---:|
| load | 104.3 s | 410.2 s |
| cache_aware | 104.3 s | 410.2 s |
| rr | 2.74 s | 65.4 s |
| **casr_lp / casr_full** | **0.413 s** | **0.413 s（逐位不变）** |

三个 arm 的 `npu_hit_tokens` 都 ≈1021（命中率 81.7%）、`pd_kv_bytes` 都是
157 MB/请求——**缓存机制在所有 arm 下都在工作，差别只在放置**。链路变慢
4–24× 时 CASR 一个数位都不变，因为它把跨域字节代价记进了边权。

## 5. 修掉的缺陷：P/D 交接缓冲区的活锁

Decode 侧交接缓冲区原本按**批次**计费、按**请求**释放。3750-token 的 prompt
在 2048 的 token budget 下要分 2 个 chunk 构建，于是被计费两次、交接一次，
每个请求漏 375 MB。32 GB 缓冲在约 85 个请求后填满，两个 Prefill 停在
`Running 0, Waiting 104, 0.0 tokens/s`，模拟时钟空转到 **3973 s** 而 205 个
请求永远排不出去。

`SIM_ADMISSION_DEBUG=1` 让闸门自己报出名字：

```
[admission-stall] gate=pd-staging-buffer: decode=1 staged=31.88GB need=0.375GB buffer=32.00GB
```

改成准入时按请求计一次、按**当初计费的实例**释放后，同一跑法 **91 s 跑完**
（模拟 168 s）。`tests/test_pd_staging_budget.py` 钉住两条不变量；把旧代码放
回去，测试会把 589 MB 报成 1.18 GB 而失败。

**影响面**：修复前所有长 prompt（多 chunk）实验的结论都不可信；同时它也解释了
上一轮 `alignment_matrix` 回归里一个卡了 10 小时的 arm。

## 6. 数据集与算法该怎样设置

### 6.1 数据集的三个必要条件

1. **KV 必须是绑定资源**：本环境 Prefill 出口只有 0.26 GB/s，1250-token 请求
   要推 157 MB ⇒ **~1.6 req/s/实例**，而算力是 ~39 req/s。要更长就
   `tests/make_phased_trace.py --pack N`（1250→3750 token）。
2. **必须有前缀复用**。CNN/DailyMail / Dolly 是零复用数据集，`cache_aware`
   与 `load` **逐字节相同**（第 3 节表里两行完全一致就是证据），用它评价缓存
   感知路由是错的。要评价缓存感知就用 ShareGPT 多轮或
   `make_hot_prefix_trace.py`。
3. **峰值要持续超过静态池的 KV 通道预算**（不只是算力预算），且维持足够长
   （容器启动 45 s 要摊平）。

### 6.2 算法侧的三条

1. **打分必须用绑定资源**。`(inflight+1)/算力容量` 形式的负载均衡在 KV 主导
   负载上会退化：算力越快、KV 越重，`inflight` 归零越快、打分越平，最后
   实例 id 成了唯一区分。
2. **缓存亲和要跟通道预算一起算**。命中前缀降低 Prefill 计算量，但在 P/D
   解耦下**不降低要推送的 KV 字节**。
3. **结构弹性的收益 = 新增推送通道**，不是新增算力。算力过剩时它会被负载
   均衡完全掩盖——这正是此前"结构弹性看不出收益"的原因。

## 7. 环境设计：四个正交旋钮

| 旋钮 | 用法 | 检验什么 |
|---|---|---|
| 硬件域 | `--domains 5090,5090,4090,4090,4090,4090` | 算力/显存异构 |
| 跨域链路 | `--cross-gbps 0.05 --cross-rtt-ms 80` | 广域下的放置 |
| 池深度 | `--min-active`（配合 `inactive_instances`） | 弹性头寸与基线公平性 |
| KV 出口预算 | `--kv-egress-gbps` | 通道主导程度 |

**修掉的一处对比不公平**：`--min-active` 原来只约束 CASR，基线可以在全部 6 个
Prefill 上路由，等于白拿弹性。改成把 spare 写进 `inactive_instances`（留在拓扑、
对所有策略不可用、控制器仍可拉起）后，热点前缀档的 rr 从 174 ms 变成 2.74 s
——**16× 就是这处不公平的量级**。

## 8. SOTA 对照

映射表见 [实验数据集与对比基线说明.md](实验数据集与对比基线说明.md) 第 3 节
（`rr` ↔ 经典轮询；`load` ↔ vLLM production-stack / Llumnix 的队列语义；
`cache_aware` ↔ SGLang Router / prefix-aware router）。

本轮新增 **`kv_aware`**：同族 least-loaded，只把打分换成"这次 push 要排多久
（已在生产者出口上的字节 + 本次串行化）与算力等待取 `max`"，即 Mooncake /
LMCache 那类按 KV 定价 pair 的路由在 P 侧的形态。它**没有** CASR 的亲和计划、
LP 与结构决策。

结论分三层：

1. 换指标就能拿 **2.24×**（403.0 → 179.7 s）——原来的 SOTA 路由不是被更强的
   规划器打败，是被一个看错资源的打分函数打败；
2. 但它只和 `rr` 打平（179.7 vs 163.7）——只摊平不按字节预算规划 ≈ 瞎转；
3. CASR 再拿 **2.75×**（`casr_full` 对 `kv_aware` 是 **4.0×**），弹性再叠
   **1.44×**——这两段才是要主张的部分。

而在 Qwen3-8B 上 `kv_aware` 反而比 `load` 差 8%（227.3 vs 210.5 s），说明
**指标退化越严重、改回来才越有用**，这恰好是混合注意力模型的方向。

## 11. 遗留问题

* 3750-token 档的 `kv_aware` 与 1250-token 档的 Qwen 六臂表还差两格；
* 真混合只有 4090 与 5090 两份 bundle，3090 / A100 仍缺（要扩容异构维度就得
  继续多卡并行采集）；
* `load` 基线按"绑定资源"重写后的版本需要在真机上用同一 trace 验证一次，
  再决定是否作为新的 SOTA 基线；
* 混合层内 MLP 的发射顺序比真实前向晚两格、权重按 6 个独立 hybrid 层求和
  （比真实 1.215B 偏大约 1.66B），都属于已在 profile 文档登记的近似。
