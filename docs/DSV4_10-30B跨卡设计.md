# DSV4 风格模型：5–30B 规模 + 3090/4090/5090/A100 全卡型可行（2026-09-18）

> 目标：自研一个 **十几 B～几十 B** 的 DSV4 风格模型，并且要在
> **RTX 3090（sm86）/ 4090（sm89）/ 5090（sm120）/ A100（sm80）** 上都能跑起来。
> （文件名仍是旧的 `10-30B`；正文实际给了四档 —— **P-5B / P-15B（主推）/
> P-29B**，外加一个 0.9B 的冒烟档。）
>
> 上一轮我已经实测过官方 vLLM 路径在小配置上的行为（见
> [DSV4小型模型设计.md](DSV4小型模型设计.md)）。本文把规模提到十几 B 之后
> 重新做一遍可行性，结论**比小模型那次更硬**：有两条硬约束需要先做工程决定。

## 0. 结论先行

1. **官方 vLLM 的 DSV4 路径不可能在四类卡上都跑**，原因不是规模，是 kernel：
   * **mHC（超连接）只有 `sm90/sm100/sm120` 的 deep_gemm kernel**
     → **A100(80)、3090(86)、4090(89) 全部不行**（实测报
     `deepgemm … hyperconnection.hpp: Unsupported architecture`）；
   * NVIDIA 路径的 **o_proj 是 fp8 DeepGEMM 专用**（`ops/o_proj.py:64`
     无条件读 `weight_scale_inv`），**这条 fp8 GEMM 路径在 sm80/sm86 上不存在**
     （实测 `torch._scaled_mm`：`only supported on CUDA devices with compute
     capability >= 9.0 or 8.9`；A100 硬件其实有 FP8 tensor core，但 PyTorch/cuBLAS
     这条路径不给 sm80，3090 则是连硬件都没有），
     纯 bf16 也起不来（实测 `AttributeError: 'ColumnParallelLinear' object has
     no attribute 'weight_scale_inv'`）。
2. **但代码库里存在可移植的参考实现**：ROCm 路径（`models/deepseek_v4/amd/`）
   用 **Triton** 实现了同一套 sparse-MLA/SWA/top-k 逻辑，且 mHC 在那边是
   "aiter / tilelang / **triton** / **torch**" 多后端分派。也就是说
   **"跨卡版 DSV4" 的技术路径是清楚的：砍掉 mHC + 用 Triton 写注意力**，
   而不是等官方支持。
3. **显存账决定了规模上限**（详见 §3）：想在 **3090/4090 单卡 bf16** 上跑，
   总参必须 **≤ ~8B（推荐 P-5B，权重 10.3 GB）**；**P-15B（权重 29.7 GB bf16）
   单卡放不下任何 24/32GB 卡**，只能 **fp8 权重（14.9 GB）** 或
   **同机 2 卡 TP**；A100 80GB 单卡可以容纳到 **P-29B bf16（59.2 GB）**。
4. **mHC 已决定砍掉**（2026-09-18）：砍它几乎不省参数与算力（官方 V4-Flash 上
   仅 33.8M 参数 / 0.3% 每 token FLOPs），换来的是**摆脱 sm90+ kernel 限制**；
   代价是训练稳定性，用 SwiGLU clamping + anticipatory routing + 常规手段替代（§2.1）。
5. **推荐配置**：**P-15B（总参 14.87B / 激活 2.15B，MoE 48 experts top-3，
   28 层）**；KV **16.56 KB/token（bf16）/ 8.28 KB（fp8）**，比 Qwen3-8B 的
   147.5 KB/token 小 8.9×。权重 **29.73 GB（bf16）/ 14.87 GB（fp8）**，
   所以**建议 bf16 + 同机 TP=2**（14.9 GB/卡，可移植、无 fp8 kernel 依赖）——
   5090 32GB 上 bf16 单卡也只剩 ~2 GB 给 KV，不实用。
   **四档（P-5B / P-15B / P-29B / 冒烟档）的完整数字见 §3，全部由参考实现报出。**
6. **主线测试对象改为自研 P-15B**（2026-09-18 定，见 §0.1）：后续实验以
   **我们自己改的 P-15B** 为准，Qwen3-8B 的结果降级为"KV 大档"对照。

### 0.1 当前计划：主线测试改用自研 P-15B（2026-09-18 定）

**决定**：接下来的调度实验**主要基于自研 P-15B**，而不是继续拿 Qwen3-8B 当
测试对象。Qwen3-8B 那一整套结果**不废弃**，降级为 **KV 大档对照**。

**为什么必须换**：现在所有调度结论的前提都是"**KV 是绑定资源**"——
Qwen3-8B 全注意力 GQA 实测 `147.5 KB/token`。而"存算协同在什么时候还值钱"
这个问题的答案，恰恰取决于 KV 有多大。用一个 KV 大 9 倍的模型去论证
"KV 不再是大头时该怎么调度"，逻辑上是不成立的。P-15B 把 KV 压到
**16.56 KB/token（bf16）/ 8.28（fp8）**，比 Qwen3-8B 小 **8.9×**，
比我们已有的压缩 KV 对照档（MLA `31.1 KB/token`）再小 **1.9×**，
正好是这条自变量轴的下一档。

**已经就位的东西**（不需要训练）：

| 组件 | 位置 | 状态 |
|---|---|---|
| P-15B 的 config 结构 | `configs/model/DeepSeek/DSV4-P15B-draft.json` | ✅ 28 层，`[0,0]+[4,128]×12+[0,0]` |
| 逐层压缩比 KV 记账 | `serving/core/memory_model.py` 的 `kv_layout` | ✅ `get_kv` / `pd_kv_bytes` / `full_cluster_kv_bytes_per_token` 三个入口都分流 |
| 两条代码路径互校 | `tests/test_dsv4_kv_layout.py` | ✅ 6 项，与 `design/dsv4_ref` 的估算器逐层对齐 |
| 跨卡可跑 | `design/dsv4_ref/verify.py` | ✅ 四类卡 fp32 指纹一致到 1e-6（§3.2） |
| 两个自研算子 | `design/dsv4_ref/triton_*.py` | ✅ 四类卡跑通（§2.3.1） |

> ⚠️ **这一阶段能回答什么、不能回答什么**：模型还不存在，draft config 里写的是
> `profile_model: Qwen/Qwen3-8B`——**算力借用 Qwen3-8B 的 kernel profile，
> 只有 KV 几何来自 DSV4 设计**（和仓库里已有的 `Qwen/Qwen3-8B-hybrid` 是同一套
> 用法）。所以用它跑出来的结论**只在"KV 缩小后调度还值多少"这个维度可信**；
> 绝对延迟、吞吐上限都不可信。完整口径见 §3.3。
>
> ⚠️ **KV 数字用哪一个，必须先定**：模拟器里 P-15B 收的是**解析值
> 16.56 KB/token**（设计下界）；而 vLLM 0.29 对同一套层结构实测要
> **97.6 KB/token**（§3.1），其中可自己修回来的部分是 **1.40×**（§3.1.2）。
> 所以这一轮实验要么明确声明"用一个理想 serving 栈的 KV 几何"，
> 要么把解析值与实测值**各跑一遍当自变量**——不能含糊过去。

**两步走**：

1. **模拟器（现在就能做）**：用 P-15B 的 config 结构在 4 个域上重跑
   CASR / 基线对照。判据：给出"KV 从 147.5 → 16.56 KB/token 后，
   CASR 相对 SOTA 的优势收敛多少"的曲线。已有 `31.1 KB` 档
   （对 SOTA `−23.0%`）作为中间点，P-15B 是它的下一档。
2. **真机（要先有模型）**：P-15B 的部署形态是 **bf16 + 同机 TP=2**
   （14.87 GB/卡；单卡 24GB 放不下，见 §4.1）。四类卡"跑得对"已验证，
   "跑得快"还没做（§2.3 的算子目前只到正确性）。

## 1. 三条硬约束（全部实测，非推断）

| # | 约束 | 证据 | 影响 |
|---|---|---|---|
| 1 | mHC 只支持 Hopper/Blackwell | 4090 报 `deepgemm hyperconnection.hpp:59 Unsupported architecture`；镜像里只编了 `sm90/sm100/sm120` 三套 kernel | **A100/3090/4090 无法运行官方 DSV4 模型类** |
| 2 | NVIDIA 路径 fp8-first | `ops/o_proj.py` 无条件调用 `fused_inv_rope_fp8_quant` + `fp8_einsum`，读 `wo_a.weight_scale(_inv)` | 即使修好 mHC，**Ampere/Ada 的 fp8 GEMM 也是问题** |
| 3 | KV cache 必须 fp8 | 4090 报 `fp8_ds_mla layout only supports fp8 kv-cache, got auto` | KV **存储**用 fp8 是可以的（任何卡都能存字节），但 **attention kernel 要能解** fp8 → 需要我们的实现 |

**已经跑通的唯一组合**（上一轮实测）：**5090（sm120）** + `kv_cache_dtype=fp8`
+ 官方 fp8 `quantization_config` + `hc_mult=4`（`(2+hc_mult)·hc_mult` 需被 8 整除）
+ 完整 12 层混合 ratio 配置 → `FULL12 BOOTED`（blocks 35634, block 4）。

**可移植参考**：`amd/rocm.py` 里是 Triton 版的 sparse gather / SWA / top-k
打包（`_pack_global_topk_ragged_kernel` 等），`amd/dspark.py:129` 注释写明
mHC head op 在 ROCm 上走 "aiter / tilelang / **triton** / **torch**" 分派。
Triton 能编译到 sm80/86/89/120 —— **这条路可以把四类卡统一**。

## 2. 可移植设计：保留什么、砍什么

| 组件 | 与"KV 压缩"的关系 | 跨卡可移植性 | 决定 |
|---|---|---|---|
| **CSA/HCA 混合压缩**（`compress_ratios` 4/128） | **就是压缩本身** | 纯数学（每 m 个 token 生成一条 compressor 输出） | **必留** |
| **MLA latent**（head_dim + 64 RoPE） | 全层的 base 成本 | 纯数学 | **必留** |
| **稀疏 indexer**（top-k 选择） | 让 CSA 在长上下文可算 | 需要 top-k/pack kernel | 留，用 Triton |
| sliding window 128 + 未压缩尾部缓冲 | 局部保真 | 纯数学 | 保留 |
| **mHC 超连接** | **与 KV 无关**（训练稳定性） | ❌ 只有 sm90+ kernel（torch 后端存在但 NVIDIA 路径硬编码 tilelang） | **已决定砍掉**（见 §2.1：标准 pre-norm 残差） |
| fp8 权重 / fp8 KV | 省显存 | sm80/sm86 无 fp8 GEMM（实测 `torch._scaled_mm` 拒绝 <9.0 且 <8.9） | **默认 bf16**，fp8 只在 5090/4090（sm89+）或"自己写 dequant 加载"时用 |
| MoE + hash layers | 省算力（非省显存） | 需要 EP 通信 | 保留 MoE，**砍掉 hash 层**（简化） |

> **砍 mHC 的代价**：论文把它列为三项升级之一，作用是"跨层信号传播稳定性"。
> 我们之前跑通的唯一配置恰恰依赖它（`hc_mult=4`）。砍掉意味着：
> ① 摆脱 sm90+ 限制（这是四类卡要求的必需条件）；
> ② 但要自己承担长上下文训练稳定性——建议先用更保守的初始化/LR 与 warmup，
> 并把"是否加回 mHC（只在 5090 上做对照）"作为一个实验项而不是前提。
> **这是本方案最大的设计取舍，需要在评审时明确。**

### 2.1 决定：砍掉 mHC（2026-09-18 定）

**决定**：自研模型**不实现 mHC**，用标准 pre-norm 残差
（`x = x + Attn(RMSNorm(x))`，`x = x + FFN_or_MoE(RMSNorm(x))`）。
config 里的 `hc_mult / hc_eps / hc_sinkhorn_iters` 一并去掉（保留注释说明来源）。

**代价的量化（算过，不是估的）**：以官方 V4-Flash 为例，
`hc_mult=4`、`hidden=4096` → `mix_hc=(2+4)·4=24`、`hc_dim=4·4096=16384`，
每个 mHC 模块 0.39M 参数、每层 2 个 → **全程 33.8M 参数**，是总参 284B 的
**0.012%**、激活参数 13B 的 **0.26%**；每 token 的混合 GEMM 约
**0.07 GFLOPs**，而 13B 激活模型每 token 约 26 GFLOPs → **占比 0.3%**。

> **所以砍 mHC 几乎不省参数、不省算力，它换来的是"能在四类卡上跑"，
> 代价只有训练稳定性。** 这是一个纯粹的可移植性权衡。

**用它换掉稳定性的方案（保持论文其余两项 + 常规手段）**：

| 手段 | 来源 | 我们的用法 |
|---|---|---|
| **SwiGLU clamping** | 论文 §4.2.3 防训练不稳的两项之一；官方 config 已有 `swiglu_limit: 10.0` | 保留（clamp 到 10） |
| **Anticipatory Routing** | 同上（防止路由塌缩） | 保留 |
| 常规手段 | —— | QK-norm、pre-norm、保守初始化、LR warmup、**先短上下文再逐步扩** |
| 可选对照 | —— | 只在 5090 上做"有 mHC"的对照，**不作为主设计的前提** |

**工程后果**：

1. **sm90+ 的依赖消失**——mHC 的 tilelang/deep_gemm hyperconnection kernel 不再被调用，
   A100/3090/4090 的这一条阻塞解除。
2. 但**可移植性还没完成**：剩下的两条是
   **fp8 o_proj（DeepGEMM，且缺 sm89 kernel）** 与 **fp8 KV + sparse MLA kernel**，
   都需要我们自己的 bf16/Triton 版本（§2.2）。
3. 如果将来要**跑官方 V4 checkpoint 做对照**，不必删代码：仓库里
   `vllm/model_executor/kernels/mhc/{torch,triton,tilelang,aiter}.py` 提供了
   `mhc_pre_torch` / `mhc_post_torch`，且 `MHCFusedPostPreOp.forward_native`
   就是 `post ∘ pre` 的组合——把 `nvidia/model.py` 里 4 处 `*_tilelang`
   调用换成它们即可（机械替换，不需要写新算子）。

### 2.2 砍完 mHC 之后剩下的两条可移植性缺口

| 缺口 | 现状（实测） | 可移植替代 |
|---|---|---|
| **o_proj（输出 LoRA）** | NVIDIA 路径无条件走 `deep_gemm_fp8_o_proj`：`fused_inv_rope_fp8_quant` + `fp8_einsum`，读 `weight_scale_inv`；Ampere/Ada 无 FP8 tensor core | 用 bf16 写等价实现：inv-RoPE → `n_heads` 按 `o_groups` 分组 einsum（`bhr,hdr->bhd`）→ `wo_b`；纯 torch/Triton 即可 |
| **attention 主算子** | 官方 CUDA 后端（FlashMLA / FlashInfer-sparse）面向 Hopper/Blackwell | 参考 **ROCm 路径的 Triton 实现**（`amd/rocm.py` 的 sparse gather / SWA / top-k 打包）重写到 CUDA Triton；支持 sm80/86/89/120 |

**结论**：`mHC` 砍掉之后，"四类卡可跑"从"被 kernel 架构卡死"变成
**"两条算子需要一个 bf16/Triton 的可移植版本"**——这是可以排期的工程量，
而不是方向性问题。

### 2.3 决定：缺的部分我们自己编（2026-09-18 定）

不再把"官方 kernel 不支持我们的卡"当成约束，而是**把缺的算子自己写、自己编**。
先确认工具链够用——**镜像 `vllm/vllm-openai:casr029` 里已经带全了**：

```text
nvcc:    CUDA 13.0 (V13.0.88)
arch:    compute_75 80 86 87 88 89 90 100 110 103 120 121     ← 四类卡全覆盖
triton:  3.7.1                                                ← JIT 可直达 sm80/86/89/120
```

也就是说 `3090(sm86) / 4090(sm89) / 5090(sm120) / A100(sm80)` **一次编译就能全覆盖**
（fatbin 里带 `80;86;89;120` 四段），不需要为每张卡改工具链。

要自己编的东西，按"省下的字节 / 工作量"排序：

| # | 要做的 | 为什么必须自己做 | 手段 |
|---|---|---|---|
| 1 | **compressor 状态缓存改 bf16 + 传对 `tokens_per_state`** | 现在它是 **fp32** 且 `tokens_per_state` 默认 1（§3.1.1 实测），一层白吃 4–8 KB/token；§3.1.2 实测只改 spec 能拿回 **1.40×** 容量 | 改 Python 侧 KV spec + **同步改算子**（block_size 一改，CuTe DSL 的 sparse-attn 就报 `only supports block_size=8`） |
| 2 | **o_proj（inv-RoPE + 分组 einsum + wo_b）** | NVIDIA 路径无条件走 fp8 DeepGEMM，A100/3090 没有 FP8 tensor core | bf16 版 Triton kernel，`triton.jit` 直接编到 sm80/86/89 |
| 3 | **sparse-MLA / SWA / top-k 打包** | 官方是 FlashMLA / FlashInfer-sparse，面向 Hopper+ | 从 `models/deepseek_v4/amd/rocm.py` 的 Triton 版移植到 CUDA Triton |
| 4 | **fp8 权重的加载期 dequant** | A100(sm80)/3090(sm86) 没有 FP8 算力；KV 用 fp8 字节存没问题，但要能解 | dequant → bf16 GEMM；省显存不省算力，是"装得下"的关键 |
| 5 | **（可选）mHC 的 torch/triton 后端** | 已决定砍掉（§2.1），但库里有 `kernels/mhc/{torch,triton}.py` | 若将来要加回，接分派即可，不需要 Hopper kernel |

**判据**（一条即可判定第 2、3 项完成）：在 **3090（sm86）与 4090（sm89）**上
跑通一个最小 MLA+CSA 层的前向，且与 §3.2 的 fp32 指纹在 1e-6 内一致。

#### 2.3.1 先编一个真的试试：sparse-state 注意力已经四卡跑通

光说"工具链够用"不算数。缺的三件里，**只有"对稀疏选中的压缩状态做注意力"
是官方只用 Hopper+ kernel（FlashMLA / FlashInfer-sparse）实现的**，其余是普通
matmul/norm/rope。所以先把它写了：`design/dsv4_ref/triton_sparse_attn.py`，
一个 `triton.jit` kernel，一个 program 负责一个 `(query, head)`，对 top-k 选中的
状态做 online softmax（`T=128, H=20, D=512, K=64, BLOCK_K=64, bf16`）：

| 卡 | 架构 | triton | kernel 误差(vs fp64) | 纯 torch bf16 误差 |
|---|---|---:|---:|---:|
| A100-SXM4-40GB | sm80 | 3.3.1 | **0.0039** | 0.0194 |
| RTX 3090 | sm86 | 3.7.1 | **0.0039** | 0.0192 |
| RTX 4090 | sm89 | 3.7.1 | 0.0078 | 0.0194 |
| RTX 5090 | sm120 | 3.7.1 | 0.0074 | 0.0194 |

**同一份 Triton 源码，四种架构都编得出来、跑得对**，而且 kernel 因为用 fp32
累加，误差比纯 torch 的 bf16 路径还小 2.5–5×。
这说明"缺的算子自己写自己编"这条路是通的。

第二个算子是 **o_proj 的 inv-RoPE 那一段**：官方把它折进 fp8 DeepGEMM
（`fused_inv_rope_fp8_quant` + `fp8_einsum`），A100/3090 跑不了；自己写的时候
最容易出的错是**"只去量化、忘了反旋转"**（数字会看着合理但全错），所以
`design/dsv4_ref/triton_o_proj.py` 主要验的是 **`inv_rope(rope(x)) == x` 的往返**，
再验组合后的 `inv-RoPE → 分组 wo_a → wo_b`：

| 卡 | 架构 | triton | 往返误差(bf16) | o_proj 误差(vs torch) |
|---|---|---:|---:|---:|
| A100-SXM4-40GB | sm80 | 3.3.1 | 2.9e-5 | 5e-6 |
| RTX 3090 | sm86 | 3.7.1 | 2.3e-5 | 6e-6 |
| RTX 4090 | sm89 | 3.7.1 | 2.8e-5 | 5e-6 |
| RTX 5090 | sm120 | 3.7.1 | 3.0e-5 | 6e-6 |

分组 matmul 与 `wo_b` 用的是 stock torch（四类卡上本来就可用），**自己写的只有
旋转那一段**——这里不把 stock 算子包装成"自研 kernel"。

**§2.3 第 2、3 条的工具链风险到此清空**：两个算子都在四类卡上跑通并对过数值。
剩下的是把它们接成完整一层、再对齐 §3.2 的指纹（§7 第 2 步的判据）。

## 3. 规模与显存：四类卡能装多大

下表**由参考实现直接报出**，不是手算：
`design/dsv4_ref/verify.py --config <name> --summary-only`（可复现，
`REF_CONFIGS` 里现在有 4 档）。结构一律是 MLA latent + indexer + compressor
+ MoE，词表 64k，compress ratio 走官方交替模式（`[0,0]+[4,128]…+[0]`）。

> 唯一做过模块树逐项对账的是 `small`：**模块树 831,341,312 vs 估算 877,000,000
> → 估算高 5.2%**。差在哪已经查清（不是猜的）：
> ① 估算器给 **每一层**都计一个 `index_n_heads` 头的 indexer（12×2.62M=31.5M），
> 而模块里 indexer 是**单头**且只存在于压缩层（实测合计 1.21M）→ **高估 30.2M**；
> ② 估算器**没有 `kv_state_proj`**（compress state → `head_dim` 那个投影），
> 模块里有 3.67M → **低估**；③ MoE 估算比模块高 1.57M/层 → 高估 18.9M。
> 三项相抵就是 +5.2%。所以**上表的绝对数是 ±5% 量级**，用来分档和做容量规划
> 可以，不要当小数点后三位的精度用。
>
> 早期文档里的"13.5B / 激活 1.66B"是**没接参考实现时的粗估**，已被
> 14.866B / 2.145B 取代；`P-13B` 这个叫法在本文件里统一改成 `P-15B`。

**关键推论**：

* 若坚持 **bf16 + 单卡**，上限是 **P-5B**（10.26 GB 权重）；**P-15B 的 29.73 GB
  在四类卡上单卡 bf16 都放不下**（5090 32GB 只剩 ~2.3 GB，KV 一下就满）。
* **P-15B 单卡必须二选一**：**fp8 权重**（14.87 GB，依赖 fp8 kernel）或
  **同机 2 卡 TP**（14.87 GB/卡，bf16，无 fp8 依赖）。
  **我建议后者**——因为我们的目标是跨卡可移植，而 bf16 在四类卡上都是稳的；
  而且 3090/4090 本来没有 fp8 GEMM。我们的机器是 3090×2 / 4090×4 / 5090×4，
  **TP=2 现成可用**。
* P-29B（59.22 GB bf16）只能在 **A100 单卡**上稳；多卡要 **4090×4 / 5090×4**
  （bf16 每卡 14.8 GB），**不是 2 卡**。

**同上下文下我们比它小 8.9 倍**，这正是"用 DSV4 架构"换来的东西。

> 在 vLLM 0.29 里压缩层的实际分配比解析值高一个量级以上。

### 3.1 实测：vLLM 0.29 对压缩层的 KV 分配**远高于**解析值

在 5090 上用同一份配置只改层数（`hf_overrides.num_hidden_layers`，
`kv_cache_dtype=fp8_ds_mla`，显式指定布局后结果一致），读引擎报的
`GPU KV cache size` 反推每 token 字节：

| 层数 | 层的构成 | 可用 KV 显存 | 引擎报的 token 容量 | **B/原始 token** | 解析值 |
|---:|---|---:|---:|---:|---:|
| 1 | 1×全 MLA | 7.73 GiB | 13,964,524 | **594** | 576 |
| 2 | 2×全 MLA | 9.1 GiB | 8,218,529 | **1,189** | 1,152 |
| 3 | 2×全 + 1×CSA(4) | 8.21 GiB | 633,952 | **13,904** | 1,664 |
| 6 | +HCA(128),CSA(4),HCA(128) | 8.10 GiB | 213,134 | **40,800** | 2,192 |
| **12** | 官方交替模式 | 7.88 GiB | 86,672 | **97,602** | 4,288 |
| 12 | **全部 ratio=4（同构）** | ~7.9 GiB | 56,395 | **150,400** | 6,144 |

**逐层边际成本**（由相邻两行差分得到）：

| 层类型 | 解析上界 | **引擎实测** | 倍数 |
|---|---:|---:|---:|
| 全 MLA（ratio 0） | 576 B/token | **594 B/token** | 1.03× |
| CSA（ratio 4） | 512 B/token | **≈12.4 KB/token** | **~24×** |
| HCA（ratio 128） | 8 B/token | **≈7.3 KB/token** | **~900×** |

**这个结果与直觉相反**：压缩层的实际分配比**不压缩的全 MLA 层还大一个量级**
（12.4 KB vs 0.594 KB）。也就是说在 vLLM 0.29 上，
**"用 CSA/HCA 省 KV"这件事目前没有兑现成容量收益**；把 12 层全做成 ratio=4
（同构、本应最省）反而更差（150 KB/token）。

**再用 `max_model_len` 扫描排除"每请求固定块摊派"这个解释**（同一份 12 层配置）：

| `max_model_len` | 可用 KV 显存 | 引擎报的 token 容量 | 折算 B/token |
|---:|---:|---:|---:|
| 1024 | 7.88 GiB | 86,059 | 98,300 |
| 4096 | 7.88 GiB | 86,672 | 97,600 |
| 16384 | 7.88 GiB | 86,827 | 97,400 |

容量**几乎不随 `max_model_len` 变化（差 0.9%）**，块数也完全相同（35,634, block 4）——
说明这 ~98 KB/token 是**真实的按 token 分配**，**不是**"每请求固定 state block 被摊到短前缀上"
的假象。也就是说：在这个引擎里，上面那张表的**逐层边际成本是可信的**。

机制方向上，**`SlidingWindowMLASpec.merge()` 要求同一 KV cache group 内所有层的
`tokens_per_state` / `sliding_window` / `extra_retained_tokens` 一致**，
不一致时只能各自成页并按最大页做 `page_size_padded` 对齐（
`kv_cache_interface.py:804-824`；`_apply_alignment_padding`）。
论文 §3.5.1 也明确说 state cache 是**每个请求一块固定大小的块**
（SWA 段 + 未攒够 m 个的尾部缓冲）——固定块在前缀短/并发少时会被摊成很高的
"每 token 成本"。

#### 3.1.1 归因（源码级，2026-09-18 补）：`tokens_per_state` 没传给 compressor

读 `vllm/models/deepseek_v4/compressor.py` 的 `get_kv_cache_spec()`（镜像 vLLM
0.29.0）可以定位到主因，**不是 padding，也不是每请求固定块摊派**：

```python
# compressor.py:151-186
assert self.dtype == torch.float32          # 压缩状态是 fp32，不是 fp8
coff = 1 + (compress_ratio == 4)
self.sliding_window = coff * compress_ratio
if compress_ratio == 4:     self.block_size = 4      # [4, 2*512*2*4]
elif compress_ratio == 128: self.block_size = 8      # [8,    512*2*4]
...
return SlidingWindowMLASpec(                # 没有传 tokens_per_state
    block_size=self.block_size, num_kv_heads=1, head_size=self.state_dim,
    dtype=self.dtype, sliding_window=self.sliding_window, alignment=576)
```

而 `AttentionSpec.get_num_kernel_states()` 是 `block_size // tokens_per_state`，
默认 `tokens_per_state = 1`。所以一页里有 `block_size` 个状态、却被记成只覆盖
`block_size` 个 token —— **可这 `block_size` 个状态实际覆盖的是
`block_size × ratio` 个 token**。对照一下：全 MLA 层（`attention.py:746`）和
indexer cache（`attention.py:791`）都老老实实传了
`tokens_per_state=self.compress_ratio`，**只有 compressor 这份 spec 漏了**。

**实测**：`design/dsv4_kv_probe.py` 包了 `AttentionSpec.page_size_bytes`，
把引擎实际构造的每一份 spec 打出来（5090，GPU2，`fp8_ds_mla`，
`max_model_len=4096`，`VLLM_ENABLE_V1_MULTIPROCESSING=0` 让 spec 留在本进程）。
12 层混合配置下一共只有 **7 种** spec，逐条如下：

| spec（引擎类） | block | head_size | tokens_per_state | dtype | num_states | page B | **B/token** | 出现在 |
|---|---:|---:|---:|---|---:|---:|---:|---|
| `SlidingWindowMLASpec`（SWA） | 64 | 512 | 1 | uint8 | 64 | 37,440 | **585.0** | 每层 |
| `MLAAttentionSpec`（main state） | 256 | 512 | 4 | uint8 | 64 | 37,440 | 146.2 | CSA 层 |
| `MLAAttentionSpec`（main state） | 256 | 512 | 128 | uint8 | 2 | 1,728 | 6.8 | HCA 层 |
| `MLAAttentionSpec`（indexer） | 256 | 132 | 4 | uint8 | 64 | 8,640 | 33.8 | CSA 层 |
| `SlidingWindowMLASpec`（indexer 状态） | 4 | 512 | 1 | **float32** | 4 | 8,640 | **2,160** | CSA 层 |
| `SlidingWindowMLASpec`（**compressor**） | 4 | 2048 | **1** | **float32** | 4 | 32,832 | **8,208** | CSA 层 |
| `SlidingWindowMLASpec`（**compressor**） | 8 | 1024 | **1** | **float32** | 8 | 32,832 | **4,104** | HCA 层 |

和按源码常数手算的预测**完全吻合**（CSA 8,208、HCA 4,104）。
一个 CSA 层挂的 spec 合计 **11,133 B/token**（含 585 的 SWA），对比解析 fp8 的
512 B → **21.7×**；一个 HCA 层合计 **4,696 B/token**，对比 8 B → **587×**。

§3.1 量到的**逐层边际**是 CSA 12.4 KB、HCA 7.3 KB——比 spec 合计再高
1.1–1.6×，这部分来自**多个 group 共享同一个 block 池**的取整效应
（报告出来的 "token 容量" 是各 group 里最小的那个），不是单层 spec 的成本。
两种口径都不影响结论：**压缩层现在比不压缩层贵一个数量级。**

**对设计的含义**：官方在 vLLM 里"压缩 KV 不省显存"是**实现层面一笔可修的账**
（fp32 存储 + `tokens_per_state` 漏传），不等于 DSV4 的压缩机制本身没收益。
真正要决定的是**容量规划建在哪一版实现上**：若 DSV4 在 vLLM 里按这个口径跑，
P-15B 的解析 16.56 KB/token 在真机上要按**每压缩层 4–8 KB/token** 重新估。

#### 3.1.2 把那笔账修对：实测拿到 1.40× 容量，但改不动算子

上面那句"可修的账"不能只停在结论上。`design/dsv4_spec_fix/` 里做了个小补丁
（挂到 `PYTHONPATH`，由 `sitecustomize.py` 在解释器启动时应用），把 compressor
的 spec 改成"一页一个状态、按 `compress_ratio` 个 token 计费"：
`block_size=ratio, tokens_per_state=ratio`。同一台 5090、同一份 12 层配置、
同样 23.67 GiB 可用 KV：

| | 引擎报的容量 | 折算 B/token |
|---|---:|---:|
| 原始 | 260,494 tokens | **97,600** |
| 修 `tokens_per_state` | **364,346 tokens** | **68,209** |
| 变化 | **1.40×** | |

逐条 spec 的省法（实测打印）：

| 缓存 | 修前 | 修后 | 倍数 |
|---|---:|---:|---:|
| compressor CSA（head 2048, fp32） | 8,208 B/token | **2,160** | 3.8× |
| compressor 的 indexer 状态（head 512, fp32） | 2,160 B/token | **576** | 3.75× |
| compressor HCA（head 1024, fp32） | 4,104 B/token | **36** | **114×** |

**但两件事必须说清楚**：

1. **改 spec 不够，算子是按旧 block 写的**。把 HCA 的 block 从 8 改成 128 之后，
   引擎在 warmup 阶段直接抛：
   `ValueError: CuTe DSL split sparse-attn wrapper only supports the real
   DeepSeek V4 C128 layout: head_size=512, state_width=512, compress_ratio=128,
   overlap=False, block_size=8.`
   ——这正是"缺的部分得自己改/自己编"的实证（§2.3 第 1、3 条要一起做）。
2. **修完之后账还是不对**：12 层的 spec 合计只有 **16.5 KB/token**，引擎仍报
   **68.2 KB/token**，差 4.1×。所以这个数字的**主导项不在单层 spec，而在 vLLM
   的 block 池 / group 划分**（多 group 共享 block 数、按最坏 group 报容量）。
   要动的是 KV cache manager，不是注意力算子。

**对设计的意义**：**DSV4 的压缩算术本身没问题**（我们的参考实现就是按它计价，
闭式与实现逐层对齐到 8.438 KB/token）；"压缩 KV 不省显存"这句话只对
**某一版 vLLM 的实现**成立，且其中至少一半是可以自己改掉的。

**对设计的直接含义（重要）**：

1. 在**这个** serving stack（vLLM 0.29.0）上，DSV4 式压缩**不省显存**，反而更费；
   官方"10% / 2%"的结论应当理解为**DeepSeek 自己推理栈**的实测口径。
   §3.1.1 已把它归因到两处可修的实现细节（fp32 状态 + `tokens_per_state`
   漏传），所以这**不代表压缩机制本身没收益**，而是"这条结论绑在某一版实现上"。
2. 即便如此，**不能按 §3 的解析表做容量规划**——解析表是理想栈的下界。
   要么先把账测准（§3.1.1 的剩余待办），要么在做模拟实验时把这个口径
   **显式当成一个自变量**（解析值 / 实测值各跑一遍），否则一个
   "KV 小 9 倍"的设计假设可能是反的。
3. 反过来说，如果我们的目标是**研究调度**，那么"KV 到底多大"必须先钉死——
   这也是为什么第 7 节的第 1 步（用解析值先跑模拟）与第 2 步（把账测准）
   必须在训练之前完成。

### 3.2 参考实现：把设计变成可执行、可跨卡验证的东西

光有配置表不够——"怎么设计"要落到能跑的代码上。所以在
`LLMServingSim/design/dsv4_ref/` 里写了一份**纯 PyTorch 参考实现**（无自定义 kernel、
无 fp8、无 tilelang、**无 mHC**），它同时是三件事：

1. **设计的规格**：MLA latent + 滑窗 + CSA/HCA 压缩状态 + indexer top-k +
   标准 pre-norm 残差，逐层的 `compress_ratios` 与官方交替模式一致；
2. **KV 账目的独立核算**：`verify.py` 逐层数一个 token 实际占多少字节，
   与设计用的闭式（全层 `head_dim+rope`、压缩层 `2·coff·head_dim/ratio`）对照；
3. **跨卡证据**：同一份代码在 **4090（sm89）** 与 **5090（sm120）** 上跑同一输入，
   比较指纹。

**实测结果（`design/dsv4_ref/verify.py`，fp32，`--config small --tokens 128`）**：

| 检查 | A100（sm80） | RTX 3090（sm86） | RTX 4090（sm89） | RTX 5090（sm120） |
|---|---|---|---|---|
| 参数（模块树） | 831,341,312 | 同 | 同 | 同 |
| 与配置估算器之差 | 5.2% | 5.2% | 5.2% | 5.2% |
| KV/token | **8.438 KB** | 8.438 KB | 8.438 KB | 8.438 KB（闭式 8.438） |
| logits checksum | **-104679376.2** | -104679319.7 | -104679385.9 | -104679321.1 |
| 与 4090 的相对差 | **9.3e-8** | 6.3e-7 | — | 6.2e-7 |

同一份模型，把稀疏注意力换成 `--kernel triton`（即 §2.3.1 的自研 kernel）：

| 检查 | fp32 / 4090 | bf16 / 4090 |
|---|---|---|
| torch 路径 checksum | -104679385.9 | -98658279.5 |
| **triton 路径 checksum** | **-104679377.5** | -99675980.9 |
| 相对差 | **8.0e-8** | 1.0e-2（bf16 量级，mean/std 到 5 位一致） |

即"用自己编的 kernel 替换掉官方只给 Hopper 的那一段，整模型的 logits 在 fp32 下
**对得上 8e-8**"——§7 第 2 步的判据到此满足。

**四类卡全覆盖**：A100-SXM4-40GB（sm80）、RTX 3090（sm86）、RTX 4090（sm89）、
RTX 5090（sm120），跨 Ampere / Ada / Blackwell 三代，logits **在 1e-6 相对误差内
一致**，差异只是浮点归约顺序。这就是"3090/4090/5090/A100 都能跑"在**数学层面**
成立的直接证据，而不是推断。

> A100 那台（`10.212.67.93`）是 k8s 主节点，8 张卡里那张 A100-40GB 被别人的业务
> 占了 34.4/40.9 GiB，我们用的是剩下的 **~6.5 GiB**；`small` 档 fp32 要 3.33 GB
> 权重，塞得下。没有用 docker，直接用节点上的 conda 环境（`envs/A100`，
> torch 2.7.1+cu126）跑的——那台盘只剩 15G，装不下 21.5G 的 vLLM 镜像。

> **本轮修掉的一个真 bug**：参考实现原来只能在 fp32 下跑——`rope()` 用 fp32 算
> `cos/sin` 后直接相乘，把整条注意力路径上采成 fp32，于是 bf16 权重在第一个
> `o_lora_a` 就报 `expected mat1 and mat2 to have the same dtype, got: float !=
> c10::BFloat16`。现在角度算完再 cast 回激活 dtype，**bf16 也能跑通**
> （4090 bf16 checksum `-98658279.5`）。这条很关键，因为部署矩阵的主推就是
> **bf16 + TP=2**——参考实现如果只能在 fp32 下成立，那"bf16 可移植"就没有证据。

> **第二个真 bug（接 Triton 路径时才暴露）**：原实现在压缩层里把**窗口**和
> **选中状态**两条支路**各自 softmax 之后直接相加**，等于无论各自有多少分数质量
> 都给它们权重 1。正确做法是二者和成**一个拼接后的联合 softmax**（mask 住无效的
> 未来状态）。修完 4090 fp32 指纹从 `-257011226.4` 变成 `-104679385.9`
> ——**这是一次语义修正，所以上面所有指纹都换成了新值**。修完两条路径（torch 与
> triton）也才真正对得上（8.0e-8）；旧写法下它们差 1.1 个 logit，就是这个 bug
> 的直接症状。

**结论**：DSV4 风格的这一套注意力（**mHC 已砍**）在 **Ampere / Ada / Blackwell**
上**数值一致到 1e-6**，也就是"四类卡统一跑"在**数学层面成立**；
剩下的是"把 torch 换成能编到 sm80/86/89 的 kernel"，是工程量问题不是可行性问题
（可编译性证据见 §2.3）。

**过程中修掉的三个设计错误（值得记录）**：

1. **compressor 不能对整窗做 dense 投影**。最初的实现按"窗口拼接 → 线性投影"
   写，参数是 `hidden × window × state`：HCA 的窗口 128、hidden 1024、state 1024
   → **每层 134M 参数**，12 层就 500M+，与配置估算器差 62%。
   改成 **窗口池化（mean）+ 小投影 `hidden → state`** 后，compressor 的成本与窗口
   长度无关，差值收敛到 5.2%。**这条对真实训练直接相关**：压缩机必须是
   "先聚合再投影"，否则 HCA 层会把模型撑爆。
2. **整行无效的稀疏选择会产生 NaN**：某次 query 的 top-k 全部落在未来时，
   softmax 里全是 `-inf`。改为有限大负数 + 事后把该块贡献置零。
3. **两条支路分别 softmax 再相加**（见上面的红框注记）：联合 softmax 才是设计
   本意，也是自研 kernel 能与参考实现对上的前提。

### 3.3 接进模拟器：逐层压缩 KV 的记账（口径警告）

上一节的参考实现证明了"设计在数学上跨卡成立"，但**调度实验要的是 KV 账目**，
不是前向数值。为了让模拟器能直接用这套几何跑调度，本轮做了两件事：

1. **`serving/core/memory_model.py` 支持逐层压缩比**：新增 `kv_layout`
   （`compress_ratios` / `head_dim` / `rope_head_dim`），在 `get_kv`、
   `pd_kv_bytes`、`full_cluster_kv_bytes_per_token` 三个入口分流。全层存
   `head_dim + rope` 值/token，压缩层每 `ratio` token 存 `2·coff·head_dim`
   值（`coff=2` 当 `ratio=4`），所以 `_kv_layout_bytes` 对 `seq` 是**线性**的
   ——边际成本与平均成本一致，这与窗口几何不同（窗口层到窗口就停止增长）。
2. **配置 `configs/model/DeepSeek/DSV4-P15B-draft.json`**：28 层，
   `compress_ratios = [0,0]+[4,128]×12+[0,0]`，`head_dim=512`、`rope=64`。

> ⚠️ **这个配置的算力是"借"来的。** 模型并不存在，所以
> `profile_model: Qwen/Qwen3-8B` —— 模拟器用 **Qwen3-8B 的 kernel profile**
> 算 FLOPs/延迟，**只有 KV 几何来自 DSV4 设计**（和仓库里已有的
> `Qwen/Qwen3-8B-hybrid` 是同一套用法）。因此用它跑出来的结论**只在
> "KV 缩小后调度还值多少"这个维度可信**，绝对延迟、吞吐上限都不可信。
> 真正的算力 profile 要等第 7 节第 2 步的算子写完之后才有。

> ⚠️ **数值口径：模拟器用的是解析下界，不是 §3.1 的引擎实测。**
> P-15B-draft 在模拟器里收 **16.56 KB/token（28 层合计，解析值）**；
> 而 §3.1 在 vLLM 0.29 上对**同一套压缩层**量到的是 **≈98 KB/token（12 层）
> vs 解析 4.29 KB —— 实测比解析高 ≈23×**。所以 16.56 这个数是
> **"设计认为应该有的值"**，对应**理想 serving 栈**；真实栈上的 KV 体量
> 必须先用 §3.1 第 1 条实验钉死，否则这个 config 会系统性地低估 KV 压力、
> 从而**高估 CASR 的优势**。

**一个测试把两条代码路径钉在一起**：`tests/test_dsv4_kv_layout.py`
（6 项）——逐层字节数、两个参考档的总量互校、长度无关性、`pd_kv_bytes`
一致性、以及与 Qwen3-8B 的 8.9× 比值。所以"参考实现说 16.56 KB/token"
和"模拟器收 16.56 KB/token"是**同一件事的两个独立算法**，任一边改动都会被发现。

## 4. 部署矩阵（每个卡型怎么起）

| 卡型 | 目标档 | 单卡/多卡 | 权重 | 备注 |
|---|---|---|---|---|
| A100 80GB | P-29B | 单卡 | bf16 | 59.2 GB 权重，最省事；P-15B 当然也放得下 |
| 5090 32GB | P-15B | **TP=2** 或单卡 fp8 | bf16 / fp8 | bf16 单卡 29.73 GB 只剩 ~2 GB 给 KV，不可用 |
| 4090 24GB | P-15B | **TP=2** | bf16 | 14.87 GB/卡；或单卡 fp8（需自研 fp8 路径） |
| 3090 24GB | P-15B | **TP=2** | bf16 | 同上；3090 无 fp8 GEMM，bf16 是唯一稳妥选择 |

### 4.1 单卡 3090（24GB）到底能不能跑 P-15B——逐条算过

结论：**单卡 3090 跑 P-15B 不行；2 卡 TP=2 行。** 四条路各自卡在哪：

| 方案 | 需要显存 | 24GB 单卡 | 卡在哪 |
|---|---:|---|---|
| bf16 权重（默认） | **29.73 GB** | ❌ | 直接超 5.7 GB，没有余地 |
| fp8 权重（14.87 GB） | 14.87 GB | ⚠️ 内存够，**这条路在 sm86 上不存在** | `torch._scaled_mm` 在 sm86 直接报 `only supported on ... >= 9.0 or 8.9`；要省这份显存只能**自己写**"fp8 常驻 + 逐层 dequant"的加载器（§2.3 第 4 条） |
| int4/4bit 量化 | ~7.4 GB | ✅ 可行 | 但这是另一条设计线（要自己做量化与换 kernel），不是我们默认方案 |
| **bf16 + 2 卡 TP=2** | **14.87 GB/卡** | ✅ **推荐** | 24GB 卡留 ~9 GB 给 KV+激活；KV 16.56 KB/token → 4K 上下文 66 MB/序列、32K 530 MB，并发够用 |

两点必须一起说：

1. **不是 kernel 问题，是显存问题**。同一个块在 3090（sm86）上已经跑通并对过指纹
   （§3.2，相对差 6.3e-7），两个自研算子也都在 sm86 上跑过（§2.3.1）。
2. **现在这两张 3090 跑不了**：`10.212.67.68` 的两张卡各被占 **19.4/24 GiB**
   （只剩 ~4.6 GiB/卡），TP=2 也放不下 29.73 GB；`10.212.70.38` 第二张卡还被
   `qemu-system-x86_64 -name conzone` 占着，只有一张可用。**TP=2 的 P-15B 实跑
   要等这些机器空出来**——这也是 §8.4 登记的"TP=2 通信要一次对照实验"。

如果只是想"在 3090 上先跑起来看效果"，**P-5B（5.131B / bf16 10.26 GB）单卡就够**。

**统一要求**：注意力用 Triton 实现（可编译到 sm80/86/89/120），
残差不带 mHC，KV 支持 bf16/fp8 两种存储。这样**一份 checkpoint + 一套代码**
覆盖四类卡，只在 TP 度、dtype 与并发上限上不同——这正是我们做跨域异构实验
需要的形态（同一模型在 4 个域上跑，域间差异来自硬件而不是模型版本）。

## 5. 训练预算（十几 B 量级）

`6 × 激活参数 × tokens`，单卡按 100 TFLOPs 有效值估；激活参数取 §3 表里
**参考实现报出**的值（不是旧稿的粗估）：

| 候选 | 激活 | 100B tokens | 1T tokens |
|---|---:|---:|---:|
| P-5B | 0.712B | **49 GPU-days**（8 卡 6 天） | 494 GPU-days（8 卡 62 天） |
| **P-15B** | **2.145B** | **149 GPU-days**（8 卡约 19 天） | 1490 GPU-days（8 卡 186 天） |
| P-29B | 3.302B | 229 GPU-days（8 卡 29 天） | 2293 GPU-days（8 卡 287 天） |

**结论**：**"从这里开始训"现实的上限是 P-15B + 100B tokens 量级（8 卡约 3 周）**；
若要压到 1 周内，就把目标降到 **P-5B + 100B tokens（8 卡 6 天）**。
再往上（1T tokens）就不是我们这张机器能承担的。
如果需要更好质量，优先级应是 **继续预训练/蒸馏**（用现成开源权重初始化）
而不是从零训到 1T。

## 6. 为什么这个规模对我们的研究有价值

我们前面所有调度结论都建立在"KV 是绑定资源"（Qwen3-8B 147.5 KB/token、
MLA 31.1 KB/token）。P-15B 把 KV 压到 **16.56 KB/token（bf16）/ 8.28（fp8）**，
直接改变三个东西：

1. **P/D handoff 成本降一个数量级** → 我们测到的"搬 vs 算"临界点整体移动，
   `KV 体积 ÷ 链路能力` 的三点刻度（−5.6% / +0.6% / +31.8%）会左移，
   **CASR 的相对优势应当收敛**——这正好是"什么时候不需要存算协同"的最强证据。
2. **权重重新成为瓶颈**：14.87B 权重（29.73 GB bf16）vs 每条序列几十 MB 的 KV，
   意味着调度要重新关注 **权重驻留与 TP/EP 拓扑**，而不是纯 KV。
3. **异构价值改变**：同一模型在 4 类卡上跑，域间差异变成算力与显存，
   而不是"能不能跑"——这让我们的异构实验更干净。

## 8. 未决问题（诚实登记）

1. **压缩层的 KV 分配为何高一个量级——已闭环（实测 + 源码级归因）**：
   §3.1 的层数扫描给出逐层边际（全 MLA 594 B/token，CSA ≈12.4 KB、
   HCA ≈7.3 KB），§3.1.1 用 `design/dsv4_kv_probe.py` 把引擎真正构造的 7 种
   spec 逐条打了出来：**compressor 的状态缓存是 fp32、且 `tokens_per_state`
   没传（默认 1）**，于是一层压掉 4–8 KB/token（CSA 8,208、HCA 4,104），
   而解析值是 512 B / 8 B。
   §3.1.2 又把记账改对实测了一遍（补丁在 `design/dsv4_spec_fix/`）：
   12 层混合从 97,600 → **68,209 B/token（1.40×）**，但 spec 合计只有
   16.5 KB/token —— 说明**剩下那 4.1× 在 vLLM 的 block 池 / group 划分**里，
   不在单层 spec 也不在算子。同时改 block_size 会被 CuTe DSL 的
   `only supports ... block_size=8` 断言挡住。
   **剩余待办**：把 group 划分 / 共享 block 数这段拆开（要动 KV cache manager）；
   并对照论文 §3.5.1 / §3.5.2 确认 DeepSeek 自己的口径。
   **在把账测准之前，任何基于"KV 缩小 9 倍"的容量假设都不成立**——但注意，
   这个"贵"是**可以改的**（见 §2.3 第 1 条），不是架构属性。
2. **fp8 权重在 Ampere/Ada 上的可行性**：如果不做 fp8 只用 bf16，
   24GB 卡就必须 TP=2；如果要用 fp8 单卡，需要确认我们需要自己写
   多少 fp8 kernel（dequant + bf16 GEMM 是最省的路）。
3. **词表 64k vs 官方 129k**：换小词表能省 0.3B 参数，但要重训 tokenizer
   与重编码数据；若目标是"尽量复用官方结构"，也可保持 129k（P-15B 多 0.4B）。
4. **P-15B 的 TP=2 通信**：MLA 的 latent 是单头（`num_key_value_heads=1`），
   TP 切分要注意 KV 不切、按 head 切 attention 与 MoE 的约定；
   需要一次 TP=2 的对照实验确认没有精度/性能意外。
